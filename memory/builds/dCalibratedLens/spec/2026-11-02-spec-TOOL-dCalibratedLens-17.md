## 1. Goal

Runtime publishes each node's capacity in its beat and charges every launch against the node's plan and
hardware ledgers, sized by an estimate per item kind (TOOL-dWellOiledMachine-52, -53), but nothing reads
those values over time: a beat replaces the one before it, a ledger holds only its live reservations, and
the estimate is computed at each admission and kept nowhere. This unit makes the Loop Review read the node
beats, the pools' ledgers and the reservation estimate per item kind at every period, the estimate
re-derived from the `trace.cost` rows by the one deriver Runtime already has, and trend each value across
the review records in the window (v2 P40, P9; cloud-and-scale `[layers]`, "observability (expansion) |
dCalibratedLens | the beats and the pools' ledgers trended, and the reservation estimate re-derived").

## 3. Non-goals (OUT)

- A second deriver of the estimate. `derive_estimate` is the factored body of TOOL-dWellOiledMachine-53's
  `derive_estimate_hours`; the loop kit reads its output and computes no p90.
- Moving any value. The trend proposes no reservation size, cap or capacity: the estimate is already
  re-derived at every admission, and a cap movement is TOOL-dCalibratedLens-4's.
- A history of beats between reviews. Each lease write replaces its record with a parentless commit
  (`tools/unattended/unattended.sh:2612`), so a beat keeps no history; the trend samples the live
  members once per period (§8 F1).
- Another node's ledgers. They are kept at that node outside every repository (TOOL-dWellOiledMachine-53
  S1); its beat's `node-plan` and `node-hold` lines are what it publishes of them, and they are read.
- The fleet's pool ledger for a plan shared across machines: cloud-and-scale `[planned]`, no build's.
- A value-ledger row for a node, pool or kind: none catches anything, so no `PROVIDERS` entry is added.

### Evidence

- A lease record keeps no history: `write_claim` builds each write as `git commit-tree "$t" -m "$msg"`
  with no parent and pushes it `--force-with-lease` onto the ref (`tools/unattended/unattended.sh:2612`,
  `:2616`), and TOOL-dPlacedRequest-1 keeps that writer; so the newest beat is the only one any node can
  read, and a trend needs one sample per review.
- `trace.cost` is a catalogue row at `tools/policy/catalogue.toml:1602` (values `tokens+wall`, `tokens`,
  `none`; default `tokens+wall`), and `python tools/policy/policy.py get trace.cost` prints `tokens+wall`
  at base. Under `tokens` and `none` the act record writes `Wall: withheld` (TOOL-dWellOiledMachine-32 S8),
  so the estimate of every kind stays at the ceiling.
- TOOL-dWellOiledMachine-53 S4 is the one place the estimate is computed today, and it returns only the
  hours; the basis and the row count are what a trend reader needs to tell a falling estimate from a
  kind that left the ceiling.

### The lines

Each is one Metrics line of the `loop-review` record, `<name>: <value> · <source>`, TOOL-dCalibratedLens-3
§4 "The record"'s grammar: the value is one or more segments joined by ` · `, and the last segment is the
source. Segments sort by tag, pool or kind.

```
node-beats: a 2/6 load 0.25 hold 0 · b 0/4 load 0.90 hold 1 · beat.py members --json
pool-ledgers: personal 6h limit-hold reserved 4.5h/2 · personal@b unknown none · ledgers.py pools, beat.py members --json
reservation-estimates: item.build.unit-pass 0.15h p90/10 · item.review.audit 1.5h ceiling/3 · trace.cost tokens+wall · ledgers.py estimate
capacity-trend: free@a 3 2 2 falling · estimate@item.build.unit-pass 1.5 0.15 falling · load@b 0.90 new · 2 record(s) in window · loop-review/
```

| Line | Segment | Fields, from |
|---|---|---|
| `node-beats` | `<tag> <free>/<capacity> load <load> hold <n>` | `members --json`: `tag`, `node-free-slots`, `node-capacity`, `node-load`, and `n` the pools `node-hold` names; `-` stays `-` |
| `pool-ledgers` | `<pool> <allowance>h <source> reserved <hours>h/<count>` | this node's `ledgers.py pools`; `allowance` `unknown` where the pool holds no reading |
| `pool-ledgers` | `<pool>@<tag> <allowance>h <source>` | each live member's `node-plan` lines, one per pool it names |
| `reservation-estimates` | `<kind> <hours>h <basis>/<rows>`, then `trace.cost <value>` | `ledgers.py estimate`; `read_loop_policy(root, "trace.cost")` |

No member, pool or kind found: the value is `none`. `searched-none · <command>: <why>` replaces the value
when S4's read fails. The node's own pools carry no `@<tag>` because the reviewing node reads them from
its own ledger, which knows no fleet tag (TOOL-dWellOiledMachine-53 S1); every other node's pools are
read from its beat.

### The trend

| Series | From |
|---|---|
| `free@<tag>`, `load@<tag>` | `node-beats` |
| `allowance@<pool>`, `reserved@<pool>` | the reviewing node's `pool-ledgers` segments |
| `allowance@<pool>@<tag>` | the beat-read `pool-ledgers` segments |
| `estimate@<kind>` | `reservation-estimates` |

A series' values are its numbers in the records the window holds, oldest file-name date first, then the
walk's own; a `-`, `unknown` or absent value is left out. Its direction compares the last value with the
first: `rising`, `falling` or `flat`; `new` when only the walk's value exists; `gone` when earlier
records hold it and the walk does not, which is how a node that stopped beating shows. Series sort by
name. The source segment names the count of records read and the home. A record a line of which
`parse_capacity_line` cannot read is skipped and counted in the source as `<n> unread`, never read as an
empty series.

## 5. Production-readiness checklist

- security — three read-only subprocesses with argument lists and bounded time; the beat's closed key set
  already keeps project names and credentials out (TOOL-dWellOiledMachine-52 S3), and the ledgers carry
  counts and hours only; nothing read reaches a shell.
- perf / scale — once per period: one `find` per 40 act records and one `show` per record for the
  estimate (TOOL-dWellOiledMachine-53 S4's cost), one lease read, one ledger read, and one `git show` per
  record in the window, about nine a window at `weekly`.
- error / empty / loading states — an absent runtime kit, a refused ledger or a timeout gives
  `searched-none` with the reason; no member, pool or kind gives `none`; an unreadable earlier record is
  counted `unread`.
- observability — the four lines are the reading; each names its source.
- risks — a node offline at the review is absent for that period and reads `gone` until it beats again
  (`ponytail:` one sample per period, the ceiling; a sample per beat needs the history §3 declines);
  under `trace.cost` `tokens` or `none` every estimate reads `ceiling`, which the line says.
- testing — §6's plants and fixture cases, and §7's two arms.
- migration — none: `derive_estimate_hours` keeps its signature and value; the verbs and lines are new.
- user docs — `help/loop-review.md` and `help/runtime.md` (S6).
