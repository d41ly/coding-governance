## 4. Design

### Evidence

Every line below was read on 2026-10-24 at `9bcca6523`, after `TOOL-dGroundRules-37` built at
`7a600abf5` and before `TOOL-dGroundRules-41` builds.

- The page is tracked at HEAD: `git ls-files help/policy.md` lists it. Only
  `TOOL-dGroundRules-41` S2's guard line is missing: the `policy fixtures` row of
  `tools/gate-legs.json` holds no `help/policy.md` entry, and
  `python tools/check-spec-tokens.py --legs-for help/policy.md` prints the path, then
  `no guarded leg`, and exits 0.
- The query is `print_legs_for` in `tools/check-spec-tokens.py`. It reads the manifest from disk and
  checks each path against the files tracked at HEAD, so a guard edit in a scratch copy's working
  tree counts without a commit, and a tracked page is never refused.
- `run_fresh_target` in `tools/policy/check_policy.py`, the `adopter-fresh-target` case, does not
  read the page at HEAD; `TOOL-dGroundRules-41` S1 adds that read. Both criteria are therefore
  observed after `TOOL-dGroundRules-41` builds: before it, AC1 prints `no guarded leg` and AC2's
  trace holds no read of the page to join.
- `run_fixture` in `tools/policy/check_policy.py` runs `check_guard_trace` and then
  `check_guard_lines` after the selected cases, so a run naming one case still runs both over that
  case's reads and the whole guard.

### The two families of guard-trace line

Both checks print under the one prefix `policy-fixture: guard-trace · `, so AC2 names the trace's
form whole rather than any `WRONG`. `check_guard_trace` (`TOOL-dGroundRules-33` S3) prints:

```text
policy-fixture: guard-trace · <n> source read(s)
policy-fixture: guard-trace · <n> ignored read(s) set aside
policy-fixture: guard-trace · WRONG <path> · not under the policy fixtures guard
policy-fixture: guard-trace · WRONG: <reason>, so no read was joined to the guard
```

`check_guard_lines` (`TOOL-dGroundRules-37` S1 and S2, built before this unit) adds:

```text
policy-fixture: guard-trace · <n> guard line(s) checked
policy-fixture: guard-trace · WRONG guard <entry> · names no file git tracks
policy-fixture: guard-trace · WRONG: the manifest did not parse: <error>, so no guard line was checked
policy-fixture: guard-trace · WRONG: the manifest holds no policy fixtures row, so no guard line was checked
```

Taking the page's entry out of the guard leaves no dead entry for `check_guard_lines` to name, so the
staged break reds the trace alone. Restored, the entry names a tracked file and `check_guard_lines`
stays silent on it. `TOOL-dGroundRules-33` AC4 staged the same break for `tools/govkit/selftest.py` on a scratch
clone and its ledger records the trace's `WRONG`, so the staging is proven.

`TOOL-dGroundRules-41` §4 says the page is read in process so the trace sees the read, and that S2's
guard line is what keeps the trace green; S2 here is that sentence staged to fail.
