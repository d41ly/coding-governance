## 1. Goal

The round-1 spec audit of this build
(`memory/builds/dGroundRules/reviews/2026-10-23-review-TOOL-dGroundRules-1-11-spec-audit-round1.md`)
exited BOUNDED with finding **id 4 at HIGH**, which shares item **H2** with id 37
(`TOOL-dGroundRules-17`). This unit is id 4's promotion. It repairs `TOOL-dGroundRules-1`, whose
adopter and AC9 the finding names, and builds at order 2, one step after that unit.

`TOOL-dGroundRules-1` ships `policy check` to adopters as a repo-subject `[[gate_leg]]`, and
`adopt-policy.sh --check` runs every arm in `ARMS`. Later units add arms that hold only on gov's own
tree, and every acceptance criterion observes gov's tree alone, so nothing would see an adopter go
red. Unit 1's AC9 observes a fresh target once, before any later arm exists. This unit makes that
observation a standing case that every later arm passes through, and writes down what each arm
grades in an adopter. It is the class gate; the arms that red today are repaired by id 37's
promotion and by ids 47 and 51 in `TOOL-dGroundRules-21`.

## 2. Scope (IN)

- **S1** — The case `adopter-fresh-target` in `CASES` of `tools/policy/check_policy.py`. It makes
  a fresh `git init` target, copies into it the policy kit and every kit its `kit.toml` `requires`
  names, each at the path its source sits at relative to the source repository's top level, runs
  `bash <copied kit>/adopt-policy.sh --scaffold --target <t>`, and runs `--check --target <t>`
  twice: before any commit, so HEAD does not resolve, and after committing the installed files, the
  scaffold and one `README.md`. Each run must exit 0 and print, for every arm, either a graded line
  with no finding or an announce line. Observed by AC1, AC2.
- **S2** — The written scope. `tools/policy/README.md` gains a section "Each arm in an adopter", a
  table with one row per entry of `ARMS`: the arm, what it grades in an adopter's tree, and what it
  announces when its subject is absent there. Observed by AC3.
- **S3** — The join. The same case reads that table and asserts its arm names equal the names in
  `ARMS`, both ways, so an arm added without a row reds, and a row whose arm left reds.
  Observed by AC3.

## 4. Design

### Evidence

- `TOOL-dGroundRules-1` §4 "The adopter": `--check --target <repo>` runs `check_policy.py --repo
  <repo>`, and `policy check` "ships as a `[[gate_leg]]`, subject `repo`".
- `TOOL-dGroundRules-1` AC9 observes `--check` on a fresh `git init` once, at that unit's commit.
- The arms the finding names: `arm_mirror_parity` (`TOOL-dGroundRules-5` §4), `legacy-homes`
  (`TOOL-dGroundRules-7` S5) and `arm_cap_census` (`TOOL-dGroundRules-9` S7), each added to `ARMS`
  after unit 1.
- A copy-installed kit carries what it needs inline or reaches a sibling through the inlined
  `resolve_kit_dir` (`tools/lib/resolve_kit_dir.py`), so the case must install what `requires`
  names or it tests an install no deployer makes.
- The install-prefix ban flags a literal kit segment followed by a file in shipped code
  (`tools/check-install-prefix.sh`), so the case derives each copy's path from its source.

### The case

1. `t` is a new directory under the system temp directory with the short prefix the fixture mode
   uses (`TOOL-dGroundRules-1` §4 "The CLIs"), and `git init` runs there.
2. The kit's own directory, `Path(__file__).resolve().parent`, is copied to the same path relative
   to `t` as it holds relative to its repository's top level; so is each kit in `kit.toml`'s
   `requires`, found with the inlined `resolve_kit_dir`.
3. `adopt-policy.sh --scaffold --target t`, then `--check --target t`: exit 0 expected.
4. `git -C t add -A` with a one-line `README.md`, `git -C t commit`, then `--check --target t`:
   exit 0 expected.
5. Each `--check` output is read per arm: a line naming a finding, or an arm that prints neither its
   graded line nor an announce line, fails the case naming the arm.

It is an outcome case: on a correct build it is green, and its RED is the staged arm of AC2.

```markdown
| Arm | In an adopter it grades | When its subject is absent |
|---|---|---|
| `arm_schema` | the target's `.governance/policy.toml` against the catalogue | announces "no policy file" |
```

One row per `ARMS` entry, in `ARMS` order. The case parses the first column's backticked names.

### Alternatives rejected

- **A scope flag per arm, run by a gov-only leg.** It adds a leg and a flag, and an adopter would
  then run fewer arms than gov does with no case proving the ones it runs are green.
- **Re-running unit 1's AC9 at the close only.** A one-off that the next arm added after this build
  never meets; the case meets every one.

## 5. Production-readiness checklist

## 6. Acceptance criteria

Every command runs from the repository root. The criteria spell the kit's files by bare name,
`check_policy.py`, `adopt-policy.sh` and `README.md` under the kit, as `TOOL-dGroundRules-5` §6 does.

- **AC1** — When `python check_policy.py --fixture adopter-fresh-target` runs with every unit of
  this build built, it prints `policy-fixture: adopter-fresh-target` with no `WRONG`, both
  `--check` runs having exited 0.
  Red when: an arm of the shipped leg finds a problem in a fresh target, before or after its first
  commit.
  permission: green only once `TOOL-dGroundRules-17` and `TOOL-dGroundRules-21` are built; this
  unit's pass observes AC2 and AC3, and the close observes this one.
- **AC2** — When an arm that reports one finding on every repository is staged into `ARMS` and the
  same `--fixture adopter-fresh-target` runs, it prints `WRONG` naming that arm; with the staged
  arm removed, the units built so far print no `WRONG` naming it.
  Red when: the case passes with an arm that reds every target, so it cannot see the class.
- **AC3** — When a name is staged into `ARMS` with no row in the kit's `README.md` table, the case
  prints `WRONG` naming it as unlisted; a row staged for an arm `ARMS` lacks prints `WRONG` naming
  it as stale.
  Red when: the written scope can drift from `ARMS` in either direction unseen.
