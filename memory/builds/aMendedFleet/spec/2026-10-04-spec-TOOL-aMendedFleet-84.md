## 1. Goal

Hygiene check 6 caps a build `README.md` at `BUILD_README_CAP_BYTES`, 25600, measured over the whole
file. Most of a large build's README is not written by anyone: the generator renders the build-index,
units, build-order and edges regions and the front matter's `ids:` line from the specs, at about 308
bytes per specced unit here. This build's README measures 39649 bytes, of which 25267 sit inside
generated regions, so a roster of its size cannot pass however its authors write, and the run had to
list it in `memory/project/curation-debt.txt` to keep going. That is the renderer-shaped overflow
the registry exists to drain. This unit makes check 6 price a build README by its AUTHORED bytes,
the file less its generated regions and its generated `ids:` line, so the generated half never bills
the cap at any roster size, and drains the two registry rows the change leaves hiding nothing.
Discovered at speccing and adopted under protocol section 11, because the build cannot land without
it.

## 2. Scope (IN)

- **S1** — THE PRICE. In check 6 of `tools/memory-tree/check-memory-hygiene.sh`, a build README's
  figure is its `wc -c` byte count less its GENERATED bytes. Generated bytes are every line from an
  opening `<!-- gen:build-index -->`, `<!-- gen:build-order -->` or `<!-- gen:build-edges -->`
  marker through its matching close marker, both markers and each line's newline included, plus the
  one `ids:` line inside the front matter. One `LC_ALL=C awk` pass over every README member computes
  them, so the count is bytes on every node. A trailing CR on a marker line still matches. Nested
  pairs, which is how `gen:build-units` sits inside the build-index region, are counted once. A
  README whose pairs do not balance is priced at its whole `wc -c` figure. Every other class is
  priced as today. Observed by AC1, AC2 and AC3.
- **S2** — THE MESSAGE. A README over cap prints
  `<path> (<authored>B authored > <cap>B; generated regions not priced; no line cap for this class)`,
  so a reader comparing the figure with `wc -c` is told why the two differ. Observed by AC2.
- **S3** — THE SCOPE OF THE CHECK, stated where a reader looks. Check 6's comment in the script and
  its entry in `tools/memory-tree/HYGIENE.template.md`, rendered into `memory/HYGIENE.md`, say that
  a build README is priced by its authored bytes, name the three region markers and the `ids:` line,
  and say what the check does NOT verify: that a region's bytes really are generated, which check 9
  establishes by re-rendering the three registered regions and byte-comparing them. The
  `BUILD_README_CAP_BYTES` comment in `tools/memory-tree/.memory-tree.conf.example` changes from
  "generated regions plus one bounded authored block" to the authored-bytes reading. Observed by AC4.
- **S4** — THE DRAIN. The `memory/builds/aMendedFleet/README.md` row and the
  `memory/builds/cBriefedPilot/README.md` row leave `memory/project/curation-debt.txt` with their
  comment blocks, because under S1 neither earns check 6, 7 or 8 and the registry reds a row that
  hides nothing. The registry's header gains one paragraph naming both rows as drained by this
  unit. Observed by AC3.
  **Readers:** by name: `memory/project/curation-debt.txt` alone spells either row; hygiene checks
  6, 7 and 8 read the file as a set. by value: NO VALUE READERS — the registry is read as path
  membership, and no tool counts its rows except the drift low-water reading unit 57 adds, for which
  fewer rows is the improving direction.
- **S5** — A new arm in `tools/memory-tree/check-memory-hygiene.test.sh`, beside the existing check-6
  cap arms: a fixture README whose generated regions alone pass the cap is silent; the same README
  with authored lines pushed past the cap is named with the S2 message; an unbalanced pair is priced
  whole. The existing arm expecting the bare `B > 25600B;` shape is updated to S2's.
  NOT OBSERVED by a criterion here: the suite runs once at the close, and the arm is declared under

## 4. Design

### Evidence

Read at base `7af5f564` and at the worktree tip `8312d315`; the kit files are byte-identical between
them, and `memory/project/curation-debt.txt` gained the aMendedFleet row after base.

- Check 6 runs one `awk` over the `wc -c` and `wc -l` streams of `INDEX_SET`, and binds a build
  README to `BUILD_README_CAP_BYTES` with no line cap. It has no notion of a region.
- `GEN_REGIONS` in `tools/memory-tree/gen_build_index.py` registers exactly the three region names
  S1 spells; `UNITS_OPEN` is nested inside the build-index pair and deliberately not registered.
  `apply_front_matter_ids` rewrites the front matter's `ids:` line from the roster.
- Measured over this build's README at the tip, a `python` pass in the scratchpad that mirrors S1,
  PINNED 2026-10-04: 39649 bytes in all; generated regions 25267, of which the units table is 16313
  over 82 rows at about 197 bytes each, the two id-gap lists 3465, the inner `ids` lines 2048 and the
  build-order region 3105; the front matter `ids:` line 2025; the authored roster 10176 over 97 rows
  at about 103 bytes each; the authored prose above it 4199.
- The same pass over all 137 tracked build READMEs: 3 pass the cap whole, and 1 passes it priced by
  S1, `memory/builds/aBoundedVerdict/README.md` at about 34.8 KB authored. `cBriefedPilot` falls
  from 27895 to about 21.4 KB and `aMendedFleet` to about 12.4 KB. No README's figure rises, since
  S1 only subtracts.
- `LC_ALL=C awk 'length($0)>350'` finds one line over check 7's budget in each of the two drained
  READMEs, and in both it is the front-matter `ids:` line, which READMEs outside the registry carry
  at up to 1787 bytes without a finding.
- The registry's own header says a row that hides nothing now reds (`TOOL-cGradedDebt-1`), and that
  the gate prints which checks each row earns.

### The awk, in outline

Per member, with `LC_ALL=C`: reset a depth and a sum at `FNR==1`; track the front matter between the
first two `---` lines and add the `ids:` line's length plus one; on a line matching one of the three
open markers, with an optional CR before the end, raise the depth; while the depth is above zero, add
the line's length plus one; on a matching close marker, lower it. At the end of each file, print the
sum and the path, or the path with a sentinel when the depth is not zero. Check 6's existing `awk`
reads that stream as a third input and subtracts it for README members only.

## 8. Open questions

- **F1** — Fix the renderer, or how check 6 prices generated regions?
  Candidates, each with the measurement that decides it, written before the pick:
  - Raise `BUILD_README_CAP_BYTES`. Loses if generated bytes grow per unit, because any constant is
    then crossed at a finite roster. Measured: about 308 generated bytes per specced unit. The
    comment on `_render_wrapped_ids` refuses a raise for this reason. Rejected.
  - Compact the renderer: range-spell the two id-gap lists, drop single-unit build-order rows, drop
    the inner `ids` lines. Loses if this build still fails after the best case. Measured upper bound
    of the saving: about 8.1 KB of the 3465, 3105 and 2048 bytes, leaving about 31.5 KB against
    25600, with the 16313-byte units table still linear in units. Rejected.
  - Price check 6 by authored bytes. Loses if any README's figure rises or this build still fails.
    Measured: every figure falls, this build's README lands near 12.4 KB, and the build READMEs over
    the cap go from 3 to 1.
  RESOLVED (agent, 2026-10-04, delegated): price by authored bytes, per S1; the only candidate that
  fits this build and stays fitting as the roster grows.
- **F2** — Is the front matter's `ids:` line priced?
  Options: priced, as authored front matter; unpriced, as generated. `apply_front_matter_ids` writes
  it from the roster, at about 21 bytes per id, so leaving it priced makes the unit count a bound
  again.
  RESOLVED (agent, 2026-10-04, delegated): unpriced, per S1.
- **F3** — Is the authored roster between the `roster:units` markers priced?
  Options: priced; unpriced. The build method makes that table the authored plan, its rows are
