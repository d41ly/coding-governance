## 1. Goal

A reader of `help/` finds each policy key, drive row, kind and instruction unit on a reference page the
one renderer writes from the registry row that defines it, so a page can never say something its row
does not; the concept, task and tutorial pages beside them are authored, and every command any page
shows is run, the tutorial in an adopter fixture. P42: "every user-facing surface is documented from
the fact that defines it", and the owner's FQ-5. Today `help/` holds two hand-written pages and an
index (`help/README.md`), no tool renders a page from a row, and the renderer only substitutes
placeholders (`render()`, `tools/playbook/render_playbook.py:979-1051`). The docs leg that gates pages
is dSafePassage's (TOOL-dSafePassage-13); this unit extends it, `tools/govkit/usage.toml` and the step
gate's class registry `tools/govkit/surface-classes.toml` (TOOL-dSafePassage-10), never a copy of any.

## 4. Design

### Data model

```toml
# tools/playbook/references.toml
[[reference]]
registry = "doc.reference.kinds"
reader = "playbook/core.py:<the kinds reader unit 7 lands>"   # returns [{tag, summary, usage, ...}]; named at the build run
page = "help/reference/kinds.md"
unit = "unit.kinds-register"
```

A reader returns a list of mappings, each with `tag`, `summary` and `usage`; the render reads no other
field. The unit registry's `reader` is unit 9's and the drive table's unit 6's. The policy schema's is
this unit's `read_policy_reference_rows` in `tools/playbook/render_playbook.py`, which finds the
policy kit through the inlined `resolve_kit_dir` (`tools/playbook/render_playbook.py:78-79`), parses
its `catalogue.toml` with `tomllib` and maps each `[[key]]` row's `name` to `tag`, as the step gate's
`policy` class reads the same file (TOOL-dSafePassage-10 §4); it never loads `policy.py`, since a kit
may not import a sibling kit (TOOL-dGroundRules-1 §4 "### Evidence"). A reader is loaded from the
tool root by path, the way the step gate loads a class reader (TOOL-dSafePassage-10 §4 "### Data
model"). A member id is `<class>:<name>` (the same table), so a kind's anchor names `kind:<tag>`.

The rendered page, one section per row:

```markdown
<!-- gov:rendered from tools/playbook/references.toml doc.reference.kinds; edit the registry, not this page -->
<!-- unit: unit.kinds-register -->
# Kinds

## `kind.skill`
<!-- usage: kind:kind.skill 3f2a91c0 -->
A Skill under `skills/<name>/`, made by `core.py new skill`.

`python tools/playbook/core.py new skill <name> --description <text>`
```

The policy page ends with the rows missing a `summary` or a `usage`, unanchored, and a summarised key
another page anchors is a link to it:

```markdown
## `help.enforce`
Documented on [the docs leg's page](../docs-leg.md).

## Not yet summarised (2)
- `flow.wait-ceiling`
- `review.max-rounds`
```

### The run arm

`docs_leg.py --run [--page <path>]` reads every page under `help/`, collects fenced `bash` and `console`
blocks (a `console` line's command is the text
after its `$ ` prompt), and for each page builds one scratch adopter with `build_target` under the
short `%TEMP%` path a fixture repository needs, exports `GOV` as gov's checkout, and runs the page's
commands in order in that target with `bash -c`, each bounded by a timeout. A non-zero exit where the
block declares none, or an exit different from a declared `expect`, is a finding naming the page, the
line and the command's last stderr line. A page whose every block is `run: no` is printed as such and
counted, never green by silence. `help.enforce` governs the verdict, as for the leg's other arms.
