## 1. Goal

A reader of `help/` finds each policy key, drive row, kind and instruction unit on a reference page the
one renderer writes from the registry row that defines it, so a page can never say something its row
does not; the concept, task and tutorial pages beside them are authored, and every command any page
shows is run, the tutorial in an adopter fixture. P42: "every user-facing surface is documented from
the fact that defines it", and the owner's FQ-5. Today `help/` holds fourteen hand-written pages,
PINNED at `05fd1b7f7`, and an index (`help/README.md`), no tool renders a page from a row, and,
unit slots aside, the renderer only substitutes
placeholders (`tools/playbook/render_playbook.py#render`). At `e0768687d` it holds seventeen pages
and the index (PINNED, counted then). The docs leg that gates pages
is dSafePassage's (TOOL-dSafePassage-13); this unit extends it, `tools/govkit/usage.toml` and the step
gate's class registry `tools/govkit/surface-classes.toml` (TOOL-dSafePassage-10), never a copy of any.
The pass lands three reference pages; the units page, every page's unit line and the check over them
land in this unit's later commit, once PLAY-dOrderedCharter-40's unit rows are tracked (section 8 F8,
F10 and F11).

## 4. Design

### Data model

```toml
# tools/playbook/references.toml
[[reference]]
registry = "doc.reference.kinds"
reader = "{prefix}/playbook/render_playbook.py:read_kind_reference_rows"
page = "help/reference/kinds.md"
unit = "unit.kinds-register"   # from the later commit (section 8 F10)
```

A reader returns `{<tag>: {"summary": ..., "usage": ...}}`; the drive, kind and unit adapters add
`"shape": "synopsis"` to each row, so the same function is the class's `rows` in `usage.toml`, and
its keys are the class's members. The render reads no field but `summary` and `usage`.

| Adapter | Reads | `tag` | `summary` | `usage` |
|---|---|---|---|---|
| `read_policy_reference_rows` | the catalogue, through `resolve_kit_dir` | the row's `name` | `summary` | `usage` |
| `read_drive_reference_rows` | `read_drive` over `root`, the drive rows of the kits its deploy selects | `drive.<stage>.<role>`, one per group | the group's `when` clauses, joined by `; ` | the group's distinct `command`s, one per line, in render order |
| `read_kind_reference_rows` | `tools/playbook/core.py#read_toml_rows` over `root`'s register | the row's `tag` | `summary` (F9) | `usage` (F9) |
| `read_unit_reference_rows` | `tools/playbook/instruction_units.py#read_units` over `root`, the units with a `usage` | the unit's `tag` | `text` | `usage` |

The policy schema's adapter finds the policy kit through the inlined
`tools/playbook/render_playbook.py#resolve_kit_dir`, parses
its `catalogue.toml` with `tomllib` and maps each `[[key]]` row's `name` to `tag`, as the step gate's
`policy` class reads the same file (TOOL-dSafePassage-10 §4); it never loads `policy.py`, since a kit
may not import a sibling kit (TOOL-dGroundRules-1 §4 "### Evidence"). It returns every key, a field
the row lacks absent, since the policy page lists the keys lacking one (S2). The other three reach
their kit's modules through `tools/playbook/render_playbook.py#load_units_module`, which puts the
engine's directory on the import path, because the step gate and the docs leg load an adapter by
path, where no sibling module imports otherwise; each joins its file under `root` at the tool root
`tools/playbook/instruction_units.py#derive_kit_prefix` names. A reader is loaded from the
tool root by path, the way the step gate loads a class reader (TOOL-dSafePassage-10 §4 "### Data
model"), the renderer answering its own path with its own module. A member id is `<class>:<name>`
(the same table), so a kind's anchor names `kind:<tag>`. A `reader` value spells the tool root as
`{prefix}/`, as `surface-classes.toml` and `usage.toml` spell theirs, and the rendered page's header
names the declaration's path as the render derives it, never a typed `tools/`, and leaves the
registry tag out of backticks, so the tag index reads no citation there.

as one indented line:

### The run arm

`docs_leg.py --run [--page <path>]` reads every page under `help/`, or the one named, and collects
its fenced `bash`, `sh` and `console` blocks through the leg's own fence reader,
`tools/govkit/docs_leg.py#read_page_lines`, a `console` line's command the text after its `$ ` or
`> ` prompt and a trailing backslash joining the next line, as
`tools/govkit/docs_leg.py#read_page_commands` reads them. A block's marker is the last non-blank line
above its fence. For each page holding a runnable block it builds one scratch adopter with
`build_target` under the short `%TEMP%` path a fixture repository needs, exports `GOV` as gov's
checkout, and runs the page's commands in order in that target, each as
`[resolve_bash(), "-c", <command>]` with the target its working directory, each bounded by a
timeout. A non-zero exit where the
block declares none, or an exit different from a declared `expect`, is a finding naming the page, the
line and the command's last stderr line. A page whose every block is `run: no` builds no adopter and
is printed as such and counted, never green by silence, and a run whose pages hold no runnable
command is the leg's non-verdict, exit 2. `help.enforce` governs the verdict, as for the leg's other
arms.

## 5. Production-readiness checklist

- security: `--run` executes commands written in tracked pages, in a scratch adopter under the run's
  own temp path and never in gov's tree, with no network fetch: a page command reaching the network
  must carry `run: no` and its reason.
