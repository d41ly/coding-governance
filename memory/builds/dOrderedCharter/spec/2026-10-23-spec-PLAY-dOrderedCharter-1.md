## 1. Goal

The charter's 36 practices are one-line rules typed into the template's section 1
(`coding-governance-agents.template.md:13-54`), with no reach and no way for an adopter to choose them
except the one `when:cross-os` fence (gap-found-02). This unit moves them into a shipped catalogue,
`tools/playbook/practices.toml`, where each practice is a tag, a one-line rule and its reach per step
(foundations R1, F1-3 "Catalogue with reach"), and makes the active set a policy, `charter.practices`,
that the renderer reads to write the charter's practice lines (v2:1143, P14).

## 2. Scope (IN)

- **S1** — The catalogue. `tools/playbook/practices.toml` holds one `[[practice]]` row per practice, in
  render order, with the fields S15 fixes: `tag` (`practice.<name>`), `line` (the rule text after
  `[<name>] `), and a `[practice.reach]` table whose keys are `reach.<step>`. It is seeded with the 36
  rows of today's section 1, in today's order and bytes, and the three methodology rows foundations R1
  names, `practice.solid`, `practice.dry` and `practice.tdd`. A top-level `foundation` array lists the
  tags of the governance foundation set, today's 36. Observed by AC1 and AC2.
- **S2** — One optional row field beyond S15, `kit`, naming the kit a line needs, so `practice.roles`
  keeps rendering only where the roles kit is adopted, as its `<!-- kit:roles -->` fence does today
  (template:47-49). Observed by AC5.
- **S3** — The reader and its check, `read_practice_catalogue` in `tools/playbook/instruction_units.py`
  (S10's one reader module). It refuses, naming the row: a tag outside the `practice.<seg>` shape of
  S4's tag grammar, a tag twice, an empty `line` or one over the one-line cap (`ONE_LINE_MAX`, 200,
  `tools/playbook/render_playbook.py:129`) once rendered, a row with no `reach.<step>` key, a reach key
  whose step is not of the `seg` shape, and a `foundation` entry naming no row. Observed by AC2.
- **S4** — The policy. `resolve_active_practices(catalogue, value)` returns the active rows in catalogue
  order. `value` is `charter.practices`, a non-empty set of practice tags (v2:1143). An empty set and a
  tag in no row are refused by name. The key is read with `read_policy_value("charter.practices", root)`
  (PLAY-dOrderedCharter-7 §4), `policy.py get` over `root`'s committed policy, `root` the render's target,
  since the choice is the adopter's. Unset, the row's default is `{ derived = ... }`, v2's default being no
  literal (TOOL-dGroundRules-1 §4), and `get` refuses it, exit 2, with "a derived default no reader
  computes yet" (TOOL-dGroundRules-21 S12). On that refusal alone the render takes the catalogue's
  `foundation` set and prints that it did; any other refusal refuses the render naming the key and the
  reader's line. How a set of practice tags passes the row's value check is §8 F4. Observed by AC3 and
  AC8.
- **S5** — The render. The template's section-1 practice lines become one `{{PRACTICES}}` line inside
  the same one-line region, and `render()` (`tools/playbook/render_playbook.py:979`) expands it into
  `- [<name>] <line>` per active row BEFORE it collects placeholders, so the `{{DEFAULT_BRANCH}}`,
  `{{HELP_DIR}}` and `{{MEMORY_ROOT}}` tokens inside lines resolve as they do today. A row whose `kit` is
  not adopted is left out. The template marker moves to `v4.5`. Gov's re-rendered `AGENTS.md` is
  byte-identical in its practice lines to today's. Observed by AC4 and AC5.
- **S6** — Today's deselection keeps working. A `deploy.toml` `drop_blocks` naming `cross-os` is read
  as the active set without `practice.cross-os`, with a `retired` note naming `charter.practices`, and
  the `cross-os` `[[block]]` row in `tools/govkit/entries/playbook.kit.toml` gains `legacy`, so a seeded
  older template carrying the fence still renders. Observed by AC6.
  **Readers:** by name: `tools/playbook/render_playbook.py`, which reads each `drop_blocks` member
  against the template's fences and notes a retired one (its line 1025); `tools/govkit/entries/playbook.kit.toml`,
  whose `[[block]]` row declares `cross-os`; `WIRE-INTO-PROJECT.md`, whose section on the one block
  that is not about a kit tells a single-OS team to drop `when:cross-os`; and `tools/roles/README.md`,
  which cites `cross-os` as fenced by `when:cross-os` · by value: `tools/roles/agents/gov-builder.agent.md`
  and `tools/roles/agents/gov-diff-reviewer.agent.md`, whose `rules:` lists take `cross-os?` as
  optional, so a charter rendered without the line still joins.
- **S7** — The page. `help/charter.md`, linked from `help/README.md`, says what the catalogue is, how
  an adopter reads its active set and how it chooses one. Observed by AC7.
- **S8** — The key's row. The `charter.practices` row of `tools/policy/catalogue.toml` lands with
  dGroundRules, owner dOrderedCharter (v2:1143), with no `summary` or `usage` and its name on the
  shrink-only `tools/policy/unsummarised-keys.txt` (TOOL-dGroundRules-1 S3, S6). This unit adds no row: it
  fills the row's `summary` and its `usage`, a line the row admits
  (`charter.practices = ["practice.yagni", "practice.reuse"]`, once F4's probe finds tags admitted), and
  drains the name in the same commit with `python <prefix>/policy/policy.py lists --write`. Observed by
  AC9.
