### M3. The bash-to-Python path handoff has no MSYS-to-Windows conversion, so the turnstile silently reads zero (id 11)

- **Where:** spec 18, section 4 "The environment a leg gets" (Added) and "The turnstile" (What is read).
- **What is wrong:** The scratch dir comes from `mktemp -d "${TMPDIR:-/tmp}/gate-profile.XXXXXXXX"` in bash. The turnstile key comes from the runner's `cd ... && pwd` expression (run-gates.sh:1513-1514). Both return MSYS spellings such as `/tmp/...` and `/c/Users/...`. Python then opens `raw/<i>.out` under the first and lists `gate-bar-queue/` and beacon `pid` files under the second, and the spec never says to convert either path.
- **Consequence:** A native Python resolves `/c/Users/x` to `C:\c\Users\x`. A probe confirmed `isdir` reads False. The raw-capture open fails or lands in a stray tree. Worse, "an absent key or queue reads as empty", so every leg records `ts_holders` and `ts_queued` as 0, and `read_runs` treats its readings as uncontended. AC15 and AC1 would expose this at build time, which keeps the effect contained.
- **Fix (skeptic: SOUND):** State that every path bash hands back is converted once with `cygpath -m` (or `-w`) before Python uses it. The envelope records both spellings: the POSIX one the legs see as TMPDIR and the Windows one the tool opens. A key that cannot be converted, or whose spelling does not match its converted form, is a refused read, not an empty one. AC15 asserts that the envelope's `turnstile_dir` passes `os.path.isdir`.
- **Left-shift gate:** a bug-class checklist entry for "a path crossing from MSYS bash to native Python is converted with cygpath, and an absent result is never read as empty", plus a lint on `measure_legs.py` that flags a subprocess stdout used as a path without passing through the converter.

### M12. A failed job assign or resume leaves a suspended root that hangs the profile (id 35)

- **Where:** spec 18, section 4 "Launching a leg" step 3, section 5 security and error states.
- **What is wrong:** The root is created CREATE_SUSPENDED, then OpenProcess, AssignProcessToJobObject, a toolhelp snapshot and ResumeThread run in turn. The spec states no outcome for any of them failing, and section 5 forbids the only cleanup available: "the code never calls a terminate".
- **Consequence:** A failed assign (for example under a host job that forbids nesting) or a failed resume leaves a suspended bash that never exits. Because "a leg that never ends keeps the run open", the profile hangs for good, and under `--serial` no later leg runs. Stall detection reports STALLED, which describes the leg wrongly. The path is narrow.
- **Fix (skeptic: SOUND):** In step 3, state that a failed OpenProcess, assign, snapshot or resume terminates the still-suspended root through the handle the tool already holds. This is the only permitted terminate, on a process that has executed nothing. The leg records `fail` with rc and reason `launch: <call> <winerror>`, and the run continues. Carve this case out of section 5's "never calls a terminate". Add a selftest arm that stages an assign failure, for example by pointing build_job at a closed handle, and asserts the leg records the launch failure and the run exits 0.
- **Left-shift gate:** a spec-template prompt in section 5 that every multi-step OS launch sequence states the outcome of each step's failure.

### M13. The turnstile read treats normal beacon and ticket churn as a refused read (id 36)

### M14. Raw unredacted captures survive a crash or a kill with no record (id 38)

- **Where:** spec 18, section 2 S11, section 4 "The record" (raw capture deleted) and Exit, section 5 security.
- **What is wrong:** F2's guarantee that only the redacted copy survives covers only a normal leg or run end and a Ctrl-C. An unhandled exception, a TerminateProcess (from `kill`, Task Manager or a closed console) or a power loss leaves every `raw/<i>.out` unredacted in a scratch dir that "is never swept", with no `raw_kept` entry.
- **Consequence:** The owner resolved F2 (b) on charter `[security]` grounds, because an unredacted capture is a credential leak. On these paths the leak persists indefinitely under `%TEMP%/gate-profile.*`, and nothing tells the operator or the next run. The leak stays in the operator's own temp dir, which keeps the effect contained.
- **Fix (skeptic: UNSOUND; the corrected fix):** At start, write the profiler's own Windows pid and process creation time into the scratch dir. A later run treats an earlier `gate-profile.*` scratch as abandoned only when that pid with that creation time is no longer alive. For each abandoned scratch, it redacts each `raw/<i>.out` into that run's record as `<i>.log.recovered`, deletes the raw file, and names each one in its own envelope as `raw_recovered`. Add an arm that stages a profiler killed mid-leg and then runs a second profile beside a live first one. Assert that the live run's raw captures are untouched and that the dead run's hold no planted credential.
- **Left-shift gate:** a checklist entry for "a guarantee that depends on cleanup states every ending it does not cover, and a sweep of another run's scratch proves that run dead by pid and creation time".
