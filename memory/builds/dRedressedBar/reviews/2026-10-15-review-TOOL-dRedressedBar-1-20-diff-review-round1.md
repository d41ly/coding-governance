## HIGH

### H1. The dead-run sweep trusts a planted `owner.json` and writes through symlinks (id 1)

- **Where:** `tools/run-gates/measure_legs.py:1406`, with `derive_abandoned_scratch` (1359-1385), `write_recovered_logs` (1406-1407), `write_atomic` (1025-1027) and the call in `main` (1545).
- **What is wrong:** The S38 sweep reads every sibling `gate-profile.*/owner.json` under `${TMPDIR:-/tmp}` and checks only its pid and creation time. It then writes the recovered log into whatever directory the file's `record` field names, tested only by `os.path.isdir(record)`. It reads `raw/<n>.out` with a plain `open(raw, "rb")`, which follows symlinks. `write_atomic` opens `dest + ".tmp"` with O_CREAT|O_TRUNC and no O_EXCL, so it writes through a link already planted at that name.
- **Consequence:** Every `--serial` or `--concurrent` run performs the sweep. A process that can write only to the temp dir needs only a dead pid. It can then make the operator's run copy any file the operator can read into a directory of its choice, with only URL userinfo masked. It can also create or overwrite `<n>.log.recovered` files anywhere the operator can write. The finder's probe planted a `record` outside the out root and a `raw/1.out` symlink to a file holding `SECRET-TOKEN=abc123`, and the secret landed in the chosen directory. A same-user process with no confinement gains nothing, so the path needs a sandboxed agent or a shared TMPDIR. That narrow path is why this is high and not blocker.
- **Fix (skeptic: SOUND):** Treat `owner.json` as untrusted in `derive_abandoned_scratch` and `write_recovered_logs`. (1) Never follow `record`. Write recovered logs under this run's own `run_dir/recovered/<scratch name>/`, or accept `record` only when its realpath is a direct child of the same out root and is not a reparse point. (2) `os.lstat` each `raw/<n>.out`, the scratch dir and `raw/`, and skip anything that is not a regular file or directory or that carries an `st_reparse_tag`. (3) Remove any stale entry at the temp name, then create the temp file with O_EXCL, so a pre-planted `.tmp` link is never written through. Add a selftest arm that plants a `record` outside the out root and a symlinked raw file, and observe it RED against the current code first.
- **Left-shift gate:** a bug-class checklist entry, "a path read from a file in a shared directory is a destination only after it is pinned under the tool's own root", plus a static arm that reds any `write_atomic` whose temp open lacks O_EXCL.

### M1. An interrupted run does not name a capture kept raw for a leg that already ended (ids 2, 14)

- **Where:** `tools/run-gates/measure_legs.py:1737`, the `except KeyboardInterrupt` branch (1737-1747), with `write_leg_end` (1637-1658, `raw_pending` set at 1650), `write_leg_capture` (1438-1439) and the run-end loop (1757-1761).
- **What is wrong:** When a leg's root exits while processes still run in its job (`left_running` > 0), `write_leg_capture(final=False)` keeps the unredacted `raw/<i>.out` and the leg is marked `raw_pending`. Only the run-end loop retries that capture or adds it to `raw_kept`. This contradicts spec 18 §5 (lines 743-744) and the README (line 761), which say a capture the tool cannot delete is named in `raw_kept`. Only a later profile's S38 sweep on the same host would recover it. The effect is contained to the owner's scratch dir.

Add an arm that interrupts a run after a leg has ended with an orphan (`stall.sh` or `forks.sh` with a background child) and asserts the capture is named. Observe that arm RED first.
- **Left-shift gate:** a checklist entry, "every exit path that writes the envelope runs the same capture-accounting step", and a single `finalize_captures` helper both paths call.

### M2. The interpreter probe counts a venv redirector, so a venv PYBIN refuses every profile (id 3)

- **Where:** `tools/run-gates/measure_legs.py:859` (`JOB_CHILD_PROGRAM`), read by `resolve_launcher_aliases` at 960.
- **What is wrong:** The probe's child program spawns `sys.executable`. Every fixture leg (`spawn.py:3-13`, `churn.py:11`, `hog.py:11`) deliberately spawns `sys._base_executable`, because a Windows venv redirector adds a process of its own. Under a venv interpreter the probe's child adds two processes, so `with_child - without_child` reads 2, not 1. The skeptic reproduced the redirector with a scratch `python -m venv` on this host.
- **Consequence:** Whenever PYBIN or GOV_PYTHON resolves to a Windows venv python, every `--serial` and `--concurrent` run exits 2 before the first leg with the false reason "the interpreter keeps no child inside a job". The `measure-legs selftest` leg also reds there, at S14.
- **Fix (skeptic: SOUND):** Spawn the base interpreter in `JOB_CHILD_PROGRAM`, the rule the fixtures follow: `import subprocess, sys; exe = getattr(sys, '_base_executable', None) or sys.executable; sys.exit(subprocess.call([exe, '-I', '-c', 'pass']))`. Add a selftest arm that runs `measure_job_children` against a scratch venv interpreter and expects a difference of 1.
- **Left-shift gate:** a static arm that reds any `sys.executable` spawn inside `measure_legs.py` or its fixtures where `sys._base_executable` is the stated rule.

### M4. The update gained loop decodes adopter stderr strictly, so its new refusal line can lie (id 5)
