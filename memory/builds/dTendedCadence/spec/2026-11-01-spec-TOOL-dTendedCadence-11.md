## 1. Goal

The night pass makes following a playbook the `repeat` disposition and says "a cyclic playbook is a
cadence item that files `repeat` intakes (dTendedCadence). The owner will expand it later; this is its
seat" (night-pass:100-110). Nothing lets a playbook say it recurs: the declaration block has no cycle
field (`memory/guides/PLAYBOOK-TEMPLATE.md:33-67`), and no cadence item files a `repeat`. This unit
builds the seat and nothing past it: a playbook declares its cycle and the pieces each cycle builds,
the playbook leg validates both, and one cadence row per period kind files one `repeat` intake per
cyclic playbook per cycle.

### The intake

The text S5 hands to the filing, one key per line, never quoting the playbook's body:

```
repeat <path>
playbook: <path>
pieces: <cycle_pieces>
cycle: <daily|weekly> <period>
```

The first line is the request; `playbook:` and `pieces:` are what ask TOOL-dTendedCadence-24's derived README copies into
its front matter.

### Alternatives rejected

- **One cadence row per playbook.** It puts a playbook's recurrence in Runtime's registry instead of
  in the playbook, a second fact about one record. The test: rename the fixture playbook; the
  declaration follows the file, while a row naming its path names a deleted file and files a `repeat`
  the resolver refuses.
- **A policy key naming the cyclic playbooks.** No clause names one, so it is a public surface outside
  the grant; the test is the catalogue, which holds no such key (`tools/policy/catalogue.toml`).
- **One daily row filing weekly playbooks too.** Its daily witness lets a weekly playbook file seven
  times a week unless the filer keeps its own per-week ledger; the two-row form needs none.
- **The piece count derived from the playbook's `grain` matches.** A cycle's pieces do not exist when
  it is filed, so the glob counts the last cycle's output, not this one's.

## 5. Production-readiness checklist

- security — a playbook path reaches the intake text only after `check_is_playbook`, which refuses a
  newline, a leading `-` or a `..` segment with exit 2 (TOOL-dIndexedDesign-10 S2); the text quotes no
  playbook body. A cadence intake ratifies nothing (§3), so a planted cyclic playbook reaches an owner
  breakpoint, never a build.
- perf / scale — one `git grep` and one resolver call per candidate, once per cycle per fleet.
- error / empty / loading states — no cyclic playbook: one `0 cyclic playbook(s)` line, exit 0; the
  unattended kit absent: `playbook-cycle — no unattended kit · nothing filed`, exit 0; a refused
  playbook: its `cycles: refused` line, the others filed; the filing failing: exit 1, so the period
  lease releases as a hand-over and the next wake retries (TOOL-dWellOiledMachine-13 S6 step 5).
- observability — one line per playbook, filed or seen; the intake receipt names the row as filer.
- risks — a weekly cycle whose build outlives its week accrues `seen` clauses rather than builds; the
  owner reads the count on the intake.
- testing — the fixture plants of §6, and §7's two arms.
- migration — N/A: two optional keys; no tracked playbook declares either.
- user docs — `help/maintain.md` (S7) and the template's paragraph (S1).
