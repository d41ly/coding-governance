## 1. Goal

Give observability its two record kinds (layer-expansions:212): the maintenance record, one per
Maintain period or event run, written as `maintain.record-when` says, and the run record, written by
the journal reader when the journal shows a run closed, as `observability.run-record` says: for every
run, for a run with an anomaly, or never (layer-expansions:251-253). Today the run record is written on
every run that served a unit, whatever the anomaly, with no key to read; the unattended kit still
instructs the agent to run its renderer (`tools/unattended/VERBS.template.md:908-920`,
`tools/unattended/SKILL.template.md:157-159`); and no maintenance record kind, home or writer exists
(gap-maint-05, gap-maint-14).

## 4. Design

### The run record, as the journal reader writes it

```
driver verb --close | --abort | --landed (primary)
  -> its END line first (write_runlog_end, unattended.sh:14300-14302)
  -> write_run_record -> python runlog.py record <slug> --write
       model = build_run_model(...)              # reads the driver journal through read_journal
       derive_closing_end(model)  none           -> "not closed in the journal", write nothing
       read_run_record_policy(root)
         none                                    -> "observability.run-record is none", write nothing
         on-anomaly and scan_anomalies(model)=[] -> "no anomaly under on-anomaly", write nothing
         per-run, or on-anomaly with an anomaly  -> write_record(...)   as today
```

The driver already writes its END line before it renders (`unattended.sh:14286-14288`,
TOOL-aMendedFleet-63), so the closing END is on disk when the reader reads the journal: the record is
written when the journal shows the run closed, literally. `derive_closing_end(model)` reads the
model's verb events (`model.py:1676-1680` already finds the terminal END the same way) and returns the
event or None; `--close` onto `LANDING` counts as closed because the close is the verb that ends a run
that lands, and `PHASES_TERMINAL` (`model.py:106`) is left unchanged. `write_run_record`'s parsing of
`runlog: record written` (`unattended.sh:14316`) already treats any other line as the answer, so a skip
needs no driver change.

### The anomalies

| Kind | Trigger, over the run's own lines | `ANOMALY_SOURCES` |
|---|---|---|
| `refusal` | a clean driver END with `rc` other than 0 and a non-empty `checks` | `driver` |
| `ceiling-breach` | a gates line whose `wall_breach` field is non-empty (`tools/run-gates/run-gates.sh:2444-2467`) | `gates` |
| `dead-probe` | a coverage source whose state is `dead` (`model.py:991-993`) | `driver`, `gates`, `pushes` |
| `red-bar` | a gates line whose `verdict` is `RED` (the value `red-behind-zero` reads, `model.py:1357`) | `gates` |

`refusal-loop` stays, the repeated case at `REFUSAL_LOOP_MIN` (`model.py:141`); a run with one refusal
now carries `refusal` and no loop. Each kind renders in the record's Anomalies table as the others do,
and the closed-list rule (`model.py:53-55`) owes each a fixture, the `New arm:` line in §7.

### The maintenance record

```markdown
# Maintenance record — 2026-11-01

**Key:** 2026-11-01
**Base:** <40-hex sha the readings were taken at>
**Read:** 27 of 27

## Readings

| Reading | Value | Of | Live | Route |
|---|---|---|---|---|
| `ledger_rows_contradicting_git` | 0 | 41 | yes | in pin |

## Lines

log-band: 0
security-head: none
retrofit-heat: not-installed
unread-nodes: none
over-pin: <signal><TAB><detail key>
```

The path is `<MEMORY_ROOT>/maintenance/<date>-maintenance-<key>.md`, `<date>` the UTC day of the
write as an ISO date, `2026-11-01` for a write on that day. `<key>` is the run's period key (`2026-11-01` daily, `2026-W44` weekly,
TOOL-dWellOiledMachine-13 S5) or its event key `<event>.<sha12>` (I7, TOOL-dTendedCadence-8's), held at
the write boundary to `^\d{4}-(\d{2}-\d{2}|W\d{2})$` or `^[a-z0-9][a-z0-9-]*\.[0-9a-f]{12}$`, so no
key is a path; anything else exits 2 before a write. The file is written through a temp file and
`os.replace`, contained under the home, as `write_record` does (`tools/runlog/record.py:1179-1201`).

Three facts are the `fields` form of the record-kinds registry, one `**Key:**` line each in this
order: `**Key:**`, `**Base:**` and `**Read:**`. The per-period facts are I10's lines, each
`<name>: <value>` at column 0 under `## Lines`, in this order: `log-band:` (the log-band count,
TOOL-dTendedCadence-14's), `security-head:` (the last reviewed head, 40 hex, `none` until a review has
run, TOOL-dTendedCadence-13's), `retrofit-heat:` (the period's share as its unit spells it, `<value>/<of>`,
`not-installed` where that reading is absent, TOOL-dTendedCadence-9's), `unread-nodes:` (one line per
node a `lease-holder` run left unread, `none` otherwise, TOOL-dTendedCadence-16's), then one
`over-pin:` line per offender standing over its pin, its value an I5 offender key verbatim, `<signal>`,
a TAB, its detail key (`drift_report.py:3985-4000`). The writer writes each value it is handed as one
line, refusing a value carrying a line break, and grades no value's grammar, which is its writing
unit's. The counts of fixed and filed readings are the Readings table's routes, derived, never a line.

stdin is one JSON object: `{"read": [<n>, <m>], "readings": [{"reading", "value", "of", "live",
"over", "route", "keys"}], "fields": {"log-band", "security-head", "retrofit-heat", "unread-nodes"}}`,
the `fields` argument of both functions, each member written as its I10 line, `unread-nodes` a list; a
missing member takes the value the example shows, and the `over-pin:` lines are
the `keys` of every reading with `over` true. A **finding**, for `on-finding`, is a reading with `over`
true or `live` false. `read_newest_record` returns `{"key", "base", "read", "log-band",
"security-head", "retrofit-heat", "unread-nodes": [...], "over-pin": [...], "path", "commit"}`, the
newest by the rule TOOL-dTendedCadence-15 F3 states, so the leg and the reader agree on one record.

## 5. Production-readiness checklist

- security — the one new write path, the maintenance record, validates its key at the write boundary so
  no key becomes a path component other than the home's own, and writes contained under the home; the
  run record's write path is unchanged.
- perf / scale — one bounded policy subprocess per record write; a maintenance record is one file per
  run, so `on-finding` is the owner's lever on its count.
- error / empty / loading states — a refused policy read takes `per-run` or `every-period` and says so;
  `newest` over an empty home exits 1 rather than reading as clean; a reading list that is empty writes
  `**Read:** 0 of <m>`; a line value carrying a line break exits 2 before a write.
- observability — every skip prints its reason on one line, so a run with no record is told from a run
  whose record failed.
