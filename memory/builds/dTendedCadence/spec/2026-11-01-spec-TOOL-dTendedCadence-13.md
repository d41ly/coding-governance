## 1. Goal

The security lens runs only when a build opts into a review, and nothing re-reads what landed for
security on a period (gap-maint-12, the owner's NP-19: "Weekly by default, owner-adjustable by
policy"). This unit makes the review recur as `maintain.security-review` says, `weekly` by default,
`every-landing` or `off`: a cadence item running dFairHearing's `security` lens over everything that
landed since the last head it reviewed, launched as an act, its security findings filed through
`maintain.file` and its reviewed head kept in the maintenance record, so the next run starts there.

## 3. Non-goals (OUT)

- A whole-tree reading. The harness diffs `base...head` (`tier2-review.js:1081`) and its skeptic
  refutes a defect "present unchanged at the base" (`:1159`), so a review reads what a range
  introduced; the clause's "over the landed tree" is carried as every landed range read once, and the
  difference is deviation 131 (§8 F1).
- A security-only lens set. `LIGHT_LENSES` leaves `security` out (`:804`), `preset` is refused beside
  `diff-review` (TOOL-dFairHearing-2 S1) and `optIn` keeps five slots (TOOL-dFairHearing-3 S2, S3), so
  the run is the full five-lens review and only the security lens's findings are filed (§8 F2). A
  `lenses` argument is a follow-up for dFairHearing, filed only if the cost is measured too high.
- Patch-routing a finding. A security finding names no fix in `maintain.fixes`, so none goes through
  `item.maintain.patch`; every one is an ask.
- Maintain's own events and the session-start host: TOOL-dTendedCadence-2 adds them to S7's tables.
- The landing record: dShippedRelease's, not an ancestor; the landed tip is the default branch's.

## 4. Design

### Evidence

- The lens and the key row exist: `DIFF_LENSES` opens at `tier2-review.js:774` with `security` first
  (`:776`), each finding carries `lens` (`:632-634`), and the catalogue row is `catalogue.toml:1175-1179`,
  default `weekly`. Nothing runs the lens on a period.
- A range is what one review can read: the whole history at `7e48dac3` diffs 9,736 files and 2,011,940
  inserted lines from the root commit, one week to that tip 2,824 files and 318,605 lines (`git diff
  --shortstat`, PINNED at `7e48dac3`, 2026-11-01).
- A cadence tick runs an argv; a Workflow needs an agent session, and `launch_act` is the bridge
  (scout D, row 13).

### One week, then a landing

| Run | `security-head` before | Range | Writes |
|---|---|---|---|
| first `weekly` period | none | week-start commit...tip | `security-head: <tip>` |
| next week | `<tip>` | `<tip>`...new tip | the new tip |
| `every-landing`, landing `L` | `<tip>` | `<tip>`...`L` | `L` |
| a failed act | unchanged | the same range again next wake | nothing |

### Alternatives rejected

- **A whole-tree reading from the root commit on the first run.** The test: its diff at `7e48dac3` is
  9,736 files, past what a lens reads, so the record would certify a tree it did not read.
- **`every-landing` as a daily period.** A day batches every landing into one range, so a landing is
  reviewed up to a day late and the value means `daily`. The test: two landings an hour apart give two
  event keys under S7 and one period key under a daily row.
- **The event wake inside TOOL-dWellOiledMachine-59's tick.** Its `events` field is declared and no
  parent fires it; an ask would leave `every-landing` unbuildable here. The tables are this build's,
  and the second cadence row that needs events outside this build extracts them to the runtime kit.
- **The review report committed beside the maintenance record.** The findings travel as asks and the
  head as one line; a report under the scratch worktree is read and removed, so no free-named file
  lands in the memory tree.

## 5. Production-readiness checklist

- security — the act is launched through `launch_act`, whose argv never carries a permission bypass
  (TOOL-dWellOiledMachine-1 S2); the review reads a detached worktree of a landed sha and writes only
  inside it; `base` and `head` are full shas the harness re-checks; nothing from the review reaches a
  shell but the shas. A finding's text becomes an ask clause through the filer's own write boundary.
- perf / scale — a week of this repository is about 2,800 files of diff (§4, PINNED); one five-lens
  review per week, or per landing under `every-landing`, which the owner chooses knowing its cost.
- error / empty / loading states — nothing landed: one line, no launch; the act failing or returning
  a refused document: exit 1, no head written, the range re-read next wake; the policy or runtime kit
  absent: one refusal line, exit 0, nothing launched; no maintenance record: the period-start base.
- observability — one line per run naming the mode, the range, the filed and the counted findings.
- risks — under `every-landing` a burst of landings launches one review each; their ranges overlap
  until the first writes its head, and the filing key folds a repeat into a `seen` clause.
- testing — the fixture plants of §6, and §7's arm.
- migration — N/A: a new row, a new record line and summary text.
- user docs — `help/maintain.md` (S9).
