## 1. Goal

A reading over its pin today gets one response, a printed `OVER PIN` (`tools/drift-audit/drift_report.py:4404-4417`),
and nothing files it, holds it or sends it anywhere. This unit builds the item `maintain.file`, which answers each
offender as `maintain.on-breach` says: `file-ask` files the ask into Plan's triage, `red-leg` files nothing and
registers a leg at Test's leg-pack point that reads the newest committed maintenance record offline and reds while an
offender stands over its pin, and `report` files nothing and sends the maintenance record through the notification
adapter (the clause, the owner's FK-5-5 and the whole-design audit's B5-F11).

## 4. Design

### Evidence

At this base nothing files a breach. `--check` prints `OVER PIN` or `over pin (report only)` per signal
(`drift_report.py:4404-4417`), and `render_drift_offenders` keys each offender `<signal>\t<detail key>`
(`:3985-4000`). The ask renderers exist and no code files an ask through them: `render_ask_row`, `render_clauses`
and `render_scope_row` (`tools/memory-tree/backlog.py:1516-1529`) have callers only in that module's own fixtures.
The one machine ask filer, `write_inherited_asks` (`tools/unattended/unattended.sh:10020`), files into the closing
build's own `BACKLOG.md` with an id minted under that build's slug by `derive_ask_seq` (`:9780`); a cadence run
closes no build. An ask always lives in a build's `BACKLOG.md` here (`.memory-tree.conf:732-734`), and a build is
opened only from an owner's id list that the owner lands (`gen_build_index.py:4123`). So the ask reaches the
backlog through the core's route for a prompt that reaches no owner session: a cadence intake, which Entry may place
only as `breakpoint` or `ask` (TOOL-dWellOiledMachine-27 S4), §8 F1.

Drift's own history cannot back the leg: it is node-local, and its own comment says a verdict built on it "would not
reproduce at a sha" (`drift_report.py:3860-3862`). The leg reads the committed record instead (settled 4).
`maintain.on-breach` reads `file-ask` today (`python tools/policy/policy.py get maintain.on-breach`, exit 0, probed at
this base) and its row carries no summary (`tools/policy/unsummarised-keys.txt:118`).

### Data flow

```
item.maintain.read / direct / patch / levels ── breaches ──▶ run_breach_route
   file-ask ─▶ open ask with the marker? ─ yes ─▶ SCOPE row, seen clause          (seen)
              └ no ─▶ intake.py file, stable text ─ key on record ─▶ receipt     (seen)
                                                   └ new key ─▶ intake          (filed)
   red-leg  ─▶ nothing filed; the record's over-pin: lines                       (held)
   report   ─▶ nothing filed; run_breach_report after item.maintain.record       (reported)
every route ─▶ item.maintain.record

maintain_file.py leg ── red-leg? ── read_newest_record at HEAD ── over-pin: count ── run_signal_leg
```

- **Declaring the leg only under `red-leg`.** Rejected by §8 F2: a declaration is static data the factory renders,

## 5. Production-readiness checklist

- security — the ask text carries a reading name, a hash and an offender key, never a secret; `report` sends only
  after the secret scan; the leg reads the object database and fetches nothing; the one tracked write outside an
  intake is a `SCOPE` row naming an ask whose text carries this unit's own marker.
- perf / scale — one `git grep` and one generator read per breach; the leg runs one `git log -1` and one `git show`.
- error / empty / loading states — no breach: nothing printed and nothing filed; a refused policy read: the default
  with its `NOTE:` line; no committed record under `red-leg`: the dead probe.
- observability — one `file —` line per breach and one `report —` line per send.
- risks — under `red-leg` an offender reds every branch until a later record drops it; that is the value's meaning.
- testing — §7's `New arm:` line, staged against a module that is absent at this base.
- migration — N/A: no row exists to move; the catalogue row keeps its values.
- user docs — `help/maintain.md` (S10).
