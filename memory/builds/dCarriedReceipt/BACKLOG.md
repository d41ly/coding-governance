Measured here 2026-08-25: rounds 1-3 of dCarriedReceipt's spec audit ran in a prior session and left no `review` rows anywhere a later run can read; round 3 confirmed 3 blockers and round 4 confirmed 3, which is exactly `review_state`'s NON-CONVERGENT condition (`:3065`), and it returned `CONVERGING` because `n` was 0. The prior rounds are recoverable only from commit subjects. The fix is not obviously "read the retired records" — a run may legitimately re-open a subject a previous run closed — so the question is whether the sequence belongs to the SUBJECT rather than the run, which would put it in the build folder beside the spec. → tools/unattended/
- TOOL-dCarriedReceipt-2 · filed 2026-08-25 · `--review` makes `CONVERGED` terminal for a subject (`unattended.sh:3135`, refusing a later round because it "would rewrite that history") while M4 makes a spec whose rev moved since its last review UNREVIEWED again. The two rules meet head-on for any spec a round both clears of blockers and edits in the fold, which is the ordinary case: a round that finds one high and no blocker converges the subject and then changes the document. Recording the round honestly wedges the next one; deferring the record leaves the loop's own history incomplete. Worked around here 2026-08-25 by recording round 4 only for the two subjects carrying blockers and the four specs taking no edit at all, and deferring the nine that take a fold until their text is final — a judgement no rule states and nothing checks. Either the terminal rule needs a rev-keyed exception, or `CONVERGED` needs to mean "converged AT rev-N". → tools/unattended/
- TOOL-dCarriedReceipt-3 · filed 2026-08-25 · a FOLD pass legitimately spans many units, and the dispatch machinery cannot express one. `pass_commit` (`lib-unattended.sh:98-109`) closes a declaration only when some commit between the declaration anchor and HEAD carries the unit id IN ITS SUBJECT and touched a declared path, and the build method's M6 states the same rule as "commit at the end of every pass, with the unit id in the subject". Both assume one unit per pass. Measured here 2026-08-25: the round-4 fold was five concurrent passes over 11 specs declared through `--dispatch`, and its single commit subject could not name eleven ids, so none of the five declarations ever closed. The next round's `--dispatch` then refused all three of its declarations with check 49 -- "a sibling pass in the same group already declared" -- naming the round-4 rows, and the run had to fall back to sequencing a fold that was provably disjoint. The refusal is CORRECT and its message is the problem: it reports the collision without reporting that the colliding pass never closed or why, so the reader diagnoses a disjointness error that does not exist. Either the closing rule needs a shape a multi-unit pass can satisfy (a trailer listing ids, say, rather than a subject), or check 49's message must name the unclosed pass's missing commit. → tools/unattended/
- TOOL-dCarriedReceipt-4 · filed 2026-08-25 · a spec that is DELIBERATELY never closed cannot be cited from tracked source without permanently redding `non_terminal_specs_cited_by_product_source`. `memory/builds/aQuarriedLantern/spec/2026-08-03-spec-aQuarriedLantern-1.md` says so in its own status line -- "NOT CLOSED — §8 Q6 is deliberately open" -- and it has read INPROGRESS since 2026-08-03. Measured 2026-08-25: DEPL-dCarriedReceipt-10 S7 declares gov's three forked memory-recall sources and its `record` field wanted the id that ratified the fork, which is exactly that spec; citing it took the signal from a baseline of 2 to 3 permanently, against pin 2. Worked around by pointing `record` at DEPL-dCarriedReceipt-10 instead, which is terminal and is the unit that adjudicated the three declarations -- accurate, but it is not the id that ratified the FORK, and the field's own refusal message asks for that one. The signal cannot currently distinguish a spec parked open by design from one a run left non-terminal by accident, and those are opposite situations: the first is a stable fact and the second is a transient. Either the signal needs a way to exempt a deliberately-open spec (a status distinct from INPROGRESS, or a waiver registry like the gate's `*.txt` ones), or a deliberately-open spec needs a terminal companion id that product source can cite. → tools/drift-audit/
