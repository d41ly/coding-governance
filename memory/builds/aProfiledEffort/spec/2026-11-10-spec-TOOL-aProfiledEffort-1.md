## 1. Goal

The effort policy holds one set of levels, and every role agent is `model: inherit`, so the same
levels apply whatever model the session runs. The owner's prompt asks for a profile per model:
today's levels stay the default, Claude Fable of any version runs every role and stage at `medium`,
and a later model takes its own levels by adding one table. This unit gives
`tools/roles/house/policy.toml` named profile tables, validates them in the policy's one validator,
seeds `fable`, and gives the two resolvers an optional model. The record is
`memory/builds/aProfiledEffort/prompts/2026-11-10-prompt-TOOL-aProfiledEffort-1-brief.md`.

### Data model

The seeded lines, placed after `[effort.stages.spec-write]` and before `[gates]`:

```toml
[effort.profiles.fable]       # a table per model family; an unmatched model takes the tables above
match = ["fable"]             # one word of the model id, any version, as in claude-fable-5-2
default = "medium"            # names no role and no stage, so every one runs at medium
# [effort.profiles.<name>.roles] and [effort.profiles.<name>.stages.<workflow>] take the keys of the
# tables above. A profile reaches an agent at dispatch, never through its rendered agent type.
```

A profile table holds four keys and no other.

| Key | Required | Holds |
|---|---|---|
| `match` | yes | a non-empty list of words, each one run of lower-case letters and digits |
| `default` | yes | the level of every role and stage this profile does not name |
| `roles` | no | a table of agent role slot to level, the grammar of `[effort.roles]` |
| `stages` | no | one table per workflow of stage key to level, the grammar of `[effort.stages.<workflow>]` |

`[effort]` gains the one key `profiles`. `POLICY_TABLES` does not move.

### Matching

The words of a model id are its maximal runs of letters and digits, read after lower-casing. A
profile matches a model when one of its `match` entries equals one of those words. An entry is a
whole word, never a substring.

| Model named | Words | Profile |
|---|---|---|
| `claude-fable-5-2` | claude, fable, 5, 2 | `fable` |
| `claude-fable-6-20270101` | claude, fable, 6, 20270101 | `fable` |
| `us.anthropic.claude-fable-5-2-v1:0` | us, anthropic, claude, fable, 5, 2, v1, 0 | `fable` |
| `Claude Fable 5.2` | claude, fable, 5, 2 | `fable` |
| `claude-opus-4-7` | claude, opus, 4, 7 | none |
| `affable-1` | affable, 1 | none |
| none, or an empty string | none | none |

`resolve_profile(policy, model)` returns the matched profile's name, or `None`. When two profiles
match one model it raises a `RolesError` naming the model and both `effort.profiles.<name>.match`
keys, under R12, so no profile wins by file order. A policy with no `profiles` key matches nothing.

### Resolution

The level table for a model is the matched profile's table, else `[effort]`.

- A role's level is that table's `roles` entry for the slot, else that table's `default`.
- A stage's level is that table's `stages.<workflow>` entry for the key, else the level of the slot
  the workflow maps the key to, read from the same table.

A matched profile is read alone. `[effort.roles]` and `[effort.stages]` never reach a model a
profile matches, which is what "its own default, role and stage levels" means in the brief. With
no model named, and with a model no profile matches, both functions return what they return today.

### Alternatives rejected

- **A profile laid over the default tables.** A missing entry would fall through to
  `[effort.roles]`, so `fable` would have to name every role the default tables set above `medium`,
  and a role added there later would run at that level on Fable. The brief gives a profile its own
  default.
- **A top-level `[profiles]` table.** It derives a new legacy-homes row, which the policy kit's
  shrink-only list refuses.
- **The first matching profile wins.** It makes a level depend on table order in an owner-edited
  file. The brief has the validator refuse two profiles matching one model.
- **A second resolver pair for the model case.** Two answers to one question. One optional argument
  on the two functions keeps one resolution.
- **A model argument on the render.** A rendered file cannot follow the session's model (§3).

## 5. Production-readiness checklist

- security: the model id is untrusted input from a dispatcher. It is lower-cased and split by one
  pattern, compared with validated words, and printed only inside a refusal. It reaches no path, no
  shell and no write. No grant moves.
- perf / scale: one pattern split and one pass over the profiles per resolve; nothing on a hook path.
- error / empty / loading states: every profile defect refuses through R12 with its dotted key. No
  model, an empty model and an unmatched model all take the default tables. A model two profiles
  match refuses.
- observability: `resolve_profile` returns the profile's name, so a caller can print which profile
  answered. This unit prints nothing new.
- risks: a model named by an alias that lacks the family word resolves to the default tables with
  no refusal, so the dispatch route must name the model id. Two different words that share one id
  are refused at resolve time only. `TOOL-dBoundRoles-21` re-points both resolvers when it resumes
  (§3).
- testing: arm 19 of the render self-test, and the probes of §6.
- migration: N/A — additive, with an absent `profiles` key read as no profile (§4 "Migration").
- user docs: the policy file's own comment lines carry the grammar; the README and the `help/` page
  are `TOOL-aProfiledEffort-3`'s.

## 8. Open questions

- **F1 — What does a profile's `match` hold, so that it matches a model family at any version?**
  The brief fixes the outcome and not the grammar. Options:
  - (a) Family words. An entry is one run of letters and digits, and it matches a model whose id
    holds that word (§4 "Matching"). It matches every spelling of a Fable id measured in §4, never a
    substring, and two profiles sharing a word are refused by the validator with no model in hand.
    Its ceiling: a profile for one version of a family cannot be written. The upgrade path is an
    entry of several words with the longest match winning, in a later unit.
  - (b) Glob patterns over the whole id. `*fable*` also matches `affable-1`, and `claude-fable-*`
    misses an id carrying a provider prefix. Two patterns overlap in ways the validator cannot
    decide, so "two profiles matching one model" is refused for identical strings only, and a
    precedence rule between a wide and a narrow pattern is a new open question.
  - (c) Id prefixes. Overlap is fully decidable, one prefix inside another. An id carrying a
    provider prefix matches nothing and falls to the default tables silently, which is the failure
    this build exists to end.
  - (d) Regular expressions. The reach of (b), with a compile failure as one more refusal class and
    the same undecidable overlap.
  No option trips an M3 veto: each adds the same policy key and no dependency. By M3's rule, (a)
  satisfies the brief's criteria 2, 3 and 5 as written; (b) and (d) satisfy 5 for identical strings
  only and open a precedence question; (c) fails criterion 2 on a prefixed id. Recommendation: (a).
  RESOLVED (agent, 2026-11-10, delegated): (a), family words, with a model two profiles match
  refused at resolve time.
