## 1. Goal

No build declares a priority and no view orders builds (gap-plan-01): 0 of the tree's build READMEs
carries one, and `LIVE.md` lists live builds in slug order. The owner chose "Front matter + generated
view" (walkthrough P1): each build declares its priority beside its `parents:` edges, and the plan view
is generated from those declarations. This unit adds the `priority:` key, renders
`<MEMORY_ROOT>/PLAN.md` beside `LIVE.md` in plan order, and acts on a live build with no priority as
`plan.unplaced` says, each of its three values seen on its planted case.

## 2. Scope (IN)

- **S1** — The key, I1. `priority: <n>` in a build README's front matter, `<n>` a positive integer,
  lower first, at most once. `parse_front_matter` (`tools/memory-tree/gen_build_index.py:405`) refuses,
  as a `Problem` naming the path and the line, a value that is not `[1-9][0-9]*` and a second
  `priority:` line, on the strict model of `_parse_order` (:458), so a malformed value never reads as
  unplaced. Where TOOL-dTotalRecall-4's `FRONT_MATTER_KEYS` stands, `priority` joins it as `("authored",
  "rank", False)` with the type `rank`, and the `build-readme` row's fields in
  `tools/memory-tree/record-kinds.toml` gain `priority`. `collect` (:1106) carries `"priority"` on each
  build dict beside `"parents"` (:1212), `None` when absent. Observed by AC1.
- **S2** — The order. `derive_plan_order(builds)` takes the placed builds, those carrying a priority and
  not terminal, and orders them by repeatedly taking, among those whose placed non-terminal parents are
  already listed, the lowest `(priority, opened, slug)`. A parent that is terminal or unplaced does not
  hold its child back. A cycle among placed builds raises a `Problem` naming every build on it.
  Observed by AC2 and AC3.
- **S3** — The view, I2. `render_plan_view(builds, m, activity, plans)` renders `<MEMORY_ROOT>/PLAN.md`,
  added to `plan()`'s artifacts (:2674) beside `LIVE.md` (:2807): the generated header, two lines of
  prose, then one table `| Build | Priority | Parents | Status | Dormant | Plan |` with one row per placed
  build in S2's order, then a `## Unplaced` heading and one bullet per live build with no priority, in
  slug order, each `<slug linked to its README> · <status> · opened <date>`. `Parents` is the build's
  `parents:` slugs, space-separated, or `none`. `Dormant` is `dormant` or `active` by
  `LIVE_DORMANT_DAYS`, through `derive_activity(builds, conf, reading)`, the derivation `render_live`
  (:2079) holds inline today, extracted so both files read one anchor; with the key blank the cell is
  `-`. `Plan` links the build's plan record `find_plan_record` returns (TOOL-dRankedPlan-16 S4), or reads
  `none`. An empty table prints `*No placed build.*` and an empty Unplaced list
  `*Every live build is placed.*`. `LIVE.md`'s bytes do not move. Observed by AC2 and AC4.
- **S4** — The view as an output. `check_index_input` (:894) answers true for `PLAN.md` as it does for

## 3. Non-goals (OUT)

- Who may write or change a priority, and the order fixed by a ratification: TOOL-dRankedPlan-2's
  `check_ratified_order` (I11). This unit renders what the front matter says.
- The disposal of a dormant build: TOOL-dRankedPlan-4's. This unit shows `Dormant` and decides nothing.
- The card's plan cell and `plan.kickoff`: TOOL-dRankedPlan-7's, reading this view.
- Placing an ask in the plan: the walkthrough's placement predicate covers asks, and this clause names

  someone places it.

## 4. Design

### Evidence

- The front matter parser reads flat `key: value` lines and keeps the last of two (`fm[k.strip()] =
  v.strip()`, :441); only `status` is checked against a closed set (:453).
- `plan()` already inverts `parents:` into children and refuses an edge to a build that does not
  exist (:2686-2698).
- `render_live` derives dormancy from the newest record date in the tree, never the clock (:2098-2111),
  and keeps ONE table "because the kickoff card counts rows under one header" (:2100): the card's `live
  —` cell counts every table row of `LIVE.md` but its header (`skills/session-kickoff/manifest-check.sh:529`),
  46 at base.
- `read_slot_mode` (:2283-2307), the generator's one policy read today, inserts the policy kit into
  `sys.path` and imports `budgets` (:2293-2296), an in-process import of a sibling kit, which
  PLAY-dOrderedCharter-7 §4 rules out ("A kit may not import a sibling kit"), so S6 does not copy it and
  reads through TOOL-dTotalRecall-8 S10's adapter instead.

### The view

```
<!-- GENERATED … -->
# memory/PLAN.md — the plan: every live build, placed in the order it is built

Derived, never authored: each row is a build README's `priority:` and `parents:`, in plan order. A build
leaves this file when every one of its units reaches a terminal status.

| Build | Priority | Parents | Status | Dormant | Plan |
|---|---|---|---|---|---|
| dC, linked to builds/dC/README.md | 1 | none | OPEN | active | none |
| dA, linked to builds/dA/README.md | 2 | none | OPEN | active | plan, linked to its record |
| dB, linked to builds/dB/README.md | 1 | dA | OPEN | dormant | none |

## Unplaced

- dD, linked to builds/dD/README.md · OPEN · opened 2026-10-01
```

`dB` carries priority 1 and is listed after `dA`, its parent: a child is never placed before a live,
placed parent.

### Alternatives rejected

- **A plan region inside `LIVE.md`.** Its rows would join the card's count of non-terminal builds (§8 F2).
- **Priority over parents.** A child placed before its live parent cannot be built first; flow-steps.md:186
  places a build "by priority and parents".
- **A view whose text names the `plan.unplaced` value.** The policy is read at the landed revision, so a
  value pushed from another node would stale the view with no local commit, the defect `render_live`'s
  record-date anchor exists to avoid.

## 5. Production-readiness checklist

- security — no new write path: the view is a generator artifact; the key's value is held to digits
  before it reaches the view.
- perf / scale — one pass over the build list and one topological walk per render; one policy read.
- error / empty / loading states — each empty region prints its own line; a malformed priority and a
  cycle refuse naming their builds.
- observability — the `warn` line names every unplaced build.
- risks — every live build sits under Unplaced at landing, so `warn` prints a long line until the owner
  places them; `review-only` silences it.
- testing — the generator's selftest arms, red and green.
- migration — none.
- user docs — `help/plan.md`, S9.

## 6. Acceptance criteria

- **AC1** — When `python tools/memory-tree/gen_build_index.py --selftest` runs its `priority-key` arm, a
  README carrying `priority: 3` parses to 3, and one carrying `priority: 0`, `priority: 2x` or two
  `priority:` lines is refused naming its path and line.
  Red when: a malformed or repeated priority reads as a value or as unplaced.
- **AC2** — When the same selftest's `plan-order` arm renders a fixture of `dA` (priority 2), `dB`
  (priority 1, `parents: dA`), `dC` (priority 1), `dD` (no priority) and `dE` (priority 1, every unit
  `CLOSED`), the rendered `PLAN.md` lists `dC`, `dA`, `dB` in that order, `dD` under `## Unplaced`, and
  no `dE`; two ready builds of equal priority are ordered by `opened:`, then slug.
  Red when: `dB` is listed before `dA`, or a terminal build is listed.
- **AC3** — When the `plan-cycle` arm gives two placed builds each other as `parents:`, the render
  refuses naming both.
  Red when: a cycle renders an order.
- **AC4** — When `python tools/memory-tree/gen_build_index.py --check` runs at the pass tip, it exits 0
