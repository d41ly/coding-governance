## 1. Goal

At every step's exit a command scores whether the step's work should be reviewed, and where the step has a
single producing role, that role then answers one question with the score handed: should this be reviewed,
and why (flow-steps.md:95-97). Both land in one `recommendation` record, and `review.recommendation` and
`review.recommendation.source` say whether the score binds and where it comes from. Today one
recommendation exists, Design's, computed inside `print_spec_audit_line`
(`tools/unattended/unattended.sh:7887-7905`) and printed to the owner; no record keeps it and no role
reasons it (`gap-flow-12`, AF-1, DA-H2).

## 2. Scope (IN)

- **S1** — The record kind `recommendation` in the record factory `tools/memory-tree/build_records.py`
  (dOrderedCharter-7 S7): fields `Stage` (`plan`, `design`, `build`, `test`, `deploy`), `Score` (`review`,
  `no-review`, `unarmed`, `none`), `Signals`, `Source` (the `review.recommendation.source` value), `Binds`
  (`yes` or `no`), `Reason`, `Role`, and `Answers` on a reason record, naming the score record it answers.

  the landed factory. Observed by AC1 and AC10.

## 4. Design

### The record

```
**Serves:** recommendation <first unit id>
- **Stage:** design
- **Score:** review
- **Signals:** 3 units in the generated region · a spec grading FORKED
- **Source:** scored-signals-and-reasoning
- **Binds:** no
- **Reason:** pending
- **Role:** command
```

A reason record carries `Score: none`, its `Reason` text, `Role` the slot that answered, and `Answers:` the
score record's file name. The factory's closed sets refuse a `Stage` or `Score` outside its set, and its
`<n>` collision numbers the second record of a stage. A stage recommended twice in one build, as a lap
re-enters Design, keeps both records; the latest score record and the reason record answering it are the
pair that decides.

### The signals

`print_spec_audit_line` computes its "why" from the unit count of the generated region and a FORKED spec
(`tools/unattended/unattended.sh:7898-7903`). Those lines move into `derive_review_signals`, which prints one
signal per line, and `print_spec_audit_line` joins them with `, ` as it does today, so its output is byte-for-byte
unchanged. The `build` stage adds a Tier-2 spec as a signal, read from the status header's `Tier-2` field.

### The score

```
--recommend <slug> --stage <s>
  source = review.recommendation.source     (default scored-signals-and-reasoning)
  binds  = review.recommendation            (default advice)
  agent-judgment                -> Score none
  stage has no signal source    -> Score unarmed
  any signal                    -> Score review
  otherwise                     -> Score no-review
  binds: binding -> yes; binding-above-tier -> yes when a spec is Tier-2; advice -> no
  Binds yes and Score review    -> print the --trigger … --cause recommendation line
  write the record through build_records.py, with S1's flags
```

The verb finds `build_records.py` with `resolve_kit_dir` (`tools/unattended/lib-unattended.sh:191`), as the
driver finds the index generator, and calls it with `run_bounded "$_py"`.

Under `signals-only` the score is the whole recommendation and the route goes straight to the breakpoint or
past it (flow-steps.md:188, :244, :363). Under `scored-signals-and-reasoning` the reason item follows the
score. Under `agent-judgment` the reason item decides with no score handed.

### The reason stage

```
SPEC -> reason (one agent, role: workflows.toml spec-write stages.reason) -> AUDIT -> DISPOSAL
```

The stage spawns one agent through the harness's `renderStageOpts`, as the DISPOSAL stage does
(`tools/workflows/unattended-build.template.js:2111`), with the score line and the question "should this be
reviewed, and why", and the schema `{review: boolean, why: string}`. Its answer is returned, never acted
on: the harness neither opts the audit in nor out on it, because the opt-in is the owner's (`specAudit`,
`:20-26`). The caller records it with `--recommend --reason`.

## 5. Production-readiness checklist

- security — no new write surface beyond one record kind written through the existing factory; the reason
  text goes into a record field through the factory's field validation, never into a shell command.
- perf / scale — one roster read and one factory call per stage exit.
- error / empty / loading states — a stage with no signal source scores `unarmed`, never `no-review`; a
  reason with no score record refuses; an absent key reads its catalogue default.
- observability — the record is the recommendation's trail, and the binding trigger line is printed.
- risks — the reason is an agent's text and decides nothing by itself unless `review.recommendation` binds,
  which only the owner sets in the guarded policy file.
- testing — the pass probes the factory, the verb on fixture repositories and the stage by a stub run; the
  arms in §7 are observed RED then GREEN by the main loop.
- migration — none.
- user docs — the verbs carrier and the workflows README.
