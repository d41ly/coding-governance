## 4. Design

### Evidence

- Probed 2026-10-24 on node `d`, git 2.54.0.windows.1, PINNED: a scratch repository where `side`
  changed line 1 of a ten-line `p.toml`, PINNED, and `main` changed line 10, merged with `--no-ff`,
  printed the merge sha and `p.toml` for `git diff-tree --cc -r --name-only HEAD`, and only the sha
  for `git diff-tree --cc -r HEAD`. `git merge-tree --write-tree HEAD^1 HEAD^2` printed a tree whose
  `p.toml` blob equalled the merge's: PINNED, that date.
- `TOOL-dDeclaredLoop-44` rev-3, built at order 16 while this spec is revised, writes the merge
  branch this unit amends: `check_push_range` reads merges, takes `git diff-tree --cc -r --name-only
  --no-commit-id <merge>` as its pre-filter, grades a listed merge's leaves against the first parent,
  and reads the change records from that list (44 S2, §8 F2). This spec is written on that committed
  text; at HEAD the arm still reads with `--no-merges` (`tools/loop/guard.py#check_push_range`).
- `tools/policy/guard.py#derive_leaf_changes` returns the leaves on which an old and a new parsed
  table differ, absent reading as `None` and values compared by `repr`; `tools/loop/guard.py#parse_policy_bytes` reads a
  missing blob as `{}` and an unparsable one as `None`; `tools/loop/guard.py#read_policy_blob` reads
  `<rev>:<path>`, which a tree id names as well as a commit; `tools/loop/guard.py#render_policy_trailer`
  renders a leaf's trailer value from its old and new values.
- `tools/loop/loop_witness.py#read_git` returns the exit and the stripped stdout without raising, so
  each `merge-tree` exit is the arm's to read.
- `tools/memory-tree/commit_trailers.py#read_commits` gives each commit its `parents` list, so the
  parent count is read, never re-derived.
- `--prepare` merges with `git merge --no-ff` and a fixed `msg=` (`tools/push-main.sh#cmd_prepare`).

### The grade

```
for merge M in the range, with parents P1..Pn, listed by 44's --cc pre-filter, P1 holding the file:
    C = parse(blob of merge-tree --write-tree P1 P2) when n == 2, it exits 0 and parses; else none,
        and the S3 line names why
    owed = keys(leaf changes P1 -> M) ∩ ... ∩ keys(leaf changes Pn -> M) [∩ keys(leaf changes C -> M)]
    each owed leaf k: trailer render_policy_trailer(k, val(P1,k), val(M,k)) and a record naming its
        row among the combined list's records, as 44 S2 reads them; each missing one is a finding
```

An absent key reads as its own value, so a key the resolution deletes is graded like one it sets. A
parent past the first lacking the file reads as the empty table. A blob that does not parse at the
merge or at any parent is the arm's existing finding, its changed keys unknown. The parents-only grade
owes a superset of what the clean leg owes, so a missing clean leg never lets a key through.

### Alternatives rejected

- **Hunks of the `--cc` patch.** git's combined diff hides a hunk where the result matches a parent
  line by line, which is right for most edits, but a multi-line value changed in separate places by
  each side is a hunk with no resolution edit; the key read with the clean re-merge has no such case.
- **Keys against the parents alone.** The same multi-line value, changed on both sides, equals neither
  parent after a clean merge and would be owed; S3 keeps it only as the fallback.
- **Sharing the `merge-tree` call with `tools/branch-reconcile/branch_reconcile.py#check_noop`.** That
  kit is copy-installed and asks a yes-or-no tree equality; the loop kit reads a blob of the tree. A
  single git call is no factory.

## 5. Production-readiness checklist

- security — a resolution's own edit still owes its trailer and record, so `floor.record-changes` is
  not bypassed, and every fallback grades more keys, never fewer.
- perf / scale — a `merge-tree` call for each listed merge that is not an octopus, a handful per landing.
- error / empty / loading states — a policy file that does not parse at the merge or a parent is the
  arm's existing finding naming the merge; a `merge-tree` that cannot start is an `OSError`, exit 2,
  as the arm's other git reads are.
- observability — S3's line names each merge graded without the clean leg, and why.
- risks — `merge-tree --write-tree` re-computes the merge base itself; a criss-cross history picks a
  virtual base, which is the same answer `git merge` gave the lander.
- testing — AC1 to AC4 as fixture plants; the arm under §7, observed at the close.
- migration — none.
- user docs — `help/policy.md`, the push-check paragraph's merge sentence, by S5.
