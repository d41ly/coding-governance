## 1. Goal

A build records what kind of work it is, and the flow it runs follows: a `scenario` is a registered
kind whose row activates rows of other kinds, a build runs the scenarios it was placed under, and two
builds of one repository can run two variants at once (the owner's NT-1, NT-6 and NT-7,
`memory/builds/dClosedLoop/build/2026-10-19-build-PLAY-dClosedLoop-1-night-pass-two.md:99-120`). Today
the register holds `kind.scenario` with no factory, gate or schema, so no row of the kind can exist,
and no build records its variant (`gap-flow-20`; research-scenarios-design's question 8, six seams, no
selector).

## 2. Scope (IN)

- **S1** — The kind's row. The register's `kind.scenario` row in `tools/playbook/kinds.toml` takes the
  `population`, `factory`, `gate`, `schema`, `summary` and `usage` §4 "Data model" gives, its `owner`
  and `binds` as they read (§8 F6), and its `kind` row of `tools/playbook/core-pending.txt`
  (`tools/playbook/core-pending.txt@e7df6c91a145:229`) is deleted in the same commit, so
  `tools/playbook/core.py#run_kinds` holds the row to `tools/playbook/core.py#check_kind_row`.
  Observed by AC11.
  **Readers:** by name: `tools/playbook/core.py`, its kinds verb, which reds a pending kind row whose factory and gate hold, and its new verb, which refuses a kind the list holds
  · by value: NO VALUE READERS — a pending row's value is its arming build, dDeclaredLoop here, which no reader prints but the meta-check's pending count.
- **S2** — The namespace. A `[[namespace]]` row `scenario` in `tools/playbook/namespaces.toml`, every
  field filled as §4 gives. Its `source` is the pack's path alone, `{prefix}/loop/scenarios.toml`,
  since `tools/playbook/overlay_rows.py#read_kind_source` reads that blob at HEAD as the kind's gov
  rows. Its extractor, `extract_scenario` in `tools/playbook/tag_index.py`, yields the tag of each
  `[[scenario]]` row of that file, as `tools/playbook/tag_index.py#extract_item` yields the
  definition's items. A repository's `scenario.adopter.<name>` rows are composed and not indexed, as a
  repository's items are. Observed by AC12.
- **S3** — The row. The schema `tools/loop/scenario-schema.toml` names the kind `scenario`, owner seat
  1, and five scalar fields: `extends`, a composed scenario tag or `none`; `admits`, a table from a fact
  name to the non-empty list of values that admit; `entry`, a gov step tag whose state a build-table
  row out of `none` enters; `activates`, a table from a kind tag to that kind's rows, in the overlay's
  row grammar; and `then`, a list of `{ at = <gov step tag>, scenario = <tag> }`, the scenario that
  takes over at that step's exit. No field declares `widens` or `fixed-by`, so each is fixed by its
  undeclared class, and a repository extends a gov scenario where it would patch one. The kinds a
  scenario may activate are derived, never listed: every kind `tools/playbook/pins.py#read_row_kinds`
  answers but `kind.scenario`, so a later build admits its kind's rows by registering its schema (§8
  F7). `check_scenarios(rows, data, kinds)` in the new module `tools/loop/scenario.py` refuses a row
  breaking any rule here, naming the row and the key. Observed by AC9 and AC12.
- **S4** — Gov's five scenarios in `tools/loop/scenarios.toml`: `scenario.feature`,
  `scenario.amendment`, `scenario.patch`, `scenario.playbook-run` and `scenario.design-only` (NT-6).
  Each admits the request's `entry` fact of its own name, but `scenario.design-only`, which admits
  `entry = feature` with `design-only = true` and extends `scenario.feature`. `scenario.patch` enters
  at `step.design`, since the build table's row out of `none` on `item.plan.dedupe`'s outcome `patch`
  enters `designing` (`tools/loop/loop.toml@848745381fea:419`); every other enters at `step.plan`. Each
  activates nothing and names no `then`, so P20 stands for every gov build. Observed by AC1 and AC12.
- **S5** — Admission. `derive_admitted_scenarios(facts, rows, default)` returns every composed
  scenario whose predicate holds, each fact its `admits` names present among the facts with a listed
  value, in the composition's row order, gov's pack before the overlay. Where none holds it returns
  `scenario.<default>`, the default being `flow.scenario-default` read through the policy kit's
  `resolve`, found by `tools/loop/loop_parents.py#read_policy_kit`, `feature` when unset. A default
  naming no composed scenario, and a value the policy kit refuses, are each refused naming the key and
  the value. The facts are a request's, which placement hands (dPlacedRequest's `entry.place`); until
  it lands they are `select --fact <name>=<value>` and the transition writer's own `--fact`. Observed
  by AC1 and AC6.
- **S6** — The composition. `derive_activated_rows(placed, rows, mode)` merges the placed scenarios'
  `activates`, each read after its `extends` chain, into one row list per kind in the declared order.
  Each list reaches its kind's composition through a new input of the playbook kit's verb,
  `overlay_rows.py compose --kind <kind> --rows -`: a JSON array of rows on standard input, appended
  after the overlay's own rows by `tools/playbook/overlay_rows.py#derive_kind_composition`, each row's
  origin the repository's and its `source` the activating scenario's tag. Every refusal the
  composition makes of an overlay row it so makes of an activated one: the owned seat, a fixed field,
  a fixed row, an edge's pin and the row checks (§8 F8). `tools/loop/loop_items.py#read_composition`
  gains a `rows` argument, and TOOL-dDeclaredLoop-26's `read_composition_at` gains `kind` and `rows`,
  each passing them through. A build's recorded changes apply after these rows, TOOL-dDeclaredLoop-28's
  layer. Observed by AC2 and AC3.
- **S7** — Conflicts, as `flow.scenario-conflict` says, read at the same revision as the rows, default
  `refuse`. Two placed scenarios activating rows of one tag that set one field to different values is a
  conflict. Under `refuse` `derive_activated_rows` raises `ScenarioConflict`, a ValueError naming both
  scenarios, the row and the field. Under `declared-order` the later scenario in the declared order
  wins and the settlement `<row tag>:<field>:<winner>:<loser>` is returned beside the rows. Observed by
  AC4 and AC5.
- **S8** — The pin and the switch. `scenario` and `scenario-settled` join
  `tools/loop/loop_transition.py#TRANSITION_FIELDS` after `composition`, each derived by
  `tools/loop/loop_transition.py#write_transition` through `derive_move_scenarios` and never supplied:
  a `--field` naming either exits 2 naming it as derived (§8 F9). `scenario` is the placed scenarios in
  declared order joined by `+`; `scenario-settled` is each settlement joined by `+`, written only where
  a conflict settled; both sit inside `tools/loop/loop_transition.py#VALUE`. At a build's first move to
  carry the field, a new build's move out of `none`, the placed scenarios are the admission over the
  move's own `--fact`, so that record stands in for the build's claim until
  dPlacedRequest's `entry.claim` lands (§8 F3). At every later move the previous move's scenarios
  carry, each whose `then` names the step whose state the move leaves giving way to the scenario it
  names, so a scenario changes only at a step boundary. The writer reads the scenario composition at
  HEAD; where it answers unarmed the move records neither field and prints `loop: scenario · unread ·
  <why>`, and a conflict under `refuse` refuses the move, exit 2, writing nothing. Observed by AC4, AC5
  and AC8.
- **S9** — The position at the pin. `tools/loop/position.py#derive_position_into` reads the newest
  move's `scenario` and, through `read_activated_rows(root, rev, placed)`, its placed scenarios'
  activated rows composed at that move's composition pin; it passes the item kind's to
  `read_composition_at` and appends `scenario=<value> · <n> activated` to its reads, `<n>` the
  activated item rows. A newest move with no `scenario` reads none and appends nothing (§8 F10).
  Observed by AC2 and AC8.
- **S10** — Successor chains. `check_scenarios` runs the `extends` edges and the `then` edges each
  through `scan_cycles`, the needs-graph helper `tools/loop/loop_lib.py` carries inline (I14), a cycle
  refusing the pack and naming its scenarios. Observed by AC9.
- **S11** — The factory: `python factories.py scenario <name> --extends <tag|none> --admit
  <fact>=<value>... --entry <step tag>` in `tools/loop/`, which `python tools/playbook/core.py new
  scenario <name> ...` runs through `tools/playbook/core.py#run_new`. It appends one gov `[[scenario]]`
  row to `tools/loop/scenarios.toml`, `activates = {}` and `then = []`, held through
  `tools/loop/factories.py#write_kind_instance`, with `scenario.py check` the gate
  `tools/loop/factories.py#run_kind_gate` runs innermost. A name that is not one tag segment or is
  `adopter`, a tag the pack holds, and an `--admit` not shaped `<fact>=<value>` each exit 2 before any
  write. A repository writes its own `[[scenario]]` rows in its overlay by hand, as it writes its items
  (§8 F11, F12). Observed by AC7.
- **S12** — The CLI, the fixture and the leg. `python scenario.py select [--fact <name>=<value>]...`,
  `check [--selftest]` and `--fixture --plant <case>` in `tools/loop/`, §4 "The CLI" and "The plants";

## 3. Non-goals (OUT)

- No placement: `entry.place` naming the scenarios, `placement.check` witnessing them and the planner's
  re-pick are dPlacedRequest's. This unit ships the admission function, the default and the `--fact`
  stand-in. The first move's `to` is not held to the placed scenarios' `entry`: that is placement's.
- No preset slot and no caps on a scenario row: a scenario's policy scope (NT-3) needs presets that
  scope per build, which dKeptSession's preset kind lands.
- No promotion of a change into a scenario: the Loop Review proposing one (NT-5) is a later program.
- No scenario per feature or per unit: they wait on the feature and unit tables (NT-7, `gap-flow-15`).
- No workflow shapes as data (NT-8).
- No reference page of the scenario rows (§8 F5). dOrderedCharter-37 renders a page only for a
  registry with its own `[[reference]]` row, its class first registered in
  `tools/govkit/surface-classes.toml` and given a `usage.toml` row (its S1, S5), and this unit lands
  none. `help/reference/kinds.md`, the kinds register's page, re-renders with `kind.scenario` filled.
- No step-gate class for scenario tags: the carried clause joins no scenario tag to the step gate, as
  it joins item and stage tags.
- No gov scenario that activates rows: gov's five activate none, and an activated row whose tag holds
  no `adopter` seat is refused by the composition's owned clause, as any repository row is.
- No move into a state an activated `[[stage]]` row derives: the move engine reads the shipped
  transition table, the follow-up TOOL-dDeclaredLoop-25's §8 F8 names; the position reads the
  activated item rows alone.
- No adopter fallback for `flow.scenario-default`: the default is `scenario.<value>`, and the
  `scenario.adopter.<value>` reading is TOOL-dDeclaredLoop-56's S45.

## 4. Design

### Evidence

- The register at the branch tip: `kind.scenario` carries `binds = ["principle.p16"]` and an empty
  `population`, `factory` and `gate`, and its pending row names dDeclaredLoop
  (`tools/playbook/kinds.toml@81a9f5107b87:176`, `tools/playbook/core-pending.txt@e7df6c91a145:229`).
  A kind off the pending list must name a factory file and a gate leg whose `enforces` holds every tag
  of its `binds`, and a pending kind that conforms is red as stale (`tools/playbook/core.py#run_kinds`,
  `tools/playbook/core.py#check_kind_row`). `population` is a git pathspec
  (`tools/playbook/core.py#read_skill_paths`).
- The pending list holds `principle principle.p8 dOrderedCharter`
  (`tools/playbook/core-pending.txt@e7df6c91a145:13`), which TOOL-dDeclaredLoop-26 S8 deletes when its
  leg enforces `principle.p8`, before this unit lands.
- An overlay table must name a kind the register lists with a `schema`
  (`tools/playbook/overlay_rows.py#read_overlay_rows`). A schema holds `[kind]`, `[[field]]` and
  `[[fixed-row]]` alone, every other top-level key refused (`tools/playbook/overlay_rows.py#TOP_KEYS`,
  `tools/playbook/overlay_rows.py#read_kind_schema`), so rev-3's `activatable` list could not sit in it.
  A field shape is `set` or `scalar`; a scalar's value may be a table, which the row's canonical form
  folds (`tools/playbook/overlay_rows.py#derive_row_canon`).
- A kind's gov rows are the blob of its namespace row's `source` at HEAD, the table of the kind's name
  in it (`tools/playbook/overlay_rows.py#read_kind_source`). The overlay's rows join after gov's, an
  unedged row as the repository's own, and a row whose field the schema does not declare is refused
  (`tools/playbook/overlay_rows.py#derive_row_composition`). `compose` takes `--kind <kind>` and nothing
  else today (`tools/playbook/overlay_rows.py#run_compose`).
- The owned clause reads one integer seat: a repository row lacking `adopter` there is refused, and so

### The rules `check_scenarios` holds

Over gov's pack as the working tree holds it, beside the repository rows the scenario composition
answers at HEAD (gov's pack alone where that composition answers unarmed), each refusal naming the row:

| Rule | A refusal names | Plant |
|---|---|---|
| each key is a schema field, and `tag` opens `scenario.` | the key | none, the composition's own refusal |
| `extends` is `none` or a composed scenario's tag | the tag | in memory |
| `admits` is a table of non-empty string lists | the fact | in memory |
| `entry` is in `tools/loop/loop_lib.py#STEP_TAGS` and its step's state is the `to` of a build row out of `none` | the step | `scenario-hand` |
| each `activates` key is `kind.<k>` for a kind `read_row_kinds` answers, not `kind.scenario`, each value a list of tables with a string `tag` | the kind | in memory |
| each `then` entry's `at` is a gov step tag and its `scenario` a composed scenario's tag | the entry | in memory |
| the `extends` edges and the `then` edges each acyclic, through `scan_cycles` | the cycle's scenarios | `extends-cycle`, `then-cycle` |
| each kind a scenario activates composes with its rows, `compose --kind <k> --rows -` answering 0 | the scenario, the row and the composition's line | `drops-stage`, `reorders-stage`, `replaces-stage` |

### Composition and conflicts

`derive_activated_rows(placed, rows, mode)` walks the placed scenarios in declared order and, per
kind, per row tag, keeps the first scenario's row; a later scenario's row of the same tag merges over
it field by field. A field both set to equal values is no conflict, so a child placed beside the
parent it extends repeats nothing. A field set to different values is a conflict: `refuse` raises
`ScenarioConflict`, `declared-order` keeps the later value and returns the settlement. The answer is
`({kind tag: [row]}, [settlement])`, each row carrying `source`, the last scenario that set it.

`compose --kind <kind> --rows -` reads a JSON array from standard input, refuses a row that is no
object or that types `origin`, as `read_overlay_rows` refuses one, sets each row's `origin` to the
repository's, keeps its `source`, and passes the list to `derive_kind_composition` as `extra`, which
appends it to the overlay's rows. Any other `--rows` value is a usage refusal, exit 2. Without the flag
the verb reads as today, and `read_kind_rows` passes no `extra`.

`read_activated_rows(root, rev, placed)` reads the scenario composition at `rev` through
`read_composition_at(root, rev, kind="scenario")`, `flow.scenario-conflict` through the policy kit at
`rev`, and answers `derive_activated_rows`' rows by kind.

### The switch at a step boundary

`derive_move_scenarios(root, state, facts, moves)` answers `(scenario, settled)` for the move
`write_transition` is recording, or None where the scenario composition at HEAD is unarmed:

1. the rows, the scenario composition at HEAD through `read_composition(root, kind="scenario")`, read
   through `derive_extended_rows`; an exit 1 is a ValueError naming its first line;
2. the placed scenarios: where no move of `moves` carries `scenario`, `derive_admitted_scenarios`
   over `facts`; otherwise the newest such move's, each passed through
   `derive_step_scenarios(placed, step, rows)`, `step` the step whose `state` is the move's `from`,
   which gives each scenario whose `then` names `step` up to the scenario that entry names, keeps the
   rest in order without repeating a tag, and refuses a placed tag no composed row holds, naming it;
3. `derive_activated_rows(placed, rows, mode)` under the mode read at HEAD, for the settlements; a
   conflict under `refuse` is the ValueError the writer prints as `loop: unanswered · ...`.

`write_transition` calls it after `derive_move` answers and after TOOL-dDeclaredLoop-26's
`composition` is set, and before any record is written. Between boundaries the scenario is the newest
move's, read at its pin by `read_activated_rows`, so two builds pinned to different scenarios each
derive their own composition at once, and a change to a scenario row landing mid-step reaches the
build at its next move.

### The CLI

```
python scenario.py select [--fact <name>=<value>]...
python scenario.py check [--selftest]
python scenario.py --fixture --plant <case>
```

`select` composes at HEAD and prints the placed tags on one line, space-separated, then one
`loop: settled · <entry>` line per settlement; exit 1 with `loop: refused · ...` on a conflict under
`refuse` or a refused default. `check` prints each refusal as `loop: refused · <scenario> · ...` and
closes with `loop: scenarios composed · <n> scenario(s) · <m> repository`. Both exit 2 printing
`loop: unarmed · <why>` where the playbook or policy kit does not resolve, the kind is unregistered,
its schema is absent or HEAD holds no pack, and on a usage error. `check --selftest` runs `check` and
`select --fact entry=patch` over the tree, then every plant, through
`tools/loop/loop_lib.py#run_selftest_cases`.

### What `check` does not check

That a fact a repository predicate names is one placement will supply; that the first move's `to` is
the placed scenarios' `entry`; that an activated row duplicates an overlay row's tag, which the
composition admits as two own rows; and the kind checks beyond the composition, the item kind's
`check_program` and the stage kind's `check_splices`, over a scenario's activated rows. A scenario no
predicate ever admits passes; the selection prints the facts it read.
