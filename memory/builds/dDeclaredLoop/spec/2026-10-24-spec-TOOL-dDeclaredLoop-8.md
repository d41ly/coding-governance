## 1. Goal

Every stored claim a session reads carries a key over what it was derived from, the commit or tree,
the base, the remote ref values and its age, and is trusted by that key and by its weakest source:
`fresh` when the key recomputes equal and no source is actor-typed, `re-derived` when the key moved
and a deriver exists, `evidence` otherwise. The startup card carries its keys, the driver's `--claims`
rows carry theirs, and the replay re-keys the card in the session's own tree, so a session can tell a
fresh claim from a stale one without re-deriving it (gap-orient-05; the `[trust]` section of
`memory/builds/dClosedLoop/build/2026-10-14-build-PLAY-dClosedLoop-1-orientation.md`).

## 2. Scope (IN)

- **S1** — The key, `derive_claim_key(sources)` in `tools/loop/claims.py`. A source is a string, either
  `<name>=<value>` (`commit`, `tree`, `base`, `toplevel`, `branch`, `dirty`, `runstate`) or a ref as
  `<ref>@<sha>`. The key is `k1:` and the first sixteen hex digits of the SHA-1 of the sources sorted
  bytewise and joined by NUL. The age is never hashed: the derivation's UTC time is stored beside the
  key as `at`, and the class bound of S3 reads it. A source the caller could not read is spelled
  `<name>=?` or `<ref>@?`, and a key over one is spelled `k1:?` before its digits, which S3 never reads
  as equal to anything. Observed by AC1, AC2.
- **S2** — The source classes, `CLAIM_CLASSES` in `tools/loop/claims.py`, the `[trust]` table's five
  rows as data, strongest first: `history` (a commit and its trailers, a verdict keyed by tree, BASE:
  trusted for that commit or tree), `view` (the card's cells, `LIVE.md`, the plan view, generated
  regions: trusted while the key matches), `remote` (leases, mailbox entries, run claims: trusted while
  the key matches and `at` is inside the class's age bound), `provenance` (the owner's verbatim words, a
  ratification through the guarded command, the policy file: authoritative for intent) and `typed`
  (status words an agent typed, README status, READY text, session logs, a compaction summary,
  auto-memory: evidence only). A claim over several sources takes its weakest class. Observed by AC3.
- **S3** — The verdict, `derive_claim_verdict(stored, recomputed, claim_class, at, now, bound)`:
  `evidence` when the class is `typed`, or when no recomputed key is given because no deriver exists;
  `fresh` when the two keys are equal, neither carries `?`, and, for `remote`, `now - at` is at most
  `bound`; `re-derived` otherwise, the caller re-deriving the claim. The `remote` bound is the caller's
  argument, the driver's `RESUME_STALE_BOUND` where the driver calls it, and the module holds no
  default (§8 F6). Observed by AC3, AC4.
- **S4** — The CLI, `python tools/loop/claims.py`: `key <source>...` prints one key, and `key --stdin`
  prints one key per input line, the line's sources TAB-separated; `verdict --stored <k> --class <c>
  [--recomputed <k>] [--at <iso>] [--bound <s>]` prints one of the three words; `card-keys` prints the
  card's keys over the tree it runs in; `--fixture --plant <case>` runs one fixture case and `--selftest`
  runs every case through `run_selftest_cases` of `tools/loop/loop_lib.py`. A claim key printed anywhere
  is spelled `key <k> · <verdict>`, the form unit 7's engine prints for each claim it used. Observed by
  AC1 to AC5.
- **S5** — The card carries its keys: `render_card` in `skills/session-kickoff/manifest-check.sh` writes
  one `keys —` cell directly after the header, `keys — view <k> · remote <k> · at <iso>`, from
  `claims.py card-keys`, resolved with `resolve_kit_file loop claims.py` as the card resolves the
  driver. The cells below the header are rendered first and printed after the `keys —` cell, so the
  remote key is taken after the `claims —` read has fetched. Each cell is joined to one key by its
  class, declared once in `CARD_CELL_CLASSES` in `tools/loop/claims.py`: `overlaps —` and `claims —`
  are `remote`, every other cell is `view`. With no loop kit the cell reads `keys — skipped: no loop
  kit resolves in this tree`, and the card still writes. Observed by AC6.
- **S6** — The replay re-keys: `print_replay` recomputes the view key with `claims.py card-keys` in the
  tree the replay runs in and compares it with the stored `keys —` cell. An equal key prints the stored
  card unchanged. A moved key, or a stored card with no `keys —` cell, re-renders the startup cells
  under `--card --replay`, carries the stored `overlaps —` and `claims —` cells, the stored remote key
  and `at`, and the card's whole TAIL (its READY line and `## route` included) byte for byte, writes
  the result under the card's cap and prints it (§8 F5). The `now —` line names the toplevel and ends
  `keys view fresh` or `keys view re-derived`, then `remote evidence`, because a replay reads no remote.
  Observed by AC7.
- **S7** — The run claims carry keys: `print_claims` in `tools/unattended/unattended.sh` adds a sixth
  TAB field to each row, the key over the claim's `refs/gov/runs/<slug>@<sha>` and `runstate=`, the
  blob id of `<MEMORY_ROOT>/builds/<slug>/RUN.md` at the remote-tracking ref of the default branch, or
  `runstate=?` where that ref or file is absent (§8 F4). The blobs come from one `git cat-file
  --batch-check` and the keys from one `claims.py key --stdin`, found with `resolve_kit_dir` from the
  driver's own directory, so no claim spawns a process of its own; where python or the loop kit does
  not resolve the field is `-`. The card's `derive_claims_line` reads six fields and prints ` · key `
  and the eight characters after `k1:` on each row, `-` where the field is `-`. Observed by AC8.
- **S8** — The leg `loop claims fixtures` in `tools/gate-legs.json`, running `python
  {prefix}/loop/claims.py --selftest` with `chunk` `selftests` and `subject` `kit`,
  a 120-second ceiling (PINNED, the value of the loop kit's selftest legs)
  and `enforces = ["principle.p23"]` (dOrderedCharter-7 S2), the tag of the v2 `[enforcement]` row naming this unit's clause `cl-dClosedLoop-0093`; gov's own
  leg, an `[[exempt_leg]]` of `tools/govkit/registry.toml`. The help for the CLI and the `keys —` cell
  is a section of `help/loop.md`. This pass deletes the row of `principle.p23` from
  `tools/playbook/core-pending.txt`, which the meta-check reds as stale once a leg enforces the tag.
  Observed by AC9, AC10.
  **Readers:** by name: `tools/playbook/core.py`, whose meta-check verb reads the pending list and
  reds a row whose tag a leg enforces · by value: NO VALUE READERS — a pending row's value is its arming
  build, which the meta-check prints only in its pending count.

## 4. Design

### Evidence

- `--claims` prints one TAB row per claim, slug, node, status, beat age and verdict, as the first five
  of the eleven fields `read_claims` builds, the sixth being the claim commit's sha
  (`tools/unattended/unattended.sh#print_claims`, `tools/unattended/unattended.sh#read_claims`). It
  decides nothing and prints `claims: off` while `RUN_CLAIMS` is off. The claim record carries eight
  keys, slug, node, host, session, keepalive, status, lease-utc and beat-utc, and no branch.
- The run's branch is a fact of its run-state file, `run-branch`, written by
  `tools/unattended/unattended.sh#write_preflight_record`, so a node reading another node's claim has
  no branch to read; the default branch is the ladder's
  (`tools/unattended/unattended.sh#default_branch`).
- The card's `claims —` cell reads the driver's `--claims` and never re-derives; its awk accepts a row
  only at five fields (`skills/session-kickoff/manifest-check.sh#derive_claims_line`, its `NF == 5`
  test).
- The script resolves the caller's toplevel and `cd`s there before any verb, and the replay prints the
  stored card and one `now —` line from `derive_head_state` in that tree
  (`skills/session-kickoff/manifest-check.sh#print_replay`). Running in the session's own tree is
  therefore built; the line does not yet name the tree.
- A stored card is STARTUP and TAIL, split by `extract_card_parts`; `add_card_body` re-renders the
  `tree —` cell alone and keeps the other startup lines
  (`skills/session-kickoff/manifest-check.sh#add_card_body`). The scratch guard admits a commit only on
  a card carrying a real READY line in the tree it names, and reads the `## route` units
  (`tools/hooks/scratch-guard.js#checkOriented`, `tools/hooks/scratch-guard.js#extractRouteUnits`).
- A key over resolved inputs, never a file's bytes, is the repository's pattern:
  `tools/memory-tree/transition_audit.py#derive_cache_key`, a sixteen-hex SHA-1 over the inputs a
  cached delta depends on.
- The remote and default branch are read through the inline `remote_ladder_py` block, canonical in
  `tools/lib/resolve_remote.py#resolve_remote`; its parity arm finds every inline copy by its marker.

### The two card keys

| Key | Sources | Read by |
|---|---|---|
| view | `commit=` HEAD, `base=` the default branch's remote-tracking sha, `toplevel=`, `branch=` and `dirty=<n>`, the inputs the `tree —` cell reads | every cell but two |
| remote | each ref under `refs/remotes/<remote>/` and under `refs/gov/`, the namespace holding the driver's claim cache, as `<ref>@<sha>` | `overlaps —`, `claims —` |

`card-keys` runs `git` in its own working directory and nowhere else, so the replay's view key is the
session tree's by construction. It prints four lines: `view <k>`, `remote <k>`, `at <iso>`, and
`remote-cells overlaps claims`, the last read from `CARD_CELL_CLASSES`, so the card's carry of S6 names
no class itself.

### What the keys do not cover

The `cli —`, `worktrees —`, `drift —`, `memory —` and `health —` cells read files and commands outside
the commit and the refs: the CLI's version, the worktree list, the drift history, the auto-memory index
and the health log. The view key does not move with them, so a `fresh` view verdict says nothing about
those five cells. A replay never re-reads the remote, so its remote verdict is always `evidence`.

### The run-claim key

For a claim on slug `<s>` with commit `<c>`: `derive_claim_key` over `refs/gov/runs/<s>@<c>` and
`runstate=<blob>`, the blob of `<MEMORY_ROOT>/builds/<s>/RUN.md` at
`refs/remotes/<remote>/<default branch>`, the claim remote `read_claims` resolved and the branch
`default_branch` prints. A claim whose run record landed or moved keys differently from the one the
card stored, which is the join `[trust]` asks for between a claim and its run record.

### The replay's carry

```
stored card  = STARTUP + TAIL
fresh        = render_card replay                        # view cells re-rendered, claims — skipped
carried      = fresh, with each remote-cells block (its head line and the indented lines under it)
               taken from the stored STARTUP, and the keys — cell's remote key and at taken from it
written card = carried + stored TAIL                     # refused above CARD_CAP_BYTES
```

An over-cap result writes nothing, prints the stored card, and the `now —` line reads
`keys view moved · not re-derived: over the cap`.

### The fixture cases

`claims.py --fixture --plant <case>` builds what the case needs under the system temp folder with a
short prefix and removes it.

| Case | Plant | Outcome |
|---|---|---|
| `key-stable` | the same sources keyed twice | equal keys |
| `key-moves` | the base sha changed | different keys |
| `key-unread` | one source spelled `?` | a `k1:?` key, and `verdict` over two of them prints `re-derived` |
| `typed-evidence` | a `typed` claim with equal keys | `evidence` |
| `remote-aged` | a `remote` claim with equal keys past its bound | `re-derived` |
| `card-keys-worktree` | a worktree whose HEAD differs from its primary's | the worktree's view key, not the primary's |

### Rollout

The `keys —` cell lands with the loop kit. A tree without it prints the skipped form, so an adopter
without the loop kit sees one new line and no failure; its replay prints the stored card and
`keys skipped: no loop kit resolves in this tree` on the `now —` line.

### Alternatives rejected

- **A per-cell key suffix.** It moves the bytes of the `tree —` cell, which the scratch guard reads,
  and repeats one of two keys on every line.
- **A key over the card file's bytes.** It moves with the written time on every write and says
  nothing about the inputs, which is what goes stale.
- **Re-deriving every cell on every replay.** It costs a kickoff per resume, the cost the card exists
  to avoid; the key decides which class moved.
- **The `keys —` cell after `claims —`.** The suite's `read_claims_cell` reads from `claims —` to
  `health —`, so the cell would join the claims cell's bytes; and above `recent —` it would part
  `health —` from `recent —`, which another arm pins.

## 5. Production-readiness checklist

- security — no new write path but the replay's re-write of the card it already writes when the card
