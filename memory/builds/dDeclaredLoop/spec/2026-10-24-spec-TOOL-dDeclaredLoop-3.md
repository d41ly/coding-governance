## 1. Goal

A build's stage transition is recorded three ways: a commit trailer, a per-build log record and a
micro-format line. `transitions.record` selects which, any subset and never empty, all three by
default (v2:1156). The trailer is the source, and one check holds each other channel to it, so the
copies never disagree silently (the owner's S4,
`memory/builds/dClosedLoop/build/2026-10-14-build-PLAY-dClosedLoop-1-walkthrough.md:83-89`). Today the
only move record is the `phase:` and `witness:` facts unattended writes into a run's RUN.md
(`tools/unattended/unattended.sh:6192-6193`), no trailer names a transition, and no check holds one
copy to another. C2-F9 asks for the key to be read, seen on a planted subset and red on an empty set.

## 4. Design

### The trailer

```
Gov-Transition: planning -> designing · build=dExample · item=item.plan.exit · sha=3f9c2a71
```

Grammar: the head `<from> -> <to>`, each a build state of `TOOL-dDeclaredLoop-13`'s `[states]` or
`none`; then ` · `-separated `<name>=<value>` fields. `build`, `item` and `sha` are required and come
first in that order; every other name must be in `TRANSITION_FIELDS`, a tuple in
`tools/loop/loop_transition.py` that this unit ships holding `stand-in` and that later units extend. A value matches `[A-Za-z0-9._:+@-]+`, so it
never holds the separator. `sha` is eight to forty hex digits. One trailer per transition commit;
a second one in one commit is refused by `check`.

### The log record

The writer passes the factory `--build <slug> --unit <anchor id>` and one field each for `From`,
`To`, `Item`, `Sha` and every extension field, written through the factory's name grammar and
`**Key:**` field regex (dOrderedCharter-7 S7). Whether its `new` verb is generic per kind is unknown
until that unit builds, since its S8 states only `new exception`, so this unit claims no
`new transition` door: the build run calls whatever writer the landed factory offers. The record:

```
**Serves:** transition TOOL-dExample-1

**Build:** dExample
**From:** planning
**To:** designing
**Item:** item.plan.exit
**Sha:** 3f9c2a71
```

The factory's kind row declares `Build`, `From`, `To`, `Item` and `Sha` required, and admits each
`TRANSITION_FIELDS` name capitalised. The record serves as `transition`, never `journal`: under
PLAY-dOrderedCharter-42 S3 a `-transition-<n>.md` file whose Serves kind is not `transition` is
malformed. The binding names one id, the anchor, so every transition record lists in the anchor
spec's records region alone and no other spec's region floods, as a `journal` binding did under check
21 (`memory/HYGIENE.md:616-631`). A move made
while the build defines no spec writes no log record; the writer's next move after the first spec
writes one for every earlier trailer of the build first, each from its trailer, oldest first, so `<n>`
follows the move order. Until then `check` prints `pending — <n> move(s) before the build's first
spec` and reads not green for the log channel. `check` compares the record's `**Key:**` fields only;
a line a later unit appends to a record, such as `TOOL-dDeclaredLoop-30`'s `draw` rows, is that
unit's to grade.

### The micro-format line

The writer prints `transition — <slug> · <from> → <to> · <item tag> · <sha>` after the commit, where
`micro-format` is selected, rendered by `render_transition_line(fields)` from the same fields the
trailer carries. It is an emitted line for the final message, as the block's other shapes are, and
stores nothing. `check` holds it to the trailer by holding its definition: the block's `transition`
line must carry exactly `TRANSITION_LINE`'s fields, so a renderer and a definition cannot drift.

### The source, by selection

| Selected | Written | Source `check` and `read_transitions` read |
|---|---|---|
| `trailer`, `log`, `micro-format` (default) | all three | the trailer |
| `trailer` and one other | those two | the trailer |
| `log` without `trailer` | the record, committed with no trailer | the log record |
| `micro-format` alone | the line only, no commit | none: `check` prints `unstored` for the move |

### The writer, in order

1. Read the channel set at `HEAD`; an empty set or an unknown member exits 2.
2. `derive_move(build level, from, item, outcome, facts)`; `TransitionRefused` exits 1.
3. Resolve `--witness` to a commit that is `HEAD` or its ancestor, else exit 2; when the item is on
   `TOOL-dDeclaredLoop-13`'s stand-in list, append the extension field `stand-in=<owner>`.
4. Refuse with exit 2 when the index holds staged changes, so a transition commit never sweeps in
   other work.
5. Back-fill missing log records, then write this move's record where `log` is selected.
6. Commit the staged record, or an empty commit, with subject
   `loop transition(<slug>): <from> -> <to>` and the trailer where `trailer` is selected.
7. Print the micro-format line where selected.

## 5. Production-readiness checklist

- security — the writer commits only its own record, refusing a dirty index; field values are held
  to a closed character class, so a trailer cannot carry a separator or a newline.
- perf / scale — one `git log` pass per check over the trailers naming the build.
- error / empty / loading states — an empty channel set exits 2; a pre-spec move reads `pending`; a
  micro-format-only selection reads `unstored`; none reads green.
- observability — each finding names the commit, the channel and the field that disagree.
- risks — a witness commit typed by a mover is a stand-in, labelled `stand-in=<owner>` on the record
  until the owning build arms the item; a forged log record still has to match a trailer to pass.
- testing — the plants of §6, run by `--selftest` under the new leg.
- migration — none.
- user docs — `help/loop.md`, `TOOL-dDeclaredLoop-1`'s page, gains the record's section (S9).
