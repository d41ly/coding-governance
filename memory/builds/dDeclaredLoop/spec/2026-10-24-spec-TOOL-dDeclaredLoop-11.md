## 1. Goal

Every checklist item is named by a semantic tag in the `item` namespace, and no reader addresses one
by its number (P11, v2:1833). The flow's step items already carry tags, `item.<step>.<name>`, declared
by `TOOL-dDeclaredLoop-12` and graded by `TOOL-dDeclaredLoop-9`. What remains is the unattended
driver's two handle registries, the seams the instruction layer names for this
(`memory/builds/dClosedLoop/build/2026-10-15-build-PLAY-dClosedLoop-1-layer-instruction.md:432-435`):
`DOD_CORE`'s Definition-of-Done items (`tools/unattended/unattended.sh@4344df262:1008`) and
`DIRECTIVES_CORE`'s method directives (`tools/unattended/unattended.sh@4344df262:1195`). This unit
maps each handle onto the declared item whose witness it reads, in the loop definition, and checks the
map both ways against the registries.

  `DIRECTIVES_CORE`), `handle` and `item`, and no other key, placed before the `[[item]]` rows and

## 4. Design

### Data model

```toml
[[checklist]]
registry = "DOD_CORE"          # DOD_CORE | DIRECTIVES_CORE, the driver constant that holds the handle
handle = "gates-green"         # the handle, exactly as the registry spells it before its first ":"
item = "item.test.verdict"     # the declared item whose witness the handle's check reads
```

The registry lines are read as `tools/unattended/check-unattended.sh#core_of` reads them: the first
line of the driver that is `<NAME>="<members>"` once a trailing CR and trailing whitespace are
stripped, its members split on whitespace, each member's handle the text before its first `:`, so
`pieces-recorded:M9:recipe` is `pieces-recorded`. The driver is found by
`resolve_kit_dir("unattended", "unattended.sh", <kit dir>)`, imported from `loop_lib.py` as
`tools/loop/loop_witness.py` imports it, so no new inline copy of the resolver joins the parity
population. The unattended kit requires the loop kit, so this reach takes no descriptor edge.

### The reader and the check

In `tools/loop/loop_lib.py`, beside `read_computed_witnesses`, and neither run by `load_loop` or
`--check`:

- `read_checklist_rows(kit_dir)` returns the `[[checklist]]` rows in file order, through
  `read_definition`; LoopError for a table that is no array of tables.
- `check_checklist_rows(rows, registries, items)`, `registries` mapping each of `CHECKLIST_REGISTRIES`
  to its handles in order and `items` the declared rows, returns `(lines, refusals)`. It refuses a row
  carrying a key outside `CHECKLIST_KEYS`, naming the key; a `registry` that is neither constant; a
  handle its registry lacks; a handle with two rows; an `item` that opens no `item.<step>.` of a gov
  step, or that no declared row holds; and a core handle with no row. It prints one line per row,
  `loop: checklist <registry> · <handle> · <item>`, and one count line per registry.

`tools/loop/loop_checklist.py` is the command. `check` reads the driver's two registry lines, the rows
and `read_items`, prints the lines and each refusal as `loop: refused · ...`, and exits 0, or 1 on a
refusal. `check --selftest` runs `check` over the tree, then every plant of `PLANTS`, each a break made
in memory on the rows or the registries as read and never on disk, each required to exit 1 naming
its break, then `show` on one mapped handle and one absent one; it exits 0 when every case holds.
`--fixture --plant <case>` runs one plant. `show <handle>` reads the rows alone and prints
`<registry> <item>`, exit 2 for a handle no row maps. A driver the resolver cannot find exits 2 naming
the kit and where it looked; a registry line absent or empty exits 2, never green over nothing; a
definition `read_items` refuses exits 1 naming it.

The plants are `missing-handle` (a DoD handle `unmapped-check` added to `DOD_CORE` as read),
`stale-row` (a row whose handle no registry holds), `two-rows` (a second row for `gates-green`),
`undeclared-item` (a row mapping onto `item.deploy.nosuch`), `bare-item` (a row mapping onto
`deploy.land`), `numbered-row` (a row carrying `number = 3`) and `bad-registry` (a row whose registry
is `DOD_EXTRA`).

WHAT IT DOES NOT CHECK, stated in the module's docstring: that a pairing is the right item, which is
a judgement per handle a review reads; that a handle's checker word agrees with its item's witness
class; the `DOD_EXTRA` and `DIRECTIVES_EXTRA` handles; and the members' fields after the handle.

### Alternatives rejected

- **A new tag per handle, `item.<step>.<handle>`.** Tags no `[[item]]` row declares, which
  `tools/playbook/tag_index.py#extract_item` never reads, so the namespace check would not see them.
- **The tag written into the driver's registry, `<handle>:<class>:<item>`.** It widens a grammar
  whose readers split each member by position (`tools/unattended/check-unattended.sh` splits
  `DIRECTIVES_CORE` into handle, section and scope; `tools/loop/loop_lib.py#check_site_witnesses`
  splits each `DOD_CORE` entry at its first `:`), and whose suites are waived for this landing, so
  nothing would observe the change.
- **Renaming M3's vetoes and re-pointing `veto (2|3)`.** A positional reference into a governance
  document, which the instruction layer assigns to Convergence.
- **The rows read in `loop_checklist.py` itself.** The definition's header says it is read through
  `loop_lib.py` and by nothing else (§8 F5).
- **The check run by `loop_lib.py --check`.** That leg ships to every adopter of the loop kit, which
  may hold no unattended driver, and the kit declares no edge to it (§8 F6).

## 5. Production-readiness checklist

- security — read-only over tracked files; it runs no subprocess and writes nothing, its plants
  breaking only what it read into memory.
- perf / scale — one read of the driver, one of the definition and one of the playbook kit's
  `layers.toml` through `read_items`; the leg's ceiling is 120 seconds, PINNED 2026-11-14 beside
  `loop definition`'s, and no `ceiling-evidence.txt` row is typed, that file being generated by the
  runner.
- error / empty / loading states — a driver the resolver cannot find exits 2 naming the kit; an
  absent or empty registry line exits 2; a refused definition exits 1 naming it; `show` of an unmapped
  handle exits 2.
- observability — every red names the registry, the handle and the row, or the key; `check` prints
