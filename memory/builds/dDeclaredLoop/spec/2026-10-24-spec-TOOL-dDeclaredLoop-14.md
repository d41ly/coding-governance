## 1. Goal

A refused item routes by default: the refusal is recorded where history can read it, and `next`
returns the frontier, the unwitnessed items of the build's step whose needs are witnessed, so a
refusal no item's own routes name still leaves the build somewhere to go. Until dWellOiledMachine
lands `next`, its stand-in is the driver's `--plan`, which prints the frontier beneath its `next:`
line. The rule is flow-steps' `[rules]`
(`memory/builds/dClosedLoop/build/2026-10-15-build-PLAY-dClosedLoop-1-flow-steps.md@d73cb002d028:31`
to :33), and `tools/playbook/principles.toml@701c20bb8c9c:150` maps this clause to P24.

### Data model

The two fields `Position` gains, beside unit 7's:

```python
"frontier": [{"item": str, "unit": str, "actor": str, "key": str}],  # derive_frontier, in order
"refusals": [{"item": str, "key": str, "reason": str, "at": str}],    # the run's refusal rows
```

`next` is `frontier[0]`, or `None` where the frontier is empty.

### The frontier

```python
def derive_frontier(items, witnessed, step) -> list[dict]:
    """The items of `step` whose witness is not in `witnessed` and each of whose needs is met by a
    witnessed tag, in composition order; each entry as unit 7's `next`."""
```

### The refusal row and its check

The `step` field carries the instance key, the one field `park` places between `item` and `reason`, so
the row's grammar is `park`'s, and its readers that take the token between ` · item ` and ` · reason `
read `<item tag> · step <key>` without change. `check_refusal(tag, key, tags)` holds where `tag` is in
the composed tags and `key` is `<tag>@<round|pass>#<inputs>` with `<inputs>` eight lowercase hex
digits, as `derive_instance_key` writes it. `--check-refusal` prints
`loop: refusal held · <tag> · <key>` at exit 0, `loop: refused · <why>` at exit 1, and `loop: unarmed · <why>` at exit 2 where the
composition does not read; the driver records only at exit 0.

unit and the figure, and `memory/DECISIONS.md` records the unit's row with the raise.

### The fixture cases

Each plant passes its items to the engine in memory as unit 7's plants do. A, B, C and D stand for item
tags the shipped definition declares, A, B and C in one step and D in a later one, so the driver's
`--check-refusal` over the scratch repository's composition and the engine's in-memory rows name the
same items. `frontier-refused`, `frontier-bad-key` and `plan-frontier` run the driver, found through
`resolve_kit_dir`, and exit 2 where it does not resolve.

| Case | Plant | Outcome |
|---|---|---|
| `frontier-chain` | A, B needs A, C needs B; D with no needs in the next step; A witnessed | `frontier — B` |
| `frontier-parallel` | A and B with no needs, neither witnessed | `frontier — A · B` |
| `frontier-refused` | `--refused` on A at its key, its witness unheld | the run-state file gains one `refusal` row; A on the frontier; one `refusal —` line |

| `frontier-none` | every item of the step witnessed | `frontier — none` |
| `plan-frontier` | the `frontier-refused` repository, then `--plan` | the line after `next:` is `frontier: A` |

### Alternatives rejected

- **A refusal record kind through the record factory.** One file per refusal in the build folder, for
  a fact the run-state file already holds rows of; and `park` already guards the line grammar.
- **A refused instance kept off the frontier.** Then a single refusal strands the build, which is the
  failure this route exists to prevent; the cost of retrying is the budget's.
- **A module and a leg of its own for the frontier.** A second walk of the predicate `derive_next_item`
  already applies, a `Position` widened with every item's witness to feed it, and a registry row, a pin,
  a budget row and usage rows for a leg whose plants unit 7's leg already runs (§8 F4).
- **The loop kit parsing `park`'s grammar itself.** A second reader of rows runlog already reads, and
  runlog's and drift-audit's copies left behind the driver's set until unit 56 (§8 F6).
