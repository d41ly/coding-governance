## 1. Goal

A move back, Test to Build, Build to Design, Design to Plan, is recorded through the same writer, in
the same channels, trailer grammar and log fields as a move forward, with no branch on direction and
no new mechanism. The walkthrough found the record written only forward (H10,
`memory/builds/dClosedLoop/build/2026-10-14-build-PLAY-dClosedLoop-1-session-model.md`, its open-items
table), and today a fix pass or a divergence leaves only an overwritten `phase:` fact in a run's
`RUN.md`, which `tools/unattended/unattended.sh#verb_phase` sets in place. Direction is derived from
the step order on every read and print, never typed, so a reader can count routes back without a
second record.

## 2. Scope (IN)

- **S1** — `derive_direction(state, to, tables)` in `tools/loop/loop_table.py`: `forward` when `to` is
  a build terminal, or when the `to` state's `[[step]]` `order` is above the `state`'s; `backward`
  when it is below; `lateral` when the two orders are equal, or when either end has no step (`none`,
  `paused`, `parked`). `to` is the resolved state `derive_move` returns, never `@prior` or `@reentry`.
  The orders come from a `step-order` key `read_transition_rows` adds to its result, `{state: order}`
  over the step rows `check_loop` returns. Observed by AC1.
- **S2** — `move` appends ` · <direction>` as the last field of its `move — ` line where the level is
  `build`, after the stand-in field where one is printed; a feature or unit move prints none.
  Observed by AC1.
- **S3** — `read_transitions` returns each move with a `direction` key, derived on read by
  `derive_direction` over the loop kit's own definition, never stored in a trailer or a record.
  Observed by AC4.
- **S4** — `record` prints the derived direction on its `loop: recorded · ` line, between the move and
  the commit; the micro-format line and `TRANSITION_LINE` are unchanged. Observed by AC2.
- **S5** — Two plants in `tools/loop/loop_transition.py`, `backward-rows` and `skip-backward`, joined
  to `PLANTS` and to `run_selftest`'s cases, and four direction cases in `loop_table.py`'s
  `check --selftest`, one of them `direction-order`. Observed by AC1, AC2, AC3 and AC4.
- **S6** — `help/loop.md` says a backward move is recorded through the same writer and channels, shows
  the direction on the `move` and `record` example lines and names the two plants; the kit's
  `tools/loop/README.md` and both modules' docstrings say the same. Observed by AC5.

## 3. Non-goals (OUT)

- Already built, so not this unit's: `write_transition` has no direction branch and writes the
  channels `transitions.record` selects for every row alike; `check_transition_channels` grades
  every `Gov-Transition` trailer whatever its direction; and the rows into `planning`, B6 and P1,
  are in the build table, so Plan is re-entered by a recorded row (§8 F2). This unit adds no code to
  either function; its plants observe that they stay so.
- No backward row of its own: every row is `TOOL-dDeclaredLoop-13`'s or `TOOL-dDeclaredLoop-15`'s.
- No budget draw for a route back: `TOOL-dDeclaredLoop-30` S4 draws `route-back` for a backward move
  this unit records.
- No new channel, field or trailer key: a `direction` field in the record would be a derived fact
  typed beside its source, and `TRANSITION_FIELDS` keeps its one member.
- No direction for a feature or unit move: their states map onto no `[[step]]`.
- No re-pointing of unattended's fix-pass or phase verbs: nothing in today's driver calls the writer,
  forward or back (`TOOL-dDeclaredLoop-3` §3).

## 4. Design

### The direction

```python
def derive_direction(state, to, tables):
    """'forward', 'backward' or 'lateral' for one resolved build move, from tables["step-order"]
    and tables["terminal"], both of what read_transition_rows returns."""
```

The rule, in order: a `to` in `tables["terminal"]` is `forward`, the build ending, whatever it left;
an end missing from `tables["step-order"]` is `lateral`; otherwise the two orders compare.
`read_transition_rows` already calls `check_loop` for each step's state
(`tools/loop/loop_table.py#read_transition_rows`), and `check_loop` refuses a definition whose
`[[step]]` rows are not `STEP_TAGS` in order with `order` equal to each row's place
(`tools/loop/loop_lib.py#check_loop`). So the shipped orders are one through five, planning to
deploying, and `derive_direction` reads them from the rows rather than from `STEP_TAGS`, so the
order is read from the one place it is declared.

| Row | Move | Derived |
|---|---|---|
| B1, B2, B3 | `none` → planning or designing | lateral |
| B4, B5, B7, B12, B15 | planning → designing → building → testing → deploying, and the resolve | forward |
| B6 | designing → planning | backward |
| B8, B9, B10, B21, B22, B23 | building → designing | backward |
| B13, B14, B24 | testing → building | backward |
| B16, B25 | testing → designing | backward |
| B17, B18 | deploying → testing | backward |
| P1 | designing, building or deploying → planning | backward |
| B19, B20 | into `paused`, and out of it to `@prior` | lateral |
| T1 to T5 | into a terminal | forward |
| B11 | an open state → `@reentry` | by the same rule, once resolved |

### Where it is printed and read

- `loop_table.py`'s `move` derives it after `derive_move` and prints
  `move — build · testing → building · item.test.attribute · stand-in dWitnessedBar · backward`.
  The field is last, so every existing `move` selftest case, which matches a line by its opening,
  still matches.
- `loop_transition.py`'s `main` derives it for `record` from the returned move's `from` and `to`, over
  `read_transition_rows` of the kit's definition, and prints
  `loop: recorded · testing -> building · backward · commit <sha8>`. `write_transition` and its return
  are unchanged.
- `read_transitions` reads the kit's definition once per call and adds `direction` to each result
  dict it builds; `read_transition_moves`, which `check_transition_channels` reads, never sees it.

### The plants

`BACKWARD_MOVES` in `loop_transition.py` lists the moves both plants make in the fixture build `tFix`,
each an argv tail for `record`: B4, B5 and B7 forward, then B13, B8 and B6 back, each with the
witness `HEAD` after the first. Every one of the six items carries a `[[stand-in]]` row, so every
trailer carries the same field set, `build`, `item`, `sha` and `stand-in`.

- `backward-rows`: records the moves in order; prints every trailer oldest first as
  `loop: fixture · trailer <value>`; the record folder; each `read_transitions` result as
  `loop: fixture · read <source> · <trailer value> · <direction>`; then
  `loop: fixture · direction stored · <t> trailer(s) · <r> record(s)`, counting the trailer values
  and record files whose text holds `direction`; then runs `check`.
- `skip-backward`: records the moves in order, deletes the newest record, the B6 move's, in its own
  commit, and runs `check`. The newest is chosen because `check` pairs a record with a trailer by
  order (`tools/loop/loop_transition.py#check_transition_channels`): an earlier record deleted reads as
  a field drift on every later move, while the newest reads as one move owing its record.
- `direction-order`, a `loop_table.py` selftest case rather than a plant, since `--fixture` there runs
  `check` alone: the case runner answers it by copying `read_transition_rows`' result, swapping the
  `step-order` values of `building` and `testing`, and printing
  `loop: direction-order · building → testing · <direction>`, owed `backward`.

The existing `read` print, made for `subset-log` and `field`, gains the trailing direction for them too;
their cases match by opening and still hold.

### Alternatives rejected

- **A `direction` column on each row.** It types a fact the step order already decides, and a
  reordered step would leave it stale.
- **A separate backward record or trailer key.** The clause asks for the forward record, and a second
  key is a second reader for every consumer.
- **The direction inside the micro-format line.** `TRANSITION_LINE` is held equal to the charter's
  definition, so changing it is a contract change for one derived word.

## 5. Production-readiness checklist

- security — no new write path; the writer and its trailer and record grammar are unchanged.
- perf / scale — one dict lookup per move; `read_transitions` reads the definition once per call.
- error / empty / loading states — a state with no step reads `lateral`, never an error; an unknown
  state is `derive_move`'s refusal before any direction is derived.
- observability — every build `move` and `record` line names its direction.
- risks — the direction of an old move is derived from today's definition, not the one at its commit
  (§8 F4); `check_loop` pins the step order to `STEP_TAGS`, so it moves only with the code. A recorded
  state renamed since reads `lateral`, which nothing checks.
- testing — the four `loop_table.py` cases and the two plants of §4, under the two existing legs.
- migration — none.
- user docs — `help/loop.md` (S6).
- write set — the map's `symbols.json` gains `derive_direction`: regenerate with
  `python tools/codebase-map/gen_map.py --write`, held by `codebase-map coverage + freshness`; the file also trips the
  `recall floor` and `recall floor arms` guards, which a regenerated map keeps green. No usage
  row moves, since no verb or flag is added, so each usage fingerprint on the help page holds. No
