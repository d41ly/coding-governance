## 1. Goal

A repository may add a stage of its own, tagged `step.adopter.<name>` with its items
`item.adopter.<stage>.<name>`, spliced between two adjacent gov stages by pinned rows of the build's
transition table. Gov's five stages stay whole and in order; the splice row is an overlay kind; stage
tags join dSafePassage's step gate; a gov stage's rename beside a splice re-points its rows; the
repository stage's items and exit item are witnessed as a gov step's are, and its boundaries are
reviewed through `review.breakpoints` (gap-flow-19; the owner's FA-3, "Repository stages";
`memory/builds/dClosedLoop/build/2026-10-15-build-PLAY-dClosedLoop-1-flow-roles-adoption.md:383-388`;
P20 as amended).

## 4. Design

### Evidence

- FA-3: "A repository stage is spliced between two adjacent gov stages by pinned rows of the build's
  transition table. Gov's five stages stay whole and in order, so the splice can neither remove,
  reorder nor replace one" (flow-roles-adoption.md:383-385); the owner's answer "Repository stages"
  (:372).
- The tags: `step.adopter.<name>` and `item.adopter.<stage>.<name>`; gov never ships the `adopter`
  segment, so no repository tag collides with a gov tag (flow-roles-adoption.md:147-153).
- The flow's frame is a fixed row set: the five stages and their order, and each level's
  transitions between gov's stages "except where a repository stage is spliced"
  (flow-roles-adoption.md:197-200).
- The flow adoption's review added the before-Plan, after-Deploy and non-adjacent plants
  (`memory/builds/dClosedLoop/reviews/2026-10-19-review-PLAY-dClosedLoop-1-flow-adoption-b.md:111`).
- Today unattended's extra phases are vocabulary with no position: `PHASES_CORE` and its extension
  (`tools/unattended/unattended.sh:852`), gap-flow-19.
- A step-gate class joins by adding its own row with a reader and a plant, and an own-record witness
  reads the class's own change record (dSafePassage-10 S1, S4).

### Data model

```toml
# .governance/instructions.toml — one repository stage
[[splice]]
tag = "step.adopter.security-review"
after = "step.test"
before = "step.deploy"
pin = "3f1c9a20"                         # the replaced gov row's hash8, dOrderedCharter-35 S6
exit = "item.adopter.security-review.exit"

[[item]]                                 # unit 24's kind, in the repository stage
tag = "item.adopter.security-review.exit"
# ... every field an item declares, its witness computed
```

```toml
# tools/playbook/kinds.toml
[[kind]]
tag = "kind.splice"
owner = "dDeclaredLoop"
binds = ["principle.p20"]
population = "python {prefix}/loop/splice.py check --list"
factory = "python {prefix}/playbook/instructions_edit.py add --manifest overlay"
gate = "loop splice check"
schema = "loop/splice-schema.toml"
```

The schema fixes `after`, `before` and `pin` (`fixed-by = ["principle=principle.p20"]`), so no
`amends` patch moves a splice's position; `exit` is open, widening by `add`.

### The expansion

For splice S between gov stages A and B, with R the build row `from = state(A)`, `item = exit(A)`,
`outcome = pass`, `to = state(B)`:

```
R  replaced by  R1: from state(A), item exit(A), outcome pass, to adopter-<name>
                R2: from adopter-<name>, item S.exit, outcome pass, to state(B)
```

Every other row of gov's table stays as shipped; a backward row into A or B is untouched, so a route
back from B to an earlier gov stage passes over the repository stage, and a build passes it whenever
it passes its two neighbours, unless a route of its own skips it.

### The fixture cases

`splice.py --fixture` builds a repository under `%TEMP%` with gov's loop definition, an overlay and a
change-record folder; `--plant <case>` runs one.

| Case | Plant | Outcome |

| `between-test-deploy` | a splice after `step.test`, before `step.deploy`, its exit item witnessed | green; the composed table holds R1 and R2 and not R |
| `removes` | an overlay exclusion of `step.test` beside a splice | red, a gov stage missing |
| `reorders` | a splice after `step.deploy`, before `step.test` | red, not adjacent in order |
| `replaces` | a splice tagged `step.test` | red, no `adopter` seat, a gov stage replaced |
| `before-plan` | a splice with no `after`, before `step.plan` | red, no gov stage precedes it |
| `after-deploy` | a splice after `step.deploy`, with no `before` | red, no gov stage follows it |
| `non-adjacent` | a splice after `step.build`, before `step.deploy` | red, the two gov stages not adjacent |

### Alternatives rejected

- **A stage as a group of items inside a gov stage.** FA-3's first option; the owner chose
  repository stages.
- **Splice rows written into gov's `loop.toml`.** It edits a shipped declaration, which "compose,
  never edit" refuses, and an update would overwrite it.
- **The repository stage's state typed on the splice.** It would be a second name for the stage; the
  state is derived from the tag.

## 5. Production-readiness checklist

- security — the overlay is already guarded by the instruction command and the policy guard; this
  unit adds a row kind and a read-only check.
- perf / scale — one composition per check, over five gov stages and the repository's splices.
- error / empty / loading states — an overlay with no splice composes to gov's table unchanged and the
  check prints `loop-splice: 0 splices`; a stale pin is refused, never silently re-pinned.
- observability — each refusal names the splice and the rule; a re-pointed splice prints its line.
- risks — a gov table change that moves the replaced row: the pin turns stale and the check reds,
  which is the FA-2 order's job to surface.
- testing — the ten fixture cases and the step-gate class's own plant.
- migration — none: no repository has a splice row at base.
- user docs — `help/loop.md`, the section "Adding a stage of your own".

  (agent, 2026-10-24, delegated): (a). widens: none · relaxes: none
