## 1. Goal

A role can change its own build's flow mid-build without moving every other build: it proposes rows
for its own build, a change that only adds applies unattended at the next step boundary and is
recorded, and one that takes away or loosens waits for the owner while the build carries on (the
owner's NT-4, `memory/builds/dClosedLoop/build/2026-10-19-build-PLAY-dClosedLoop-1-night-pass-two.md:109-114`).
Today a structural change goes only through the repository-wide overlay `.governance/instructions.toml`,
composed at `HEAD` by `tools/playbook/overlay_rows.py#derive_kind_composition`, and no record keeps one
build's adaptation (`gap-flow-21`); and nothing compares the path a build walked with the flow it was
pinned to, so an unrecorded skip leaves no trace.

## 2. Scope (IN)

- **S1** — `flow.adapt`, its catalogue row in `tools/policy/catalogue.toml` already written (I10), values
  `additive-recorded` (default), `owner-approves` and `off`, read at `HEAD` through the policy kit's
  `resolve`, the kit found by `tools/loop/loop_parents.py#read_policy_kit`, as
  `tools/loop/loop_transition.py#read_record_channels` reads `transitions.record`. A value the kit
  refuses is a ValueError naming the key, which `record` answers exit 2 `unanswered`. Observed by AC1,
  AC2, AC3.
- **S2** — The proposal, a flow form of `tools/unattended/unattended.sh#verb_rescope`:
  `--rescope <slug> --flow <row tag> --act add|amend|exclude|supersede --item <unit id> [--row <path>]
  --reason <r>`, `--item` the unit whose pass proposes. The form is taken when `--flow` is given, before
  the unit form's act case. It runs the unit form's own checks of the run-state file, the terminal phase
  and `--reason` (`check_run_state`, `refuse_if_terminal`, `check_verb_flag`), then
  `python <loop>/adapt.py propose`, found by the driver library's `resolve_kit_dir` as `--refused` finds
  the position engine, with the driver's `BYPASS_BAN` passed as `--ban` where it is set. It relays the
  verb's lines; any exit but 0 is one driver refusal, `fail 48`, naming the verb's first line (§8 F8);
  on 0 it stages the run-state file with `stage_or_fail`. `propose` refuses, exit 1 and writing
  nothing: a field holding an LF, a CR or the separator ` · `, or spelling `--ban`'s value; `--row`
  absent on `add`, `amend` or `supersede`, or given on `exclude`; and an act the row disagrees with
  (S3). It appends `<ts> rescope · flow <act> <row tag>[ · change <record stem>] · reason <r>` to the
  build's `RUN.md`, one LF-ended line, and prints `unchanged` with exit 0 where a row equal past its
  timestamp is already there. The unit form's act case and its row keep their bytes, so every reader
  anchored on ` rescope · item ` reads the same rows. Observed by AC6 and AC7.
- **S3** — The rows. Each `add`, `amend` or `supersede` proposal writes one change record (I13,
  dOrderedCharter-15 S7) in the build's `build/` folder, `<date>-build-<unit id>-change-<n>.md`, through
  the memory-tree kit's `write_change`, which gains a `lines` argument it passes to `write_record` as
  the acceptance kind's writer does. Its fields: `Unit` the row's tag, `Action` `add`, `Before` `none`,
  `After` `<tag>@<hash8>` from `tools/loop/policy_edit.py#derive_blob_pin` over the fence's text, `Mark`
  `semantic`, `Proof` `none — flow proposal` and `Caused-by` the unit. Its lines are the row file's
  text in a TOML fence (§8 F5), and `propose` stages the record. The row file holds exactly one array of
  one table, `[[<kind>]]`, whose `tag` is `--flow`. The act must agree with the row's `edges` key: an
  `add` holds none, an `amend` holds `amends=<gov tag>@<hash8>`, a `supersede` holds
  `supersedes=<gov tag>@<hash8>`; a disagreement refuses the proposal naming the act and the row. An
  `exclude` writes no record: `--flow` is gov's tag, which the rescope row holds. Observed by AC6.
- **S4** — The class, derived and never typed, by `derive_change_class(act, operations)` in the new
  module `tools/loop/adapt.py`: `additive` for an `add`, and for an `amend` whose every operation the
  composition's `operations` lists for the row reads `narrows` (dOrderedCharter-36 S5's classifier,
  `tools/playbook/row_checks.py#derive_patch_class`); `loosening` for an `exclude`, a `supersede`, and
  an `amend` with any operation read `widens`. Observed by AC1 and AC4.
- **S5** — The application at the step boundary. `write_flow_states(root, build, mode)` runs inside
  `tools/loop/loop_transition.py#write_transition` on a move whose direction
  `tools/loop/loop_table.py#derive_direction` reads `forward` or `backward`, after the move is answered
  and before any record is written. For each pending flow row of the build's `RUN.md` it appends the
  state row `<ts> rescope · flow-state <row tag> · applied|held|refused · class <class> · flow.adapt
  <value>[ · disposition <record stem>]`. A row is composed first, through `read_composition` with its
  kind and, as `rows`, the build's layer plus this row (S6): an answer other than 0, a fence whose text the
  `After` pin does not match, or a kind the verb answers `unarmed` is `refused · class none`. Then
  under `additive-recorded` an additive change is `applied` and a loosening one `held`; under
  `owner-approves` every change is `held`; under `off` every change is `refused`. A held row is
  released by the newest disposition record (I9, TOOL-dDeclaredLoop-16 S4) whose `Item` is its tag and
  whose stem no state row of that tag names: `continue` applies it and `none` refuses it, each state
  row naming the stem. `write_flow_states` grades the word against those two itself, since no item
  declares a change's tag and `tools/loop/loop_lib.py#check_disposition_record` reads such a record
  `unarmed`. The state rows ride the move's commit; a refused commit cuts `RUN.md` back to its length
  before the boundary. A build with no `RUN.md` holds no flow row. Observed by AC1 to AC4.
- **S6** — The composition. A build's applied rows are the last layer of its composition, and they
  reach it through the one input TOOL-dDeclaredLoop-27 S6 lands for rows beyond the overlay, the
  playbook kit's `overlay_rows.py compose --kind <kind> --rows -`, a JSON array on standard input; this
  unit adds no compose input (§8 F6). `read_flow_layer(root, build, kind)` answers the build's layer of
  `kind` as that array's elements: each applied record's fenced row of `kind`, oldest first, its
  `source` the record's stem, then one element `{"exclude": "<tag>"}` per applied exclusion; an empty
  list where nothing is applied. The array's reader in `tools/playbook/overlay_rows.py#run_compose`
  gains that one element form, an object whose only key is `exclude` holding a tag: its tag joins
  `instructions.exclude`'s tags before `tools/playbook/overlay_rows.py#derive_row_composition` runs,

## 4. Design

### Data model

The run-state rows, one proposal and its state:

```
2026-11-02T10:14:03Z rescope · flow add item.build.adopter.lint-pass · change 2026-11-02-build-TOOL-dX-4-change-1 · reason the lint gate needs a pass item
2026-11-02T11:40:55Z rescope · flow-state item.build.adopter.lint-pass · applied · class additive · flow.adapt additive-recorded
```

The change record's fields, then its lines, the row in a TOML fence:

| Field | Value |
|---|---|
| `Unit` | `item.build.adopter.lint-pass` |
| `Action` | `add` |
| `Before` | `none` |
| `After` | `item.build.adopter.lint-pass@<hash8>`, `derive_blob_pin` over the fence's text |
| `Mark` | `semantic` |
| `Proof` | `none — flow proposal` |
| `Caused-by` | the proposing unit |

```toml
[[item]]
tag = "item.build.adopter.lint-pass"
step = "step.build"
actor = "command:lint"
needs = ["item.build.unit-pass"]
```

The build's item layer `read_flow_layer` answers, appended after any activated item rows to the
`rows` argument TOOL-dDeclaredLoop-27 gives `read_composition` and `read_composition_at`, which write
the array to `compose --kind item --rows -`'s standard input:

```json
[{"tag": "item.build.adopter.lint-pass", "step": "step.build", "actor": "command:lint",
  "needs": ["item.build.unit-pass"], "source": "2026-11-02-build-TOOL-dX-4-change-1"},
 {"exclude": "item.test.flakes"}]
```

Each row element is a record's fenced row as `tomllib` reads it, plus `source`; 27's reader refuses an
element that types `origin` and sets each row's `origin` to the repository's. The `exclude` element
is the one form this unit adds to that reader.

### The acts as write verbs

| Act | Change record | `Action` | The row |
|---|---|---|---|
| `add` | one | `add` | a new row, no `edges` |
| `amend` | one | `add` | a patch row, `edges = "amends=<gov tag>@<hash8>"`, its `add` and `remove` tables |
| `supersede` | one | `add` | a replacing row, `edges = "supersedes=<gov tag>@<hash8>"` |
| `exclude` | none | none | gov's tag, on the rescope row alone |

Each recorded act adds one row of the build's layer under an `adopter` tag, so it is the verb `add`,
and `Before` is `none`. An exclusion is not a `remove` record: the playbook kit's
`tools/playbook/instruction_units.py#derive_status` reads a `remove` as its tag ending with no successor,
for every build and the repository's own composition, where an exclusion here is this build's alone.
An `add` record ends no tag, so the tag index reads none of these records.

### The step boundary, in order

At a move from state A into state B, inside `write_transition`, after `derive_move` answers:

1. TOOL-dDeclaredLoop-26's `write_ended_orders`, where its pin moved;
2. on a forward move, `derive_path_deviations` over the position, its deviations filed as orders;
3. on a forward or backward move, `write_flow_states`, each pending row given its state row;
4. TOOL-dDeclaredLoop-26's `composition` field, then the records, `RUN.md` staged beside them, and the
   commit.

Pending means a flow row with no state row after it, or whose newest state row reads `held`. Every step
is idempotent by its rows: a retried boundary finds the state rows written and the order files of the
same names. `write_transition` imports `adapt` inside the function, since `adapt.py` imports
`loop_transition` for `read_transitions`.

### Alternatives rejected

- **A second record beside the rescope rows.** The brief's ruling: widen `verb_rescope`'s grammar,
  which already holds a run's amendments of its own scope.
- **The rows inline in the run-state row.** An item row carries an actor, needs, a witness and routes,
  which no single line holds; a change record pins the row by its hash, and its lines hold the row.
- **An exclusion as a `remove` change record.** The tag index would read gov's tag as ended for every
  build.
- **A class typed by the proposer.** A role could call an exclusion additive; the classifier derives
  it from the rows.
- **The record written by the role through `build_records.py new change`.** The door writes fields
  only, and its `After` would be typed by hand; `propose` derives the pin from the bytes it writes.
- **A compose input of this unit's own, rev-5's layer flag naming a file.** A second input for the
  job TOOL-dDeclaredLoop-27's `--rows -` already does, and a temp file per read (§8 F6).
- **The flow row written by the driver's `park`.** `park` writes `<kind> · item <item>`, so the row
  would read ` rescope · item ` to the unit form's readers, or need a new park kind.
