## 1. Goal

A role can change its own build's flow mid-build without moving every other build: it proposes rows
for its own build, a change that only adds applies unattended at the next step boundary and is
recorded, and one that takes away or loosens waits for the owner while the build carries on (the
owner's NT-4, `memory/builds/dClosedLoop/build/2026-10-19-build-PLAY-dClosedLoop-1-night-pass-two.md:109-114`).
Today a structural change goes only through the repository-wide overlay, and no record keeps one
build's adaptation (`gap-flow-21`); and nothing compares the path a build walked with the flow it was
pinned to, so an unrecorded skip leaves no trace.

- **S2** — The proposal, `verb_rescope`'s row grammar widened (`tools/unattended/unattended.sh:13296`).
  `--rescope <slug> --flow <row tag> --act add|amend|exclude|supersede --change <record> --reason <r>`
  appends `<ts> rescope · flow <act> <row tag>[ -> <successor>] · change <record stem> · reason <r>` to

  dOrderedCharter-35's row operations. The unit form's closed case and its row stay byte-identical, so

  build's `build/` folder, `<date>-build-<unit id>-change-<n>.md`, its `After` field a TOML fence of
  overlay-grammar rows, `<unit id>` the unit whose pass proposed it. The row's act must agree with the
  rows: an `add` holds only rows whose tags carry the `adopter` seat, an `amend` only `amends` patches,
  an `exclude` only tags, a `supersede` one replacing row; a disagreement refuses the proposal.
  Observed by AC6.
- **S4** — The class, derived and never typed, by `classify_change(rows, composition)` in the new
  module `tools/loop/adapt.py`: `additive` when every row adds an item, role or stage row, or is a patch
  dOrderedCharter-36 S5's classifier reads `narrows`; `loosening` otherwise, an exclusion, a
  supersession, a reorder or any patch read `widens` among them. Observed by AC1 and AC4.
- **S5** — The application at the next step boundary. Before `write_transition`
  (`tools/loop/loop_transition.py`, TOOL-dDeclaredLoop-3 S5) records a transition into a step, `apply_changes(build, mode)` takes every pending flow row and appends its state
  row `<ts> rescope · flow-state <row tag> · applied|held|refused · class <class> · flow.adapt <value>`:
  under `additive-recorded` an additive change is applied and a loosening one held; under
  `owner-approves` every change is held; under `off` every change is refused. A held change is
  applied at the first boundary after an owner's disposition record (I9, TOOL-dDeclaredLoop-16 S4)
  whose `Item` names its row tag and whose `Disposition` is `continue`, and refused at the first after
  one reading `none`; `apply_changes` grades that value against those two words itself, since no item
  declares a change's tag and `check_disposition_record` reads such a record `unarmed`. Observed by AC1
  to AC4.
- **S6** — The composition. Applied rows are the build's own recorded changes, the last layer of its
  composition after the scenarios it was placed under (TOOL-dDeclaredLoop-27 S6), composed by
  dOrderedCharter-35's `compose_rows`, so every row check reads them. A held or refused row is absent.
  Observed by AC1 and AC8.
- **S7** — The path comparison. At each transition out of a step, `compare_path(build, step)` sets the
  items the step's pinned composition declares against the items TOOL-dDeclaredLoop-7's
  `derive_position` (`tools/loop/position.py`) reads witnessed: a declared item with no witness at the exit is a `skip`, a witnessed item the
  composition does not declare is an `extra`. Each files one order through `write_row_order`
  (dSafePassage-9 S2), kind `flow-deviation`, naming the build, the step, the item and the class.
  Observed by AC5.
- **S8** — The fixture: `python tools/loop/adapt.py --fixture --plant <case>` builds a scratch build
  with a run-state file, a change record, transition records and witnesses, each plant run against its

  argv `python {prefix}/loop/adapt.py --fixture`, declared in `tools/loop/kit.toml`. Observed by AC1 to

## 4. Design

### Data model

The run-state rows, one proposal and its state:

```
2026-11-02T10:14:03Z rescope · flow add item.build.adopter.lint-pass · change 2026-11-02-build-TOOL-dX-4-change-1 · reason the lint gate needs a pass item
2026-11-02T11:40:55Z rescope · flow-state item.build.adopter.lint-pass · applied · class additive · flow.adapt additive-recorded
```

The change record's `After` field:

```toml
[[item]]
tag = "item.build.adopter.lint-pass"
actor = "command"
needs = ["item.build.unit-pass"]
```

### The step boundary, in order

At a transition from step A into step B, before `write_transition`:

1. `compare_path(build, A)`, its deviations filed as orders;
2. `apply_changes(build, mode)`, each pending row given its state row;
3. TOOL-dDeclaredLoop-26's move pins the composition revision, TOOL-dDeclaredLoop-27's the scenarios;
4. the writer records the transition.

Pending means a flow row with no state row, or a `held` state row newer than any owner disposition
naming its tag. Every step is idempotent by its rows: a retried boundary finds the state rows written.

### Inventory

| Minted | Kind |
|---|---|
| `--flow`, `--change`, and `--act` taking `add`, `amend`, `exclude` or `supersede` | `--rescope` flags, the flow form |
| `rescope · flow`, `rescope · flow-state` | run-state row subjects |
| `classify_change`, `apply_changes`, `compare_path` | functions, `tools/loop/adapt.py` |
| `additive`, `loosening` | the derived class |
| `flow-deviation` | outbox order kind |

The `--flow` flag passes the lexicon's flag cell, and each function name is put to
`python tools/lexicon/lexicon.py --suggest <name> --as py.function` in the build pass.

### Alternatives rejected

- **A second record beside the rescope rows.** The brief's ruling: widen `verb_rescope`'s grammar,
  which already holds a run's amendments of its own scope.
- **The rows inline in the run-state row.** An item row carries an actor, needs, a witness and routes,
  which no single line holds; the change record already carries rows (dOrderedCharter-35 S7).
- **A class typed by the proposer.** A role could call an exclusion additive; the classifier derives
  it from the rows.

## 5. Production-readiness checklist

- security — the agent-reachable write is a run-state row and a change record in the build's own
  folder; nothing a role proposes reaches the composition unless the class and `flow.adapt` admit it,
  and a loosening one waits for the owner's record.
- perf / scale — one classification per pending row and one set comparison per boundary.
- error / empty / loading states — no pending row applies nothing; a malformed proposal refuses by
  name; an unknown `flow.adapt` value refuses naming the key.
- observability — every proposal and its state are run-state rows; every deviation is an order.
- risks — a `skip` order on a build whose optional items were legitimately not run adds noise; the
  order names the item so an owner can see it.
- testing — the fixture plants of S8, run by the pass; the suite arm in §7 at the close.
- migration — none.
- user docs — `help/loop.md` gains the section; the verbs reference gains the flow form.

## 6. Acceptance criteria

- **AC1** — When `python adapt.py --fixture --plant additive` proposes an `add` of
  `item.build.adopter.lint-pass` under `flow.adapt` = `additive-recorded` and the build crosses its next
  boundary, the state row reads `applied · class additive`, and the composition into the next step
  carries the item.
  Red when: the change applies at the proposal, inside the step.
- **AC2** — When the same plant runs under `owner-approves`, the state row reads `held`, the next step's
  composition lacks the item and the build's transition still records; after the fixture writes an
  owner's disposition record naming the item with `continue`, the following boundary's state row reads
  `applied`.
  Red when: a held change stops the build's transition.
- **AC3** — When the same plant runs under `off`, the state row reads `refused` and the composition
  never carries the item.
  Red when: `off` is read as `owner-approves`, so the change waits instead of being refused.
- **AC4** — When `python adapt.py --fixture --plant loosening` proposes an `exclude` of a gov item under
  `additive-recorded`, the state row reads `held · class loosening`.
  Red when: the class follows the act's word, so a role's exclusion applies unattended.
- **AC5** — When `python adapt.py --fixture --plant unrecorded-skip` crosses a step's exit with one item
  of the pinned composition unwitnessed and no recorded change touching it, one order file whose name
  carries `flow-deviation` appears in the fixture repository's outbox folder, naming the item and
  `skip`.
  Red when: the comparison reads the tip's composition, so an item the pin declared is not missed.
- **AC6** — When `bash tools/unattended/unattended.sh --rescope` takes `--flow` with `--act add` and a
  change record holding an `amends` patch of a gov row, it refuses naming the act and the row, and
  writes no row.
  Red when: the act is recorded without its rows being read, so the class reads a mislabelled record.
- **AC7** — When the fixture run-state file holds both a flow row and the unit row
  `rescope · item add FIX-dAdapt-2`, `python tools/memory-tree/deviation_join.py --fixture` reads exactly
  the unit row, as it does without the flow row.
  Red when: the flow form changes the unit form's bytes, so `RESCOPE` at
  `tools/memory-tree/deviation_join.py:162` stops matching.
- **AC8** — When `python adapt.py --fixture --plant mid-step` proposes an additive change while the build
  is inside a step, the position read inside that step is unchanged until the next boundary.
  Red when: the composition reads pending rows, so a proposal moves the build at once.
- **AC9** — When `grep -n "owner-approves" loop.md` runs over the help page at this unit's commit, it
  finds the section naming `flow.adapt`'s three values and the `flow-deviation` order.
  Red when: the route ships and the page leaves a role no way to learn what it may change.
