## High

### H1. 87: the conf-constant class leaves out module names bound under `global` in a function, and module-level walrus, `for` and `with` targets (id 19)

- **Where:** 2026-10-24-spec-TOOL-dDeclaredLoop-87.md, §2 S1; §3; §4 sketch. Inherited by 88 §2 S13.
- **What is wrong:** S1 counts only an Assign, AnnAssign or AugAssign that no function and no class encloses. The repo's lazy-init idiom, `CONF = None` at module level and then `def load(): global CONF; CONF = HERE.parent / ".unattended.conf"`, falls outside the class. So do module-level NamedExpr, For and With targets. §3's non-goal covers only a conf path that a function builds and that is read through a call. It does not cover a module reading `ll.CONF` after a global loader. `global` occurs 20 times under tools/.
- **Consequence:** A module that reads `ll.CONF` set by such a loader passes `no-own-conf-read`. It is certified as reading no conf of its own when it does. The path is narrow. 88 S13's rule-2 slice keeps the gap, because rule 1 charges a constant inside a function to the function, never to the module name.
- **Fix (skeptic judged the finder's fix UNSOUND; the skeptic's correction):** Name these forms as an explicit 87 §3 non-goal and price them in §5 risks: a module name assigned under `global` in a function, and module-level NamedExpr, For and With targets. If they must be covered instead, add them as a pass of `derive_conf_constants` separate from 88's rule-2 slice, and state that in both 87 S1 and 88 S13. Only then add the `global CONF` loader row to S3/AC1 and AC2.
- **Left-shift gate:** a checklist entry, "a class defined over binding statements names every way the language binds a module name (Assign kinds, `global` in a function, NamedExpr, For, With, import) and puts each in the class or in a priced non-goal".
