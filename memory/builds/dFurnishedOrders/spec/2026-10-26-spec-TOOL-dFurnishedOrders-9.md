## 1. Goal

The role-to-step relation is typed, never derived or joined: the roles round's item map and the step
definitions' Actor cells are authored tables, and nothing checks that every actor is declared and
every core role acts (`gap-roles-15`, gap register line 167). The roles layer's `[matrix]`
(`layer-roles.md:391-459`) says the relation "is derived from the item declarations, never typed",
checked both ways, and that "each role's static block renders only its own row". Once dDeclaredLoop
declares the items as data, the matrix is derived from that definition (`:458-459`). This unit builds
that derivation, the one arm no parent carries (every core item role acts in at least one core item),
and the per-role row.

## 4. Design

### The derivation

```
derive_role_matrix(items, index) -> {steps, roles, kinds, undeclared}
  steps      = the step segment of every item tag, in loop order
  roles      = {slot: {} for slot in index.roles}
  for item in items:
      kind, name = item.actor            (TOOL-dDeclaredLoop-9's form; bare executor/owner have no name)
      if kind == "role":
          if name in roles: roles[name].setdefault(step, []).append(item.tag)
          else:             undeclared.append({item: item.tag, actor: item.actor})
      else:
          kinds[kind].setdefault(step, []).append(item.tag)
```

The matrix is a value computed at each call, never written to a file: the loop definition and the
role index are its only inputs, so nothing typed can drift beside it.

### The arms, both ways

| Direction | Arm | Owner | Refusal |
|---|---|---|---|
| item to role | 1: every actor a kind or a declared role | TOOL-dDeclaredLoop-9 | the item and its actor, read from `undeclared` |
| item to role | 3: no expansion or cycle role in a core item | TOOL-dBoundRoles-1 | the item, the role and its layer |
| role to item | 2: every core item role acts in a core item | this unit | `role.<slot>: a core item role that acts in no core item` |

A core item is an item of the composed loop definition: gov's rows and the repository's overlay rows,
the loop being a core kit's, while an expansion's items arrive from its own kit (TOOL-dBoundRoles-1
§4 "The item arm"). Arm 2 reads the composition, never gov's rows alone (`layer-roles.md:451-452`).

### The row

```
## Items

- item.build.unit-pass
  - inputs: spec, brief
  - return: outcome:built|diverged|refused, …
- item.build.fix-pass
  - …
```

Only the role's own items render: a builder never loads the loop (`layer-roles.md:456-457`).
