## 1. Goal

A problem found on one node reaches another only if its finder addresses that build (gap-conc-10,
`memory/builds/dClosedLoop/build/2026-10-14-build-PLAY-dClosedLoop-1-gap-register.md:331`). The
problem register TOOL-dPlacedRequest-12 files problems by subject on the remote; the owner's NT-18 asks
that "a work order cut later is handed the problems whose subject meets its item's seed"
(`memory/builds/dClosedLoop/build/2026-10-19-build-PLAY-dClosedLoop-1-night-pass-two.md:333-335`). This
unit reads the register when a work order is cut, keeps every problem whose subject meets the item's
seed, and hands each one in the order as a `finding` row the return must answer.

## 2. Scope (IN)

- **S1** — One reader of a `refs/gov/*` namespace. The bounded fetch half of `read_claims`
  (`tools/unattended/unattended.sh:2118-2150`: the one remote through `resolve_claim_remote`, a scratch
  directory, `observe_remote` fetching `+<ns>/*:<cache>/*` with no tags and no `FETCH_HEAD`, and the
  three failure reasons) moves into `read_gov_namespace <policy> <ns>…`, which fetches every named
  namespace in one bounded fetch, one refspec `+<ns>/*:refs/gov/remote/<name>/*` each, `<name>` the
  namespace's last component, and leaves the caches' `for-each-ref` records in a file and its reason
  in `GN_WHY`. `read_claims` calls it with TOOL-dPlacedRequest-1 S4's two namespaces,
  `refs/gov/leases` and the legacy `refs/gov/runs`, in one call (`refs/gov/runs` alone where that
  section has not landed at the pass), its rows, its `strict`, `soft` and `quiet` lines and its
  status unchanged. Observed by AC1 and AC7.
- **S2** — The verb. `unattended.sh --problems-for <item>` reads the item's seed paths on stdin, one
  per line, reads `refs/gov/problems` into `refs/gov/remote/problems` through S1 under the `soft`
  policy, and prints one state line and then one row per problem whose subject meets a seed path
  (§4 "### The verb's output"). It writes no ref but its private cache and no record. It joins
  `VERBS_INLINE` (`tools/unattended/unattended.sh:114`), dispatched beside `--claims` (`:14530`), and
  the usage block at the head of the file. Observed by AC1, AC2 and AC3.
- **S3** — The meet. A subject is a path when it passes the path-token rule of `read_files_touched`
  (`tools/unattended/unattended.sh:3404`, moved into `read_path_tokens` by TOOL-dPlacedRequest-8 S5),
  and a path subject meets the seed when `overlaps` (`tools/unattended/lib-unattended.sh:750`) holds for
  it and some seed path, the containment `check_writes_intersect`
  (`tools/memory-tree/design_lib.py:601`) answers and the `TOOL-dGroundRules-40` arm of
  `tools/check-spec-tokens.test.sh` holds equal to it. A subject that is not a path (a definition, a
  tag or a node fact) meets nothing until dTotalRecall's `code` record keys it, and is counted on the
  state line, never lost silently. Observed by AC1 and AC2.
- **S4** — The states. The verb's state is `filled` when a row prints, `searched-empty` when the
  register was read and nothing met the seed or the seed held no path, and
  `not-installed: <why>` when the register was not read: `RUN_CLAIMS` is `off` (the coordination
  switch TOOL-dPlacedRequest-12 S7 writes under, `tools/unattended/unattended.sh:671-676`), or S1
  returned a reason. Exit 0 in every state; exit 2 only for a missing item or a refused argument.
  Observed by AC3.
- **S5** — The slot. `render_handoff` (`tools/roles/handoff.py:312`), for a work order cut with
  `--item <tag>` (TOOL-dBoundRoles-3 S1), adds the `### problems` block through
  `read_order_problems(root, slug, unit, item, question)` in `handoff.py`: it takes the item's seed
  from `read_item_seed(root, slug, unit, item, question)` in `handoff.py`, the one call of
  TOOL-dPlacedRequest-8 S4's `python tools/loop/loop_lib.py seed <item tag> --build <slug>

  printing `unarmed — <source>: <why>`, or no unattended driver resolved through
  `roles_lib.resolve_kit_dir`, renders `not-installed: <why>`. With no loop kit found,
  TOOL-dBoundRoles-3 S1 refuses the `--item` render with exit 1 before any block is built, so the

  Observed by AC4 and AC6.

- **S8** — The docs. `tools/unattended/VERBS.template.md` (rendered to

## 3. Non-goals (OUT)

- Filing a problem, its encoder, its id and its record: TOOL-dPlacedRequest-12. This unit reads the
  record grammar that unit's S6 writes and writes no register entry.
- A problem's resolution. The register is create-only and no record carries a closed state, so every
  filed problem meeting the seed is handed; a role answers a stale one `not-applicable` with its
  reason. Closing a problem is no clause of this build.
- Meeting a definition, a tag or a node-fact subject: dTotalRecall's `code` record (cl-dClosedLoop-0219)
  gives those subjects paths. Until then they are counted, not handed.
- Secret scanning of a problem's body: gap-rt-44, dWellOiledMachine's. This unit hands the first body
  line only, cut to 200 bytes.
- The item seed itself and its `unarmed` sources: TOOL-dPlacedRequest-8. The `code` slot that reads the
  same seed: TOOL-dFurnishedOrders-17.
- The return's join of answered rows: TOOL-dDeclaredLoop-29 S6's `join_upstream` and
  TOOL-dFurnishedOrders-19's schema.

## 4. Design

### The record read

TOOL-dPlacedRequest-12 S6 writes each problem as a commit over the empty tree whose message is:

```
gov-problem <encoded subject>/<problem id>

subject: <raw subject>
item: <item tag, or none>
session: <session id>

<body, at most 4096 bytes>
```

The verb reads the cache with one `for-each-ref --format='%01%(refname)%09%(objectname)%0a%(contents)'`
and one `awk` pass, as `read_claims` does (`tools/unattended/unattended.sh:2151-2170`): the id is the
last ref component, the subject is the `subject:` value, never the decoded ref, and the row text is
the first non-blank body line with tabs folded to spaces, cut to 200 bytes. A record with no
`subject:` line is counted `malformed` on the state line and handed nowhere.

### The verb's output

```
$ printf 'tools/lib/\n' | bash tools/unattended/unattended.sh --problems-for item.build.unit-pass
problems-for item.build.unit-pass · filled · 3 read · 1 met · 1 non-path · 0 malformed
- problem#3b18e512cc0f · finding · tools/lib/x.sh — the resolver exits 9009 under the MS-Store stub
```

The rows are sorted by subject, then id, so two renders of one register print one byte sequence.
The `not-installed` form ends the first line with `: <why>` after the state and prints no row.

### The meet

```
for each record r:
  "`" r.subject "`" | read_path_tokens        -> empty: non-path, counted
  for each seed path s: overlaps r.subject s  -> any true: met
```

`overlaps` runs in the driver's own shell over `normpath`'s `_np` answer, so the meet costs no fork
per pair (`tools/unattended/lib-unattended.sh:737-750`). A trap subject such as `tools/lib-extra/y.sh`
against the seed `tools/lib` does not meet, which a raw prefix test would call met.

### The slot

```
### problems

slot problems · filled

- problem#3b18e512cc0f · finding · tools/lib/x.sh — the resolver exits 9009 under the MS-Store stub
```

The block sits in TOOL-dBoundRoles-23's `material` slot, after the `reads` blocks. Its rows follow
TOOL-dDeclaredLoop-29 S3's row grammar, `- <row id> · <kind> · <text>`, with the id
`problem#<problem id>` read as `<item>#<row id>` where the register is the item.

### Alternatives rejected

- **A copy of `read_claims` for the problem namespace.** It is the second instance of the bounded
  namespace read, so the charter's `[reuse]` rule asks for the factory S1 extracts.
- **The containment test by `design_lib.py` in a Python subprocess per render.** It has no command

  the driver's `overlaps` is the same rule held equal to it by a gate arm.
- **The driver resolving the seed itself.** It would make the driver find the loop kit; the renderer
  already resolves kits, and the seed resolver calls back into the driver for `write-set`.

## 5. Production-readiness checklist

- security — no new write path: the verb writes only its private cache refs, as `--claims` does. A
  register body is another session's claim, so the block hands one line per problem, cut to 200
  bytes, as a `finding` row the role answers, never as an instruction; the body's secret scan is
  dWellOiledMachine's.
- perf / scale — one bounded fetch and one `for-each-ref` per render; the meet is in-shell. The row
  count is not capped: a seed meeting many problems hands them all, each one line.
- error / empty / loading states — `filled`, `searched-empty` and `not-installed: <why>`, never an
  empty block; a remote that does not answer reads `not-installed` naming the fetch's exit.
- observability — the state line counts read, met, non-path and malformed records.
- risks — the fetch adds the remote's latency to a render; the bound is the kit's `REMOTE_BOUND`.
- testing — AC1 to AC7 over a scratch clone and a bare remote; the arms of §7 at the close.
- migration — none, as §4 says.
- user docs — `help/roles.md` names the `### problems` block (S8).
