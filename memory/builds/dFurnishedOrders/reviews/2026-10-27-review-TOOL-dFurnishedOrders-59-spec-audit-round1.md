## Medium

### M1. Spec 60 AC6 counts NEAR `[guards]` tokens that no waiver row can match (ids 1, 9, 27)

- **Where:** spec 60, section 6 AC6, against section 2 S7.
- **What is wrong:** S7 limits the population to `govkit selftest <- ` tokens on `HIT` or `WAIVED` `[guards]` lines. AC6 drops that limit and compares the tokens on all `[guards]` lines of `--list` with the waiver rows. `--list` already prints two NEAR `[guards]` lines carrying that token, from live pre-cutoff specs: aDeclaredBound-4 (`<- tools/hooks/kit.toml`) and aQuarriedLantern-1 (`<- tools/settings-merge.py`). The waivers file holds 0 such rows.
- **Consequence:** AC6 reds on a correct build. If the builder adds waiver rows for the NEAR tokens, those rows go `STALE WAIVER` and red the spec-token run, because `seen_waived` is filled from hits only (check-spec-tokens.py:1719-1729).
- **Fix (judged SOUND):** reword AC6 to S7's population: the `govkit selftest <- ` tokens on `HIT` or `WAIVED` `[guards]` lines equal the waiver rows with that prefix. State that a NEAR line never counts. Add a fixture spec dated before the cutoff, or a case in the AC5 clone, whose NEAR-only token must not count.
- **Left-shift gate:** a spec-lint check that an AC reading a `--list` population carries the same status filter as the S item it observes. Or add a checklist entry "AC population narrower or wider than its S item".

### M2. Spec 60 AC9 reads a landing merge as a guard gain by a non-pass commit (id 2)

- **Where:** spec 60, section 2 S10 and section 6 AC9.
- **What is wrong:** S10 and AC9 diff `tools/gate-legs.json` at each commit in an undefined "build range" against its first parent. This build lands by `merge: <build> — land onto origin/main`, and after a re-prepare that merge sits inside the build side's history (as the dKeptSession landing merge d2e071573 shows). Its first parent is main, so the diff shows it gaining every guard row the build added. Its subject names no unit, so `derive_pass_units` attributes it to nothing.
- **Consequence:** AC9 reds a correct build after a re-prepare. A merge of main that carries another build's guard edit has the same effect. This is a false red on a narrow path. The current range has no merges.
- **Fix (judged SOUND):** define the build range as `<merge-base>..<tip>` and skip merges (`git rev-list --no-merges`), or attribute a merge's gains to the side that introduced them. Stage both cases in a scratch repo: a guard row added by a non-pass commit reds AC9, and a landing-style merge stays green.
- **Left-shift gate:** this is the class named in memory/gotchas/a-merge-of-the-default-branch-read-as-additions.md. Add a spec-lint rule that any AC diffing commits "against the first parent" must name its range and its merge handling.
