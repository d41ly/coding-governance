## Verdict: BLOCKED

The counts sit here rather than on the heading, because that line's token is a closed set and a tally appended to it turns a structural check into a semantic one.

Eight blocker rows over five distinct blocking defects, and the build README's own prediction held: the predecessor shipped two fail-opens in this file and had both caught by review, and this spec set ships more. Each of the three units is blocked on its own mechanism, not on its prose.

`TOOL-aPairedLexer-2` is the worst of the three, and it is blocked in the direction the build exists to close. S1 points `offendingLines` at `renderCodeView(script)` with no `unterminated` fallback, while rule 2 has carried one since `TOOL-aLexedStripper-5` and the sibling `-1` is adding one to rule 3 in the same build. Reproduced on three different legal, runnable scripts: a regex literal carrying a backtick blanks every line below it to `''`, and a real raw `parallel(` under it goes from DENY at BASE to ADMIT. That is a new fail-open in the raw-primitive ban — the rule the spec's own §4 calls the one where hiding a primitive is worst — introduced by the unit next door to the one closing the identical class. §5's dismissal ("a template literal is a string, and the executable half is the interpolation") is refuted by the file's own header at `agent-cap.js:275-277`: below a false opener the blanked text is not a string, it is code.

`TOOL-aPairedLexer-1` is blocked from both sides. The fallback it chooses fires on legal scripts and DENIES them (a `(` in prompt prose unbalances the forward paren join that rule 3 is built on; a block comment naming `boundedParallel(thunks, cap)` becomes a denial), because `blankLiterals` exists precisely so rule 3 need not read a view that unbalances its parens — §4's claim that the per-line view "can only ADD findings, never remove them" is false in the other direction too, since that view also feeds `intConsts` and an ADDED const binding REMOVES a finding. And the signal it picks is template-only by construction, so the `block` half of `blankLiterals`' own three-mode carry is left standing: `/[/*]/` above a cap of 500 still ADMITS with the specced fix applied, on valid JavaScript, where the shape the unit does close is not valid JavaScript at all.

`TOOL-aPairedLexer-3` is blocked on scope its stated defect does not require. S1 mandates blanking string and template CONTENTS, which BASE never does and comment-strip ORDER does not need; implemented literally over this repo's own tracked JS it removes eight real definitions and adds none, because the pass models neither regex literals nor unpaired quotes — the same unsoundness the sibling `-2` refuses block blanking over, in the same build. AC8 then contradicts S1 outright by requiring a diff with additions and no removals.

Underneath the blockers sits one repeated shape across all three units: a criterion that cannot fail on the mechanism it names. `-1`'s AC1–AC7 pass identically whether the fallback is conditional or unconditional, so the guard the whole safety argument rests on is unpinned. `-2`'s deny-expecting criteria assert a bare exit code, and rule order means an earlier rule masks rule 1 behind an identical `2` — AC3, the regression guard for the rule this unit rewrites, is green with rule 1 entirely broken. `-3`'s AC7 exemption list is wrong about two of its rows and names a third whose subject does not exist at BASE.

Round 2's exit condition is a strictly falling confirmed-blocker count. This round sets the ceiling at 8.

## What round 2 must not repeat

Three of the five distinct blocking defects are the same shape one level up: **a fix that swaps which VIEW a rule reads, argued from what the new view does to one channel, while the rule reads three.** `-1` reasons about the finding scan and forgets `intConsts` and `joinCall`; `-2` reasons about template contents and forgets that `renderCodeView` models neither regex literals nor block comments; `-3` reasons about comment ORDER and ships string blanking nobody asked for. The predecessor build shipped exactly this shape twice and had both caught here.

The cheapest structural answer is not another lens. It is a rule for this file's specs: **a unit that changes which view a rule reads enumerates every consumer of that view, and carries one AC per consumer.** `capFindings` has three. `offendingLines` has one, which is why `-2`'s defect is a single fallback line and `-1`'s is not.
