## High

### H1. The departures report's range reads every build that landed meanwhile as this run's work (id 12)

- **Where:** plan:179 (`git diff --name-only <base>..HEAD`), plan:205 ("every `Decided:` trailer in the build's range"), and README rule 4 (plan:329-334).
- **What is wrong:** `<base>` and "the build's range" are defined nowhere in the plan. Rule 4 runs the report on the prepared merge. Per `check_prepared_merge` (tools/push-main.sh:505-538), that merge's first parent is the advertised origin/main tip. So read from the run's starting base, the range takes in everything main gained since then.
- **Consequence:** Every path another chain build landed in that window shows up as this run's outside write. That block is the interim path-exclusion check in [cannot]. Every other build's `Decided:` trailer also becomes one the validating arm requires the report to show. The arm then reds, or the report lists other builds' forks as this build's. With three nodes running at once, nearly every run has such a window. The only red test plants a positive, so this false-positive path is never checked.
- **Fix:** The skeptic rejected the finder's fix. The corrected fix: define the range from the prepared merge's first parent, the advertised tip T. Take paths from `git diff --name-only T...HEAD` and trailers from `git log T..HEAD`, which excludes every commit main gained. Add a red test: main gains another build's file and trailer between the run's base and `--prepare`, and neither may be listed or required. See that test red against the `<base>..HEAD` shape first.
- **Note:** The skeptic could not reproduce the finder's d2190c9a probe, because that merge's merge base equals its first parent. The git semantics alone establish the defect. This is the same defect as M1. The two items are kept apart only because their binding grades differ, so fix them together.
- **Left-shift gate:** In P0.2's self-test, a standing fixture of a prepared merge whose upstream side lands another build's path and trailer. Add a checklist entry, "a range on a prepared merge read from the run's base".

### H3. The retirement table needs edits to deviations.py, and the fold's pin rule leaves those edits no route (id 20)

- **Where:** plan:559-567 (the new column "What the report and the packet read from then on"). Also P0.2 at plan:177-178 and the pin rule at plan:698-701.
- **What is wrong:** The column has `--report` switch from `carries.py --report` to the README coverage region, and later to the outputs of the classifier, `deviation.approval` and `deviation.gate`. The edit and the re-pin happen in an owner-asked landing that lands nothing else, recorded as a decision row. Add the route to the retirement table's last column and to the [owner] table.

### M2. The instrument pin guard overclaims, and P0.3 never specifies it (ids 1, 8, 13)

- **Where:** plan:698-701 ("a run that edits an instrument cannot re-pin it away"), P0.3 at plan:223-252 (`--check` at plan:250), row 10's plant at plan:148, and "What nothing catches" at plan:958-960.

Until the chain unit's merge-bar check, the only guard is the owner's landing-diff check of every `memory/builds/dClosedLoop/build/*.py` path and of the packet's pin line.
  - Add "a run edits its own packet's pin line" to the instrument row in [cannot].
  - Give row 10's plant the re-render scope only, and add no plant that expects a hand-edited pin to stay red.
  - Give P0.3 a pin-keeping re-render mode. Add a separate pin arm to `--check`: for each field-1 instrument, compare the pinned blob with `git rev-parse HEAD:<instrument>` and exit 1 on a mismatch, whatever the byte compare says. The red names its cause ("instrument <path> moved").
  - Name the owner's re-pin command, refused inside a chain run (see H3).
  - Plant: edit one byte of `carries.py` and re-render with pins kept. The pin arm reds while the byte compare stays green. With the pin arm removed, `--check` is seen green on the same plant.
- **Left-shift gate:** The pin-arm plant above, in P0.3's self-test. Add a checklist entry: "a guard whose pin is stored in state the guarded actor rewrites", and a claim that must match the row it cites.
