## High

### H1. The composition's fixed set for rows has no check that can fail (ids 1, 12, 16)

- **Where:** adoption:190-202 (item 9), v2:1501 (dOrderedCharter's row clause), v2:1503 (dDeclaredLoop), v2:1506 (dBoundRoles).
- **What is wrong:** Item 9 fixes whole rows (floor items, exit items, the cycle roles) and fields inside open rows (a gov item's tag, step, witness and outcome set; a core role's write class and return schema; the matrix arms, the kinds, the lens slots, the canary key set). It says "the class is derived, never typed". FA-5 lets a patch widen only an open field. In v2, the class derivation and "a fixed unit refusing all three" exist only in dOrderedCharter's unit clause. The row clause derives no class and refuses nothing, and it is only "seen on a planted row of a fixture kind". dDeclaredLoop says only that gov's floor, needs and routes change "only by a pinned patch", which still admits a pinned `supersedes` of a floor item. dBoundRoles has no red case for a core role's write class or return schema. The only fixed-row refusals in v2 are `instructions.exclude` (v2:1027) and dWitnessedBar's "dropped fixed leg" (v2:1512).
- **Consequence:** A repository row with `supersedes=<gov floor item>@<hash>` replaces the whole row, witness and outcome set included. An `amends` can swap a computed witness for an attested one or widen a core role's write class. Both pass every check the chain plans. The fixed set protects against exclusion only, so the design claims a guarantee nothing enforces.
- **Fix (finders' fixes judged UNSOUND; the skeptics' corrected fix):** Give dOrderedCharter's row mechanism a generic class arm. Each kind's schema declares its fixed rows and fields, derived from item 9's three sources and never typed, and an undeclared class reads as fixed. An `amends` that touches a fixed field, a `supersedes` or `exclude` of a fixed row, and a widening of a fixed field are refused, each seen red on a planted fixture-kind row. The red cases must not name gov items, floor items or core roles on dOrderedCharter, because those kinds are registered by later builds. Each kind's own build then declares its fixed list and plants its own reds: dDeclaredLoop on a patch of a gov item's witness or outcome set and a supersede of a floor or exit item; dBoundRoles on a patch or widening of a core role's write class or return schema and a supersede of a cycle role; dWitnessedBar on a patch of the canary's key set or a composition-checking leg.
- **Left-shift gate:** A clause-coverage check over v2: every "fixed" or "never" set a design record states must map to a named refusal with a seen-red arm on the build that registers the kind. Add the bug-class checklist entry "rule-stated-with-no-check-that-fails" for row kinds.
