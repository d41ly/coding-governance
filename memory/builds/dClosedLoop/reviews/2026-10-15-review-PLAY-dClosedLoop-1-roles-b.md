## High

### H1. A repaired fact is keyed to an immutable return and never goes stale (id 47)

- **Where:** [trust] item 7 against item 3; [forks] F3-4 settlement.
- **What is wrong:** Item 7 and F3-4 hand a repaired fact onward "keyed to the repairing return". Item 3 re-cuts only facts whose key moved. A return never changes, so the repaired fact passes the spawn check indefinitely, even after the code it describes has changed. No rule covers two parallel producers filing different repairs of one fact.
- **Consequence:** Item 3's guarantee breaks for exactly the facts already shown to be fragile. Under `roles.trust=keyed` and `refuse`, the receiving role acts on a stale repaired fact without re-checking it. With parallel builders or a review fan, which repair gets handed onward is undefined.
- **Fix (skeptic judged it sound):** Key a repaired fact to the source its repair read, which item 7 already records as "the key of what it read". Keep the return only as provenance. Item 3 then re-cuts it like any other keyed fact. Class it as `claimed`. State a rule for conflicting repairs, for example the latest repair at the newest source key, or park the fact with an ask.
- **Gate:** add a fixture that repairs a fact, changes the source it read, and expects the next cut to re-key or drop it. Add a second fixture with two conflicting repairs of one fact that expects the declared resolution.
