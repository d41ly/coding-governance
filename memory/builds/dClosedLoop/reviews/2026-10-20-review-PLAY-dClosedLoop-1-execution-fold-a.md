## High

### H1. The instrument pin has no check that compares it with the instrument (ids 20, 23)

- **Where:** plan:250-252 (P0.3's `--check`), plan:148 (P0.1 row 10's plant), plan:578 and plan:699-701 ([handoffs]).
- **What is wrong:** the fold says a re-render keeps the pins the packet already carries, and that a moved instrument blob stays red until the owner lands a new pin. But P0.3's `--check` is only a byte compare against a fresh render, plus completeness arms for clause ids, gaps, parents, `[owed]` lines and roster units. No arm compares a carried pin with the instrument's blob at HEAD. Row 10's plant edits one byte of `carries.py` and then runs "the recovery step". For a moved blob that step is now "stop", so the plant never re-renders and cannot tell a `--write` that keeps pins from one that refreshes them. No section names who lands a new pin, with which command, or in which commit.
- **Consequence:** under the keep-pins rule, a re-render reproduces the old pin. A one-byte instrument edit that does not change the output therefore reads green. That is a guard certifying what it does not check. A `packet.py` whose `--write` re-pins, the escape this fold row was meant to close, also passes the plant.
- **Fix:**
  - Add an explicit P0.3 `--check` arm: each carried instrument pin must equal `git hash-object` of that instrument at HEAD. It reds on a mismatch, and `--write` keeps the pins the packet carries.
  - Replace row 10's plant. Edit one byte of `carries.py`, make the packet stale by another cause (for example an `[owed]` line), run `packet.py --write`, and `--check` must still be red. Its control is a `packet.py` variant whose `--write` re-pins, which must turn the plant green, so the test is seen red.
  - In [owner], state the pin-landing step: who lands it, with which command, in which commit.
- **Left-shift gate:** a bug-class checklist entry: "a guard's plant must exercise the escape the guard names, with a control variant that turns it green".

### H2. The new spec-run test classes a whole run as a spec run (id 22)

- **Where:** plan:481-483 (the spec-run definition) and plan:491 (the replaced refusal).
- **What is wrong:** at base, the extra unit refused "a unit added by a run that closes a unit, a build run or a whole run". The fold replaced that with "a unit added by any other run". It now defines a spec run purely as one whose starting roster, read by `baseline_units`, has any unit MISSING. dTrueNorth's whole run starts with all seven units MISSING. Under the fold's own authored-roster fallback (plan:493-498), the driver reads that roster, and dTrueNorth lands through the new code (plan:509-510).
- **Consequence:** the driver treats dTrueNorth's whole run, and every later whole run with an authored roster, as a spec run. It may then defer and carry forward a unit its closing review promoted. That breaks M4, which the plan restates at plan:532 ("its promoted units are built in this run") and plan:64. None of red cases 1-7 is a whole-run fixture, so the extra unit's spec would build this loosening as written.
- **Fix:** define a spec run as one whose starting roster has a unit MISSING and that closes with no unit it built, or have the driver read the README's whole-run rule. Restore the explicit whole-run refusal at plan:491. Add red case 8: a whole-run fixture with all units MISSING at its start defers a unit its closing review added, and is refused both before and after the change.
- **Left-shift gate:** a checklist entry for `amendment-leaves-its-other-half-standing`: when a definition is widened, every case the old wording excluded gets a red case.
- **Related:** M4 below (id 5) is the same reach, graded medium by its skeptic.

### M2. The instrument pin lives in a file the guarded run writes (id 1)

- **Where:** plan:699-701 ([handoffs]), with the pin field at plan:229-232 (P0.3 field 1) and the write rule at plan:340 (README rule 7).
- **What is wrong:** the pin sits in field 1 of the run's own packet under `memory/builds/<slug>/prompts/`, and README rule 7 lets the run write there. That is the exact class the fold row names: a guard whose pin is stored in state the guarded actor rewrites.
- **Consequence:** the plan overclaims, and the rule reads two ways. Row 10 says the pin "narrows the escape and does not close it". The real guard is the owner's landing-diff check for `memory/builds/dClosedLoop/build/*.py` ([cannot] plan:1078, [owner] plan:1032-1033), which sees the edited instrument whatever the packet says.
- **Fix:** keep pins out of every run-writable file: compare each instrument's blob with its blob at the opening landing commit, read from git. Otherwise, state in [handoffs], P0.1 row 10 and [cannot] that a run can re-pin by editing its own packet, and that the owner's landing-diff check is the only guard. That check should also cover a pin line changing in any `*-packet.md`. Add a plant that hand-edits the pin to the edited blob, and record what reds.
- **Left-shift gate:** the existing checklist class for a pin stored in state the guarded actor rewrites, applied as a plant that tries the dishonest re-pin and not only the honest recovery.
