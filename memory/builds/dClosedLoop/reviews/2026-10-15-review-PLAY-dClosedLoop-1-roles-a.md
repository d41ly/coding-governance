## Medium

### M1. The derived matrix gives items more than one actor kind (ids 1, 13)
- **Where:** [matrix] (the derived table and its Counts) and [instrument] role_matrix.py.
- **What is wrong:** role_matrix.py collects every keyword hit in the prose of a flow-steps Actor cell. build.unit-pass ("builder ... commits queued by the executor") is credited to the executor. entry.intake ("command: the prompt-submit hook") and test.verdict ("command: the bar, through the hook") are credited to both hook and command. The stated counts, 60 actor-item pairs and 14 actors, are artefacts of this. The true figures are 55 items, and the cells name 11 roles plus command.
- **Consequence:** runtime [terms] dispatches each item by exactly one actor kind. It runs command and executor items and awaits hook items. Items with two kinds have no single dispatch, and dBoundRoles' "joined both ways" check would accept them.
- **Fix (skeptic judged it sound):** give each item declaration exactly one typed actor kind, plus a role where the kind is role. Keep prose apart as a note. Derive the matrix from that field. Add a check that every item has exactly one kind. Restate the counts as 55 items and 55 pairs.
- **Left-shift gate:** a matrix-leg fixture where an Actor cell declares two kinds must exit 1.

### M2. The matrix check's "both ways" arms are not implemented, never seen red, and fail on the record's own roster (ids 2, 12, 35, 39)
- **Where:** [matrix] "The check runs both ways" and "Seen red", [roster], and [instrument] role_matrix.py.
- **What is wrong:** [matrix] states three arms. The instrument has only one failure path: a cell that matches no keyword. Measured probes show the gap.
  - Changing "builder" to "buildr" exits 0, because the cell still matches "executor", and the builder silently drops out of the matrix.
  - Removing the tester from test.attribute exits 0.
  - An undeclared actor named next to a known word exits 0.
  - The arm "every core role acts in at least one core item" would fail on the design itself. [roster] makes the prompt writer core, while [matrix] says it appears in no Actor cell.
  - The P28 arm, "an expansion role acts only in its expansion's items", has no code and no failing fixture.
- **Consequence:** the record presents as seen red a join that certifies far less than it claims. If it is built as written, it either fails on the correct design or needs an undeclared exemption. Ids 39, 12 and 2 were re-graded or kept at medium: the build writes its own check, and this instrument is design evidence.
- **Fix (skeptic judged it sound):**
  - Implement the declared-role, core-coverage and expansion arms as separate predicates over a declared actor field, tokenising each cell against the roster rather than taking regex hits.
  - Choose how the prompt writer is handled: either declare its act as an item of every role item's cycle, or exempt it through a declared field such as `acts-in: cycle`.
  - Record a seen-red run for each arm on the real record: "buildr" in build.unit-pass, the tester deleted from test.attribute, a core role stripped from every item, and "deployer" placed in a core item. Each must exit 1.
- **Left-shift gate:** dBoundRoles' matrix leg carries one planted-red fixture per arm, and the leg fails if any arm has no fixture.

### M4. R3-F's acceptance cannot be observed with the instrument it names (ids 4, 16, 33)
- **Where:** [more] R3-F Acceptance and [instrument] role_orientation.py.
- **What is wrong:** the acceptance requires "answered calls at zero under refuse", but role_orientation.py has no measure for it.
  - klass() returns only state, locate, method and content, and the output has no answered or refused column.
  - A refused call is still counted as a tool_use.
  - The population is only gov-* subagent .meta.json files, so headless acts, one `claude -p` per agent, are invisible.
  - "Briefed" and own-prompt detection key on the `gov:handoff ... path=` marker, which the work order replaces.
  - parent-had is computed only for direct spawns.
  - The instrument exists only in the record, not in the tree.
- **Consequence:** the criterion certifies nothing about re-orientation. The method and locate comparison can run over an empty or partial population. Id 33 was re-graded from high to medium: no answered-call number is printed at all, so a build would find the gap rather than certify a false zero.
- **Fix (skeptic judged it sound):**
  - Add an answered-call class: a call whose answer the work order already holds, joined to the work order by task-sha, counted as attempted vs refused vs admitted from the hook's journal.
  - Add headless act transcripts to the population.
  - Key "briefed" detection on the work-order marker.
  - Restate the acceptance as "attempted answered calls fall below baseline, and refusals are journaled". Attempts measure the packet; refusals measure the hook.
  - State the CLI-version caveat.
- **Left-shift gate:** a planted transcript that re-reads a handed range must raise the count to 1. The population must be non-zero for each backend in use.

### M5. R3-H's agent-file hook contradicts runtime's single enforcement surface (ids 5, 17, 28, 32)

### M6. The work order and the answered-call hook are bound by agent id, which headless acts do not have (ids 6, 37, 44)
- **Where:** [settled] "The two blocks" ("bound to the agent's calls by its agent id") and [trust] item 10 ("A PreToolUse hook, bound to the agent id").
- **What is wrong:** runtime keys returns by task-sha because agent_id is unstable across sessions, and it binds sessions through a SessionStart binding record and an epoch. Its headless backend runs each role agent as a top-level `claude -p` session that has no subagent agent_id.
- **Consequence:** under `runtime.spawn-backend=headless`, the hook has no key to look up the work order. Refuse either silently becomes allow or refuses every call. This is medium because headless defaults to in-session until the spike runs.
- **Fix (skeptic judged it sound):** bind through the act's session binding record (session-id plus task-sha, with the epoch) under headless, and through agent_id mapped via the SubagentStart spawn marker in-session. State both and cite runtime [act] and [spawn].
- **Left-shift gate:** one answered call per backend, each observed refused.

### M7. "Fresh at the spawn, by construction" is not delivered by the runtime layer (ids 7, 41)
- **Where:** [trust] item 3, and P29 in v2, against runtime [act] and [spawn].
- **What is wrong:** the supervisor cuts the work order once, before it launches the act session. Inside that session, the Workflow harness spawns the prompt writer and only then the role agent, or a staged fan. It has no shell, and no step re-keys the order. Attended acts name no cutter at all.
- **Consequence:** a key that moves in the window reaches the role as fresh, while the role is told never to check freshness. Examples are the base, the build's position, or a commit from a parallel pass. This is a contained staleness on a narrow path. Id 41 was re-graded from high to medium.
- **Fix:**
  - Id 7's fix (skeptic judged it sound): restate the guarantee as "fresh at act launch", or record the window as accepted, and name the attended cutter.
  - Id 41's finder proposal was REJECTED by the skeptic; this is the skeptic's corrected fix. Drop "by construction" and state where the key check runs for each backend.
    - Headless: the supervisor re-cuts the work order immediately before each agent it launches.
    - In-session: record the cut time and the keys handed. At SubagentStop, or at the act's reconciliation, compare each handed key with its current value. Exclude keys in the role's own write set and anything the role's own return records as changed. Void and re-run only a return whose untouched handed keys moved.
- **Left-shift gate:** move the base between the cut and the role spawn, and the return must be voided. A builder's edits to its own files must not void its return.

### M8. Refusing answered state calls kills the repair path for a stale HEAD (id 11)

- **Fix (skeptic judged it sound):** restate item 3 so the key check sits at the act's cut. In item 10, have the hook recompute the live key at call time (rev-parse for state, filtered hash-object for a range). Refuse only while the live key still equals the handed key; otherwise admit the call and journal the moved fact as a repair input.
- **Left-shift gate:** a parallel pass commits between the cut and a builder's `git rev-parse HEAD`, and the call must be admitted.

### M15. Repair-and-record has no closure against frozen records and no rule for conflicting repairs (id 46)
- **Where:** [trust] item 7 and [forks] F3-4 as settled.
- **What is wrong:** a repaired fact is handed "until that record is fixed", but a built spec stays frozen (P19), so it is never fixed. Two concurrent roles can repair one key differently, and nothing chooses between them. The repaired fact's class is never assigned.
- **Consequence:** a repair, which is itself a claimed fact, propagates unverified and forever. The executor holds two keyed facts for one key.
- **Fix (skeptic judged it sound):**
  - A repair against a frozen record closes when a fold or a new unit supersedes it; otherwise it stays as a capped owner ask.
  - Conflicting repairs are withheld and routed as a contradiction.
  - A repaired fact is classed claimed and keyed to the repairing return.
- **Left-shift gate:** two parallel passes return different repairs of one fact, and the next work order must hand neither as trusted.
