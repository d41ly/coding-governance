## High

### H1: Every chain spec run fails carry-forward because the base roster cannot be read (id 13)
- **Where:** plan:409, and also :271 and :481-483.
- **What is wrong:** The plan says every chain spec run closes by carry-forward, with the other four terms unchanged. But term 2 reads the starting roster through `baseline_units` (lib-unattended.sh:1950-2018, called from unattended.sh:5173-5180). That function reads the README's generated `gen:build-units` region at the run's preflight commit. gen_build_index.py:1405-1424 renders that region only from specs that carry a status header. A chain build at its opening has no spec, because P0.5 writes only the authored `roster:units`. The region therefore names no id, and the function refuses with "that roster cannot be read" (:2011-2015).
- **Consequence:** dGroundRules' spec run fails `build-complete` at `--close`, and so do all 21 spec runs. The extra unit relaxes only the added-unit branch, which is never reached, and none of its four red cases is a README with no spec at base. The failure is loud and nothing wrong ships, so the skeptic graded it high rather than blocker. Even so, the plan cannot be operated.
- **Fix (finder's fix judged UNSOUND, so this is the skeptic's corrected fix):** Widen only dTrueNorth's extra unit. When the units region at a spec run's baseline commit names no unit, read the starting roster from the authored `roster:units` pair at that same commit. Apply the same change to the checker's caller at unattended.sh:13257, so the driver and the checker agree. Add a fifth red case: a base README with `roster:units` rows and no spec is refused before the change and carries all its units after it. Drop the stub-spec alternative.
- **Left-shift gate:** Add a scratch-clone plant to the extra unit's red cases. It opens one build as P0.5 specifies, preflights it, defers one unit and runs `--close`. Make it a standing fixture in the driver's test leg.

### H2: The instrument-blob pin lives in a file the guarded run re-renders (id 1)
- **Where:** plan:137 (P0.1 row 10), together with :478 and the [handoffs] text at :585-591.
- **What is wrong:** Row 10 says the TOOL-aStandingWrit-7 escape ("any run can edit the instruments under memory/") is closed, because the packet pins each instrument's blob and the next `packet.py --check` turns red. But [handoffs] lists "an instrument's blob moves" as a reason a packet goes stale and tells the run to re-render and commit on red, and the spec-run table at :478 says the same. The lander's carry check (push-main.sh:548-561, :603-626) grades only commits that came in through the local default branch, so it does not refuse a run's own commit.
- **Consequence:** A run can weaken `carries.py` or `deviations.py`, re-render its packet with the new blob, and pass `packet.py --check`. Its diff is memory/-only, which is exactly what :552 tells the owner to expect. Before dTrueNorth lands, the strict detection that [deviations] claims rests on instruments that a run can rewrite with no red. The path is narrow, but a run fixing a false red by editing the instrument would plausibly take it.
- **Fix (finder's fix judged UNSOUND, so this is the skeptic's corrected fix):**
  - Drop "an instrument's blob moves" from the re-render triggers, so a moved blob stays red until the owner lands a new pin.
  - Put the comparison where the run cannot rewrite it. One part is the owner's landing-diff checklist. The other is a check outside memory/, under the merge bar, that compares every instrument blob with its blob at the opening landing commit; a run's diff would visibly have to touch it.
  - Until that check exists, list "a change to any path under `memory/builds/dClosedLoop/build/*.py` in a chain run's diff" under 'What nothing catches', as something the owner must look for at every landing.
- **Left-shift gate:** Add this to the bug-class checklist: "a guard whose pin is stored in state the guarded actor rewrites". Add the plant: edit `carries.py`, re-render the packet, and the merge-bar check must still turn red.
