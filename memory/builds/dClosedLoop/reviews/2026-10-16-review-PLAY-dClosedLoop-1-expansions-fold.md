### H1. `kits.offer` claims `GOVKIT_RERENDER=0` refuses target-side execution, but govkit's update runs each touched kit's `[check]` argv in the target (ids 1, 21)

- **Where:** layer-expansions:439 (`kits.offer`, "with target-side execution refused (GOVKIT_RERENDER=0)"), layer-expansions:642 ([revised]) and v2:935 (dShippedRelease's row), which both say the offer "runs no adopter code". Also gap-register:240 (gap-deploy-13) and foreign-code-runs-on-the-ambient-credential.md:38 (the class's fixture).
- **What is wrong:** `_cmd_update` in tools/govkit/govkit.py calls `run_kit_check` for every touched kit before any write (:10015) and again in the verify pass (:11214). Neither call checks `GOVKIT_RERENDER`. That switch is read only at :10850 and gates only the regenerate and adopter steps (:10926, :11046, :11093, :11114). `run_kit_check` (:5021) runs the resolved argv with `cwd=str(target)` (:5051). The argv resolves `{kit}` into the target's tree, for example `bash {kit}/adopt-lexicon.sh --check` (tools/lexicon/kit.toml:107) or drift-audit's `adopt-drift-audit.sh --check`. At the baseline call, that is the adopter's own pre-update copy, which the adopter's committers control. gap-deploy-13 cites :10986, :11114-11119 and :7360-7363, and :7360-7363 sits in `_cmd_apply`, not update. None of these is the check-argv site. The class's fixture plants only a `[[regenerate]]` argv, which `GOVKIT_RERENDER=0` already suppresses, so the fixture cannot fail on this path.
- **Consequence:** The design states a guarantee the tree does not give. A planted check script runs inside the sandbox and can, for example, plant a hook in the throwaway workspace that fires when the scoped-grant push happens. No route sees this execution, so the outbox route ("an update that needs target-side execution") never fires for it. The sandbox (no credential helper, an emptied environment) and the scoped grant still bound the exposure. dShippedRelease would build to the false guarantee.
- **Fix (judged SOUND by the skeptic, both findings):** In `kits.offer`, gap-deploy-13 and the gotcha, name `run_kit_check`'s pre-write and post-write runs (govkit.py:10015 and :11214, with :5051 as the cwd site) as target-side execution, and add them to gap-deploy-13's evidence. Then choose one of two options. Either make the sandbox the only guarantee and drop "runs no adopter code", treating the check runs as untrusted. Or require a govkit mode that runs no kit `[check]` argv from the target: it skips the baseline and verify passes and records them as unrun, or reads the checks from gov's own copy. Widen the class's fixture so it plants a payload in a kit's adopt script that the check run executes, plus a workspace hook. Each reads the credential helper and the environment, and the fixture expects both to find none.
- **Left-shift gate:** A probe for dShippedRelease: `grep -n 'run_kit_check(' tools/govkit/govkit.py` inside `_cmd_update` lists every unguarded call, and the offer's design must name each one. Add a checklist entry: "a claim that a switch refuses execution cites every execution site in the command, not only the ones the switch gates."

### H2. The secret value scan binds at the lander's prepare but claims refs the core pushes at other times (id 2)

- **Where:** layer-runtime:770-778 ([extend], the secret value scan).
- **What is wrong:** The scan binds "at the lander's prepare" (`test.merge`), yet its stated population is "every refs/gov/* object the core pushes (mailbox, card, leases and claims)". The core pushes those refs at other times. `entry.claim` (flow-steps:72) pushes `refs/gov/claims/<slug>` at the start of the build. `deploy.notify` (flow-steps:330) posts mailbox messages after `deploy.land`. `deploy.snapshot` (flow-steps:332) commits the card's terminal snapshot after that. Mailbox and card refs are also pushed at every transition through the build. The journal and transcripts are in the same list but are never pushed at all. Run A's skeptic-corrected fix (review a, M13) also required that "the lander and the ref-writing commands accept a push only against that runner's witness". The fold took only the lander half, so the finding is fixed only in part.
- **Consequence:** A secret written into a post-landing mailbox message or the terminal snapshot is published without being scanned. "A hit refuses the push" has no arm for those pushes. The witness still "names what it read" as the whole population, so it certifies coverage it lacks.
- **Fix (judged SOUND by the skeptic):** Bind the value scan at every push of a `refs/gov/*` object, in the one ref-push path the coordination engine owns, as well as at the lander's prepare. Alternatively, cut the population at prepare to what that push publishes, and register a second scan at the ref-push boundary. Move the journal and transcripts into a separate node-local population, not one under "everything a push publishes". Add a seen-red fixture that plants the value in a mailbox post written after the landing. The fixture's wider gaps are M8 (id 24).
- **Left-shift gate:** Add a checklist entry: "a scan's population is limited to what crosses the boundary it binds at; every other boundary that publishes the same population registers its own scan." Back it with the post-landing mailbox fixture above.

### H3. Under `close-only`, `deploy.unlease` removes the lease and mailbox that `deploy.released` and `deploy.close` still need (id 14)

- **Where:** flow-steps:331-334 ([deploy] table: `deploy.released`, `deploy.snapshot`, `deploy.unlease`, `deploy.close`) and flow-steps:45 ([rules]' "Closing a mailbox", which still says `deploy.unlease` "closes a build").
- **What is wrong:** Under the default `build.release-hold: close-only`, `deploy.snapshot` needs only `deploy.notify`. `deploy.unlease` then deletes the build's lease refs and closes its mailbox. Only after that do `deploy.released` and `deploy.close` wait for the release slot's exit record. Runtime starts the supervisor only "when none beats under a live run lease" and renews that lease on each beat (layer-runtime:365, :370). v2:246 says `record` is "minted under the build's lease", and layer-memory:322 says every later record mints "under the build's lease". Owner items travel by "the mailbox and the notification adapter" (layer-runtime:289-291). After unlease, nothing asks `next` for the build again, so `deploy.released` never re-reads the exit record. If it did, its held, rolled-forward, rolled-back or halted owner item would have no mailbox to land in, and `deploy.close`'s transition record would have no lease to mint under. RH-1's option text, that the build "stays open until a release record verifies", names no mechanism for this, and the fold added none.
- **Consequence:** `guarded` selects `after-release-verifies` with `close-only` (v2:853), so every `guarded` build reaches this path. The build stays open in `deploying` for good.
- **Fix:** The skeptic judged the finder's fix UNSOUND. This is the skeptic's corrected fix. Make `deploy.released` an event wait that is woken by the release slot's exit record for a SHA that contains the build's own. The supervisor runs it under that wake's own run lease. State that `deploy.close`'s transition record mints under that lease or under the build's claim ref. State that the held/halted owner item goes through the owner's notification adapter, not the build's pruned mailbox. Amend [rules]' "Closing a mailbox" so that under `close-only`, `deploy.unlease` releases the build's leases and mailbox but does not close the build; `deploy.close` does. Write the same into layer-runtime's supervisor answers.
- **Left-shift gate:** A probe: walk `guarded`'s values through [deploy]'s table, and confirm that every item after `deploy.unlease` names a driver, a lease it mints under, and a channel for its owner item. Add a checklist entry: "an item ordered after a resource's release names what it runs under instead."
