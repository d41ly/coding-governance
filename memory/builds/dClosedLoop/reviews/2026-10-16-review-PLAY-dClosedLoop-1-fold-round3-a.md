### M1. deploy.core has no route when post-merge.sh's publication fails, and "a red is also published" is unconditional — ids 1, 7

- **Where:** `memory/builds/dClosedLoop/build/2026-10-15-build-PLAY-dClosedLoop-1-flow-steps.md:350` and `:353`.
- **What is wrong:** The fold has deploy.core read the post-merge verdict from the per-SHA log `<common-dir>/gate-post-merge-<sha8>.log`, "never from the single last-verdict file". It also says post-merge.sh "answers green, red or REFUSED, and a red is also published as refs/gov/bar-red".
  - That log is post-merge.sh's stdout (`tools/push-main.sh:454-455`).
  - When publication fails (`PM_PUB=failed`), post-merge.sh prints only `post-merge: publish FAILED — <why>` (`post-merge.sh:396-406`). That line names neither GREEN nor RED.
  - The verdict then exists only in the single-slot `gate-post-merge` file, which the design forbids deploy.core to read.
  - The script exits 1 for both a red and a failed publication.
  - The RED branch also keeps the ref and pushes nothing when the existing ref is not an ancestor (`PM_PUB=kept`, `post-merge.sh:383`).
- **Consequence:** A finished bar whose publication failed matches none of deploy.core's outcomes (green, red, refused, still running). deploy.core waits out the act's ceiling and raises an owner item although a verdict exists, and a red can be lost this way. The witness also claims a `refs/gov/bar-red` that the writer does not always produce.
- **Fix (skeptic judged it sound):**
  - Name a publication failure as post-merge.sh's own fourth outcome, with its own route: re-publish once, then raise an owner item. Another option is to read the run record under `gate-run/<run id>/`.
  - Qualify `:353`: a red is published unless the ref is kept or publication fails.
  - Add to gap-deploy-02 the contract that the per-SHA verdict record carries the verdict and the publication state separately, on every exit path, the publish failure included.
  - Probe: run post-merge.sh with the remote's push refused, then grep the per-SHA log for GREEN or RED. Today it holds neither.
- **Left-shift gate:** Use the existing class `route-names-an-output-its-actor-never-emits`. Add a checklist line: for every script whose output a design item reads, list every exit path from the script's echo lines, and show that each one maps to a named route.

### M3. The per-family ask claim ref is create-once, so it cannot serialise a family's later ask mints — ids 3, 10

- **Where:** `memory/builds/dClosedLoop/build/2026-10-15-build-PLAY-dClosedLoop-1-layer-memory.md:325-328`; gap-mem-13 at `2026-10-14-build-PLAY-dClosedLoop-1-gap-register.md:147`.
- **What is wrong:** An ask filed outside any build "mints under its family's claim ref, created the same compare-and-swap way". That way is a create-only push (`:319`; `unattended.sh:2423` passes an empty `--force-with-lease` value for a create).
  - A per-family ref can be created only once.
  - The design names no update, release or advance step for it.
  - The ref is never pruned, so it persists after the first create.
  - The paragraph's closing claim, "So two clones never mint one id", therefore holds for slugs but not for asks.
  - gap-mem-13 states only that the ref is absent.
- **Consequence:** For a family's second and later asks outside a build, the create is either refused and loops on the "claimed elsewhere" route, or the ask mints with no claim at all. Two clones can then mint one ask id, which is the collision the contract exists to prevent. dTotalRecall, building from this text, would implement a ref that excludes nothing.
- **Fix (skeptic judged it sound):**
  - Specify the family ref as a counter advanced on every mint by a compare-and-swap update: a `--force-with-lease` on its observed value, with the new id written into it. `unattended.sh:2361-2362` already leases updates this way.
  - Alternatively, key ask ids by content, or use one create-only ref per minted ask id.
  - Have gap-mem-13 carry the chosen contract.
- **Left-shift gate:** Add a bug-class checklist entry: a lock or claim that must serialise repeated acts names its advance or release step, not only its creation.

### M7. test.flakes files a duplicate held-flaky-leg ask on every later flake — id 12

- **Where:** `memory/builds/dClosedLoop/build/2026-10-15-build-PLAY-dClosedLoop-1-flow-steps.md:264`; the [asks] forms are at `layer-memory.md:455-472`.
- **What is wrong:** Under `quarantine`, test.flakes files "an ask ... in the held-flaky-leg form" for each leg past the threshold. It has no idempotence key and no check for an open ask. A leg stays past the threshold, and test.route (`:262`) sends every red-then-green leg back to test.flakes. So every later flake, whether in a route-back or in a later build's Test, files another ask. memory's `record` is idempotent only on its kind's key (`layer-memory:329`), and an ask's key is its freshly minted id.
- **Consequence:** Each held leg adds one duplicate ask per flake, and each duplicate carries the same acceptance, so closing one leaves the others open. This is reachable when verdict.held is peer-or-cadence or push-selected, not under the default on-demand, so the effect is contained.
- **Fix (skeptic judged it sound):** Key the held-flaky-leg ask by the leg's name key. File it only when no open ask in that form names the leg, so a repeat is a no-op, as deploy.notify does with the landing SHA. State the key in the memory [asks] form.
- **Left-shift gate:** Use the class `append-without-an-idempotence-key`. Add a checklist line: every ask form a non-Maintain item files names its dedupe key.
