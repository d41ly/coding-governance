## High

### H1. `record` is never specified as content-addressed or idempotent, though the runtime layer depends on it (id 2)

- **Where:** [contract], the `record` command.
- **What is wrong:** The memory contract (layer-memory.md:304-308) and v2's dTotalRecall row (v2:753) say only that `record` "mints the id; renders the template; refuses an invalid value". The runtime layer, settled later, rests its take-over reconcile on "`record` is content-addressed ... So a take-over never pushes twice" (layer-runtime.md:408-414). It keys returns by `task-sha` (:493-494) and names `record` as dWellOiledMachine's input from dTotalRecall (:829-833).
- **Consequence:** Built as written, with minted sequential ids, a supervisor take-over that replays a write mints a second record under a new id. That is the duplicate effect the runtime design says cannot happen. Runtime's `idempotence` fixture (:986-987) exercises only the lander, so nothing catches a replayed shared-record write (decision rows, the run record).
- **Fix (skeptic judged SOUND):** Add to [contract]: every `record` write is idempotent per kind. The id is derived from the content or from a declared natural key such as item plus task-sha, or the kind declares a reconcile probe. Make this an acceptance of the `record` unit.
- **Gate:** write the same return through `record` twice and observe exactly one record.
- **See also:** M4 (id 47), the same omission confirmed at medium, which adds concurrent minting.

## Medium

### M1. The reuse entry has two exclusive writers: `record` and the instruction command (ids 4, 35, 46, 56)

- **Where:** [contract] "`record` is the only writer of record structure" (:304) and its Knowledge kind list naming "reuse entry" (:315-316), against [decisions] item 1, Home and Lifecycle (:394-408).
- **What is wrong:** [contract] makes the reuse entry a Knowledge record kind, which only `record` writes. [decisions] makes the same entry a level-3 instruction unit that "changes only through the instruction layer's write path (R-I, `instructions.edit`)". Runtime's `one-door` invariant (layer-runtime.md:764) says "Records change only through `record`, instructions only through the instruction command". No line says which door writes `<feature>.reuse.toml`.
- **Consequence:** A builder cannot tell which door the `one-door` coverage check expects for this kind. Either the registry check refuses an entry the instruction command wrote, or `record` bypasses the instruction layer's refusal-at-write. An entry edited through R-I skips the registry's schema and minted id. One written by `record` skips R-I's ranking and promotion checks.
- **Fix (skeptic judged SOUND):** Pick one door, and say so in both [decisions] and [contract]. The recommended choice: the reuse entry is an instruction unit whose source file is the sidecar, written only by `instructions.edit`, with `record`'s schema check and id minting called inside it. The registry lists it as "writer: instruction command", a read-side kind. Reword [contract] "only writer of record structure" to exclude instruction-unit kinds. The reverse is also acceptable if stated: a record whose `record` writer delegates to `instructions.edit`.
- **Gate:** the `one-door` coverage check gets one expected writer per registered kind. A fixture write of a reuse entry through the other door must go red.

### M2. No path turns an agent's proposed reuse entry into a real entry inside the build that needs it (id 1)

### M4. `record` states no semantics for a replayed write or a concurrent mint (id 47)

- **Where:** [contract] the `record` command; [names]; [determinism].
- **What is wrong:** `record` is specified only as minting ids, rendering templates and refusing bad values (:304-308, :357-358, :535). Nothing covers a replayed write or two writers minting at once. Runtime lists `record` among the command adapters that need an idempotence probe (layer-runtime.md:739). SubagentStop hooks for a fan of up to five agents write through it concurrently. `ROW_DUPLICATE_PIN="3"` (.memory-tree.conf:688) shows that ids already collide today. Slug collisions are checked against the local clone only.
- **Consequence:** A replayed return or row lands twice under two ids. Two nodes or two parallel hooks can mint the same sequential N.
- **Fix (skeptic judged SOUND):** In [contract], state `record`'s write semantics. (a) It is content-addressed, or keyed by a caller-supplied idempotence key such as task-sha, so a replay is a no-op. (b) A sequential id is minted without collision across nodes and concurrent hooks, for example allocated against the shared remote as the card's ref is, or under a lock. (c) The slug collision check runs against the remote's build refs, not only the clone.
- **Gate:** two concurrent `record` calls for the same kind, plus one replayed call, end with exactly one record per logical write and no duplicate id.
- **See also:** H1 (id 2).
