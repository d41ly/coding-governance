## 1. Goal

A project map can say what a node is for only where its purpose is declared (project map
`[purpose]`), and PLAY-dOrderedCharter-22 S2 reds every member of a namespace whose
`purpose-source` names a field the member lacks. TOOL-dWellOiledMachine-20 points the `hook` row at
the fragments' `purpose` and the `point` row at the registry's, and no fragment carries one. This
unit gives both members a `purpose` field in one shape, and reviews every existing hook and point
once, deriving what its own sources state and putting the rest to the owner, as PM-5's `review`
orders and TOOL-dTotalRecall-16 does for the record kinds (the clause's "reviewed").

## 2. Scope (IN)

- **S1** — The hook member's field. A fragment's optional `purpose` is either a string of one line
  and at most 120 bytes, or the object `{"pending": "<ask id>"}`, TOOL-dTotalRecall-16 S1's pending
  form. `load_fragment` (`tools/settings-merge.py:252`) admits it in either shape, refuses any other
  naming the file, and never renders it into a settings entry; the fragment schema in the module's
  docstring names it. Observed by AC4.
- **S2** — The point member's field. A `[[point]]` row's `purpose` takes the same two shapes, the
  pending form as an inline table `{ pending = "<ask id>" }`, and `check_points`
  (TOOL-dWellOiledMachine-20 S4) refuses any other naming the row. Observed by AC5.
- **S3** — The review, `python tools/runtime/purposes.py review`, over every hook and point member
  with no `purpose`, in TOOL-dTotalRecall-16 S3's order — the member's own field, then its source's
  header, then nothing — and in its line format:
  - a hook whose fragment is the only tracked fragment naming its `hook_path` script, and whose
    script's header comment opens `<name> — <sentence>`, prints
    `derived hook.<name> · <sentence> · <script>:<line>`, the sentence at most 120 bytes;
  - a hook whose script another fragment shares, whose header states no such sentence, or whose
    sentence is longer, prints `none hook.<name> · <what was found>`, since one header cannot say
    what each of two entries is for;
  - a point row with no `purpose` prints `none <name> · declared by <layer row>`, its only source
    being the declaring layer's name.
  Observed by AC1, AC2.
- **S4** — The write, `purposes.py review --write --ask <id>`: each derived sentence is written as
  the member's `purpose` string, and each `none` member's `purpose` becomes the pending form naming
  `<id>`. The pass files the ask first, one in `memory/builds/dWellOiledMachine/BACKLOG.md` listing
  every `none` member with what was found, through the main loop, and then writes. A second `review`
  prints `review — nothing to review · <n> member(s) carry a purpose`. Observed by AC3.
- **S5** — The review record. The pass commits the review's printed lines as
  `memory/builds/dWellOiledMachine/build/<date>-build-TOOL-dWellOiledMachine-22-purpose-review.md`,
  `**Serves:** research TOOL-dWellOiledMachine-22`, the source of every derived purpose cited there.
  NOT OBSERVED by a criterion: a record, graded by the memory hygiene leg's binding check at the
  close.

## 3. Non-goals (OUT)

- The rule for a new member: PLAY-dOrderedCharter-22 S2 already reds a member with no `purpose`,
  which is `memory.map-purpose`'s `review` for a new node; this unit adds no second check of it.
- `memory.map-purpose`'s other values (`ledger`, `derive`, `refuse`): TOOL-dTotalRecall-16 arms
  them for every namespace at once.
- Rendering purposes into the map: TOOL-dTotalRecall-14 reads the fields.
- Answering the ask: the owner's; a `pending` member stays pending until the answer is written.
- Every later member's purpose: each unit that adds a pack or a point writes it with the row.

## 4. Design

### The review at this base

The twelve fragments (`git ls-files '*.fragment.json'`, 2026-10-26) name nine scripts. Three
scripts each serve two fragments: `manifest-check.sh` (`orientation-card`, `orientation-replay`),
`scratch-guard.js` (`scratch-guard`, `scratch-guard-subagent`) and `procmon-hook.js`
(`procmon-report`, `procmon-session`). Those six are `none`: one header, two entries. The other six,
`check-wiring`, `format-guard`, `recall-opened`, `gate-guard`, `stall-recorder` and `stop-guard`,
each open with a `<name> — <sentence>` header; whether each sentence fits 120 bytes is the review's
to measure, and the longer ones are `none`. PINNED at that date; the pass re-derives it, and the
record (S5) holds what it found.

### The fields

```json
{ "name": "stop-guard", "purpose": "a Stop hook that refuses the turn end of a session bound to a non-terminal unattended run", "...": "..." }
{ "name": "orientation-card", "purpose": { "pending": "<ask id>" }, "...": "..." }
```

```toml
[[point]]
name = "point.memory.record-home"
purpose = { pending = "<ask id>" }
contract = "declared by layer.memory in tools/playbook/layers.toml"
```

`<ask id>` stands for the id the main loop files; the pass writes that id.

### Alternatives rejected

- **A purposes file beside the fragments.** Every hook's name would sit in two files with a join to
  keep them equal; the fragment is the pack's one declaration.
- **Running TOOL-dTotalRecall-16's generic review over these namespaces.** For a hook it reads the
  fragment, a JSON file with no header, so every hook would come back `none`; the hook's purpose is
  in its script, which only the fragment's `hook_path` reaches.

## 5. Production-readiness checklist

- security — a purpose is prose, refused over 120 bytes and never rendered into a command.
- perf / scale — one review per pass over a dozen fragments and the registry.
- error / empty / loading states — a member with nothing to derive is `none` and pending, never a
  guessed sentence.
- observability — the `derived` and `none` lines, kept in S5's record.
- risks — a header sentence true of the script but not of one entry; S3 refuses that case by
  sending a shared script's entries to the owner.
- testing — the criteria of §6 and the arm in §7.
- migration — none: an added optional field.
- user docs — `help/tags.md` (TOOL-dWellOiledMachine-20's section) gains what a hook's and a point's
  purpose is and where it is written.

## 6. Acceptance criteria

Each `purposes.py` command runs over a scratch repository holding fixture fragments, their scripts
and a registry.

- **AC1** — When `python purposes.py review` runs over a fragment `solo` whose script opens
  `solo — a Stop hook that refuses a turn end` and two fragments `pair-a` and `pair-b` naming one
  script, it prints `derived hook.solo · a Stop hook that refuses a turn end · ` with the script's
  line, `none hook.pair-a` and `none hook.pair-b`.
  Red when: a shared script yields a `derived` line for either entry.
- **AC2** — When `review` runs over a fragment whose header sentence is 121 bytes, and over a point
  row with no `purpose`, each prints a `none` line and no `derived` one.
  Red when: the long sentence is cut and printed as derived.
- **AC3** — When `review --write --ask fixture-ask` runs over AC1's fixture, `solo`'s fragment
  carries the derived string, `pair-a` and `pair-b` carry `{"pending": "fixture-ask"}`, and a second
  `review` prints `review — nothing to review`.
  Red when: a `none` member is written with a sentence, or the second run reviews again.
- **AC4** — When `load_fragment` reads fragments whose `purpose` is 121 bytes, `{"pending": ""}` or
  a number, each raises naming the file; a 120-byte string and a pending object load.
  Red when: a malformed `purpose` loads.
- **AC5** — When `points.py check` runs over a registry copy whose `[[point]]` carries
  `purpose = 7`, it exits 1 naming the row; `purpose = { pending = "x" }` passes.
  Red when: the numeric purpose passes.
