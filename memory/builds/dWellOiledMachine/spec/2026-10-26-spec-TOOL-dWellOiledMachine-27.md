## 1. Goal

The intake hook writes only in the owner's session, so a request that arrives through the mailbox or
a cadence is placed with no intake record (gap-orient-17). This unit files those requests into the
same record (I27) with their origin marked, the owner-bound hook, a mailbox sender or a cadence
filer; lets only owner-origin intake, or mailbox intake carrying the owner binding's proof, ratify a
request; routes the rest to an owner breakpoint or an ask; and drains the interim roots
TOOL-dTotalRecall-19 stands in, so a new build's records root at its intake or its binding rather
than at its README or claim (night pass, point 1).

## 2. Scope (IN)

- **S1** — The filer, `python intake.py file --origin <mailbox|cadence> …` in
  `tools/runtime/intake.py`, through TOOL-dWellOiledMachine-4's one writer `write_intake`, the text
  on stdin. `--origin mailbox --message <id> --sender <from-session> --tag <from-tag> [--proof
  <content key>]` writes the receipt `origin=mailbox sender=<id> tag=<tag> message=<id>
  proof=<key|none>`, refusing a second receipt for one message id; `--origin cadence --filer <item
  tag>` writes `origin=cadence filer=<item tag>`. Each receipt carries `received-utc`, `redacted`,
  `bytes` and `capped` as the hook's does. Observed by AC1.
- **S2** — The mailbox origin. KICK-dKeptSession-10 S5's mail kind `intake`, an amendment from a
  session that does not hold the build's lease, is filed where it is read: `read_mail_interrupts`
  (`tools/loop/position.py`, KICK-dKeptSession-10 S2) files each `intake` row it prints, before
  printing it, with the message's text and its `from-session` and `from-tag` keys
  (KICK-dKeptSession-5 S4) and, where the message names a request ref, `--proof` its content key.
  Govkit's `intake` verb (`cmd_intake`, `tools/govkit/govkit.py:13122`) writes a kit target
  descriptor and is unrelated to this record. Observed by AC1.
- **S3** — Which intake ratifies, `check_intake_ratifies(receipt, repo)` in `intake.py`, and `python
  intake.py ratifies <key>`, which prints `intake — <key> · ratifies · <origin>` exit 0 when any
  receipt does, else `intake — <key> · does not ratify · <origins>` exit 1. A receipt ratifies when
  its origin is `hook`, which TOOL-dWellOiledMachine-4 writes only for a session whose binding reads
  `owner: yes`; or when its origin is `mailbox` and its `proof` names a request whose ref passes
  `check_request_proof` (TOOL-dWellOiledMachine-57 S6), the owner binding's proof that an owner-bound
  session published it, asked through the new verb `unattended.sh --request-check <key>`, which runs
  that function after the same bounded fetch and prints its line. A `cadence` receipt never ratifies.
  Observed by AC2, AC3.
- **S4** — The rest routed. `placement.py check` (TOOL-dPlacedRequest-4 S5) gains one fact: for a
  request whose intake holds no ratifying receipt, a placement whose disposition is neither
  `breakpoint` nor `ask` is refused `placement: refused — <disposition> · intake <origins> does not
  ratify`, the route back to `entry.place`, so a non-owner request reaches an owner breakpoint
  (TOOL-dPlacedRequest-5) or an ask and never a build. An act that posts an `intake` proposing a new
  build is that case: its receipt is `mailbox` with no proof, since an act's binding never reads
  `owner: yes` and `--request-publish` refuses it (TOOL-dWellOiledMachine-57 S4). Observed by AC3.
- **S5** — The interim roots drained. The `build-readme` and `claim` rows of
  `tools/memory-tree/record-kinds.toml`, `root = true` as TOOL-dTotalRecall-19 S3 stands them in,
  gain `root-until = "<date>"`, the date this unit's build pass lands; `check_causes`
  (`tools/memory-tree/record_causes.py`, TOOL-dTotalRecall-19 S8) reads a record of either kind dated
  on or after it, a README by its `opened:` key and a claim by its commit date, as no root, so its
  `Caused-by` must resolve. Records dated before it stay roots, so nothing landed turns red. A new
  root resolves through one of three native classes: `intake-key`, a `[[native]]` row this unit adds
  to `tools/playbook/namespaces.toml` (PLAY-dOrderedCharter-28 S2) with `pattern = "intake:KEY_RE"`,
  twelve lower-case hex, and `resolver = "intake:print_keys"`, the keys of the local `.intake` files
  and of `refs/gov/requests/*`; and TOOL-dWellOiledMachine-35's `act` and `session` classes for a
  build an act or a session opened with no request. The README's writer, the one the `build-readme`
  row names, writes `**Caused-by:** <content key>` from the claim's `content-key`
  (TOOL-dPlacedRequest-21) where it has one, else the writing session's id. Observed by AC4, AC5.
- **S6** — The page `help/runtime.md` gains the three origins, what ratifies, the routing and the
  drain date. Observed by AC6.

## 4. Design

### The receipts

```
origin=hook session=6c1e… received-utc=… redacted=0 bytes=412 capped=no                      ratifies
origin=mailbox sender=9a2b… tag=b message=m-17 proof=3f2a9c01b4de received-utc=… …           ratifies when the proof checks
origin=mailbox sender=act-0a1b2c3d4e5f tag=a message=m-18 proof=none received-utc=… …         does not
origin=cadence filer=item.maintain.sweep received-utc=… …                                     does not
```

### The routing

| Intake | Placement dispositions admitted |
|---|---|
| ratifies | every disposition TOOL-dPlacedRequest-4 admits |
| does not ratify | `breakpoint`, the owner's, or `ask` |

### Alternatives rejected

- **A record per origin.** Three homes for one request's words; TOOL-dPlacedRequest-19 keys the text
  once and every reader keys by it.
- **A mailbox sender's own binding as proof.** The receiving node cannot read the sender's local
  binding; the published request ref is the one record both nodes see.
- **The roots drained by flipping `root` off.** Every README and claim landed since the legacy
  ledger was seeded would turn red at once; the dated ratchet is this corpus's way of moving a gate
  forward without retrofitting landed records.

## 5. Production-readiness checklist

- security — only two receipts ratify, and the mailbox one only through a check of the owner
  binding's proof; a relayed request stays data with provenance (TOOL-dPlacedRequest-19 S5).
- perf / scale — one append per filed message, one bounded fetch per proof check.
- error / empty / loading states — a message filed twice is refused by id; a proof whose fetch fails
  reads as not ratifying, with the reason.
- observability — the receipts, `intake.py ratifies` and the placement refusal line.
- risks — a non-owner request waits on the owner's breakpoint, the clause's intent.
- testing — the criteria of §6 and the arm in §7.
- migration — S5's date leaves every record before it a root.
- user docs — `help/runtime.md` (S6).

## 6. Acceptance criteria

Each case runs `python intake.py fixture --case <name>` from the runtime kit directory in a scratch
repository with planted bindings, mail rows and request refs.

- **AC1** — When `--case origins` files one mailbox message and one cadence text, `python intake.py
  show <key>` prints `origin=mailbox` with its sender, tag and message id and `origin=cadence` with its
  filer, and filing the same message id again exits 2 with no new receipt.
  Red when: a receipt lacks its origin, or one message is filed twice.
- **AC2** — When `--case proof` files a mailbox intake whose `proof` names a request ref that passes
  `check_request_proof`, `python intake.py ratifies <key>` prints `ratifies · mailbox`; with the ref's
  `proof` line planted wrong it prints `does not ratify · mailbox`.
  Red when: the forged proof ratifies.
- **AC3** — When `--case act-proposes` files an `intake` an act session posted proposing a new build,
  `intake.py ratifies` prints `does not ratify · mailbox`, and `placement.py check` over a `new`
  placement for it prints `placement: refused — new · intake mailbox does not ratify`, while a
  `breakpoint` placement passes.
  fixture: needs TOOL-dPlacedRequest-4's `placement.py`, specced and unbuilt at this base.
  Red when: the act's proposal is placed `new`.
- **AC4** — When `--case drain` plants two build READMEs without `Caused-by`, one `opened` the day
  before `root-until` and one on it, `check_causes` passes the first and reds the second; a third
  opened on it with `**Caused-by:** <a planted intake key>` passes.
  fixture: needs TOOL-dTotalRecall-19's `record_causes.py`, specced and unbuilt at this base.
  Red when: a record before the date turns red, or one on it passes with no cause.
- **AC5** — When `grep -n -A4 'class = "intake-key"' namespaces.toml` runs over the namespace
  registry, it prints the row with `intake:KEY_RE` and `intake:print_keys`, and `python intake.py
  print-keys` prints a planted local key and a planted `refs/gov/requests/` key.
  Red when: the row is missing or a planted key is not printed.
- **AC6** — When `grep -n "origin=cadence" runtime.md` runs over the runtime help page, it names the
  three origins and which ratify.
  Red when: an origin or the ratifying rule is missing.
