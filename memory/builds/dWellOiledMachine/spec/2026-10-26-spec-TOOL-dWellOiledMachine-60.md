## 1. Goal

TOOL-dPlacedRequest-15 fences the lander's push with the holder's lease beat and leaves out the
`landed` notice and the commit queue's pushes, each to join "through the `fence` act" when it lands
(its §3). Separate pushes leave orphans: with the endpoint down after the main push, main says
landed, the lease still reads live and no mail is written (research P5). This unit carries the
lander's push to the default branch, the build's lease beat and its `landed` notice in one
`git push --atomic`, the push releasing nothing so the lease lives on for the Deploy items after it,
and routes the commit queue's branch push through the same fence (P40; the owner's FK-2-1).

## 2. Scope (IN)

- **S1** — The chain builder, `build_mail_chain <tip read> <message> [<message> ...]` in
  `tools/unattended/unattended.sh`: the commit-building half of KICK-dKeptSession-63 S12's
  `write_mail_ref`, extracted so that function calls it and then lands its last commit with
  `write_gov_ref`, its bytes and exit codes unchanged; it prints the chain's last commit and writes
  no ref. Observed by AC5.
- **S2** — The notice, `unattended.sh --mail landing <slug> <landed sha>`: builds, never pushes, the
  `landed` messages KICK-dKeptSession-7 S5 posts, one per dependent, subject `landing <slug>`, body
  the landed sha, each through KICK-dKeptSession-5's `build_gov_message`, chained by
  `build_mail_chain` on this session's mail ref tip read with one bounded fetch, and prints one
  line: `notice — <mail ref> <tip read or 0> <chain tip>`, or `notice — none · <why>` with
  `RUN_CLAIMS` off, no session id or no dependent, exit 0 both ways and 2 when a message is refused.
  Observed by AC1, AC5.
- **S3** — The landing push: in `tools/push-main.sh`, after TOOL-dPlacedRequest-15 S3's fence line
  and before the verdict files are cleared, the lander runs S2 for the sha it will push and, on a
  `notice —` line, pushes
  `git push --atomic "--force-with-lease=<lease>:<tip>" "--force-with-lease=<mail ref>:<mail tip>" <remote> <branch refspec> <beat>:<lease> <chain tip>:<mail ref>`,
  under `--land --slug` and under the attended landing given `--slug`, a mail ref the remote lacks
  expected absent. On `notice — none` it pushes TOOL-dPlacedRequest-15's two refspecs; on
  `fence — none` it pushes as that unit says. Observed by AC1, AC2.
- **S4** — The push releases nothing: `check_fence_beat <tip> <beat>` (TOOL-dPlacedRequest-15) also
  refuses a beat whose record's `status` differs from the tip's or whose `renews` is not `no`,
  before anything is sent, printing `push-main: the landing beat must release nothing (<field>)`. So
  the lease lives on after the landing, and a build that dies between its landing and its close
  keeps a lease that expires or hands over by TOOL-dPlacedRequest-16 and -17's rules. Observed by
  AC3.
- **S5** — A failed landing push lands nothing of the three: TOOL-dPlacedRequest-15 S4's classes
  hold, and the `unfenced` line names the three refspecs it sent, so a notice the remote refused
  reads as a landing that did not happen. Observed by AC2.
- **S6** — A re-run landing finds its sha already held: before S2 runs, a lander whose pushed sha
  equals the remote tip it read (`check_push_allow`'s "already held" branch,
  `tools/push-main.sh:342`) builds no beat and no notice and pushes nothing, so the first landing's
  notice is the only one. Observed by AC4.
- **S7** — The commit queue's push through the fence: TOOL-dWellOiledMachine-40's `run_build_push`
  in `commit_queue.py` runs `--lease fence build <slug>` once per push and, on a fence line, pushes
  `git push --atomic "--force-with-lease=<lease>:<tip>" <remote> HEAD:refs/heads/<branch> <beat>:<lease>`
  with the lease ref the lease store's `git-refs` adapter names (TOOL-dWellOiledMachine-55);
  `fence — none` pushes as that unit says, and a refusal pushes nothing and prints
  `build push — not pushed: lease refused`. Observed by AC6.
- **S8** — The documentation: the lander's header comment, the verbs guide's `--mail landing` row
  (`tools/unattended/VERBS.template.md`, rendered to `memory/guides/UNATTENDED-VERBS.md`), and
  `help/runtime.md`'s build-push section naming the fence. Observed by AC7.

## 4. Design

### Evidence

- The lander pushes one ref: `git push "$remote" "HEAD:refs/heads/$def"` under `--land`
  (`tools/push-main.sh:978`) and `git push "$remote" "$def"` on the attended path (`:1128`); a
  failed push is classified by `derive_push_failure` (`:262-292`).
- `check_push_allow` already reports a push whose sha the remote held before it (`:342-347`).
- TOOL-dPlacedRequest-15 §3 names the release with `landed` and the commit queue as later joiners
  of its fence, through the `fence` act.
- `verb_landed` (`tools/unattended/unattended.sh:6316`) is where KICK-dKeptSession-7 S5 posts the
  `landed` notice after the landing, and KICK-dKeptSession-22's `check_mail_duplicate` refuses a
  message whose id is already held.
- P5 measured one atomic push of main, lease and `landed` mail writing all three or none
  (`memory/builds/dClosedLoop/build/2026-10-19-build-PLAY-dClosedLoop-1-research-cloud-headless.md:40-41`);
  the owner's FK-2-1 kept the release out of the landing push, so the lease lives on.

## 5. Production-readiness checklist

- security — the push writes the default branch, the lease ref and this session's own mail ref, each
  under its own `--force-with-lease`; no new credential path.
- perf / scale — one more bounded fetch of one mail ref per landing, one push.
- error / empty / loading states — no dependent or `RUN_CLAIMS` off reads `notice — none`, and the
  landing pushes the two refspecs; a refused message exits 2 before anything is pushed.
- observability — the `notice —` line and the `unfenced` or `fenced` line name every ref sent.
- risks — a remote refusing `--atomic` lands nothing, which TOOL-dPlacedRequest-15's `unfenced`
  class names with its remedy.
- testing — the fixture cases AC1 to AC6 and the arms in §7.
- migration — none.
- user docs — the verbs guide and `help/runtime.md` (S8).

## 6. Acceptance criteria

The fixture is a bare remote and two clones, `na` and `nb`, under `%TEMP%` with short names,
`RUN_CLAIMS` on, a build `fx` with one dependent `fy`, and `na`'s session holding `fx`'s build lease.

- **AC1** — When `bash push-main.sh --land --slug fx` lands from `na`, one push moves the default
  branch, `refs/gov/leases/fx/build` to a beat whose parent is the tip read, and `na`'s mail ref to
  a commit whose subject is `gov-mail fx/<id>` of kind `landed` to `build:fy`, all three read by
  `git ls-remote` after it.
  Red when: any of the three is written by a second push, or missing.
- **AC2** — When the remote's planted `pre-receive` refuses the mail ref, the landing exits 1
  printing `unfenced` and naming the three refspecs, and `git ls-remote` shows the default branch,
  the lease and the mail ref each at its value before the landing.
  Red when: the branch lands while the notice is dropped.
- **AC3** — When the lander is planted to build a beat with `status: released`, it exits before the
  push printing `the landing beat must release nothing (status)`; after AC1's landing,
  `--lease read build fx` shows the lease live, its epoch and status unchanged.
  Red when: a landing push writes a released lease.
- **AC4** — When `push-main.sh --land --slug fx` runs again after AC1, it prints `already held`,
  pushes nothing, and `fy`'s mailbox holds exactly one `landed` row for the sha.
  Red when: a second notice or a second beat is pushed.
- **AC5** — When `--mail landing fx <sha>` runs, it prints one `notice —` line and the remote gains
  no ref; and `--mail post` over a fixed input writes a ref byte-equal to its output before S1's
  extraction.
  Red when: the verb pushes, or the post's bytes move.
- **AC6** — When `nb` takes `fx`'s lease over after `na` read it, a lander stubbed to re-read the
  epoch and then push normally lands its stale write, which shows the case is live; the unstubbed
  `push-main.sh` in `na` exits 1 printing `fenced` and the branch is unchanged; and `na`'s queue
  push prints `build push — not pushed: lease refused`.
  Red when: the unstubbed lander or the queue lands a write after the take-over.
- **AC7** — When `grep -n -- "--mail landing"` runs over `VERBS.template.md`, and `grep -n "fence"`
  over the runtime kit's page `runtime.md`, each names the notice and the fenced branch push.
  Red when: either is missing.
