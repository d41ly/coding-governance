## 1. Goal

Until the intake hook lands, Plan's ratification falls back to an owner breakpoint and a placement's
disposition rides the claim commit (RC-9; TOOL-dPlacedRequest-4 S7, "until dWellOiledMachine's
intake kind lands"). Draining that fallback globally strands a harness with no prompt-submit event
at Plan's exit (DA-M14), and re-pointing the readers to the intake alone re-derives builds witnessed
under the fallback as unratified (DA-M15, FM3). This unit re-points the readers to the intake
record, drains the fallback per harness, only where an adapter's capability table declares the
prompt-submit event, and keeps a fallback witness readable: at any time from an adapter without the
event, and from any other only before its own drain landed.

## 4. Design

### The witness rule

```
check_ratification_witness(repo, build, key)
  any receipt of read_intake(key) passes check_intake_ratifies   -> intake · <origin>      (exit 0)
  owner disposition releasing item.plan.exit, committed at C:
    A = runtime.owner-harness at C ; D = derive_drain_commit(repo, A)
    D is None                                                    -> fallback · A undrained (exit 0)
    not (D ancestor-of C)                                        -> fallback · before drain (exit 0)
    otherwise                                                    -> fallback refused       (exit 1)
  nothing                                                        -> none                   (exit 1)
```

### A build crossing the drain

| First-parent order | Commit | Build A's witness read | Build B's witness read |
|---|---|---|---|
| 1 | A's plan gate released by the owner's disposition | `fallback · before drain` | — |
| 2 | `ratify.py` lands and claude-code's `prompt-submit` reads `yes`: D | `fallback · before drain` | — |
| 3 | B's plan gate released by the owner's disposition | `fallback · before drain` | `fallback refused · claude-code drained at <D8>` |

### Alternatives rejected

- **A drain date or sha typed into a table.** The drain is a fact of the history; typing it beside
  what it describes is the derive-over-author rule's defect, and a typed sha can name the wrong commit.
- **The drain judged by the reader's clock against the witness's date.** A rebased or late-pushed
  witness carries a date that orders nothing; first-parent ancestry orders the landings.
- **One global drain.** DA-M14: a harness with no prompt-submit event would never leave Plan.

## 5. Production-readiness checklist

- security — a ratification is accepted only from an owner-origin receipt or an owner disposition the
  drain rule admits; a capable harness's late fallback is refused, so the fallback cannot outlive the
  hook as a side door.
- perf / scale — S1 walks the default branch's first-parent commits touching two paths, once per
  adapter per check.
- error / empty / loading states — no intake and no disposition reads `none`; an unreadable history
  exits 2 naming the git error, never an acceptance.
- observability — S3's verdict line, printed at the gate and by `ratify.py check`.
- risks — a witness on a branch not yet merged has no first-parent position; it reads as after the
  drain where D exists, the safe side.
- testing — the criteria of §6 and the arm in §7.
- migration — S3's fallback branch is the migration: every fallback-era build reads as it did.
- user docs — `help/runtime.md` (S7).
