## 1. Goal

No tool names the next step: nothing ends with the caller's next command, so the loop advances only by
agents re-deriving it (gap-found-06), and a model session decides every next act (gap-rt-01). P15 says
every gov command ends with a `next —` line and a `next` verb answers "what now"
(`memory/builds/dClosedLoop/build/2026-10-14-build-PLAY-dClosedLoop-1-architecture-v2.md:963-966`); the
layer splits it, the position function dDeclaredLoop's and the verb, the micro-format and the check
Runtime's (layer-runtime `[decide]`, :315-330). This unit builds the `next` verb over TOOL-dDeclaredLoop-7's
`derive_position`, the `next —` micro-format, the check that every declared command ends with one or
declares itself terminal, its laggard list drained to empty before the unit closes (M3), and re-points
the readers of `--plan` and `--status` that ask what comes next.

## 2. Scope (IN)

- **S1** — The verb (I13), `python tools/runtime/next.py <slug> [--json]`: it calls `derive_position(repo,
  slug)` (TOOL-dDeclaredLoop-7 S1) and prints the engine's line output (TOOL-dDeclaredLoop-7 §4 "Line
  output") unchanged, ending with exactly one `next —` line. For the answer `act` that last line is the
  engine's own `next — <item tag> · actor <actor> · key <instance key>`, the key the item instance key
  (I14, TOOL-dDeclaredLoop-7 S3); for any other answer the engine prints no `next —` line and the verb
  appends the terminal `next — none · <answer> · <reason>`. `--json` prints the engine's JSON object with
  one more field, `next`, holding that line. Exit 0 for every answer but `invalid-input`, which exits 2,
  as the engine does. Observed by AC1.
- **S2** — The tail, `python tools/runtime/next.py --tail [<slug>]`, which prints only S1's last line,
  for a command to end with. With no slug and no `GOV_BUILD` in the environment it prints
  `next — none · unbound · no build named` and exits 0. Observed by AC2.
- **S3** — The micro-format, one definition in the charter template's fence

### The two line forms


### What the check does not check

S5 grades whether a command's `run` file spells the tail, never whether the tail is the last line on
every exit path: an early `exit` before the call passes it. A runtime arm would have to run every
declared command, the lander among them, in a fixture. Each command's own suite owns its exit paths.

### Alternatives rejected

- **A second renderer of the `act` line in `next.py`.** The engine already prints it; the verb adds only
  the terminal form, so each form has one renderer.
- **Running each declared command in a fixture to read its last line.** It runs the lander and every
  other side-effecting command, and needs a probe invocation per row (§4 What the check does not check).
- **A hand-typed laggard list.** KICK-dKeptSession-19's factory is the shrink-only list's one
  implementation; a fourth hand-rolled list is what that unit exists to stop.

## 5. Production-readiness checklist

- security — read-only: the verb reads witnesses through the engine and writes nothing; `--write`
  writes only the laggard list.
- perf / scale — one engine call per run; the check reads each kit descriptor once.
- error / empty / loading states — an engine `invalid-input` exits 2 with its terminal line; no slug
  prints the `unbound` line; zero commands prints `unarmed`.
- observability — the check prints its population and each laggard by tag.
- risks — a command whose early exit skips its tail passes the check (§4).

- migration — §4 Migration.
