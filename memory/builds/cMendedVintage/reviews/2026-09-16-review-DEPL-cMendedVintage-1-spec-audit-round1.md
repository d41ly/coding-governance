## Verdict: BLOCKED

One blocker stands. `DEPL-cMendedVintage-10` specifies a `.gitattributes` entry into the pre-write
snapshot without saying what `kit` key it carries, and the two consumers that read that field — the
rollback restore loop and the orphan sweep — both key on it. Built as written, the unit's own AC4
cannot pass and every run that rewrites the pin block prints a spurious `NOT VERIFIED` line. That is
a spec that cannot be built correctly from its own text, not a document that reads badly.

Six high findings sit behind it, and they cluster into one shape worth naming before the table: an
acceptance criterion that cannot fail for the reason its own Red-when gives. `DEPL-4` AC3 is a grep
whose pattern cannot see six of the fourteen live occurrences it is written to drive to zero,
including the single site its Red-when calls the likeliest miss. `DEPL-13` AC6 grades bytes that an
ordinary in-place write produces identically, so the atomic write `§4 Rollout` calls the answer to
the unit's sharpest risk is ungraded. `TOOL-9` AC1 observes a hang directly and never touches the
suite arm that S4 exists to ship. Three units, three mitigations, nothing that reds if any of them is
silently dropped — and the build closes green in each case.

The design the set implements is not in dispute. No finding below asks for `update`'s new
install-effect stage to be reconsidered, and the phase ordering survived the pass untouched. What is
wrong is downstream and local: units that state a mechanism correctly in section 2 and then fail to
put an observation under it, and two units whose section 4 prose describes an engine behaviour the
engine does not produce.

### B1 — blocker — `DEPL-cMendedVintage-10` §2 S2 and §4 "The ordering that makes this correct", site 1

**The defect.** S2 tells the implementer to make the `.gitattributes` row "join the pre-write
snapshot" carrying an `origin` value, and §4's ordering table says when the entry is taken. Neither
section, nor the Inventory, ever says what `kit` key the entry carries — and `kit` is the field both
consumers read.

`apply` stamps that row `"kit": "(govkit)"` (`tools/govkit/govkit.py:4627`), a synthetic id that no
registry entry claims. The rollback restore loop is
`for s in [x for x in snap_rows if x["kit"] == eid]` (`:7569`), running inside a `for eid in
touched_kits` loop whose population is real claimed ids (`:7728`). No `eid` equals `(govkit)`, so the
entry is selected by no kit's rollback and the restore never reaches it. The same key then falls
through `orphan_kits` (`:6730`), which sweeps every snapshot entry whose kit is not in `claimed`.

Two consequences, both on the unit's own acceptance surface. AC4 stages a kit green-to-red and
requires the pre-run `.gitattributes` block to come back; as specified it does not come back, the run
reports a successful rollback, and the file stands at gov's newly written bytes — which is verbatim
the state AC4's Red-when describes. And every run that rewrites the block prints a spurious
`verify (govkit): NOT VERIFIED` line at `:7714`.

One correction to the finding as delivered, because it was reported twice from two directions and one
of the two called the row kitless. It is not kitless; it carries `(govkit)`. The conclusion is
unchanged and slightly worse, since a value that exists but matches nothing also reaches the orphan
sweep, which a genuinely absent key would not.

Severity is blocker rather than high because this is not a document that reads badly. It is a unit
whose stated acceptance criterion cannot pass on any implementation faithful to its section 2, and
whose builder has no way to discover the missing decision except by hitting it.

**Fix.** State in S2 which `kit` value the entry carries and how the restore reaches it — either bind
the entry to the kits whose `[[lf_pin]]` produced the block, or give the restore a second pass over
`origin == "attributes"` entries outside the per-kit filter — and exclude the synthetic id from
`orphan_kits`. Name in AC4 the kit whose rollback is expected to restore the block, and add a
criterion asserting no orphan line is printed for `(govkit)`.

**Left-shift.** A `tools/govkit/matrix.py` arm on shape 5, where the installed thing runs: a target
with a written pin block, one kit staged to fail verify, assert the pre-run `.gitattributes` bytes
return AND that the run's output carries no `NOT VERIFIED` line naming a kit the registry does not
claim. The class is "a snapshot entry whose key no consumer loop can select", and the arm that grades
it is the one that grades the rollback end-to-end rather than the one that grades the snapshot
builder.

### H1 — high — `DEPL-cMendedVintage-5` §2 S4, against §3's memory-recall non-goal

**The defect.** S4 declares a lexicon `[[outcome]]` of `code = 1` plus `must_not_exist =
".lexicon.conf"` plus `ok = true`. That is the same move §3 refuses one bullet later for
memory-recall, on the stated grounds that an outcome table is read by `apply`'s CONFIGURE as well as
by the regenerate — and the spec never says why lexicon is different.

The objection is correct and it bites here. `classify_outcome` reads the kit-level `desc["outcome"]`
list (`tools/govkit/govkit.py:3750`) and is consulted by `apply`'s CONFIGURE (`:4894`), by `check`
(`:2970`) and by the re-render stage (`:7438`) alike; there is no per-step scoping. Lexicon's
`[adopt]` argv is `adopt-lexicon.sh --scaffold`, whose first-install failure path is
`"$PY" "$KIT_DIR/scaffold_lexicon.py" "$CONF" || exit 1` (`tools/lexicon/adopt-lexicon.sh:497`) —
exit 1 with `.lexicon.conf` absent, because the conf is what the failed program was writing.

After S4, `outcome_accepted` returns True for that exit and `apply` classifies a failed first install
as the accepted stop `no-project-layer`: kit adopted-and-stopped-ok, no Skill on disk, no conf. BASE
reports that same run as `landed-but-inert ... surfaced rather than swallowed`. The comment
immediately beneath the failure path (`adopt-lexicon.sh:498`) records that this exact wedge already
happened once, when a failed render printed a success line and exited 0.

A decline reported as a success is the class this build exists to close, so shipping one inside it is
worth a high on its own.

**Fix.** Narrow the probe so it cannot match the scaffold path: add a `must_exist` term the `--render`
case satisfies and a failed first scaffold does not — the rendered Skill, or the adoption marker. If
the widening is deliberate, say in S4 why `apply`'s acceptance may widen for lexicon and not for
memory-recall, and give the decision its own criterion in §6.

**Left-shift.** A `tools/govkit/matrix.py` arm that stages a scaffold failure — make
`scaffold_lexicon.py` unwritable at its destination, or point it at a read-only conf path — and
asserts `apply` reports the kit as NOT adopted. The class assertion that generalises it belongs in the
same file: for every registry entry declaring an `[[outcome]]` with `ok = true` and a `must_not_exist`
term, the named path must not be a file the entry's own `[adopt]` argv creates.

### H2 — high — `DEPL-cMendedVintage-10` §5 "error / empty / loading states", first clause

**The defect.** The clause reads "a target with no pins skips every site". It is false, and the
falsehood is load-bearing because no criterion in §6 exercises a zero-pin target.

At `tools/govkit/govkit.py:6387-6398` the `pins` arm sets `_om, _cm, _text = ("", "", "")` when
`_pins` is empty, leaves `_span` at `None` and `_held` at `None`, and therefore evaluates `v` to
`pins-moved` with `pins_order = ""`. The arm does not skip; it reports a moved block.

The reachable population is precise: a target that HAD pins, since only then does `apply` synthesize
the `attributes` row at all (`:4620`, `if pins:`), and whose claimed kits now declare none — a kit
dropped from `receipt["kits"]`. S1 then calls `write_block(cur, "", "", "", "append")`, and
`find_block`'s marker test matches every blank line in `.gitattributes`. Two or more blank lines raise
the "expected exactly one marker pair" Refusal mid-run; one blank line splices over it; zero appends a
stray line to a file gov does not own. On every run.

§8 Q2 reasons only about a target that never declared a pin, which is the case that genuinely skips,
and that is how the withdrawal case slipped through.

**Fix.** Make S1 gate the write on a non-empty recomputed pin set, say what the arm should report for
that state instead of `pins-moved`, and add an acceptance criterion over a target whose claimed kits
declare no `[[lf_pin]]` after having declared one.

**Left-shift.** A `tools/govkit/matrix.py` arm on a target whose receipt carries an `attributes` row
and whose claimed set has since lost every pin-declaring kit: assert `update` neither raises nor
writes. Pair it with a `refusal_join.py` anchor for the "expected exactly one marker pair" branch, so
a refusal reachable only through an empty-marker call is attributed to an arm rather than discovered
by an adopter.

### H3 — high — `DEPL-cMendedVintage-2` §2 S2 and §4 "The gate"

**The defect.** S2 gates the `withdrawn_rows.remove(s["row"])` at `tools/govkit/govkit.py:7666`
together with the `ROLLBACK_FIELDS` revert, on the assumption that no snapshot entry is simultaneously
a withdrawn row. `_touching` at `:6692` admits `withdrawn` whenever `--write-withdrawals` is passed,
so on those runs a withdrawn row IS a snapshot entry and its path lands in `deleted` and then in
`written_paths` (`:7502`).

The withdrawn arm mutates no `ROLLBACK_FIELDS`, so the gate's only effect on such an entry is to skip
the removal — and `withdrawn_rows` is the DELETE list, consumed at `:7818-7819`, which strips every
row still in it from the receipt. On a `--write-withdrawals` run whose rollback cannot restore a
withdrawn path, the row is dropped from the receipt entirely: the receipt then describes neither the
bytes on disk nor the path, which is the exact inverse of §4's stated invariant that "the row
describes the bytes that are actually on disk".

It also inverts the sibling rule the spec says it is hoisting. The landed branch keeps its row
precisely because "the row is what a later `update` needs in order to see them at all"; this branch
loses the row for a file the run deleted and could not restore.

The failure is reachable with the spec's own fixture technique. A directory at the worktree path makes
`checkout-index -f` refuse, and the withdrawn arm's `dp.unlink()` is guarded by `is_file()`, so a
directory still reaches `deleted`. No non-goal scopes withdrawals out of this unit.

**Fix.** Split the two effects. Gate only the field revert on `_left`, and state separately what a
withdrawn-and-unrestored row does — keep it in `withdrawn_rows`, or take it out and leave it forward —
with the reason. Add a criterion over a `--write-withdrawals` run whose restore fails.

**Left-shift.** A `tools/govkit/selftest.py` arm, since this is a mechanism rather than a repo shape:
a receipt with one withdrawn row, a directory planted at its worktree path, `update --write
--write-withdrawals`, then assert the post-run receipt still carries a row for that path. The class is
"a row removed from the receipt for a path still on disk", and it is assertable as an invariant over
every arm that exercises rollback: no path may end a run both absent from `files[]` and present in the
worktree.

### H4 — high — `DEPL-cMendedVintage-6` §4 Migration

**The defect.** The Migration paragraph — "Those report as withdrawn with an order written to the
outbox" — describes an outcome the engine does not produce, on the one unit whose whole subject is
stopping a clobber at a live adopter.

`t_state` is decided solely by whether gov's source blob exists at `to_commit` (`classify_row`,
`tools/govkit/govkit.py:5781` and `:5787`), and `withdrawn` is the grid cell `("equal", "absent")` at
`:5379`. S1 and §4 keep both records tracked in gov's tree, so `theirs` is never absent and no row can
grade `withdrawn` at all. §4 compounds it by describing the adopter's rows as ones "whose descriptor
no longer claims them", while S3 deliberately claims that exact `{kit}/{relpath}` destination as
`project-owned`.

Role is re-resolved only for `schema < 2` (`:6331`), so a schema-3 row keeps `engine` and keeps taking
the full `table` disposition against a rule that no longer supplies bytes for it — and
`UPDATE_ROLE["project-owned"]` is `skip` (`:5438`), so the new rule supplies nothing to compare
against. An adopter's renamed-away copy grades `missing` and is restored rather than reported.

The absent re-resolution is already recorded, as OPEN backlog row `DEPL-dPolishedVitrine-1`
(`memory/backlog/DEPL.md:60`): "`update` keeps a schema-3 row's role, so an engine-to-`rendered` move
stays engine on gov's render". The spec set cites it nowhere, and §3's non-goal rests on the same
unmeasured outcome the Migration paragraph asserts.

**Fix.** Cite `DEPL-dPolishedVitrine-1` in §3 Non-goals. Replace the Migration paragraph with what the
engine actually does to a pre-existing `engine` row whose destination is now claimed by a
`project-owned` rule. Add an acceptance criterion observing that transition on a fixture whose receipt
was written BEFORE the descriptor change — every scratch-target criterion in §6 starts from a fresh
install and cannot reach it.

**Left-shift.** A `tools/govkit/matrix.py` arm built on an aged receipt rather than a fresh install:
write a schema-3 receipt with an `engine` row, change the descriptor to claim that destination as
`project-owned`, run `update`, and assert the reported disposition against the one the spec names.
More generally, the missing gate here is a spec-level one — a spec §4 that names a verdict token
(`withdrawn`, `missing`, `table`) should have that token reachable on the fixture the spec's own §6
builds, and nothing today joins those two.

### H5 — high — `DEPL-cMendedVintage-4` §6 AC3, against §2 S3

**The defect.** AC3 is `grep -c 'allow_ungraded' tools/govkit/govkit.py` returning 0, with the
Red-when "one of the ten sites S3 enumerates is missed — most likely the `parse_args` return element".
The pattern is case-sensitive and underscore-only, and it cannot see six of the fourteen live
occurrences.

Measured in this worktree at the pinned blob: `grep -c 'allow_ungraded'` returns 8, while
`grep -cE 'allow[_-]ungraded|ALLOW_UNGRADED'` returns 14. The six the criterion is blind to are
`:7853` (`or pass --allow-ungraded to stamp anyway`), `:7866` (the `over ... --allow-ungraded`
clause), `:8522` (the USAGE line), `:8535` (the USAGE sentence), `:8601`
(`elif a == "--allow-ungraded":`) and `:8958` (`ALLOW_UNGRADED)` in the `parse_args` unpack).

The last one is the sharpest. `:8958` is precisely the site AC3's own Red-when names as the likeliest
miss, and it is spelled in upper case. The criterion written to catch that case cannot fail for it.
Meanwhile the USAGE line, the USAGE sentence and the `over` clause — the three an operator actually
reads — can all survive intact with AC3 green and AC2 green, since AC2 exercises only the argv arm and
AC4 grades the `unattributed` / `--re-adopt` / `--pin` strings. §5's claim that "the `over ...
--allow-ungraded` clause disappears with the flag" is therefore ungraded.

**Fix.** Widen the predicate to `grep -cE 'allow[_-]ungraded|ALLOW_UNGRADED'` returning 0, and spell
the same pattern in S3 so the enumeration and the check share one expression rather than two.

**Left-shift.** This is a `tools/check-spec-tokens.py` join, and it is the natural fifth after `legs`,
`paths`, `cites` and `bar`: when an acceptance criterion's backticked invocation is a `grep` whose
pattern is a literal, run it and compare the reported figure with the criterion's own expected value
at lint time. The case here is stronger than most, because AC3 already declares
`figure: DERIVED by that grep at observation time` — the lint only has to derive it one commit
earlier. Failing that, a `selftest.py` arm asserting the flag is absent under every spelling gives the
class a home that does not depend on a criterion being written correctly.

### H6 — high — `DEPL-cMendedVintage-13` §2 S6, against §6 AC6

**The defect.** S6 makes the manifest write-back atomic — `write_text` to a sibling temp path followed
by `os.replace` — and names AC6 as its observation. AC6 runs `apply --target <fixture> --write`
against a fixture after the extraction and requires the runner file to be byte-identical to the one
the same command produced before it, with a Red-when about row order and dropped fields.

An ordinary in-place `write_text` produces exactly those bytes. AC6 is green whether or not the
temp-sibling and `os.replace` ever land, and nothing else in the spec reaches the write mechanism:
neither new arm in §7 mentions it, and no other criterion touches it.

That matters more here than it would elsewhere, because §4 Rollout names S6 as THE answer to the
unit's sharpest risk — a half-written leg manifest on a file an adopter's whole bar reads — and §5
repeats it. The one mitigation the spec elevates above the others is the one with an observer that
cannot fail, so it can be dropped silently and the build still closes green.

The set knows how to write a falsifiable criterion for this shape: `TOOL-9` AC5 and `DEPL-6` AC2's
"the repath loop is gone" are both source-level class assertions. The instrument was available and was
not used.

**Fix.** Add a criterion that can fail for S6's reason. Either assert at source level that the write
goes through a temp sibling followed by `os.replace`, in the style of `DEPL-4` AC4; or stage a raise
between the temp write and the replace and assert the previous runner file survives intact with no
`*.tmp` sibling left behind. The second is stronger and is the one §4's risk language implies.

**Left-shift.** A `tools/govkit/selftest.py` arm that injects the failure between the two steps, plus
a class check with a wider blast radius: every write to a path an adopter's bar reads goes through the
atomic helper, assertable as a source-level ban on direct `write_text` to those destinations. The
generalisable rule for the spec layer is the one this finding is an instance of — a mitigation named
in §4 Rollout or §5 risks must be named by a criterion that fails when it is absent, which is a join
`check-spec-tokens.py` could make between the two sections without reading either for meaning.

### M1 — medium — `TOOL-cMendedVintage-1` §2 S2, against §5 risks

**The defect.** `tools/memory-tree/adopt-memory-tree.sh:109` renders `HYGIENE.md` with an `else`
fallback that writes a one-line stub when `$HERE/HYGIENE.template.md` is absent:
`else echo "# ${M}/ retention & hygiene" > "$M/HYGIENE.md"`. The other three `render_doc` calls
(`:110`, `:113`, `:116`) have no else. S2 folds all four into one `render_all` called by both modes
and states that the set "cannot diverge", which carries the fallback into `--render`.

In `--scaffold` the fallback writes a stub where nothing existed. In `--render` the target file
already exists and holds the adopter's committed rule set plus the `gov:kit memory-tree@` marker that
S3's own guard reads. Overwriting it wedges the tree in both directions: `--render` then refuses for a
missing marker, and `--scaffold` refuses at `:74-75` because `$M` exists without one.

The code's own `[ -f ... ]` guards show the missing-template case is contemplated. §4 never requires
the four templates to be present, and §5's risk covers a partial render SET rather than a destructive
fallback, so nothing in the spec catches it.

**Fix.** State in S2 that `--render` refuses on a missing template rather than inheriting the
scaffold's create-from-nothing fallback, and add a criterion staging an absent `HYGIENE.template.md`
against an adopted tree.

**Left-shift.** An arm in the memory-tree kit's own suite that runs `--render` with one template moved
aside and asserts the adopter's `HYGIENE.md` is unchanged. The class — a render path that can create
where it was only ever meant to replace — generalises to a shell lint over the kit adopters: a
`render_doc` guarded by `[ -f <template> ]` may not carry an `else` that writes the destination.

### M2 — medium — `DEPL-cMendedVintage-4` §2 S3, against §4 Inventory and §4 "Files touched"

**The defect.** S3 enumerates nine removal sites. §4 "Files touched" and AC3 both call it "the ten
sites S3 enumerates". §4 Inventory says the unit deletes "one module-level constant", which S3 does
not list and which does not exist.

Both halves check out. The enumeration is the USAGE line, its sentence, the argv arm, the `parse_args`
return element, its unpack, two parameters, the `and not` guard and the `over` clause. Three live
occurrences are unlisted: `:5934` (`_cmd_update(root, target, to_rev, write, write_withdrawals,
allow_ungraded, kits)`), `:8558` (`allow_ungraded = False`) and `:8993`
(`allow_ungraded=ALLOW_UNGRADED`). A builder working from the closed list who deletes the parameters
at `:5930` and `:5940` breaks the call at `:5934`. And `main()` begins at `:8951`, so `ALLOW_UNGRADED`
at `:8958` is a local — the Inventory names a module-level constant that is not there.

It stays medium rather than high because the broken call surfaces on the first run of anything. The
cost is a builder with no way to tell whether the enumeration is complete or which site is the tenth.

**Fix.** Re-derive the site list at build time and make S3 the single enumeration. Drop "one
module-level constant" from the Inventory or name the thing it means. Either say "the sites S3
enumerates" without a count, or make the count match the list.

**Left-shift.** A `check-spec-tokens.py` join over counts: a spec sentence of the form "the N sites
S<x> enumerates" must agree with the number of backticked citations inside that S item. It is a
purely structural join over one file, needs no source resolution, and catches the whole "a number
typed beside the thing it counts" class the charter's §7 already bans in prose.

### M3 — medium — `TOOL-cMendedVintage-6` §5 Production-readiness checklist, risks

**The defect.** §5 confines the leg's false-red class to "a receipt written before the D9 fold". That
is the wrong population, and the right one was already measured: finding 36 of
`memory/builds/aSealedCaravan/reviews/2026-08-10-review-TOOL-aSealedCaravan-1-1.md` records that the
receipt hashes working-tree bytes, so the check false-reds on every clone that is not the install
machine.

The mechanism survives the D9 fold. `sha256` is stamped from the worktree of the machine that ran
`apply` (`tools/govkit/govkit.py:8149-8155`), and the fold only made the two READERS agree on a
population — it did not make the hash clone-independent. gov's `.gitattributes` is `* text=auto` with
`eol=lf` pinned on `*.sh`, `gate-legs.json`, `*.fragment.json` and a handful of named files, so
shipped `.py` and `.md` engine rows re-expand on any clone with `core.autocrlf=true`.

This leg is declared `subject = "repo"`, so it runs on an adopter's merge bar — in CI and on every
other developer's clone. The population §5 says is not at risk is the population most likely to red.
The prior record also carried the two remedies this spec does not weigh, and §3's non-goal covers
`install.sums` rather than `files[].sha256`, so nothing withholds the question.

**Fix.** Cite finding 36 of that review in §5 and restate the risk as "any clone that is not the
install machine, for any receipt-covered path no `[[lf_pin]]` covers". Then decide it in §2: scope
S1's population to rows a claimed `[[lf_pin]]` covers, or hash normalized content, or add an
acceptance criterion observing the leg on a CRLF-expanded clone so the residue is measured rather than
asserted away.

**Left-shift.** An arm that clones the fixture target with `core.autocrlf=true` and runs the leg,
asserting whatever disposition the decision picks. The durable version is a rule rather than a test:
any check comparing a stored hash against worktree bytes declares, in its own header, which paths it
is valid for — which is `AGENTS.md` §7's "a gate's OWN header states what it does NOT check" applied
to a population rather than to a behaviour.

### M4 — medium — `DEPL-cMendedVintage-2` §2 S1 and S3

**The defect.** The containment refusal at `tools/govkit/govkit.py:7580-7583` runs BEFORE the
`p not in written_paths` test at `:7584`. A path it refuses is therefore in neither `restored` nor
`untouched`, and need not be in `written_paths` at all — the branch's own header says it exists for "a
receipt row spelling `../../x` that the write loop refused", which is a path absent from

### M5 — medium — `TOOL-cMendedVintage-9` §2 S4, against §6 AC1

**The defect.** S4 requires `skills/session-kickoff/manifest-check.test.sh` to gain an arm holding

### M6 — medium — `TOOL-cMendedVintage-9` §10 Reuse audit, against §4

**The defect.** §4 states plainly: "This makes `--session` beat the hook's JSON when a caller supplies
both. That is a behaviour change." §10 states the change "restores the documented order rather than
inventing one", citing `KICK-aReplayedCard-1` §S2.

the cited section and the implementing line.

## What round 2 should carry

Three of the six highs and the blocker are the same underlying omission — a mechanism specified in
section 2 with no observation under it in section 6 — so the cheapest round-2 pass is not another
lens fan. It is one mechanical sweep over all 23 specs asking, for every `S<n>` that names an observer,
whether the named criterion can fail when that S item is absent. `DEPL-13` S6, `TOOL-9` S4 and
`DEPL-4` AC3 were all found that way here, one at a time, by three different lenses.

The priming change worth making: require a `file:line` from the tree in every finding. It is what
separates the 14 that survived from most of the 30 that did not, and it is the same correction the
`dTracedLattice` round-1 record wrote down and nobody has yet applied to a lens prompt.
