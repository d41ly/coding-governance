## 1. Goal

Widen the change feed from governance ref writes to record writes. Every commit that touches a
record joins the feed once it lands, whether the `record` door or a hand commit made it, so a
mirror or a reader replaying the feed sees memory change in landing order (the owner's NT-14,
memory-plan.md:97). An uncommitted write never reaches the feed, and the feed's census and check
red on a landing path that skips the append and on a landed record the feed lacks.

## 2. Scope (IN)

Every surface below extends TOOL-dPlacedRequest-13's feed as that spec names it: the file
`<git-common-dir>/gov-feed.log` (S1), `add_feed_event` in the `gov_feed_sh` block of
`tools/lib/gov-feed.sh` (S2), `derive_feed_events` (S5), `check_feed` (S6) and `scan_feed_writers`
(S9). TOOL-dPlacedRequest-15 S5 carries that block inline in `tools/push-main.sh`. Both specs are
DEFERRED at base `462d20f3`.

- **S1** — The record event (shared interface I17). It is one feed line in the six TAB fields of
  TOOL-dPlacedRequest-13 S1: `kind` is `record`, `ref` the landed branch's remote name
  (`refs/heads/<default>`), `blob` the record file's blob at that commit (`-` when the file is absent
  at that commit), and `commit` the commit. One event per record file a commit touches. The key stays
  (`ref`, `blob`, `commit`). Observed by AC1.
- **S2** — The record path: a tracked path under the conf's `MEMORY_ROOT`, read from
  `.memory-tree.conf` as every memory-tree reader reads it. Observed by AC1.
- **S3** — The appender, `add_record_events <ref> <tip>`, in the `gov_feed_sh` block. Under the
  block's own lock it finds the newest record event the feed holds for `<ref>`, lists every non-merge
  commit in `<that commit>..<tip>` (the whole history when none) that touches a record path, with one
  `git log --reverse --no-merges --no-renames --raw`, and appends their events in that order in one
  write, `seq` rising from the counter. It appends nothing for an event whose key the feed holds.
  Observed by AC1, AC2 and AC5.
- **S4** — The landing joins. `cmd_land` in `tools/push-main.sh` calls
  `add_record_events "refs/heads/$def" "$pushed"` on its landed branch (`push-main.sh:977-984`),
  beside `run_post_merge`. The walk starts at the feed's newest record commit, not at the tip
  before the push, so another node's landings this node fetched join too. Observed by AC2.
- **S5** — The check, `check_feed`'s record arm. For each `ref` carrying record events,
  `derive_record_events <ref> <newest>` derives the events of every record-touching commit reachable
  from the newest commit the feed holds for that ref. Those must equal the feed's record events for
  the ref, in order. A derived event the feed lacks prints `missing`, and a feed event whose commit is
  not on that history prints `extra`. Both exit 1. Observed by AC3 and AC4.
- **S6** — The census, `scan_feed_writers`' landing arm. Every line of a shipped shell file that
  pushes to the default branch (a `push` carrying `refs/heads/$def`, `HEAD:refs/heads/`, or the
  default branch's name as its refspec) must sit in a function whose body calls
  `add_record_events`. Each other one prints `<file>:<line>`. An empty population reds the arm.
  Observed by AC6.
- **S7** — The verb. `unattended.sh --feed check` runs S5 beside the ref arms, and
  `unattended.sh --feed rebuild` writes the derived record events after the ref events. Observed
  by AC4.

## 3. Non-goals (OUT)

- No edge fields on the line. A record event names its blob, and a reader takes the record's edges
  from that blob through the index (§8 F1). TOOL-dPlacedRequest-13 S1's six fields stay six.
- No append from the door itself. `gov_record.py` writes files and commits nothing that has landed,
  so its writes join at landing like any hand commit. A door that appended anyway would append
  nothing, since the key already holds.
- No mirror and no relay: dWellOiledMachine's memory-mirror point reads the feed.
- Records outside `MEMORY_ROOT`, and merge commits' own conflict resolutions: a merge's record
  changes are its parents' commits, which the walk lists.
- A landing that bypasses the lander (`git push --no-verify`) is not prevented. The next landing's
  walk appends its commits, and S5 names them `missing` until then.

### Edges

- **consumes-from** `TOOL-dTotalRecall-2` — `gov_record.py`, whose `new <kind>` writes the record the fixture commits and lands, so a door-made and a hand-made commit are seen joining the feed alike

## 4. Design

### The line

```
18	refs/heads/main	record	9f2c41e0…	5c1d77ab…	2026-11-02T10:14:03Z
```

`blob` is the record file's blob from the `--raw` line's new-object field, so the walk spawns no
process per file. A delete carries `-`, as a ref deletion does in TOOL-dPlacedRequest-13 S1.

### Appending a range in one write

`add_feed_event` appends one line under a lock and a `grep -qF` key test. Called once per event, a
first walk over gov's history would grep a growing file 34,089 times (PINNED, measured 2026-10-26 at
`462d20f3`: 34,089 record events over 5,801 commits, listed in 0.6 s). `add_record_events` therefore
takes the lock once, reads the feed's newest record commit for the ref with one `awk` pass, builds the
new lines in a scratch file beside the feed, appends them with one `cat >>`, and writes the counter
once. The lock, the counter and the failure rule (a `feed: NOTE -` line and return 0) are the
block's own, so units that change them (TOOL-dPlacedRequest-24's lock factory,
TOOL-dPlacedRequest-27's append-once read) change this path too.

### Why the walk starts at the feed

The lander knows the remote's tip before its push. A walk from that tip would skip commits another
node landed that this node only fetched, and every check on this node would then name them
`missing`. Starting at the newest record commit the feed holds covers them, and S5 compares only up
to that commit. A node's feed is everything it recorded, as TOOL-dPlacedRequest-13 §8 F2 reads the
ref arms.

### Inventory

Minted: the functions `add_record_events` and `derive_record_events`, the event kind `record`,
`check_feed`'s record arm and `scan_feed_writers`' landing arm. Naming cells: `add` and `derive`, OK
in the shell lexicon as TOOL-dPlacedRequest-13 found.

### Migration

A node's first landing after this unit appends every record event in its history once, each
`seen-utc` that landing's time. `unattended.sh --feed rebuild` on a node with no feed writes the same
events.

### Rollout

Live on landing, wherever the lander runs. The kit version markers of the kits whose bytes move are
moved in the same commit, as the `kit epoch` leg requires.

### Files touched (estimate)

- `tools/lib/gov-feed.sh`: the canonical block gains `add_record_events`, `derive_record_events`, the
  record arm of `check_feed` and the landing arm of `scan_feed_writers`
- `tools/unattended/unattended.sh`: its inline copy, and `--feed check` and `--feed rebuild` run the
  record arm
- `tools/run-gates/post-merge.sh`: its inline copy
- `tools/push-main.sh`: its inline copy, and `cmd_land` calls `add_record_events`
- `tools/lib/resolve-python.test.sh`: the census over every shipped shell file runs the landing arm
- `tools/unattended/unattended.test.sh`: the record arms
- `tools/push-main.test.sh`: the lander's landed branch appends

### Alternatives rejected

- **Append from a post-commit hook.** It fires for an unlanded commit, which the clause keeps out,
  and a rebase would leave events for commits that never land.
- **Walk from the tip before the push.** It skips fetched landings, as "Why the walk starts at the
  feed" shows.
- **A seventh field for edges.** It changes TOOL-dPlacedRequest-13's contract for every reader, and
  the blob already names the bytes the edges are read from.

## 5. Production-readiness checklist

- security — no new write path beyond the node-local feed file the block already writes; the walk
  reads git objects only.
- perf / scale — one `git log` per landing over the new range; the first walk is 0.6 s over gov's
  history (§4).
- error / empty / loading states — a lock or write failure prints the block's NOTE line and returns
  0, since the landing has already happened; the next check names what is missing.
- observability — `--feed check` prints each `missing` and `extra` record event.
- risks — the feed grows by about 5 MB on gov at the first walk; it is append-only by
  TOOL-dPlacedRequest-13's non-goal, so no rotation applies.
- testing — AC1 to AC6 by a pass; the arms of §7 at the close.
- migration — the first landing's backfill, as §4 says.
- user docs — none under `help/`: the feed has no help page; `tools/unattended/STOPS.template.md`
  section 7 names the verbs, and their names do not change.

## 6. Acceptance criteria

- **AC1** — When a probe sources `gov-feed.sh` in a fixture repository under `%TEMP%` holding three
  commits (one written through `python gov_record.py new <kind>` for a kind the registry holds, one a
  hand edit of a record, one
  touching only a file outside `MEMORY_ROOT`) and calls `add_record_events refs/heads/main <tip>`, the
  feed gains exactly one `record` line per record file of the first two commits, each naming the
  file's blob at its commit, and none for the third.
  Red when: an event names the commit's tree instead of the file's blob, or the third commit appears.
- **AC2** — When the same `add_record_events` call runs twice, and when a second clone lands a
  record commit that the fixture fetches before its own landing, the feed holds each event once,
  and the fetched commit's event sits before the fixture's own.
  Red when: a repeated call appends a duplicate key, or the walk starts at the pre-push tip and skips
  the fetched commit.
- **AC3** — When a record file is written and left uncommitted, and `check_feed`'s record arm runs,
  the feed holds no event for it and the check exits 0; when a line naming a commit that is on no
  branch is appended by hand, the check exits 1 with `extra`.
  Red when: an uncommitted write appears, or a planted off-history event passes.
- **AC4** — When a hand commit touching a record lands with `git push --no-verify`, a later commit's
  event is appended directly with `add_feed_event`, and `unattended.sh --feed check` runs, it exits 1
  naming the hand commit's record event `missing`.
  Red when: a landed record commit the live feed lacks passes the check.
- **AC5** — When `add_record_events` runs over a fixture history of 2,000 record commits, it takes
  the lock once and writes the counter once.
  Red when: it appends through one `add_feed_event` call per event.
  figure: 2,000 is the fixture's size, PINNED; it stands for gov's measured 34,089 events.
- **AC6** — When `scan_feed_writers` reads `tools/push-main.sh`, it prints nothing; when it reads a
  scratch file holding a function that runs `git push origin HEAD:refs/heads/main` with no
  `add_record_events` call, it prints that file and line.
  Red when: the landing arm is absent, or reads no line and passes on an empty population.

## 8. Open questions

- **F1 — Where does a record event carry "its edges"?** Options: (a) by blob: the event names the
  record file's blob, and a reader takes the edges from it through the index; (b) a seventh field;
  (c) one event per edge. (b) changes TOOL-dPlacedRequest-13 S1's line for every reader. (c) gives
  one change many keys that a replay must regroup, and an edge has no blob of its own. RESOLVED
  (agent, 2026-10-26, delegated): (a), rung 3, tie-broken by TOOL-dPlacedRequest-13 §8 F4, which
  already promised this build's record writes name their file's blob. widens: none · relaxes: none
- **F2 — What is "once it lands"?** Options: (a) the lander's landed branch, with fetched landings
  joining through the walk; (b) a post-commit hook; (c) post-merge on any branch. (b) and (c) append
  commits that may never land, against the clause's "an uncommitted write never in the feed".
  RESOLVED (agent, 2026-10-26, delegated): (a), rung 1, the clause's "once it lands". widens: none ·
  relaxes: none
- **F3 — Which paths are records?** Options: (a) every tracked path under `MEMORY_ROOT`; (b) the
  `home` paths of the kind registry's rows. (b) misses a record whose kind has no home row yet. The
  registry completes homes only in unit 18, and nothing in this clause names it. RESOLVED (agent,
  2026-10-26, delegated): (a), rung 3. widens: none · relaxes: none
