## 1. Goal

Widen the change feed from governance ref writes to record writes. Every commit that touches a
record joins the feed once it lands, whether the `record` door or a hand commit made it, so a
mirror or a reader replaying the feed sees memory change in landing order (the owner's NT-14,
`memory/builds/dClosedLoop/build/2026-10-18-build-PLAY-dClosedLoop-1-memory-plan.md@4ddb0f115:97`).
An uncommitted write never reaches the feed, and the feed's census and check red on a landing path
that skips the append and on a landed record the feed lacks.

## 2. Scope (IN)

Every surface below extends TOOL-dPlacedRequest-13's feed as it landed (CLOSED): the file
`<git-common-dir>/gov-feed.log`, `tools/lib/gov-feed.sh#add_feed_event`, `#check_feed` and
`#write_feed` inside the `gov_feed_sh` block, and the census `#scan_feed_writers`, which sits below
the block's closing marker and ships in no carrier. The block is carried byte-identical inline by
four carriers, held to the canonical by the parity table in `tools/lib/resolve-python.test.sh`
(DERIVED: `git grep -l '^# >>> gov_feed_sh' -- '*.sh' '*.py' '.githooks/*' WIRE-INTO-PROJECT.md`,
less `tools/lib/gov-feed.sh`): `tools/push-main.sh`, `tools/unattended/unattended.sh`,
`tools/run-gates/post-merge.sh` and `tools/memory-tree/gov-claim.sh`.

A dependency this unit does not fix: at HEAD `4ddb0f115` the census already prints a limb-2 line
for the unleased push of `refs/gov/candidate/<sha>` in `tools/push-main.sh#check_landing_verdict`,
which TOOL-dWitnessedBar-6 (CLOSED) landed. So the
`python resolver` leg's census arm is red before this unit; S6's lines carry their own suffix so
its observations stand apart from that hit.

- **S1** — The record event (shared interface I17). It is one feed line in the block's six TAB
  fields: `kind` is `record`, `ref` the landed branch's remote name (`refs/heads/<default>`), `blob`
  the record file's blob at that commit (`-` where the file is absent at that commit), and `commit`
  the commit.
  The key stays (`ref`, `blob`, `commit`), so a commit yields one event per distinct key: record
  files of one commit that share a blob, two files absent after it say, give one event (§8 F5). Observed by AC1
  and AC8.
- **S2** — The record path: a tracked path under `MEMORY_ROOT`, read by `read_record_root` from the
  top level's `.memory-tree.conf`, sourced in a subshell with `MEMORY_ROOT` unset first, as
  `skills/session-kickoff/manifest-check.sh#read_memory_root` reads it. An absent conf, or one
  declaring none, reads `memory`, the default `tools/memory-tree/gov_record.py` and the hygiene
  gate take. A value that is not a plain relative path (a byte outside `A-Za-z0-9_./-`, a leading
  `/`, a `..` segment) is refused: the appender prints one `feed: NOTE -` line and returns 0, and
  the check prints `unread <ref> MEMORY_ROOT <value>` and exits 1. Observed by AC1 and AC10.
- **S3** — The appender, `add_record_events <ref> <tip>`, and the shared core it calls. The
  lock-count-append body of `add_feed_event`, its contained subshell (TOOL-dPlacedRequest-39), is
  extracted into `write_feed_lines`, which both appenders call. Under the node lock it runs the
  caller's row builder against the log, numbers the rows it prints from one more than the larger
  of the counter and the log's last `seq`, closes a torn last byte, appends every row in one write
  and writes the counter once. `add_feed_event`'s key test, NOTE texts and exit behaviour do not
  change, and its trap and take lines stay byte-identical, since the carrier-alone arm's plants match
  them by text. The record builder reads the newest `record` line of `<ref>` in file order and
  prints `derive_record_events <ref> <tip> <that commit>`, the whole history when there is none. A
  walk git refuses, from a commit this clone no longer holds say, prints one `feed: NOTE -` line and
  appends nothing. The clock, common-dir and tip checks are `add_feed_event`'s, each a NOTE and 0.
  Observed by AC1, AC2 and AC5.
- **S4** — The walk, `derive_record_events <ref> <tip> [<from>]`: one `git log --reverse
  --topo-order --no-merges --no-renames --raw --no-abbrev` over `<from>..<tip>` (or `<tip>`), run
  at the top level with the pathspec `<MEMORY_ROOT>/`, printing `ref TAB record TAB blob TAB commit`
  per distinct key in walk order. `--topo-order` puts every parent's events before its child's
  (§8 F6), and `--no-abbrev` makes the `--raw` new-object field the 40-hex blob. Observed by AC1
  and AC2.
- **S5** — The landing joins. Both of the lander's landing paths push through
  `tools/push-main.sh#write_effect_push`: `cmd_land`'s `HEAD:refs/heads/$def` and the attended
  path's `$def` or `refs/heads/$def:refs/heads/$def` in the file's top-level body
  (`tools/push-main.sh@4ddb0f115:2225`). Each success branch calls
  `add_record_events "refs/heads/$def" "$pushed"` as its first statement, before `check_push_allow`,
  since the push has landed whatever the allow record reads. The walk starts at the feed's newest
  record commit, not at the tip before the push, so another node's landings this node fetched join
  too. Observed by AC2 and AC7.
- **S6** — The check, `check_feed`'s record arm. R is every commit reachable from the clone's
  branches and remote-tracking branches, one `git rev-list --branches --remotes`. For each `ref`
  carrying `record` lines in the feed read, the arm's tip is the newest such line whose commit is in
  R; it compares the keys `derive_record_events <ref> <tip>` prints with the feed's record keys for
  the ref as sets (§8 F6). A derived key the feed lacks prints `missing <ref> <commit>`, a feed key
  not derived prints `extra <ref> <commit>`, and `check_feed` exits 1 when either arm found
  anything. A feed holding no record line runs nothing new. Observed by AC3, AC4 and AC8.
- **S7** — The census, `scan_feed_writers`' landing arm. A landing line is a joined, non-comment
  line carrying `refs/heads/$def` or `refs/heads/${def}` that runs `git` with the word `push` after
  it, or calls a name on `FEED_LANDING_PUSH_FNS`, declared beside the census lists as
  `write_effect_push`. Each scope holding one must call `add_record_events`, or each such line
  prints `<file>:<line> landing`. A list entry naming no function of the files read, or whose body
  holds no `git push` line, prints a line naming it; a scan that finds no landing line prints one
  line saying so, never a pass. Over the real tree the population is the lander's two landing lines
  (DERIVED: the predicate run over the census population on 2026-11-22). It does not check a
  default branch held in a variable other than `def`, or a landing pusher off the list whose call
  line runs no `git push`. Observed by AC6.
- **S8** — The verbs. `unattended.sh --feed check` runs S6 through `check_feed` with no dispatch
  change. `--feed rebuild`, once `write_feed` returns 0, resolves the remote and default branch
  through `resolve_remote_sh` as `tools/unattended/unattended.sh#default_branch` does and calls
  `add_record_events "refs/heads/<branch>" "refs/remotes/<remote>/<branch>"`. Where either does not
  resolve, or the tracking ref is absent, it prints `feed: no record events were rebuilt: <why>`
  and exits 2. Observed by AC9.
- **S9** — Every carrier's copy runs the record path alone. The carrier-alone arm's scratch
  repository's commit touches a record path, and its calls gain one `add_record_events` of it, so a

## 3. Non-goals (OUT)

- No edge fields on the line. A record event names its blob, and a reader takes the record's edges
  from that blob through the index (§8 F1). The six fields stay six, and no path field joins them:
  a reader takes a blob's paths from its commit.
- No append from the door itself. `gov_record.py` writes and stages files and commits nothing, so
  its writes join at landing like any hand commit.
- No mirror and no relay: dWellOiledMachine's memory-mirror point reads the feed.
- Records outside `MEMORY_ROOT`, and merge commits' own conflict resolutions: a merge's record
  changes are its parents' commits, which the walk lists.
- A landing that bypasses the lander (`git push --no-verify`) is not prevented. The next landing's
  walk appends its commits. S6 compares only up to the feed's newest record commit in R, so it names
  such a commit `missing` only once a later commit's event is in the feed.
- A default branch rewritten under force: a walk from a commit off the new history can list commits
  the feed already holds.
- Fixing the census's limb-2 hit at `tools/push-main.sh#check_landing_verdict` (§2).

### Edges

- **consumes-from** `TOOL-dTotalRecall-2` — `gov_record.py`, whose `new <kind>` writes the record the fixture commits and lands, so a door-made and a hand-made commit are seen joining the feed alike

## 4. Design

### The line

```
18	refs/heads/main	record	9f2c41e0…	5c1d77ab…	2026-11-02T10:14:03Z
```

`blob` is the record file's blob from the `--raw` line's new-object field, so the walk spawns no
process per file. A delete carries `-`, as a ref deletion does in the block's own lines.

### One core, two appenders

`add_feed_event` appends one line under the node lock after an `awk` key test over the whole log.
Called once per event, a first walk over gov's history would run that test 68,698 times (PINNED,
measured 2026-11-22 at `4ddb0f115`: 68,698 record events over 9,738 record-touching commits, walked
and built in 1.03 s). So `write_feed_lines` takes the lock once per call, and `add_record_events`
hands it every row of the range at once. The core stays the block's single append path: the node
lock of TOOL-dPlacedRequest-24, the counter rule, and the NOTE-and-0 failure rule. The
append-once read of TOOL-dPlacedRequest-27 stays `add_feed_event`'s own builder.

### Why the walk starts at the feed

The lander knows the remote's tip before its push. A walk from that tip would skip commits another
node landed that this node only fetched, and every check on this node would then name them
`missing`. Starting at the newest record commit the feed holds covers them, and S6 compares only up
to that commit. A node's feed is everything it recorded.

### The lock's hold

The walk runs under the node lock, so the first walk is the longest hold the lock covers: 1.03 s
over gov's history (PINNED, 2026-11-22, above), under `tools/lib/gov-feed.sh#NODE_LOCK_BOUND`'s 10 s.
The builder re-measures it on its node and adds it to that bound's comment beside the offline
write's hold, which the comment requires of every section the bound covers.

### Inventory

Minted: the functions `write_feed_lines`, `add_record_events`, `derive_record_events` and
`read_record_root`, the census list `FEED_LANDING_PUSH_FNS`, the event kind `record`, the finding
`unread`, `check_feed`'s record arm and `scan_feed_writers`' landing arm. Naming cells: `write`,
`add`, `derive` and `read`, each a verb of `.lexicon.conf`'s VERBS table. No name collides with a
function in any carrier (DERIVED: `git grep -nE` over `tools/`, `skills/` and `.githooks/`, none).

### Migration

A node's first landing after this unit appends every record event in its history once, each
`seen-utc` that landing's time. `unattended.sh --feed rebuild` on a node with no feed writes the
same events after the ref events.

### Rollout

Live on landing, wherever the lander runs. The kit version markers of the kits whose bytes move are
moved in the same commit, as the `kit epoch` leg requires.

### Alternatives rejected

- **Append from a post-commit hook.** It fires for an unlanded commit, which the clause keeps out,
  and a rebase would leave events for commits that never land.
- **Walk from the tip before the push.** It skips fetched landings, as "Why the walk starts at the
  feed" shows.
- **A seventh field for edges.** It changes the block's line for every reader, and the blob already
  names the bytes the edges are read from.
- **Call `add_record_events` inside `write_effect_push`.** One site, but its push names its refspec
  as `"$1"`, so no census can tell a landing push there from any other.

## 5. Production-readiness checklist

- security — no new write path beyond the node-local feed file the block already writes; the walk
  reads git objects only, and the conf is sourced in a subshell as the kickoff engine sources it.
- perf / scale — one `git log` per landing over the new range; the first walk is 1.03 s (§4). The
  first walk grows gov's feed by 9,055,470 B (PINNED, 2026-11-22, the built rows' size), and
  `add_feed_event`'s key test over a log that size took 37 ms (PINNED, 2026-11-22, node d).
- error / empty / loading states — a lock, walk or write failure prints the block's NOTE line and
  returns 0, since the landing has already happened; the next landing's walk appends what was
  missed.
- observability — `--feed check` prints each `missing`, `extra` and `unread` record finding.
- risks — the feed is append-only by TOOL-dPlacedRequest-13's non-goal, so no rotation applies; the
  core's extraction touches every governance write's append, which the block's existing arms hold.
- testing — AC1 to AC11 by a pass; the arms of §7 at the close.
- migration — the first landing's backfill, as §4 says.
- user docs — `help/loop.md`'s change-feed paragraph, and the verb and stop guides' `--feed` and
  section 7 text, each naming record events.

## 6. Acceptance criteria

- **AC1** — When a probe sources `gov-feed.sh` in a fixture repository under `%TEMP%` holding three
  commits (one of a record written through `python gov_record.py new research --name <stem>` in a

  file of the first two commits, each naming `git rev-parse <commit>:<path>`, and none for the third.
  Red when: an event names the commit's tree or an abbreviated blob, or the third commit appears.
- **AC2** — When the same `add_record_events` call runs twice, and when a second clone lands a
  record commit that the fixture fetches before its own landing, the feed holds each event once,
  and the fetched commit's event sits before the fixture's own.
  Red when: a repeated call appends a duplicate key, or the walk starts at the pre-push tip and skips
  the fetched commit.
- **AC3** — When a record file is written and left uncommitted, and `check_feed`'s record arm runs,
  the feed holds no event for it and the check exits 0; when a `record` line naming a commit on no
  branch (a `git commit-tree` object) is appended by hand, the check exits 1 with `extra`.
  Red when: an uncommitted write appears, or a planted off-history event passes.
- **AC4** — When a hand commit touching a record lands with `git push --no-verify`, a later landed
  commit's `record` line is appended by hand in the six fields, and `unattended.sh --feed check`
  runs, it exits 1 naming the hand commit `missing`.
  Red when: a landed record commit the live feed lacks passes the check.
- **AC5** — When `add_record_events` runs over a fixture history of 2,000 record commits built by
  one `git fast-import`, a wrapper counting calls sees `write_dir_lock_wait` once and
  `add_feed_event` never, the new `seq` values run unbroken, and `gov-feed.seq` holds the last.
  Red when: it appends through one `add_feed_event` call per event.
  figure: 2,000 is the fixture's size, PINNED; it stands for gov's measured 68,698 events.
- **AC6** — When `scan_feed_writers` reads the census population (every tracked `*.sh` and hook less
  the suites), it prints no line ending ` landing`; with a scratch file
  holding a function that runs `git push "$remote" "HEAD:refs/heads/$def"` and no
  `add_record_events` call, it prints that file and line with ` landing`; and with
  `FEED_LANDING_PUSH_FNS` naming no function of the files read, it prints that entry.
  Red when: the landing arm is absent, or reads no line and passes on an empty population.
- **AC7** — When `push-main.sh` lands a fixture branch carrying a record commit, once through
  `--land` and once through the attended path, the fixture's feed gains that commit's `record`
  events each time.
  Red when: either success branch lacks its `add_record_events` call.
- **AC8** — When one commit deletes two record files and adds two byte-identical ones, the walk
  appends one `-` event and one event for the shared blob, and `check_feed` over that feed prints no
  `duplicate` and exits 0.
  Red when: the walk appends one event per file, so `check_feed` names `duplicate`.
- **AC9** — When `unattended.sh --feed rebuild` runs on a fixture node with no feed, whose remote
  default branch's tracking ref carries record commits, the feed holds the derived ref events and
  then those commits' `record` events, and `--feed check` then exits 0.
  Red when: the rebuild writes no record event.
- **AC10** — When the fixture's conf sets `MEMORY_ROOT=../x`, `add_record_events` appends nothing
  and prints one `feed: NOTE -` line, and `check_feed` over a feed holding a `record` line exits 1
  with `unread`.
  Red when: the walk runs over the refused value, or the check passes.
- **AC11** — When the carrier-alone arm sources each carrier's block copy under `set -u` in its
  scratch repository, whose commit touches a file under its memory root, `add_record_events` grows the log by one
  line in each.
