## 2. Scope (IN)

Preconditions this unit calls and does not build: `check_cause_writers`, `CAUSE_WRITER_KEPT` and

and `id_grammar.py#parse_id_parts`.

- **S1** — The census reads the instruments. `check_cause_writers` in
  `tools/memory-tree/record_causes.py` also reads every tracked `*.py`, `*.sh` or `*.js` file under
  `<memory root>/builds/*/build/`, the root `record_kinds.py#read_memory_root` reads, each glob through
  `record_kinds.py#read_tracked`, test-named files excepted as unit 36 S7 excepts them. Such a file is
  a record whose own binding sits in its first `BIND_HEAD_LINES` lines (`tree_lib.py#BIND_HEAD_LINES`,
  the window `tree_lib.py#read_bindings` reads), so both census tests read it past that window: it is
  a census file when it spells a `**Serves:** ` literal there and no `Caused-by` there. Each is
  disposed as unit 36's are, by `CAUSE_WRITER_KEPT` keyed by its repository path, or by S2's row. A
  kept build-folder file carries one of two reasons: `pinned instrument`, for a file the dClosedLoop
  packet's `INSTRUMENTS` names, or `outside the write set`, for any other, the reasons
  `TOOL-dTotalRecall-55` S3 carries into its table. Its lines take unit 36's shape, and its count line
  counts the build-folder files apart. Observed by AC1.
- **S2** — The pinned-writer row. `CAUSE_WRITER_PINNED` in the same module holds one
  `(instrument, glob, ask id)` row per pinned instrument that writes a record with no cause: the
  instrument's repository path, the glob of the records it writes, and the id of the ask that asks its
  owner for the line. The deviations row's glob is `memory/builds/*/build/*-build-*-departures-*.md`,
  the name `deviations.py#derive_report_path` gives the record. A row is red, named with its ask id,
  when its instrument is not tracked; when the instrument spells `Caused-by` past its binding window
  (drain the row); or when its ask id is not a filed ask, one `backlog.parse_file` reads as an ask of
  the `BACKLOG.md` of the build `parse_id_parts` names in the id. The rows are read only where
  `--check` is armed: an adopter's tree holds no `legacy-records` registration and prints `unarmed`
  (`TOOL-dTotalRecall-19` §3). Observed by AC1 and AC2.
- **S3** — The interim read. A record a standing row's glob matches, with no legacy row and no
  `Caused-by`, is read as caused by its first Serves id, bare, in `check_causes` and in
  `check_orphans` alike, one reading both take: the cause must resolve, as `TOOL-dTotalRecall-19` S8
  grades a typed kind whose fields declare none (its §8 F7 (d)), and the orphan walk reaches the record
  when that unit is reached. A record outside every row's glob is graded as before. Observed by AC3.
- **S4** — The ask. One ask filed by the record door,
  `python tools/memory-tree/gov_record.py new ask --build dClosedLoop --family PLAY --text <text>
  --sev LOW <why> --clause accept <value>`, which writes its ask row and its `SEV` row into
  `memory/builds/dClosedLoop/BACKLOG.md` under an id the `PLAY` counter mints; the README's write rule
  admits an ask in another build's `BACKLOG.md`, and `memory/backlog/PLAY.md` is a shared render. Its
  text: the departures instrument writes `**Caused-by:** <first>` on the line after its Serves line,
  and its owner repins it with `packet.py --repin`. Its accept clause: a departures record the
  repinned instrument writes carries that line, and the causes check's pinned-writer row for it is gone.
  Neither spells a chain build's slug, so the packet's `read_asks` lists it in no chain packet and no
  packet moves. The severity is §8 F3's. Its id is the one S2's row names. Observed by AC1.

### Alternatives rejected

- **Hand-backfill the departures record.** Its `--check` re-renders it and compares bytes.
- **Seed the departures record into the legacy population.** It does not exist at the seed, and the
  ledger is shrink-only.
- **Read the build folders' `.py` files alone.** The class is the build folders' scripts; a `.sh` or
  `.js` one that writes a record would escape, and the two globs cost one `git ls-files` each.

## 5. Production-readiness checklist

- security — no new write surface: one ask through the existing door and one constant.

- migration — none.
- user docs — none under `help/`.
