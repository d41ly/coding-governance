### H4. The restore listing runs with rename detection, so a deleted record can go unlisted (id 15)

- **Where:** spec 92 §4 "The restore" (lines 354 and 358) and §6 AC11.
- **What is wrong:** the listing `git log --diff-filter=D --format='%H' --name-only 462d20f3..HEAD -- '<build>/*-deviation-*.md'` runs with git's default rename detection. Suppose a record is deleted in the same commit that adds a similar file. Git shows that as a rename (R), not a deletion (D). Deviation records share most of their template, so another record written in that commit can be similar enough. The companion `git diff --name-only --diff-filter=M` has the same exposure.

Today the listing prints nothing either way, because no deletion has happened yet.
- **Fix (skeptic: SOUND):** spell the listing `git log --no-renames --diff-filter=D ...`, and the companion `git diff --no-renames --name-only --diff-filter=M`. Add an AC11 fixture: a scratch repo where one commit deletes a record and adds a near-copy, and the listing must name the deleted path.
- **Left-shift gate:** a spec lint over probe fences that flags any `git log` or `git diff` that carries `--diff-filter` without `--no-renames`.

### H5. Every tip-scan criterion is the absence of a line, so a scan that crashes passes them all (id 29)

- **Where:** spec 92 §4 "The tip scan", and §6 AC8, AC11, AC15, AC16, AC18 and AC22.
- **What is wrong:** each criterion asks only that the scan print no `malformed`, `untracked`, `shared-n` or `dup` line, or at most one `by` line per unit. - **Consequence:** in several cases the scan exits non-zero with empty stdout:
  - it is run from outside the repository root;
  - a record is not UTF-8, or `read_record` raises on it;
  - the bare `python` is the MS-Store stub.

  In each case, AC8, AC11's dup half, AC15, AC16, AC18 and the tip half of AC22 certify a folder the scan never read.
- **Fix (skeptic: UNSOUND, corrected fix written here):**

  - The scan prints a `records <n>` line, which must equal the glob count.
  - The counts on its `by` lines must sum to the number of live records.
  - A read failure prints `red unreadable <path>`.
  - The scan runs through the python that tools/lib/resolve-python.sh resolves.
  - The build stages the break: it runs the scan from outside the repository and observes the criterion read red.
- **Left-shift gate:** a checklist entry: "a criterion stated as the absence of output also requires exit 0 and a positive population count". The failure-envelope lens checks it against every "prints no X line" criterion.
