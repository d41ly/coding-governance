## 1. Goal

A scalar pin over a population is a waiver: a fixed offender and a new one net to zero, so the pin
reads green while the set it bounds changes (gap-test-16). This unit replaces the seven record and row
pins of `.memory-tree.conf` and `.codebase-map.conf` with populations keyed by the records or rows they
count, registers the two unset ones unseeded, and registers every date cutoff in the tracked confs as a
`cutoff` population whose date may never move later without a widen record (retrofit.md:285-303).

## 4. Design

### The pins

| Pin | Value at `19d6aae6` | Population | Key kind · fields | Read by |
|---|---|---|---|---|
| `ORPHAN_ID_PIN` | 0 | `id-orphan-waiver` (unit 16) | record · id | `corpus_ids.py` checks 13-15 |
| `DEAD_PATH_PIN` | 0 | `corpus-path-unresolved` (unit 16) | site · citing path, cited path | `corpus_ids.py` |
| `ROW_DUPLICATE_PIN` | 3 | `row-duplicates` | record · shard, row key | `row_grammar.py` check 20 |
| `RECORD_UNBOUND_PIN` | 16 | `unbound-records` | record · record path | `check-memory-hygiene.sh` check 21 |
| `DOSSIER_DECISIONS_EMPTY_PIN` | 16 | `dossier-decisions-empty` | key · feature | `test_codebase_map.py` |
| `SEVERITY_UNLABELLED_PIN` | unset | `severity-unlabelled`, unseeded | record · shard, row key | `row_grammar.py` |
| `LIVE_ROW_PIN` | unset | `live-rows`, unseeded | record · shard, row key | `row_grammar.py` |

Values PINNED at `19d6aae6` (2026-10-25). A pin of 0 over a waiver already keyed by the offender is
the waiver's own both-ways rule, so the two zero pins fold rather than mint a population; the three
counted pins become their offenders' keys, seeded at the base so their rows number what the pin did
(`row-duplicates` 3, `unbound-records` 16 and `dossier-decisions-empty` 16 at `19d6aae6`, re-measured
by the seed at the build run's base).

### The cutoffs

```
# ledger · date-cutoffs · key cutoff conf,key · direction ceiling · drain none
.memory-tree.conf	SPEC_TIER1_CUTOFF	20261010	<base sha>	seeded
.unattended.conf	PASS_ORDER_CUTOFF	<date>	<base sha>	seeded
```

At `cdfbd1cf` and `19d6aae6` the tracked root confs hold 36 cutoff keys, 26 in `.memory-tree.conf` and
10 in `.unattended.conf` (PINNED, measured by `grep -cE '^[A-Z0-9_]+_CUTOFF='`); the seed derives
the set at the build run's base, so the row count is never typed. The rule matches drift's
`build_cutoff_keys_armed` (`tools/drift-audit/drift_report.py:2158`), which reads every tracked root
`.<name>.conf`, and a cutoff a new conf adds is a measured key with no row, red in `ratchet (both
ways)` until its row is written through the widen route or a seed.

### Alternatives rejected

- **A cutoff keyed by its date.** A date moved earlier would read as a gained key, and retrofit.md:298
  admits it; the count field, as a ceiling, holds "never later" exactly.
- **One population per conf's cutoffs.** A conf that later gains a cutoff would need a registration
  first; one population over every tracked root conf is the class.
- **Keep the two zero pins as arming switches.** A `*_PIN` key whose value no longer bounds anything is
  a name that says the opposite of what it does, and the `ratchet` pack's scalar leg would read it as a
  pin.

## 5. Production-readiness checklist

- security — no new write path beyond the factory's atomic writer and the seed verb.
- perf / scale — each check reads one population file where it read one conf key.
- error / empty / loading states — an unseeded registration reads `unarmed`, never green; a check whose
  population is `unarmed` says so where it said the pin was unset.
- observability — each check prints its population's count where it printed the pin.
- risks — checks 13-15 now arm on a seeded population, so an adopter whose seed fails reads them
  disarmed with the seed's reason, which is the state an unset pin gave it.
- testing — AC1 to AC10; the arms in §7 are observed RED then GREEN by the main loop at the close.
- migration — §4 and S8.
- user docs — `tools/memory-tree/README.md`, `memory/HYGIENE.md` through its template and
  `WIRE-INTO-PROJECT.md` replace each pin's instructions with its population; no page under `help/`
  documents a pin.
