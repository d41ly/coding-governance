## 1. Goal

A leg has a name and nothing that says what it is for: the project map's purpose table lists the leg
as the one namespace whose source is "none: the leg has a name only", and assigns "`purpose` in
`gate-legs.json`" to this build (`memory/builds/dClosedLoop/build/2026-10-17-build-PLAY-dClosedLoop-1-project-map.md:654`).
This unit adds the field, reviews every leg the manifest holds at the build run's base, derives each
purpose from what the leg already carries by the rule §4 states, and puts every leg the rule cannot
reach to the owner instead of guessing (PM-5, v2:390).

## 4. Design

### The rule

Each leg's purpose comes from the first of these steps that reaches it. A step reaches a leg when its
source exists and says something about this leg that it does not say about every other leg running
the same gate script.

| Step | Source | Reaches |
|---|---|---|
| 1 | the parenthetical in the leg's `name` | 22 legs at `19d6aae6` (PINNED, 2026-10-25): it names the defect the leg catches |
| 2 | the comment block directly above the leg's `[[gate_leg]]` row in its descriptor | a descriptor-claimed leg whose row carries one |
| 3 | the gate script's header, its module docstring or leading comment, first sentence, qualified by the `argv` word that tells this leg from every other leg running that script | every leg: each of the 142 rows names a tracked script carrying a header, and every pair of legs sharing a script differs by a mode flag or a target path (PINNED, 2026-10-25, measured over `tools/gate-legs.json` at `19d6aae6`) |
| 4 | the `title` of the dossier whose `[claims] gate-legs` names the leg, qualified as in step 3 | 122 legs at `19d6aae6` (PINNED) |
| — | none of the four | put to the owner (S6, S7) |

The pass reads each source and writes at most 60 characters that say what the source says, citing it.
The 60 is the project map's line grammar, `purpose := at most 60 characters, verbatim from the
namespace's declared purpose source` (project-map.md:555): the field is that declared source, so the
map renders it verbatim. Two worked rows, from the tree at `19d6aae6`:

| Leg | Step | Source | Purpose |
|---|---|---|---|
| `charter size` | 3 | `tools/check-template-size.sh:2`, argv word `AGENTS.md` | `caps the charter's bytes at its declared ceiling` |
| `shell hygiene (a fork spent on builtin work)` | 1 | its name | `catches a fork spent on builtin work in a shell file` |

What no probe sees: whether the 60 characters say what the cited line says. The closing review reads
the record's rows against their cites; the probes of §6 see presence, shape, uniqueness and that each
cite resolves.

### The review record

```
| Leg | Purpose | Step | Source |
|---|---|---|---|
| charter size | caps the charter's bytes at its declared ceiling | 3 | tools/check-template-size.sh:2 |
```

One row per leg of the base manifest, a leg name escaped where it holds a `|`, then a section "Put to
the owner" listing each underived leg with what each step found, or `none`. `**Serves:** research
TOOL-dWitnessedBar-19`. The record cites; it is never read by a gate.

### The 7h arms

Read from the manifest, as `subject` is, so the 74 `[[exempt_leg]]` legs are graded by the same arm as
the 68 claimed ones (`selfcheck` notes `legs: 142 in the manifest · 68 claimed · 74 exempt` at
`19d6aae6`, PINNED). Each finding names the leg and the arm:

| Arm | Red on |
|---|---|
| presence | a manifest row with no `purpose` whose name is no row of the pending population; a pending row whose leg carries a `purpose` or is no longer in the manifest |
| shape | a `purpose` that is not a string, is empty, exceeds 60 characters, holds a line break, or has leading or trailing space; two legs carrying the same `purpose` |
| agreement | a descriptor `[[gate_leg]]` whose `purpose` differs from its manifest row's, or is present on one side only |

The pending population is read through the factory's reader, never parsed here; while it has no
file, the presence arm has no exception list at all.

### Inventory

Minted: the row key `purpose`; the `LEG_KEY_FLOORS` row `purpose`; the 7h arms of the table above and
the note field `purposes`; the record `…-TOOL-dWitnessedBar-19-purpose-review.md`; conditionally the
population `leg-purpose-pending` and its file. Naming cells: none minted as a function; a helper the
pass adds to 7h is asked of `python tools/lexicon/lexicon.py --suggest <name> --as py.function`.

### Migration

Additive. Every row gains one key. The runner's held-tier row hash is the SHA-1 of the whole row as
sorted JSON (`tools/run-gates/run-gates.sh:2852`), so every held record earned before this commit reads
stale once and is re-earned; no reader of the hash compares it to anything older. A target's canary
below the `purpose` floor never receives the key (S8).

### Rollout

Live at landing. The pass runs `python tools/run-gates/owed_rows.py --base HEAD` before its commit, the
rule PLAY-dOrderedCharter-50 S6 hands every key-adding unit, and writes the rows it names. The run-gates
kit's version moves with its canary's key set, which is what the `purpose` floor row names.

### Alternatives rejected

- **The dossier title first.** A dossier claims every leg of its feature, so its title states the
  feature's purpose; 122 legs would share far fewer distinct values, and S2's uniqueness half exists to
  refuse exactly that.
- **A sentinel value for an underived leg** (`"?"` or `null`). A new leg could declare the sentinel and
  pass; telling a pending leg from a new one needs the base, which is what a `shrink-only` population
  already compares against.
- **Purpose in the manifest only.** The emitter builds an adopter's rows from the descriptors, so the
  field would never reach an adopter's map; `doc_reads` took the same two-spelling route
  (TOOL-dThriftyLanding-4) until unit 11 folds them.
