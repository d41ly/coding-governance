## 1. Goal

The round-1 spec audit (`memory/builds/dWitnessedBar/reviews/2026-10-25-review-TOOL-dWitnessedBar-1-spec-audit-round1.md`)
confirmed finding **id 63 at HIGH**, its item **H4**, alone in that item. `TOOL-dWitnessedBar-6` S6 and
S9 apply the source rule, the pin over `verdict.remote.pin-scope`'s files, to `remote-ci` alone; it
answers gap-test-11, a verdict whose definition sits in the tree it judges. `verify-peer` (S5) runs the
candidate's own runner and manifest, and the tag it pushes carries a free-text `node` line any holder of
the push grant can write. Under `verdict = peer-node`, also `TOOL-dWitnessedBar-2`'s off-node witness for
`hooks.bypass = refused`, a candidate that empties `tools/gate-legs.json` gets a peer GREEN, and a landing
node can push its own `refs/gov/verdict/<sha>` naming another node. This unit takes the report's fix. It
repairs `TOOL-dWitnessedBar-6`.

## 2. Scope (IN)

- **S1** — The source rule for `peer-node`. `read_peer_verdict` applies the same source check
  `read_remote_verdict` applies (S6 of unit 6), today inline in its body
  (`tools/run-gates/remote_verdict.py#read_remote_verdict`): the files `read_scope_paths` derives from
  `verdict.remote.pin-scope` derive at the SHA, through `derive_pin`, the id `verdict.remote.pin` holds,
  as `verdict.remote.trust` says, the three keys read once by `read_remote_keys`. That check becomes one
  function, `check_pin_source(backend, sha, keys, repo=".")` in `tools/run-gates/remote_verdict.py`,
  `keys` being `read_remote_keys`' triple, which both readers call: it returns `HELD` naming the pinned
  files and both ids where they differ, `HELD` with `no pin` where no pin is set, `GREEN` witness
  `claimed` under `app-only`, `GREEN` witness `witnessed` where they derive the pin, and raises
  `DeadProbe` for a SHA the clone lacks. `read_remote_verdict`'s early no-pin return becomes that
  function's no-pin `Verdict`, so the wording is written once and every `remote-ci` state is unchanged.
  Under `peer-node`, a `verdict.remote.pin-scope` of `workflow` reads `HELD` naming the key, outside
  `app-only`, because that scope pins only `.github/workflows/remote-ci.yml`, which no peer runs (§8
  F4). The peer reader reaches the module through `read_remote_module`
  (`tools/run-gates/verdict_backends.py#read_remote_module`). Observed by AC1.
- **S2** — The signer list. A policy key `verdict.peer.signers`, set-valued, each member one allowed
  signers line `<node tag> <key type> <base64 key>` and no options field (§8 F3), joins `OWNER_ONLY_KEYS`
  (`tools/loop/guard.py#OWNER_ONLY_KEYS`, unit 6 S9), so the guard's owner-only step refuses an agent's
  staged change to it as it refuses one to `verdict.remote.pin`: admitted only from the owner's terminal
  or on a live run's branch through the loop kit's `policy_edit.py set`, unit 6 §8 F7's admission. Its
  catalogue row in `tools/policy/catalogue.toml` has `allowed = { type = "set", item = <the line's
  pattern> }`, `empty = "never"`, a derived default naming none, `summary` and `usage`, the shape
  `charter.practices` carries. Observed by AC3.
- **S3** — The signed tag. `write_peer_tag` (`tools/run-gates/verdict_backends.py#write_peer_tag`), which
  today builds the tag with `git mktag`, creates it with `git -c gpg.format=ssh tag -s` under the
  operator's own `user.signingkey` and pushes its object as `refs/gov/verdict/<sha>` as before, leaving
  no local tag name behind. `run_verify_peer`
  (`tools/run-gates/verdict_backends.py#run_verify_peer`) refuses beside its `GOV_NODE` refusal, before
  any `ls-remote`, exit 2 naming `user.signingkey` when `git config user.signingkey` reads empty. Observed
  by AC2.
- **S4** — The reader verifies the signer. `read_peer_verdict` reads `verdict.peer.signers` at the
  landed revision through `read_policy_value` (`tools/run-gates/verdict_backends.py#read_policy_value`),
  the read `read_remote_keys` makes, never from the working tree or the candidate; that function gains a
  keyword returning every line `policy.py get` prints, a set printing one member per line
  (`tools/policy/policy.py#cmd_get`). It writes the members to a temp allowed-signers file under the
  clone's common git dir and runs `git -c gpg.ssh.allowedSignersFile=<file> verify-tag --raw
  refs/gov/verdict/<sha>`, whose verdict line git writes to standard error, which `run_git`
  (`tools/run-gates/verdict_backends.py#run_git`) does not return today, so it gains a keyword returning
  both streams. The verdict stands only when that exits 0, the `Good "git" signature for <principal>` line
  names a principal equal to the tag's `node` line, and that principal is not the reading node's tag. An
  unsigned tag, an unknown key or a principal that differs from `node` reads `NONE` naming why; a derived
  default refusal of the key reads `NONE` naming `no signer table`; any other refusal, or a verify that
  cannot run, reads `DEAD PROBE`. Observed by AC2 and AC4.

## 4. Design

### Evidence

- Unit 6 as landed (`0b7e0fceb`, `5b3fbe429`, red fix `b0e8c63b9`): `read_peer_verdict` stands when the
  fetched tag points at the SHA, its `tree` line is the SHA's tree, its `node` line is set and is not
  `GOV_NODE`, and its `verdict` line reads `GREEN`; it applies no source check and no signature check,
  as its module docstring's `WHAT THIS DOES NOT CHECK` names this unit
  (`tools/run-gates/verdict_backends.py#read_peer_verdict`). The source check sits inline in
  `read_remote_verdict` after its liveness check, its no-pin return before any API read.
- `write_peer_tag` builds the tag body by hand and writes it with `git mktag`, so it carries no
  signature (`tools/run-gates/verdict_backends.py#write_peer_tag`).
- The `peer-node` row in `tools/run-gates/kit.toml` declares no `workflow`, so `read_scope_paths` names
  `.github/workflows/remote-ci.yml` for it under `workflow`, and under `dispatch-closure` adds this kit's
  `run-gates.sh`, the leg manifest and `.githooks/gate-env.sh`
  (`tools/run-gates/remote_verdict.py#read_scope_paths`).
- The guard's owner-only step tests `k in OWNER_ONLY_KEYS`, a whole-leaf match
  (`tools/loop/guard.py#check_staged`), and `derive_leaf_changes` walks a table into one leaf per member
  while an array is one leaf (`tools/policy/guard.py#derive_leaf_changes`). The catalogue's `map` type
  admits only the literal values its `of` lists (`tools/policy/policy.py#check_member`).
- `git verify-tag --raw` over an SSH-signed annotated tag exits 0 and writes `Good "git" signature for
  <principal> with ED25519 key SHA256:<fp>` to standard error, nothing to standard output,
  `<principal>` the first field of the allowed-signers line whose key signed it; an unsigned tag exits
  non-zero printing `error: no signature found`; a key no line names exits non-zero printing `No
  principal matched.`; `git tag -s` under `gpg.format = ssh` with `user.signingkey` unset exits non-zero
  naming `user.signingKey` (measured on node d, git 2.54.0.windows.1, DERIVED 2026-11-20, in a scratch
  repository under the session scratch directory with throwaway keys). The principal comes from the
  owner's list and never from the tag.

### The read

```
read_peer_verdict(sha, tree):
  tag = fetch refs/gov/verdict/<sha>                      -> NONE when absent
  unit 6's tag checks (points at sha, tree, node set and not this node's)
  signers = read_policy_value(verdict.peer.signers, every line)  -> NONE "no signer table"
  verify-tag --raw against signers                        -> NONE "unsigned" | "unknown key"
  principal == tag's node line, != this node's tag         -> NONE "signer <p> is not node <n>" | "own verdict"
  verdict line GREEN                                       -> RED | DEAD PROBE as today
  keys = read_remote_keys; pin-scope workflow, not app-only -> HELD "verdict.remote.pin-scope"
  check_pin_source(backend, sha, keys)                     -> HELD "<file>" | HELD "no pin" | witness claimed
  GREEN, witness witnessed
```

The signer list is read at the landed revision, never from the working tree or the candidate, so a
landing node cannot add its own key by editing the tree it lands. A member carries no options field, so
no line the owner sets can grant `cert-authority` or a namespace.

| Plant | State |
|---|---|
| `peer-swapped-manifest` | a GREEN signed by node b's registered key whose candidate's `tools/gate-legs.json` blob differs from the pin under `dispatch-closure`: `HELD` naming that file; the same under `workflow`: `HELD` naming `verdict.remote.pin-scope`; the first under `app-only`: `GREEN` witness `claimed` |
| `peer-self-tag` | a tag whose `node` line reads `b`, signed by node a's key: `NONE` naming `a` |
| `peer-unsigned` | an unsigned tag from node b: `NONE` naming `unsigned`; then `verify-peer` with `user.signingkey` unset: exit 2 naming it |
| `peer-signed` | a GREEN signed by node b's registered key, pinned blobs equal: `GREEN` witness `witnessed` on node a |

Each plant generates its throwaway keys with `ssh-keygen -N ""` in its scratch directory, commits the
list and the pin on `main` before it pushes, so the landed revision carries them, and prints `not run`
when no `ssh-keygen` runs. The existing `peer` plant is re-planted over the same signed, pinned setup,
its three states unchanged.

### Alternatives rejected

- **The peer runs its own default-branch runner and manifest on the candidate.** The legs' scripts
  still come from the candidate, so the pin's file set would be bypassed by editing a leg's script; one
  source rule for both backends is one fact.
- **A signer list tracked as a plain file.** Any pusher can edit it in the tree it lands; a policy key
  under `OWNER_ONLY_KEYS`, read at the landed revision, is written only through the terminal proof.
- **GPG signing.** It needs an install the fleet does not carry; SSH signing uses git's own verifier and
  the `ssh-keygen` Git for Windows ships.
