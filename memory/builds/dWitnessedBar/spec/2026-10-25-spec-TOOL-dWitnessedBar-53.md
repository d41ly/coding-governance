```

cp .memory-tree.conf.example S/.memory-tree.conf; append FOO_PIN="3"   (untracked, §8 F3)

keys-not-scalar exits 0 naming FOO_PIN              # S3, after
for p in P: remove its home; seed --population p
for p in P: key and count columns of the new home == the saved home's     # S1
```

SHA of `TOOL-dWitnessedBar-61` and the re-seed stamps the new commit.

### Alternatives rejected

- **P from a `seed --all` listing run's `present` lines.** It lists the read-back homes the scaffold
  writes by shell, which no re-seed can rebuild once removed (§8 F4).

## 5. Production-readiness checklist

- risks — a registration whose seed is not deterministic across a commit reds the arm; that is the

- testing — AC1 to AC3 by fixture; the arm of §7 at the close.
- migration — none.
- user docs — none.

## 6. Acceptance criteria

- **AC1** — When the arm's scaffold runs in a scratch target with nothing committed, its output names
  `armed conf-scalar-pins`, and after the commit, with each home of P removed and re-seeded by
  `python tools/memory-tree/legacy_ledger.py seed --population <p>`, each home's key and count columns
  equal the saved copy's.
  Red when: a seed reads tracked files only, so the home before the commit is empty and the re-seed is
  not; or no `armed` line is printed and the arm passes over nothing.
  fixture: a scratch `git init` target under `%TEMP%/<short-name>`, built by the suite, its kit copy
  staged and its conf untracked.
- **AC2** — When the kit copy's `python ratchet.py keys-not-scalar` runs at that scaffold's root before
  the commit and after it, each run exits 0 and names the planted `FOO_PIN` row.
