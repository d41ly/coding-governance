### H1 — AC12 plants its only CR on a `verdict` line the hook never reads, so the staged red "removing the hook's CR strip" cannot turn the arm red (id 6)
- **Where:** spec-65 §6 AC12, the §7 `run-gates.gov.test.sh` arm, and §2 S15.
- **What is wrong:** AC12 says the hook's `read_green_file` reads `GREEN` from a planted `verdict<TAB>GREEN<CR>` line. `read_green_file` (`.githooks/pre-push:1350-1369`) sets only `rec_sha`, `rec_fp`, `rec_blob`, `rec_man`, `rec_st`, `rec_reused` and `rec_reused_cache`. It reads the keys `sha`, `fingerprint`, `manifest_blob`, `manifest`, `selftests`, `reused` and `reused_cache`, and no `verdict` key. No sibling spec adds one: unit 63 S19 changes only how the existing keys are read. In the planted record the only CR sits on the `verdict` line, and the `sha` lines carry none.
- **Consequence:** The hook's CR strip that S15 requires is never exercised. A scratch copy with the strip removed leaves the arm green, so the arm certifies a strip it does not test. A builder will notice the hook half cannot pass, so this is not a silent false green. It still pushes the build toward either unscoped behaviour or an arm that tests nothing.
- **Fix (skeptic: sound):** Plant the CR on a key `read_green_file` actually reads. For example, make the second `sha` line `sha<TAB><40-hex><CR>`, or use `fingerprint<TAB>...<CR>`. Assert that `rec_sha` equals the bare hex with no CR, and that `read --backend local-hook` reads the same value. Keep `verdict<TAB>GREEN<CR>` for the local-hook reader only. Before claiming the arm, the build must observe the staged red with the hook's CR strip removed in a scratch copy.
- **Left-shift gate:** add a checklist entry, "a staged red whose plant sits on input the changed code never reads". The spec audit should require each staged break to name the variable or output the plant reaches.

### M5 — Unit 64's corrupt fixtures inherit the machine's default branch name and ref backend (id 13)
- **Where:** spec-64 §2 S4 (fixture table, lines 51-56) and §4 Evidence.
- **What is wrong:** S4 builds its corrupt fixtures by writing loose ref files under `.git/refs/heads/` and `.git/HEAD` in a plain `git init`. The spec never makes the backend explicit, even though its own §4 Alternatives (lines 131-133) says reftable repositories exist. Run section `2l`'s git calls with `GIT_CONFIG_NOSYSTEM=1` and `GIT_CONFIG_GLOBAL` pointed at an empty scratch file. State in S4 that the fixtures are files-backend by construction.
- **Left-shift gate:** a lint over the test suites: every `git init` in a suite passes `-b` (or `-c init.defaultBranch=`), and a suite that writes under `.git/refs/` also passes `--ref-format=files`.

### M8 — S10's existence check resolves a hex-spelled `--sha` that is also a ref name to that ref's commit (id 17)
- **Where:** spec-65 §2 S10 (lines 94-98) and §6 AC8.
- **What is wrong:** S10 checks `--sha` with `git rev-parse --verify --quiet <sha>^{commit}`. Where a branch or tag has an all-hex name, git resolves the ref instead of the abbreviated object. In a scratch repo with `git branch deadbeef HEAD~1`, both `deadbeef^{commit}` and `DEADBEEF^{commit}` printed HEAD~1's SHA with rc=0. A branch named with HEAD's own first 8 hex characters, pointing at HEAD~1, made `rev-parse --verify '6bb74eb5^{commit}'` print HEAD~1, not HEAD. Unit 63 AC23 forbids stamping a symbolic `--sha`.
- **Consequence:** The seed records a baseline SHA other than the object the operator abbreviated, and later compares (unit 14 S9) read it as the population's origin. AC8 builds no hex-named ref, so the arm cannot red. The path is narrow and the stamped value is still a real commit, so the effect is contained.
- **Fix (skeptic: sound):** After `rev-parse` succeeds, S10 should require the printed full SHA to start with the lowercased given hex, and otherwise exit 2 naming `--sha`. Alternatively, resolve through `git rev-parse --disambiguate=<hex>`, which reads objects only. AC8 should add a fixture with branches named `deadbeef` and `cafe1234` pointing at HEAD~1, and red when `seed --sha deadbeef` arms.
- **Left-shift gate:** a checklist entry, "a user-supplied object id resolved through a revision parser that also accepts ref names". Require a hex-named-ref fixture beside any such check.

### M9 — S11 hardens only the sweep's unlink, but its directory scan and age read can also raise under the same race (id 18)
- **Where:** spec-65 §2 S11 (lines 99-102) and §6 AC9 (lines 306-311).
- **What is wrong:** S11 says "each unlink catches `OSError`", and AC9 replaces only `os.unlink`. Unit 63 S20 requires removing temps "older than `PEER_SIGNERS_GRACE_S`", which needs an age read. `DirEntry.is_file` swallows `FileNotFoundError`, but `DirEntry.stat()` (a syscall on POSIX), `os.stat` and `os.path.getmtime` raise it when a concurrent reader has already unlinked the entry. S11's "the verdict never depends on the sweep" is stated as a goal, not as a clause that covers the stat.

Reader B lists `peer-signers-x`, reader A unlinks it, and B's stat raises before B reaches its guarded unlink. That traceback goes into the verdict read. AC9 cannot see it. The race is rare and the effect is one failed read, so it is contained.

Any other `OSError` writes one stderr line and the read goes on. AC9 should add a stand-in for the age read (`os.stat` or `DirEntry.stat`) that raises `FileNotFoundError` for one entry, and red when the read raises.
- **Left-shift gate:** a checklist entry, "a hardening clause names one call where the class is every filesystem call of the routine". The spec audit should list the routine's calls and check each against the clause.
