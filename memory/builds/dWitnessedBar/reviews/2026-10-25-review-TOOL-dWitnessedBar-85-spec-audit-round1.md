## Medium

### M1. Unit 87's staged `rec_fp` skip ignores 84 S14's visited count (ids 2, 6)

- **Where:** `spec-TOOL-dWitnessedBar-87.md` §2 S1, §4 Evidence (fifth bullet), §6 AC1, and the Edges.
- **What is wrong:** S1 and AC1 stage a `check_canary_keys` that skips `rec_fp` and require that no `rec_sha byte check` line prints. TOOL-dWitnessedBar-84 S14 makes the same function count the CANARY_KEYS pairs it visits and fail with `gov-canary: the canary visited <n> of <m> CANARY_KEYS pairs`. Unit 84 builds at order 44. Unit 87 builds at order 42, but its run happens at the close over the built tree, so S14 is in force. Unit 87 never cites 84 S14. It does not say whether the skip comes before or after the count. Its Evidence asserts that `rec_sha`'s variants are untouched by the break.
- **Consequence:** A skip placed before the count is exactly 84 AC14's staged "stops after the first pair" break, and it prints `the canary visited 1 of 2`. If that line enters the captured stdout, `check_canary_keys` on `rec_sha`'s mutant no longer outputs exactly `rec_sha`, as 88 S3 and 76/79/80 require. A `rec_sha byte check was not seen red` line then prints, and AC1 goes red on a correct build. If the line goes elsewhere, the break prints a third failure line that S2 never records in unit 76's ledger. Two builders staging the same named break can get opposite verdicts.
- **Fix (judged SOUND by the skeptic):** Add 84 S14 to §4 Evidence and to the Edges as consumes-from. In S1 and AC1, pin the break. One option: the skip suppresses only the printing of `rec_fp` after the visited count, so the canary still visits 2 of 2. The other option: require 84's `the canary visited 1 of 2` line, state the stream it prints to so it cannot enter the captured variable output (or relax AC1's `rec_sha` exclusion to match), and have S2 record that line in unit 76's ledger beside AC2. Correct the Evidence bullet.
- **Left-shift gate:** add a checklist item. A spec that stages a break inside a function must cite every sibling scope item that adds a check to that function, and must say where the break sits relative to each one.

### M2. 88 AC19 applies the platform rule to every line naming unit 81, not only the break records (id 1)

### M3. 88 S3's return contract for `check_canary_keys` omits 84 S14's visited-count failure (id 7)

- **Where:** `spec-TOOL-dWitnessedBar-88.md` §2 S3 and §6 AC3.
- **What is wrong:** S3 states "one return contract": 0 when nothing was printed, 1 when a variable was printed, 2 when any call returned 2. 84 S14 gives the same function a visited-count failure (`visited <n> of <m> CANARY_KEYS pairs`), and S3 does not mention it. AC3 never stages an emptied or partly visited CANARY_KEYS.
- **Consequence:** A run that visits 0 of 0 or 1 of 2 pairs and prints no variable returns 0, the pass code. A caller testing the code reads a skipped or emptied key list as a pass. 84 S14's failure then depends on a side effect that is lost in the `$(...)` subshell the loop captures through. No criterion catches this.
- **Fix (the finder's fix was judged UNSOUND because it allowed rc 2, which the liveness loop maps to 84 S13's read-failure reason; this is the skeptic's corrected fix):** Give the visited-count failure its own return code, 3, separate from 0, 1 and 2. Send the `gov-canary: the canary visited <n> of <m> CANARY_KEYS pairs` line to stderr so it never enters the captured variable output. Have the liveness loop and the canary treat rc 3 as a failure that prints that line, not the rc 2 read-failure reason. Add an AC3 clause: with `CANARY_KEYS` emptied in the probe, the cut `check_canary_keys` returns 3, not 0, and prints no variable on stdout.
- **Left-shift gate:** add a checklist item (class amendment-leaves-its-other-half-standing). A spec that restates a function's return contract must list every failure path that sibling specs give that function.

### M4. 85 AC1 stages only the length variant's failure, so the tail variant's gating is never observed (id 13)

### M5. 88 S10's widened match takes the prefix of an arm that carries a parameter modifier (id 14)

- **Where:** `spec-TOOL-dWitnessedBar-88.md` §2 S10, §5 risks, §6 AC10.
- **What is wrong:** S10's match makes `{` and `}` independently optional. So on `sha) rec_sha=${_rg_v%$'\r'} ;;` it matches the prefix `${_rg_v` and rewrites the arm to `rec_sha=${_rg_v:1}%$'\r'} ;;`. On `${_rg_v:-}` it produces `${_rg_v:1}:-}`. Each counts as a one-line change. The skeptic reproduced both. §5 claims that bash refuses every extra spelling the match admits, and these two are balanced and valid.
- **Consequence:** The "length variant" is seen red without isolating the count. One form fails both the count and tail tests; the other fails the tail test only (41 bytes after the canary's sed, not 43 as the finder said). A `-ge 0` break no longer reaches its reason, and the variant certifies isolation on a value that does not isolate it. The base unit 74 match failed such arms loudly with `changed 0 lines`; S10 makes the case silent. The path is narrow, because unit 69 S1 writes bare `$_rg_v` arms.
- **Fix (judged SOUND by the skeptic):** Close the match on a whole token: `\$_rg_v` or `\${_rg_v}`, followed by a required boundary `\([[:space:];"]\|$\)`, with no independently optional braces. Add an AC10 row: a scratch copy whose `sha)` arm reads `rec_sha=${_rg_v%$'\r'}` must give `variant changed 0 lines`. Strike §5's sentence that bash refuses every admitted extra spelling.
- **Left-shift gate:** add a checklist item. Every mutation regex in a spec must be probed against balanced modifier spellings (`${x%...}`, `${x:-}`) as well as the bare forms.

### M6. 86 AC1's exact-equality arithmetic rests on an unpinned placement of 84 S14's increment (id 16)

- **Where:** `spec-TOOL-dWitnessedBar-86.md` §2 S1 and §6 AC1, and 85 §2 S1 ("the loop's added count is therefore two for every pair").
- **What is wrong:** 86 requires a missing variant to move `a` by exactly the word count of CANARY_KEYS. 84 S14 also adds to `a` for `check_canary_keys`'s visited check. Neither 84, 85 nor 86 pins whether that check runs once or on every call. `check_canary_keys` is called on every variant's mutant.
- **Consequence:** If the increment sits in the function body and the function is called outside a `$(...)` subshell, a copy missing one variant also loses one visited increment per key. The difference is then twice the word count, and 86 AC1 goes red on a build that is correct by 84. The skeptic did not confirm the secondary claim about 86 S2: 84 builds after 82's pass commit.
- **Fix (judged SOUND by the skeptic):** In 85 S1 and 86 S1, pin the arithmetic to the increments the specs name. One option: state that 84 S14's visited-count check adds to `a` once per pass of each loop, outside `check_canary_keys`'s per-call body, and add a grep criterion for that placement. The other option: derive 86's expected difference at observation time, as the per-variant increments plus any per-call increments the copy lost, and require it to be at least `${#CANARY_KEYS[@]}`. Record the observed difference in the ledger.
- **Left-shift gate:** add a checklist item. An AC that asserts an exact counter delta must list every scope item in the build that increments that counter, and must pin where each increment runs.
