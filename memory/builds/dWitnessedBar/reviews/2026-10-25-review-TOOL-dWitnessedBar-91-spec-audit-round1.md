## High

### H1. The note check reports a correct note as MISPLACED when one label and token answer two criteria (id 1)

- **Where:** spec-92 §4 The note table and The note check; §6 AC4 and AC12; §5 risks.
- **What is wrong:** Five `92|S4` rows share one label (`TOOL-dWitnessedBar-92 S4`) and one token (`resolve_python:`) across two answers in the same ledger. In unit 88's ledger they answer AC6 and AC18, and in unit 89's they answer AC9 and AC12. For each row, the awk prints the opener of every line that carries the label and token, so it collects both `- AC6` and `- AC18`. `grep -qvE "^- (\*\*)?AC6[^0-9]"` then matches the AC18 opener and prints `MISPLACED`. The skeptic reproduced this: correct notes under both 88 AC6 and AC18 printed `MISPLACED 92 S4 resolve_python:` twice, exit 1. §5's claim that "a row whose token two notes carry passes on either" is false.
- **Consequence:** A correctly built unit 92 fails AC4 (`NOTES OK 5`) and AC12 (`NOTES OK 29`). To get green, a builder would have to drop or merge correctly placed notes, which undoes S4's per-criterion record of each derivation run.
- **Fix (judged SOUND by the skeptic):** Make the placement test pass when at least one selected note sits under the row's `- <answer>` line, and report MISPLACED only when none does. Alternatively, give each S4 row a token unique to its answer, for example `resolve_python: (88 AC6)`, and spell the notes to match. Then add a fixture to AC4 with correct notes under both 88 AC6 and AC18 that must print `NOTES OK 2`, and correct §5's risk line.
- **Left-shift gate:** a spec-lint rule that runs every note-check row over a fixture ledger holding all of the table's correct notes, and requires `NOTES OK <rows>`. This catches any row pair whose (label, token) collide across answers.

### H2. The note check matches a label anywhere on a line, so another note's prose can stand in for a missing note (id 5)

- **Where:** spec-92 §4 The note check (awk selector, line 281) and §2 S3; graded by AC1-AC5 and AC7-AC12.
- **What is wrong:** The selector is `awk -v k="TOOL-dWitnessedBar-$u $s([^0-9]|\$)"` tested with `$0 ~ k`, which matches the label anywhere on a line. S3 and unit 91 S2 both say a note "opens with the label", and S3 claims "no item's clause can pass on another item's line". The skeptic reproduced the opposite: an 89 ledger whose only note under `- AC4` is 90 S9's, with prose citing `TOOL-dWitnessedBar-90 S1`, printed `NOTES OK 2` for rows 90|S1 and 90|S9.
- **Consequence:** Any `NOTES OK <n>` the criteria require can print with an item's note missing, provided another note under the same answer mentions that item's label. Notes in this build routinely cross-cite items. The check would certify that ledger clauses are answered when they are not, which is the selector defect S3 exists to close. It fires only on the cross-citing path, so the grade is high, not blocker.
- **Fix (judged SOUND by the skeptic):** Anchor the label at the start of the indented continuation line, which S3 and unit 91 S2 already require. For example, set `k="^[[:space:]]+TOOL-dWitnessedBar-$u $s([^0-9]|\$)"` in the awk call. Then extend AC3 with a staged red: a scratch ledger where 90 S1's note is absent but 90 S9's note prose cites `TOOL-dWitnessedBar-90 S1` must print `NO NOTE 90 S1`.
- **Left-shift gate:** a spec-lint rule that a ledger selector matching a label must anchor it with `^`, and that a spec claiming "opens with" has a criterion whose pattern carries the anchor.

### H4. AC4's staged break cannot red, because the check reads neither the interpreter nor the exit (id 15)

- **Where:** spec-92 §6 AC4 (staged break), §2 S4, §4 The note check line 281.
- **What is wrong:** The note check tests only that the literal token `resolve_python:` appears (`index($0, t)`). AC4's staged break is a note that "has lost its `resolve_python:` path", and the check passes it. The skeptic reproduced `NOTES OK 1`, exit 0, for `  TOOL-dWitnessedBar-92 S4 resolve_python: , exit 0` and for `resolve_python: python exit 0`. Only deleting the token itself printed `NO NOTE 92 S4 resolve_python:`. The same substring test lets row `90|S10|...|AC4 AC6 AC7 AC10 AC12` pass a note listing `AC1 AC4 AC6 AC7 AC10 AC12`.
- **Consequence:** S4 requires each note to quote the interpreter `resolve_python` printed and the derivation's exit, and the check verifies neither. AC4's Red-when ("a close that runs a derivation through a bare launcher records no resolved interpreter and passes") is certified by a check that never reads the interpreter. This happens on the narrow path of a note written with the token but no value.
- **Fix (the finder's fix was judged UNSOUND; this is the skeptic's corrected fix):** Add a fifth, optional pattern column to the note table and match it with `$0 ~ p` only when it is set. Every other row keeps `index($0, t)`. For the 92|S4 rows, the pattern is `resolve_python: (python3?|py|[^ ,]+)[ ,].*exit 0`, so a note with an empty value or no exit fails. Restate AC4's staged break as a note reading `resolve_python: , exit 0`, which must print `NO NOTE 92 S4 resolve_python:`. Do not require an absolute path: `resolve_python` prints a launcher word, so that would red a correct build. Reconcile this fix with M1's corrected fix and settle one note spelling.
- **Left-shift gate:** this is the checklist class `staged-break-substitutes-a-synthetic-value`. A spec-lint rule requires each staged break's expected output to be recorded by running it, before the criterion is pinned.

### M3. AC2's third clone is never required to be isolated, so its staged red can prove nothing (id 4)

- **Where:** spec-92 §2 S2 and §6 AC2 (third clone).
- **What is wrong:** The staged-red third clone is defined only as "a third clone with the same added line and a call site handling 0, 1 and 2 alone". Unlike 90 AC1's isolated clones (spec-90:298-302), it never states the `_iso=1` call or the early stop after the first pair in `check_canary_keys`. Without those, `check_canary_keys` visits every pair and returns 0. Per spec-89 S4 it returns 3, and prints `the canary visited <n> of <m>`, only on a visited failure. A clone that is not isolated therefore ends `PASS (` whatever the call site does with 3.
- **Consequence:** The staged red that 90 §7 and AC2 rely on can be built so that it never triggers a visited failure. It then appears to prove that the arm depends on the call site's verdict while proving nothing, and the main loop pins it as the arm's seen-red.
- **Fix (judged SOUND by the skeptic):** State that the third clone is 90 AC1's first isolated clone, with `_iso=1` set for the call and `check_canary_keys` stopping after its first pair, plus S2's added line and a call site whose `case` handles 0, 1 and 2 alone. Have AC2 also require that the third clone's output holds `the canary visited 1 of` on stderr, so the visited failure is shown to fire.
- **Left-shift gate:** this is the checklist class `fixture-passes-by-finding-nothing`. A spec-lint rule requires every staged red to name the line that shows its failure mode fired, not only the absence of `PASS (`.

### M4. AC5 finds pass commits with a second pass-commit rule (id 9)

- **Where:** spec-92 §6 AC5.
- **What is wrong:** AC5 finds units 89 and 90's pass commits with `git log --format=%H -E --grep='^Pass: TOOL-dWitnessedBar-(89|90)$' cdfbd1cf..HEAD`. 88 S5 and 62 S16 rule that pass-commit lookups go through the shipped seam and that "the `git log | grep` spelling ... is not used". 62 AC10 is red when "a second pass-commit rule answers for a unit", and review-79 round-1 M4 flagged the same pattern. The regex misses a commit whose trailer names both ids or adds another token, which `--check-commit` admits (`for u in $trl`, unattended.sh:13540). It also misses a commit with no trailer that names the unit in its subject, and a trailer line with trailing text. AC5 has no floor on the number of commits it finds.
- **Consequence:** If the regex misses a pass commit, AC5 reads zero commits and its "reads the same through GEN_REGION_AWK" clause passes vacuously. The miss path is narrow.
- **Fix (the finder's fix was judged UNSOUND; this is the skeptic's corrected fix):** Enumerate one commit per dispatched pass, not one per unit. For each dispatch row of TOOL-dWitnessedBar-89 and TOOL-dWitnessedBar-90 that `read_pass_declarations memory/builds/dWitnessedBar/RUN.md` prints, take `pass_commit <its anchor> <unit> memory/builds/dWitnessedBar/RUN.md <the next row's anchor, or HEAD>` with `tools/unattended/lib-unattended.sh` sourced. Grade every sha it prints. Make AC5 red when either unit yields no commit. Record each sha and the word `pass_commit` in note row 92|S5. Cite 62 S16 and 88 S5 in §10. Do not use `build_commit`: it returns only the earliest commit that touches something outside the build folder, so it skips later fix passes and build-folder-only passes, which are the commits that could edit another spec.
- **Left-shift gate:** a spec-lint rule that refuses `git log --grep='^Pass:` in a criterion and points to `pass_commit` and `build_commit`, with a required floor on the commits found.

### M5. 91 AC2 hand-writes a note selector that cannot red its own case (id 11)

- **Where:** spec-91 §6 AC2 and §2 S2.
- **What is wrong:** 91 AC2 uses its own selector, `awk '/^\*\*Evidences:\*\*|^#/{o=""} /^- /{o=$0} /TOOL-dWitnessedBar-91 S2([^0-9]|$)/{print o}'`, beside spec-92 §4's note check, which answers the same question. The copy drops the token test, so "The note line itself holds ..." is prose with no command behind it. ### M6. The note check and AC6 assume one acceptance ledger per unit (ids 12, 14)

- **Where:** spec-92 §4 The note check (lines 279-280), §2 S6 and §6 AC6.
- **What is wrong:** The note check takes `f=$(ls $b/*TOOL-dWitnessedBar-${l}-*acceptance-ledger*)`, requires exactly one match, and otherwise prints `NO SINGLE LEDGER`. AC6 runs `grep -cE "^- AC${n} "` over the same glob. Ledger names carry a pass number (`-<unit>-<pass>-acceptance-ledger.md`), and a unit dispatched for a second pass gets a second file. This is real: the tree holds 26 `-2-acceptance-ledger.md` files, and lib-unattended.sh:1022-1023 says a unit "legitimately owns several dispatch rows". The skeptic reproduced it: with `-89-1-` and `-89-2-` ledgers and a correctly placed note, row `90|S1|89|AC4|` printed `NO SINGLE LEDGER 89`, exit 1, and AC6 printed one `file:1` line per ledger instead of a bare `1`. S6, §4 and AC6 never say which ledger a note goes in. The same assumption in 91 AC2's selector does not break it: that awk still prints one line when the note sits in one of two ledgers.
- **Consequence:** If unit 87, 88, 89 or 90 gets a second pass, a correct build fails every criterion that feeds the note check, and AC6 cannot print a bare `1`. A builder chasing green would merge or delete a ledger record, or pick a ledger by guesswork. The failure is a loud false red, not a false green.
- **Fix (both finders' fixes were judged UNSOUND; these are the skeptics' corrected fixes, and the spec must choose one):**
  - Grade the last pass's ledger (id 12): state in §4 that the note check and AC6 read the ledger of the unit's last pass, the highest `-<k>-acceptance-ledger.md` the glob matches, and that S6's notes are written there. AC6 counts `^- AC<n> ` exactly once within that one file. Add a fixture arm: a scratch copy holding unit 89's `-1-` and `-2-` ledgers, with the notes in the `-2-` file, where the check prints `NOTES OK` and AC6 prints 1.
  - Grade across all ledgers (id 14): feed every ledger in the glob to the awk, which already resets `o` at each `#` heading, and require that the note's printed openers include the row's answer. For AC6, require the per-ledger count to be at most 1 in each ledger and the summed count to be at least 1. Add two staged two-ledger arms, one where pass 2 re-answers every criterion and one where pass 2 carries only a delta, and state the expected output of each.
  - A third option, from id 12: state as a design rule that each of units 87-90 closes with exactly one ledger, and add a fixture arm where a two-ledger copy prints `NO SINGLE LEDGER 89` and exits 1.
  - Do not concatenate the ledgers and count the total: a second pass re-answers criteria, so `cat <glob> | grep -cE '^- AC4 '` prints 2 on a correct build.
- **Left-shift gate:** a spec-lint rule that any glob over `*acceptance-ledger*` in a criterion states its multi-pass behaviour, with a two-ledger fixture arm.

### M7. A label mentioned in prose, even on the answer line, passes as a note (id 16)

- **Where:** spec-92 §4 The note check line 281 and the empty-token rows (90|S1, 90|S4, 90|S6, 90|S14); §2 S3 and S6; spec-91 §6 AC2.
- **What is wrong:** This is the same unanchored-label defect as H2, bound at medium, here seen on the answer line itself. `/^- /{o=$0}` fires on the `- AC<n>` line first, so a label inside that answer line counts as a placed note. An empty-token row then passes with no continuation note at all. The skeptic reproduced it: an 89 ledger whose `- AC4` answer reads "see TOOL-dWitnessedBar-90 S1 and TOOL-dWitnessedBar-90 S14", with no continuation lines, printed `NOTES OK 1` for row `90|S1|89|AC4|`. S6's exact count does not catch this, because the answer count stays at 1.
- **Consequence:** 89's own answer saying "see TOOL-dWitnessedBar-90 S1" certifies 90 S1's note as present and placed. In the other direction, a correct note plus a prose mention of its label under another answer fails with MISPLACED. S3's "opens with the label" and S6's "two spaces in" go ungraded. The effect stays inside the ledgers.
- **Fix (judged SOUND by the skeptic):** Anchor the label to a continuation line: match `^  +TOOL-dWitnessedBar-<u> <s>([^0-9]|$)` (two or more leading spaces, label first) instead of `$0 ~ k` anywhere. Use the same anchor in 91 AC2's selector. Add a staged arm to AC3: a scratch 89 ledger where the only occurrence of `TOOL-dWitnessedBar-90 S1` is inside the `- AC4` answer line must print `NO NOTE 90 S1`.
- **Left-shift gate:** as H2.

- **Where:** spec-92 §6 AC5 (per-path comparison) and §10.
- **What is wrong:** AC5 requires each spec path in a pass commit's diff to read "the same through `GEN_REGION_AWK` from `tools/unattended/lib-unattended.sh` before and after". `check_gen_region_only` (lib-unattended.sh:1137) already compares two blobs through GEN_REGION_AWK, and S5 and §10 name it as the seam. Take the commit set C from M4's corrected fix (`pass_commit` per dispatched pass), not from `build_commit`, which the skeptic on id 9 judged too narrow.
- **Left-shift gate:** a spec-lint rule that a criterion naming `GEN_REGION_AWK` must call `check_gen_region_only` and not pipe the constant by hand.
