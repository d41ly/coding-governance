## 1. Goal

The owner's NT-3 answer, "Yes, scoped", lets a scenario set policy for its builds: "a scenario's
preset slot scopes a preset and overrides to its builds, never a key presets never touch, so a
high-precision scenario can run strict while the repository runs standard"
(`2026-10-19-build-PLAY-dClosedLoop-1-night-pass-two.md:107-108`). dDeclaredLoop's scenario kind
left the slot to this build, since it needs presets that scope per build (TOOL-dDeclaredLoop-27 §3).
This unit adds the slot to the scenario row, a step to dGroundRules' one reader that answers it for a
build placed under the scenario, and the load check that refuses a slot naming a key presets never
touch, seen on two builds under scenarios with different presets.

## 2. Scope (IN)

- **S1** — The slot (shared interface I9). Two optional fields of a TOOL-dDeclaredLoop-27 S3
  scenario row, declared in `tools/loop/scenario-schema.toml`: `preset = "<name>"`, a shipped preset
  of KICK-dKeptSession-1's store, and `overrides = { "<key>" = <value> }`, both inherited through
  `extends` as the row's other fields are, a child's `overrides` laid over its parent's key by key.
  Observed by AC1 and AC4.
- **S2** — The load check, `check_scenario_policy(row, table)` in `tools/loop/scenario.py`, run where
  the scenario pack and overlay are loaded: the preset is a shipped name; each override key is a
  catalogue key on no `never` row and its value passes `check_value`; and the pair rules hold over
  the slot's assignment, the slot's preset with its overrides on top and the repository file's own
  keys on top of both. Each refusal names the scenario, the key and the rule. Observed by AC4 and
  AC5.
- **S3** — The build on a read. `read_revision(repo, rev, rows, build=None)` carries `read["build"]`,
  `resolve(key, repo, rev, build=None)` passes it, and `python policy.py get <key> --build <slug>`
  names it; each step of `RESOLUTION_ORDER` takes a keyword-only `build=None` that
  `read_ordered_value` passes, every existing step ignoring it, so a read with no build answers
  exactly as before. Observed by AC1 and AC3.
- **S4** — The step `read_scenario_value(path, row, table, rev_phrase, *, build=None)`, inserted
  after `read_file_value` and before KICK-dKeptSession-2's `read_preset_value`: it answers `None`
  with no build, for a build whose transition record names no scenario, and for a `never` key;
  otherwise it reads the build's placed scenarios from TOOL-dDeclaredLoop-27 S8's
  `derive_step_scenarios(build)`, composes their slots in declared order, and answers an override, or
  else the slot preset's value through `derive_preset_assignment`, as `Resolution(<value>, "preset",
  "scenario <tag> preset <name> at <rev>")`, `override` in place of `preset <name>` for an override.
  Observed by AC1, AC2 and AC3.
- **S5** — Two placed scenarios whose slots disagree on a key, or name two presets, settle as
  `flow.scenario-conflict` says, through TOOL-dDeclaredLoop-27 S7's rule: under `refuse` the read is
  a `Refusal` naming both scenarios and the key, under `declared-order` the later scenario wins.
  Observed by AC6.
- **S6** — The pages: `help/policy.md` states the four sources a build's read takes, and
  `help/loop.md`'s scenarios section names the slot. Observed by AC7.

## 3. Non-goals (OUT)

- A scenario naming a repository-declared preset: a scenario in gov's pack cannot see a repository's
  declarations, and an overlay scenario overrides keys instead.
- Build scope for the JS mirror: `policy.json` is rendered per revision, never per build, so a hook
  reading `readPolicy` reads the repository's values; a build-scoped JS read is a later need.
- Re-plumbing every caller to pass its build: a caller that needs its scenario's posture passes
  `build=`; the rest read the repository's values, as today.
- Caps on a scenario row: NT-1 names them, and they are not this clause.
- Placement: which scenarios a build runs is dPlacedRequest's and TOOL-dDeclaredLoop-27's.

## 4. Design

### The order a build's read takes

```
RESOLUTION_ORDER = (read_file_value, read_scenario_value, read_preset_value, read_default_value)

read_scenario_value(path, row, table, rev_phrase, *, build=None):
    if build is None or row["name"] in never:          return None
    tags = derive_step_scenarios(build)                  # the transition record's scenario= field
    if not tags:                                         return None
    slot = compose the tags' slots in declared order     # S5 settles a disagreement
    if path in slot.overrides:                           return Resolution(v, "preset", "scenario <tag> override at <rev>")
    if slot.preset: v = derive_preset_assignment(slot.preset, ...).get(path); if v: return Resolution(...)
    return None
```

The repository's own explicit values stay first; the scenario stands in for the repository's preset
for its builds, ahead of it (§8 F1). With no build, every read is KICK-dKeptSession-2's.

### Data model

```toml
# a scenario row, TOOL-dDeclaredLoop-27 S3, with the slot
[[scenario]]
tag = "scenario.high-precision"
extends = "scenario.feature"
preset = "strict"
overrides = { "review.max-rounds" = 5 }
```

### Alternatives rejected

- **The scenario ahead of the repository file.** §8 F1: it would let a scenario row override a value
  the owner set in the guarded policy file.
- **A new `Resolution` source `scenario`.** The source vocabulary is closed (GR `policy.py:199`) and
  read by the mirror and `--explain`; a scenario's slot is a preset scoped to a build, so it answers
  as `preset` with a reason naming the scenario.
- **Copying a scenario's slot into the policy file per build.** The file is per repository and
  guarded; a per-build copy would be a second policy store.

## 5. Production-readiness checklist

- security — a scenario row is written by the scenario factory in gov's pack or through the overlay's
  guarded edit path (TOOL-dDeclaredLoop-27 S1), so a slot is an owner-proofed write; the slot can
  never set a `never` key, the guard and attendance among them, and never beats the file's explicit
  values. The residual risk, a slot loosening a loop bound the repository's preset sets, is the
  stall census's SC-comp-5 (`2026-10-19-build-PLAY-dClosedLoop-1-research-stall-scenarios.md:123`).
- perf / scale — one transition-record read per build per `read_revision`, cached on the read.
- error / empty / loading states — no build, no record or no slot: the step answers `None`.
- observability — `get --build <slug> --explain` names the scenario and its preset.
- risks — a caller that forgets `build=` reads the repository's values: the read is still valid, only
  unscoped.
- testing — the case of §6 and the arm in §7.
- migration — none.
- user docs — `help/policy.md`, `help/loop.md`, S6.

## 6. Acceptance criteria

The case is `scenario-preset`: a scratch repository under `%TEMP%` with the policy and loop kits, a
policy file naming `standard`, gov's scenario pack copied with two planted rows,
`scenario.planted-strict` (`preset = "strict"`) and `scenario.planted-velocity` (`preset =
"velocity"`), and transition records placing build `bA` under the first and build `bB` under the
second.

- **AC1** — When the case runs `python policy.py get hooks.bypass --build bA --explain` and the same
  for `bB`, `bA` prints `refused` and `bB` prints `allowed`, each with source `preset` and a reason
  naming its scenario; `get review.max-rounds --build bB` prints `2`.
  Red when: two builds under scenarios with different presets read one value.
- **AC2** — When the case's policy file adds `[hooks]` `bypass = "allowed"`, `get hooks.bypass
  --build bA` prints `allowed` with source `file`.
  Red when: a scenario's slot beats the repository's explicit value.
- **AC3** — When the case runs `get hooks.bypass` with no `--build`, and with `--build bC` for a
  build whose record names no scenario, both print `allowed` with source `preset` naming
  `standard`, the repository's own preset.
  Red when: a scenario's slot leaks to a build not placed under it.
- **AC4** — When `python scenario.py --fixture --plant slot-never` loads a pack whose planted row sets
  `overrides = { "runtime.agents-in-flight" = 9 }`, the load refuses naming the scenario and
  `runtime.agents-in-flight` as a key presets never touch, and the unplanted pack loads.
  Red when: a slot sets a `never` key.
- **AC5** — When `python scenario.py --fixture --plant slot-pair` loads a planted row setting
  `overrides = { "review.design.round-count" = 4 }` under `preset = "velocity"`, whose
  `review.max-rounds` is 2, the load refuses naming the pair.
  Red when: a slot breaks a pair rule.
- **AC6** — When `bA`'s record places both planted scenarios and `flow.scenario-conflict` is
  `refuse`, `get hooks.bypass --build bA` exits 2 naming both scenarios and the key; under
  `declared-order` it prints the later scenario's value.
  Red when: a disagreement settles silently.
- **AC7** — When `grep -n "scenario" policy.md` runs in the help directory, the resolution-order
  paragraph names the file, the scenario, the preset and the default in that order.
  Red when: the page omits the build's scenario source.

## 8. Open questions

- **F1 — What does "read … before the repository's own values" order?** (a) The scenario first,
  ahead of the policy file: file values, the repository's preset and the defaults all below it; (b)
  the scenario after the file's explicit values and ahead of the repository's preset and the
  defaults. (a) lets a scenario row, written outside the guarded policy file, override a value the
  owner set in it, a policy change the file's guard never sees, so it widens the policy write surface
  past this unit's tier: veto 3. (b) runs a high-precision scenario strict in a repository naming
  standard, NT-3's case, and keeps the owner's explicit values. RESOLVED (agent, 2026-10-26,
  delegated): (b), rung 3 after veto 3 discards (a); the scenario's slot is read before the
  repository's preset and its defaults, the values a repository gets without setting them; shared
  interface I9 as the brief spells it. widens: none · relaxes: none
- **F2 — May a scenario name a repository-declared preset?** (a) Shipped presets only; (b) any name
  the policy file declares. A scenario in gov's pack cannot know a repository's names, and (b) makes
  a pack row's validity depend on each adopter's file. RESOLVED (agent, 2026-10-26, delegated): (a),
  rung 3, fewer open questions; an overlay scenario reaches a repository's posture through
  `overrides`. widens: none · relaxes: none
