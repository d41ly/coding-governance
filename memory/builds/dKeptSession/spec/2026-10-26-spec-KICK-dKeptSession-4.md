## 1. Goal

A repository's posture is one choice, its `preset`, and v2 makes choosing it a policy change,
"guarded and recorded like any other"
(`memory/builds/dClosedLoop/build/2026-10-14-build-PLAY-dClosedLoop-1-architecture-v2.md@9bf3b4c9:1416`).
At HEAD the policy kit's scaffold writes dGroundRules' literal defaults and no `preset` key
(`tools/policy/policy.py#render_scaffold`), so a new adopter starts with no preset named and nobody
was asked. This unit puts the choice at govkit intake: the deployer asks for the preset once, records
the answer in the target's `deploy.toml`, and the scaffold writes it as the policy file's first key,
through the answer route intake already derives from a kit's argv.

## 2. Scope (IN)

- **S1** — The token (shared interface I6). The `[adopt]` argv in `tools/policy/kit.toml` becomes
  `["bash", "{kit}/adopt-policy.sh", "--scaffold", "--preset", "{preset}"]`. `needed_answers`
  (`tools/govkit/govkit.py#needed_answers`) scans each selected kit's `[adopt]` argv for
  `TOKEN_RX` tokens, so it derives `preset` for every selection holding the policy kit, and
  `cmd_intake` (`tools/govkit/govkit.py#cmd_intake`) records it under `[answers]`, never under the
  `[policy]` table it writes itself. `target_context` (`tools/govkit/upgrade_steps.py#target_context`)
  enters the answer because the policy descriptor names the token. The `[[regenerate]]` argv is
  unchanged. Observed by AC1 and AC2.
- **S2** — The scaffold. The `scaffold` branch of `main` in `tools/policy/policy.py`
  (`tools/policy/policy.py#main`) takes `--preset <name>`, and `USAGE` spells it; a call naming no
  preset exits 2 with the usage line (§8 F2). A name the catalogue's `preset` row refuses through
  `check_value` (`tools/policy/policy.py#check_value`) exits 2 with that reason on stderr, which names
  the name and the row's `of` list, and nothing on stdout. `render_scaffold(rows, preset=None)` writes
  `preset = "<name>"` as the first key, the line after `SCAFFOLD_HEADER` and above dGroundRules'
  tables, LF through `sys.stdout.buffer` as today; `None` writes today's bytes for the existing
  callers. `adopt-policy.sh --scaffold --preset <name>` passes the name on; `--preset` beside
  `--check`, or with no value, is the usage line, exit 2. With no policy file and no `--preset` the
  adopter exits 2 naming the flag before its `mkdir`. Every new refusal exits 2 or passes an exit
  through, never a reasoned `exit 1`, so `check-arms.py`'s census of the adopter holds (§4).
  Observed by AC3 and AC4.
- **S3** — A kept file. Where `.governance/policy.toml` exists, `adopt-policy.sh --scaffold --preset
  <name>` keeps it as today and runs `policy.py scaffold --preset <name> --kept <file>`, which checks
  the name as S2 does, reads the file's top-level `preset` through `parse_policy`
  (`tools/policy/policy.py#parse_policy`), the `preset` row's catalogue default where the file sets
  none, and, when that differs from the answer, prints one line on stdout naming the file, its
  preset and the answer, exit 0 either way. It writes nothing. A non-zero exit of that call, an
  unknown or unresolved name, ends the adopter with that exit before the settings render; exit 0
  goes on as today. A file that does not decode or that `parse_policy` refuses prints no line and
  exits 0: the mirror step after it reports an invalid file, as today. With no `--preset`, the
  `[[regenerate]]` form, the kept branch compares nothing. Observed by AC5.
- **S4** — Fixture answers. Every answer set a gov fixture hands the deployer for a selection whose
  `requires` closure holds `policy` gains `preset = "standard"`. At HEAD those are `DEPLOY_FULL`
  (`tools/govkit/selftest.py#DEPLOY_FULL`), whose `[answers]` `DEPLOY_REGISTRY_DEFAULT` copies and
  `read_deploy_answers` (`tools/policy/check_policy.py#read_deploy_answers`) hands every install
  `build_install_target` makes; and, in `tools/govkit/matrix.py`, `INSTALL_ANSWERS` and the `fixed`
  answers `main` hands `render_deploy_tail` for `SCRATCH_KITS`, which holds `playbook-render`.
  Each arm of `tools/policy/adopt-policy.test.sh` that reaches the written branch, arms 1, 2 and 3,
  arm 4's first `--scaffold` and its `empty` target, the `limit-fresh-target-spawn` case of
  `run_limit_case`, and the two bare `policy.py scaffold` runs,
  `tools/govkit/selftest.py#check_fanout_step` and
  `tools/govkit/steps/kickoff_facts_to_overlay.py#build_fact_fixture`, gain `--preset standard`; the
  two bare runs read stdout only, so without it each would write an empty policy file and no exit
  would say so. `run_fresh_target` (`tools/policy/check_policy.py#run_fresh_target`) derives the key
  count its `arm_schema` line must print from `render_scaffold(rows, preset=<the preset answer>)`,
  the answer `read_deploy_answers` gives, since the installed file now carries the `preset` key the
  count lacked. `build_install_target` takes `answers=None`, `read_deploy_answers`'s when None, the
  one override the `intake-preset` case passes. Observed by AC1, AC2 and AC6.
- **S5** — The pages. `help/policy.md#install` says intake asks for the preset, answered on one line

## 3. Non-goals (OUT)

- A default answer: intake asks, and refuses with none, as for every other answer (§8 F1).
- A repository-declared preset at intake: one is declared in the policy file a repository already
  has, after intake (KICK-dKeptSession-1 S3).
- Switching a preset after install: a policy change through the policy guard, not the deployer.
- Any change to `needed_answers`, `cmd_intake`, `resolve_tokens` or `resolve_adopter_argv`: the
  token is the whole hook.
- The written branch passing the scaffold's exit 2 and stderr through: KICK-dKeptSession-44 S13.
  Until it lands, that branch exits 1 with its generic line and writes no file.
- Which rows the scaffold writes under a named preset: KICK-dKeptSession-32.
- An answer in gov's own `.governance/deploy.toml`, and the runbook's intake line in
  `WIRE-INTO-PROJECT.md`: gov's preset is the owner's to answer (§8 F1), and intake names a missing
  answer itself.

### The route

```
kit.toml [adopt] argv  ... "--preset", "{preset}"
  -> needed_answers: {preset}                          (derived, never listed)
  -> govkit intake --answer preset=strict
  -> deploy.toml  [answers]  preset = "strict"
  -> apply: adopt-policy.sh --scaffold --preset strict
  -> policy.py scaffold --preset strict                 (main's branch; check_value on the preset row)
  -> .governance/policy.toml:  header, preset = "strict", then dGroundRules' tables
kept file: policy.py scaffold --preset strict --kept <file>  -> one line where they differ
```

### Migration

A target whose `deploy.toml` predates this unit carries no `preset` answer. `update` reads none: it
re-runs no installed adopter, and `[[regenerate]]` names no token. A re-run `apply`, or an `update`
that gains the policy kit, runs the `[adopt]` argv with `{preset}` unresolved, and the scaffold
refuses that literal as no shipped preset: with no policy file the written branch exits 1, and over
a kept one the kept call's exit 2 ends the adopter (S3), so `apply` reports the adopter's exit
either way and writes no guessed posture. The upgrade step is one line under `[answers]`, `preset = "<name>"`; `help/policy.md#install`
states it.

### Alternatives rejected

- **The answer in deploy.toml's `[policy]` table.** That table is the deployer's own two switches
  (`on_baseline_red`, `on_hook_block`); a preset there would give one table two owners.
- **A probe deriving the preset.** Nothing in a target's tree says which posture its owner wants; a
  derived answer would be a guessed one.
- **The kept file's preset read by `policy.py get`.** `get` reads the landed revision, and on an
  install the file is not committed yet; `parse_policy` over the file is the one parser.

## 5. Production-readiness checklist

- security — deny by default: no answer is invented, an unknown or unresolved name writes nothing,
  a scaffold with no preset named writes nothing, and a kept file is never rewritten by the deployer.
- perf / scale — one more argv token, and one `policy.py` run on a kept file.
