## 1. Goal

dGroundRules' one reader answers a key from the policy file, else from the catalogue default, and a
file naming `preset = "strict"` reads every key it does not set at its default: `hooks.bypass` reads
`allowed` where strict says `refused` (DA-M10, `reviews/2026-10-18-review-PLAY-dClosedLoop-1-design-audit.md:222-232`).
dGroundRules left the slot and a sentence saying the preset is not applied until this build. This
unit adds the step between the file and the default, so a key the file does not override reads the
named preset's value, and rewrites the sentence and the fixture case asserting it.

## 4. Design

### The order

```
RESOLUTION_ORDER = (read_file_value, read_preset_value, read_default_value)

read_preset_value(path, row, table, rev_phrase):
    if table is None or ("preset",) not in table:   return None   # absent file, or no preset named
    if row["name"] in never:                        return None   # presets never touch it
    a = derive_preset_assignment(table[("preset",)], load_presets(KIT), table)
    v = a.get(path, a.get(parse_key(row["name"]), MISSING))
    return None if v is MISSING else Resolution(v, "preset", f"preset {name} at {rev_phrase}")
```

`Resolution`'s source vocabulary already holds `preset` (GR `policy.py:199`). A file naming a preset
`validate` refuses is not read here: `resolve_read` sends invalid text to the last valid revision,
whose own order runs this step over that revision's table.

### The reasons `get --explain` prints

| Case | Source | Reason |
|---|---|---|
| the file sets the key | `file` | `set in .governance/policy.toml at <rev>` (unchanged) |
| the file names a preset that assigns it | `preset` | `preset <name> at <rev>` |
| the file names no preset, or the key is never touched | `default` | dGroundRules' reason, the not-applied clause gone |
| the file is absent | `default` | `.governance/policy.toml is absent at <rev>; the catalogue default` (unchanged) |

### Migration

A repository whose policy file names a preset reads that preset's values from this unit's landing
where it read defaults before. `standard` equals the catalogue defaults (KICK-dKeptSession-1 S2), so
a `standard`-named file reads the same values with source `preset`; a `strict`- or `guarded`-named
file changes posture, which is the clause.

### Files touched (estimate)

- `tools/policy/policy.py`: the step, the order, the reason
- `tools/policy/check_policy.py`: the `preset-named` case rewritten, `preset-every-key` added
- `tools/policy/README.md`: the order
- `help/policy.md`

### Alternatives rejected

- **A preset read inside `read_default_value`.** The order is the one place a source is chosen
  (TOOL-dGroundRules-3 S1); a default step that sometimes answers a preset hides a source.
- **Reading `standard` when the file names no preset.** DA-M10's fix reads the default "only when
  the file names no preset", and `standard` equals the defaults, so the answer is the same and the
  source stays `default`.

## 5. Production-readiness checklist

- security — tightens: a strict- or guarded-named repository now refuses hook bypass and the other
  keys its preset sets; no write path is added.
- perf / scale — `load_presets` once per `read_revision` read, cached on the read dict, so a mirror
  render reads the store once.
- error / empty / loading states — an absent store is a `Refusal` naming `presets.toml`, never a
  silent default.
- observability — `get --explain` names `preset` and the preset's name.
- risks — a repository naming `strict` before dWitnessedBar's reliability bar may stall on hook
  refusals (v2:1467-1469); the preset says so in `help/policy.md`.
- testing — the cases of §6 and the arm in §7.
- migration — §4.
- user docs — `help/policy.md`, S4.

## 6. Acceptance criteria

The fixture is dGroundRules' `run_resolution_order`: one repository per case, read at `--rev HEAD`.

- **AC1** — When the `preset-named` case commits a policy file setting only `preset = "strict"`,
  `python policy.py get hooks.bypass --rev HEAD --explain` prints `refused`, source `preset` and a
  reason naming `strict`.
  Red when: a strict-named file with no override reads `hooks.bypass` as anything but `refused`.
- **AC2** — When the `preset-overridden` case adds `[hooks]` `bypass = "allowed"` beside `preset =
  "strict"`, the same command prints `allowed` with source `file`.
  Red when: the preset wins over the file's override.
- **AC3** — When `python check_policy.py --fixture preset-every-key` runs, it prints one
  `policy-fixture:` line per shipped preset reading every presettable key at its preset value with
  source `preset` and every `never` key at its default.
  Red when: one key of one preset reads its default, as `velocity`'s `review.max-rounds` read 3
  before this step.
  figure: the key count is DERIVED from the catalogue and the store's `never` list.
- **AC4** — When the `file-silent` case reads `runtime.agents-in-flight` from a file naming no
  preset, it prints the default with source `default`.
  Red when: a file naming no preset reads a preset source.
- **AC5** — When a case commits `[presets.ours]` with `extends = "strict"` and `"hooks.bypass" =
  "allowed"`, and `preset = "ours"`, `get hooks.bypass --explain` prints `allowed` with source `preset`
  naming `ours`, and `get leases --explain` prints `refuse` naming `ours`.
  Red when: a declared preset's own key or its shipped base is not read.
- **AC6** — When `grep -rn "not applied until dKeptSession" .` runs in the policy kit and in the help
  directory, it prints nothing.
  Red when: the old sentence survives in a reason, a fixture or a page.
- **AC7** — When `grep -n "preset" policy.md` runs in the help directory, the resolution-order
  paragraph names the file, the preset and the default in that order.
