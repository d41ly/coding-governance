## 1. Goal

A compacted or fresh session reorients from its card, and the card says where the build started, not
where it is: TOOL-dPlacedRequest-2 re-renders the whole build card at transitions under
`card.follows`, and nothing between two transitions moves it. The owner's CX-1 answer asks for
pointers updated as the build progresses, "the latest records by tag, the open forks, the item in
flight", beside `card.follows`
(`memory/builds/dClosedLoop/build/2026-10-15-build-PLAY-dClosedLoop-1-compaction-results.md:336-345`;
v2:1240). This unit writes a `## pointers` section into the build card by `card.pointers`, and
defines the item boundary, I12, the one point every later session unit reads at.

## 2. Scope (IN)

- **S1** — The item boundary, I12. `derive_item_boundary(repo, slug, pointer)` in
  `tools/loop/position.py` calls TOOL-dDeclaredLoop-7's `derive_position` and returns the build's
  current item, the `act` answer's instance key (TOOL-dDeclaredLoop-7 S3, `<item tag>@<round|pass>#<inputs>`)
  or `none` for any other answer, when it differs from `pointer`, and `None` when it does not. The
  CLI `python tools/loop/position.py <slug> --boundary <key|none>` prints `boundary — <pointer> →
  <key|none>` or `boundary — none crossed · item <pointer>`, exit 0 both ways and 2 on
  `invalid-input`. Observed by AC4.
- **S2** — The section, I11. `render_pointers <slug>` in `skills/session-kickoff/manifest-check.sh`
  prints `## pointers` and three lines: `records — <kind> <path> · …`, the newest record of each
  `**Serves:**` kind of the build; `forks — <spec path>§8 · …`, every spec of the build the driver's
  `--plan <slug> --paths` reads `FORKED`, or `none`; and `item — <instance key|none> · at <sha8>`,
  the current item from `position.py <slug> --json` and the HEAD it was derived at. A source that
  does not resolve prints its own `skipped: <why>` on its line. KICK-dKeptSession-26 and
  KICK-dKeptSession-5 add the `budget —` and `mail —` lines below these. The section's required
  lines are one list, `POINTER_LINES="records forks item"`, which `check_card_pointers` reads: a
  stored card whose `## pointers` lacks a listed line fails `--card --check`, naming the line, and
  each later unit appends its own word. Observed by AC1, AC11.
- **S3** — The records reader. `python tools/memory-tree/gen_build_index.py --latest-records <slug>`
  prints one `<kind> <path>` line per kind of `RECORD_KIND_TOKENS`

### Alternatives rejected

- **A full re-render at every item.** `card.follows` already re-renders at transitions; the clause
  asks for pointers beside it, and a full render re-runs every startup cell's bounded reads.
- **The boundary computed inside the hook.** The hook would need its own copy of the engine's
  answer; it compares one sha and hands the rest to S1.
- **The section in the session card only.** A fresh session on another node reads the build card,
  so the pointers must travel with it.

## 5. Production-readiness checklist

- security — no new store: the section is written through `publish_build_card`'s compare-and-swap
  and the session card file; the slug is held to the route grammar before it reaches a path or a
  ref, as TOOL-dPlacedRequest-2 holds it.
- perf / scale — the hook adds one `git rev-parse` per shell call of the main session, and the
  verb's bounded call only after HEAD moves, which is at most once per commit.
- error / empty / loading states — each line names its own skipped source; an over-cap section is
  refused, the card left as it was.
- observability — every crossing prints `boundary — <from> → <to>`.
- risks — two sessions on one build race the ref; `publish_build_card`'s one re-render on a lost
  compare-and-swap keeps both pointer sets in the ref's history.
- testing — S9's plants and the hook arm, red and green.
- migration — none.
- user docs — `help/orientation-card.md`, S10.
