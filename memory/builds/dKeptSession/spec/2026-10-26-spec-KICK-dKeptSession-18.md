## 1. Goal

Playbook mode has its seat in the flow through the `repeat` disposition, which enters Design as a patch
build does and lets a `playbook` supply the feature design (night-pass point 1,
`memory/builds/dClosedLoop/build/2026-10-18-build-PLAY-dClosedLoop-1-night-pass.md:103-109`; P20, v2:918-919).

(TOOL-dDeclaredLoop-16 S1), its `none` row is the build table's B3, `none` to `designing` on
`item.entry.claim`'s `claimed` outcome with disposition `repeat` (TOOL-dDeclaredLoop-13 §4), the placement
check resolves the `playbook:` path (TOOL-dPlacedRequest-4 §4) and the claim writes `mode: recipe` with
`playbook: <path>` (TOOL-dPlacedRequest-21 S4). This unit carries the clause by citing them, adds no second
row, and adds the one arm nothing has: a join, both ways, between the dispositions the claim admits and the
table's `none` rows, so `repeat`'s set member and its row are seen together. The playbook record kind is
dIndexedDesign's (`TOOL-dIndexedDesign-10`, `cl-dClosedLoop-0392`); until it lands, a `repeat` routes onto a
playbook by its path, and the hand-over is filed as an ask.

## 4. Design

### The join

```
admitted = CLAIM_DISPOSITIONS                      # tools/loop/claim.py
entry    = [r for r in build rows if r.from == ["none"] and r.item == "item.entry.claim"]
for d in admitted:  d in dispositions.set, and exactly one r in entry with r.disposition == d
for r in entry:     r.disposition in admitted
```

Both halves are the class, not B3 alone: a disposition the claim admits with no row is a request claimed
into no state, and a row the claim can never fire is dead. `repeat` is one instance of each half, and the
plants see it on both.

### What it does not check

The row's `to`. P20 puts `repeat` at Design, and B3 says so; the arm prints each `to` on its line and leaves
the value to TOOL-dDeclaredLoop-13's own source rows (flow-steps.md:735).
