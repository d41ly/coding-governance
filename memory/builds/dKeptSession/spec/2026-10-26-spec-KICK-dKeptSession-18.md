## 1. Goal

Playbook mode has its seat in the flow through the `repeat` disposition, which enters Design as a patch
build does and lets a `playbook` supply the feature design (night-pass point 6,
`memory/builds/dClosedLoop/build/2026-10-18-build-PLAY-dClosedLoop-1-night-pass.md@4f5e5809:103`; P20,
`memory/builds/dClosedLoop/build/2026-10-14-build-PLAY-dClosedLoop-1-architecture-v2.md@9bf3b4c9:919`).
dDeclaredLoop and dPlacedRequest have landed every part: `repeat` is a member of the `[dispositions]` set
of `tools/loop/loop.toml`; its build row from `none` fires on `item.entry.claim`'s `claimed` with
disposition `repeat` into `designing`; the placement check holds a `repeat`'s playbook path at HEAD
(`tools/loop/placement.py#check_disposition_fact`); and the claim writes `authorized-by: recipe`,
`playbook:` and `pieces:` into the build's README, which the driver's recipe mode follows
(`tools/unattended/unattended.sh#check_authorization`). The claim's admitted dispositions and each one's
first move are one fact, `FIRST_MOVES` in `tools/loop/claim.py`. This unit carries the clause by citing
them, adds no row, and adds the one arm nothing has: a join, both ways, between `FIRST_MOVES` and the
build table's rows from `none`, so `repeat`'s set member, its first move and its row are seen together.
The playbook record kind is dIndexedDesign's (`TOOL-dIndexedDesign-10`, `cl-dClosedLoop-0392`); until it
lands, a `repeat` routes onto a playbook by its path, and the hand-over stands filed as an ask.

## 4. Design

### The join

```
first   = FIRST_MOVES                             # tools/loop/claim.py: {disposition: (item, outcome)}
entry   = [r for r in build rows if r.from == ["none"]]
fires(r, d) = (r.item, r.outcome) == first[d] and r.get("disposition", d) == d
for d in first:  d in [dispositions].set, and exactly one r in entry with fires(r, d)
for r in entry:  some d in first with fires(r, d)
```

At base the three rows from `none` are `item.entry.claim` `claimed` with `new` into `planning`,
`item.plan.dedupe` `patch` with no disposition into `designing`, and `item.entry.claim` `claimed` with
`repeat` into `designing`, and each fires one key's first move. Both halves are the class, not the
`repeat` row alone: a disposition the claim admits with no row is a request claimed into no state, and
a row no claim fires is dead. `repeat` is one instance of each half, and the plants see it on both.

### What it does not check

The row's `to`. P20 puts `repeat` at Design, and its row says so; the arm prints each `to` on its line
and leaves the value to the table's own source rows
(`memory/builds/dClosedLoop/build/2026-10-15-build-PLAY-dClosedLoop-1-flow-steps.md@d73cb002:735`). Nor
does it read a row from `none` that no claim ever fires for another reason: every such row is refused,
so a future entry that is no claim answers this arm in its own landing.
