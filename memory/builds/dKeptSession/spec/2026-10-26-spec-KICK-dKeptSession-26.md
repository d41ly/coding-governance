## 1. Goal

Every way a build repeats draws on one rework budget per build (P39,
`memory/builds/dClosedLoop/build/2026-10-14-build-PLAY-dClosedLoop-1-architecture-v2.md@9bf3b4c9:1068`),
and the landed loop kit keeps that budget on the build's records and answers its state with
`budget_state` (`tools/loop/budget.py#budget_state`), but a session never sees it:
TOOL-dDeclaredLoop-30 §3 hands the card line to this build in so many words, "the remaining budget
on the card is dKeptSession's render of this record". This unit gives `budget.py` the one-line
reader its shell callers lack, puts a `budget —` line in the card's `## pointers` section beside the
pointers KICK-dKeptSession-13 writes, and makes a card that omits it fail the card check, seen red on
a planted card that omits it.

## 4. Design

### The line

```
## pointers
records — journal memory/builds/dX/build/2026-10-27-build-KICK-dX-1-agent-ledger.md
forks — none
item — item.build.base@KICK-dX-2#3f9c2a71 · at 8c1e0b42
budget — open 3/10
```

| `budget_state` | Line |
|---|---|
| `open 3/10` | `budget — open 3/10` |
| `spent` | `budget — spent` |
| `unfrozen 1/4` | `budget — unfrozen 1/4` |
| no loop kit | `budget — skipped: no loop kit` |
| a failed or slow call | `budget — skipped: budget.py state exited <rc>` or `… did not answer within <n>s` |

The answer is printed as the module prints it, never re-derived here: the card shows the record's own
reading, so it can never disagree with the reader the draw sites use. `budget_state` answers
`unfrozen <spent>/<total>` where no freeze row is held, the total then the base
(`tools/loop/budget.py#budget_state`).

### Alternatives rejected

- **The budget computed in the card writer** from the transition records. A second reader of the
  draw rows would be a second answer to `budget_state`'s question, and TOOL-dDeclaredLoop-48 already
  reads those rows across four homes.

  the section's.
- **An in-process import of `budget.py` by path from the kickoff engine.** The engine is shell and
  reaches every sibling kit through a bounded subprocess, as it reaches `claims.py`.

## 5. Production-readiness checklist

- security — the line carries the module's one-line answer, held to `budget — ` plus at most one
  line of printable text before it is written.
- perf / scale — one bounded call per pointers render.
- error / empty / loading states — every failure is a `skipped` line naming why; the card is still
  written.
- observability — the line itself.
- risks — a stub or absent loop kit hides the budget behind `skipped`; the help page says so.
- testing — S4's plants and S6's case, red and green.
- migration — none.
- user docs — `help/orientation-card.md`, S5; `help/loop.md`, S6's verb.
