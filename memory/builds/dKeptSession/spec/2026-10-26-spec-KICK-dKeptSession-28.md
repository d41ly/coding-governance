## 1. Goal

One grammar for who a mailbox message is for, checked once at the write: a build, one of its units,
a node named by its fleet tag, or the whole project. The coordination design states a recipient as
"a build, or one of its units"
(`memory/builds/dClosedLoop/build/2026-10-14-build-PLAY-dClosedLoop-1-coordination.md@4a13cbc82a99:107`),
so nothing addresses a node or the project (the cloud round's deciding point 2,
`memory/builds/dClosedLoop/build/2026-10-19-build-PLAY-dClosedLoop-1-cloud-and-scale.md@7a90ffec17e2:109`;
P40; the owner's CL-4). The unit ships the grammar's checker and its matcher; the mailbox that writes
and reads messages is KICK-dKeptSession-5's. A node's membership is asked of the driver's landed
`check_fleet_tag`, so this unit adds no fleet reader and no flag.

## 2. Scope (IN)

- **S1** — The grammar (I14), four forms and nothing else: `build:<slug>`, `unit:<id>`, `node:<fleet
  tag>` and the bare word `project`. Observed by AC1.
- **S2** — The checker, `check_mail_recipient <to>` in `tools/unattended/unattended.sh`: rc 0 on a legal
  recipient, rc 2 with one `mail — refused · recipient <to>: <why>` line on stderr otherwise.
  `build:<slug>` passes `check_slug_shape` (`tools/unattended/unattended.sh#check_slug_shape`).
  `unit:<id>` matches the driver's one unit-id spelling, `UNIT_ID_ERE` anchored at both ends
  (`tools/unattended/unattended.sh#UNIT_ID_ERE`), and its middle segment, the slug, passes
  `check_slug_shape`, which refuses the leading digit `UNIT_ID_ERE` admits. `node:<tag>` is a tag
  the fleet registry holds (S3). Any other text, an empty one included, is refused naming the four
  forms. Observed by AC1, AC2.
- **S3** — The node's membership. `check_mail_recipient` asks `check_fleet_tag <tag>`
  (`tools/unattended/unattended.sh#check_fleet_tag`, TOOL-dPlacedRequest-20 S1), the driver's one
  membership check over the playbook kit's `read_fleet` (`tools/playbook/render_playbook.py#read_fleet`).
  Its rc 1 and its rc 2 each refuse the recipient, the refusal's `<why>` being the `LEASE_WHY` it
  sets, which names `fleet.toml` in every cause. A recipient of any other form starts no Python. The
  membership check itself is landed, so this unit only calls it. Observed by AC2, AC3.
- **S4** — The matcher, `check_mail_addressed <to> <who>` in the same file: rc 0 when `<to>` equals
  `<who>`, or when `<who>` is `build:<slug>` and `<to>` is a `unit:` id whose slug segment is `<slug>`;
  rc 1 otherwise. It checks neither argument's form: `<to>` passed `check_mail_recipient` at its post,
  and `<who>` is the reader's own. Every reader decides "addressed to me" by this one predicate,
  asking once per recipient it answers for. Observed by AC4.

## 3. Non-goals (OUT)

- No message writer, reader or ref: KICK-dKeptSession-5 calls `check_mail_recipient` at the write and
  `check_mail_addressed` in its reader.
- No routing of a `project` message to a node, and no offer or claim of one: a project-level request
  any node claims by lease is dPlacedRequest's, landed as `--request` and the `request` lease
  (`tools/unattended/unattended.sh#write_request_record`;
  `memory/builds/dClosedLoop/build/2026-10-19-build-PLAY-dClosedLoop-1-cloud-and-scale.md@7a90ffec17e2:244`).
- No resolution of this node's own tag: `resolve_fleet_tag`
  (`tools/unattended/lib-unattended.sh#resolve_fleet_tag`) answers "which tag am I", and
  `check_fleet_tag` answers "is this a tag of the fleet".
- No new fleet reader and no `render_playbook.py` flag (F1).
- No gate on a transition from a `node:` or `project` message: which recipients gate a build's
  transition is KICK-dKeptSession-5's (its §8).
- No guide or help text: KICK-dKeptSession-5's `--mail` entry in the verbs guide and its
  `help/loop.md` paragraph state the four forms, since a recipient reaches a user only through
  `--mail post --to` (F3).

## 4. Design

### Evidence

- `check_fleet_tag` asks `read_fleet` through the playbook kit `resolve_kit_dir` finds beside the
  driver, writes no bytecode, and returns 0 held, 1 absent or 2 unread, its cause in `LEASE_WHY`;
  `run_lease_verb`'s offer is its one caller today (`tools/unattended/unattended.sh#check_fleet_tag`,
  `#run_lease_verb`).
- `read_fleet` validates every row, each `tag` one lowercase letter and unique, and refuses an empty
  registry (`tools/playbook/render_playbook.py#read_fleet`); `tools/playbook/fleet.toml` holds the
  tags `a`, `b`, `c` and `d`.
- `render_playbook.py` has `--fleet-tag`, which names one node by its user, and no flag listing every
  tag (`tools/playbook/render_playbook.py#main`).
- `UNIT_ID_ERE` is the one unit-id spelling `_ids_of`, `write_chain_round` and
  `derive_chain_verdict` read (`tools/unattended/unattended.sh#UNIT_ID_ERE`), and a slug is
  `check_slug_shape`'s.
- The unattended kit's `requires` names no playbook kit, though `check_fleet_tag` and
  `resolve_fleet_tag` already read one (`tools/unattended/kit.toml`); KICK-dKeptSession-44 S27 adds it.
- No recipient code exists: `git grep -n -i recipient -- tools skills` finds nothing at this tree.
- A probe sourcing the driver at this tree (2026-11-21) read `check_fleet_tag` 0 for `a` and `b`, and
  1 for `z` and for the empty tag, `LEASE_WHY` naming `fleet.toml`; `check_slug_shape` 0 for `fx`, 1
  for `3x` and the empty slug; `UNIT_ID_ERE` anchored matching `KICK-fx-3` and `KICK-3x-3`, never
  `fx` or `KICK-fx-x`. These are the exits AC1 to AC3 name.
- The suite's lease arms run the tracked driver, `bash "$SCRIPT"` (`run_lease_arm` in
  `tools/unattended/unattended.test.sh`), so `check_fleet_tag` there reads the tracked
  `tools/playbook/fleet.toml`, as this unit's arm does; no fixture copy of the driver is made.
- `memory/map/generated/symbols.json` lists every shell function of `unattended.sh` by name, so the
  two minted here move it.

## 5. Production-readiness checklist

- security — the recipient is validated at the write, once, against a closed grammar; a node tag
  must be the fleet's, and it reaches Python only as an argument.
- perf / scale — one Python start per `node:` recipient checked, `check_fleet_tag`'s; the other
  forms are bash alone.
- error / empty / loading states — an empty or unknown form is refused naming the four; an unread
  fleet registry refuses `node:` with `check_fleet_tag`'s cause, which names `fleet.toml`.
- observability — every refusal is one `mail — refused · recipient` line naming the cause.
- risks — a node removed from `fleet.toml` leaves earlier `node:` messages addressed to nobody; the
  matcher still matches them by tag.
- testing — the fixture cases under AC1 to AC4 and the suite arm in §7.
- migration — none: no message exists yet.
- user docs — KICK-dKeptSession-5's `--mail` entry in the verbs guide and its paragraph in
  `help/loop.md`, the page that describes `--register` and `--lease` (F3).

## 6. Acceptance criteria

- **AC1** — When a probe sources `unattended.sh` and runs `check_mail_recipient` on `build:fx`,
  `unit:KICK-fx-3`, `node:a` and `project`, each returns 0; on `build:`, `unit:fx`, `unit:KICK-fx-x`,
  `unit:KICK-3x-3`, `everyone`, `Project` and the empty string each returns 2 with one
  `mail — refused · recipient` line.
  Red when: any illegal form returns 0, as a planted checker accepting any `unit:` text shows.
- **AC2** — When `check_mail_recipient node:z` runs in this tree, whose `fleet.toml` holds no `z`, it
  returns 2 with one refusal line naming `fleet.toml`; `node:b` returns 0.
  Red when: an unknown tag passes, or a known one is refused.
- **AC3** — When a probe sources `unattended.sh`, redefines `check_fleet_tag` to append one line to a
  scratch counter, set `LEASE_WHY` to `fleet.toml could not be read: planted` and return 2, then runs
  `check_mail_recipient node:a` and `check_mail_recipient build:fx`, the first returns 2 with one
  refusal line carrying that cause, the second returns 0, and the counter holds one line.
  Red when: an unread registry passes a `node:` recipient, or a recipient of another form asks the
  registry.
- **AC4** — When `check_mail_addressed` runs with `<who>` `build:fx`, it returns 0 for `build:fx` and
  `unit:KICK-fx-3` and 1 for `build:fy`, `unit:KICK-fy-3`, `node:a` and `project`; with `node:a` it
  returns 0 for `node:a` only, and with `project` for `project` only.
  Red when: a message to another build or node matches, or a build reads a node's message as its own.
