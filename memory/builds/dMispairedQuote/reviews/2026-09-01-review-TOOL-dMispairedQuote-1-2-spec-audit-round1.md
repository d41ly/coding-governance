## Verdict: BLOCKED

The count sits here rather than on the heading, because that line's token comes from a closed set and a tally appended to it turns a structural check into a semantic one.

Two confirmed blockers, both in `TOOL-dMispairedQuote-1`, and both the same shape as the defect the unit exists to remove: a fail-closed half added to one view produces a reproduced DENY-to-ADMIT move on the only mechanical control against an unbounded agent burst, and no acceptance criterion in §6 can observe it. Unit 1's §5 states the opposite property in one sentence — "the change moves every measured case toward DENY and none toward ADMIT" — and both blockers falsify it directly, on rule 1 and on rule 3 respectively, by two independent mechanisms.

The first is S3's interaction with an ordering the file documents deliberately. `stripStrings` is called BEFORE the line-comment strip, on purpose (`agent-cap.js:69`), so a whole-line fail-closed hands the raw line to `.split('//')[0]`: a `//` sitting inside a string literal on an unblanked line now truncates the view, and a `parallel(` after it is gone. `const u = 'http://x'; const re = /won't/; await parallel(all.map(f))` DENIES at HEAD and ADMITS under the pass §2 specifies. The same mechanism runs the other way on the corpus §5 names as its evidence: an apostrophe in a trailing `//` comment — don't, can't, it's — unblanks the whole line, and `log('parallel(') // we don't allow it` becomes a newly DENIED legal script, voiding the guarantee stated three lines above `stripStrings` itself. Six such lines sit in `tools/workflows/*.js` today.

The second is S5 read against rule 3's actual code path. Unlike rules 1 and 2, `capFindings` balances parens ACROSS lines through `joinCall`, and `blankLiterals`' own header names that as the reason the view exists at all. An S5 fail-closed line returns raw, so a `)` inside a string or comment re-enters the join, closes a multi-line `boundedParallel(` early, and `topLevelArgs` yields one argument — at which point the call falls through to the helper's DEFAULT of 5 and a declared cap of 50 is never read. Rule 3 was probed with three cases in §4 and none of them is a multi-line call site, which is where every shipped harness writes its fan-out.

`TOOL-dMispairedQuote-1` carries six further confirmed findings and none of them is cosmetic: the two new function names cannot pass the `lexicon naming predicates` leg the unit's own §7 invokes, `stripStrings` has a third consumer neither §2 nor §4's candidate table acknowledges, S4's substitution is reachable on a template-continuation line where it re-injects the exact prose spellings `TOOL-aLexedStripper-2` measured as false denials, and a landed safety argument — `TOOL-aLexedStripper-5`'s "it cannot regress in either direction, because it IS the shipped behaviour" — is falsified by S3 with no scope item, no AC and no supersession naming it.

`TOOL-dMispairedQuote-2` carries no blocker. Its defect is uniform and is the one it was written to prevent: the carrier list is short. Two carriers of the `-5` fallback claim and the `blankLiterals` header — the function unit 1 edits, whose comment records the prior author's refusal of exactly this re-baselining — are out of scope, and the last was already flagged as a stale carrier in `aLexedStripper` spec-audit round 1 and still stands unedited at HEAD.

## Two notes on what the fan did NOT find

**No contradiction between the two specs was confirmed, and that is itself the finding.** The hunt was explicitly for one. What turned up instead is a systematic UNDER-reach in unit 2: unit 1 changes three functions and unit 2's carrier list covers the headers of one of them plus two notes. Findings 33 and 34 are the same defect filed against different lines — unit 2 was scoped from the reported defect's carriers rather than from unit 1's touched set. The two specs do not disagree; unit 2 simply does not describe all of what unit 1 does. The mechanical fix is to derive unit 2's carrier list FROM unit 1's files-touched rather than authoring it, which is §6's own rule applied to a spec instead of to a document.

**Both blockers are the same architectural mistake, made twice.** S3 and S5 each add a per-line fail-closed to a view, and each was reasoned about as though that view's consumer read one line at a time. Rule 1's consumer does not — it strips `//` afterwards, and `stripStrings` runs first on purpose. Rule 3's consumer does not — `joinCall` balances forward across up to 200 lines, which its own header says is the whole mechanism. A fail-closed that returns a RAW line is only fail-closed with respect to the view; with respect to the consumer it is a fail-OPEN, because the raw line carries delimiters the blanked one had neutralised. If round 2 takes one design idea from this report it should be that: blank literal CONTENTS and keep the delimiters, so an unpairable quote costs precision rather than structure.
