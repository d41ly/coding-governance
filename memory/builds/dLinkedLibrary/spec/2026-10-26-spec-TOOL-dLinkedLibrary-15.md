## 1. Goal

Enrichment keyed by file or feature rots: 25 of 31 dossiers are stale at HEAD, and 60% of code files
change in a week against 3.4% of definition bodies (gap-mem-29, research-code-orientation.md:92).
This unit gives each definition of the `code` record a purpose: derived first from its docstring or
header comment, which 69.1% of Python definitions and 49.6% of shell functions carry, then from an
agent's pass as `memory.code-enrich` says, each written purpose keyed to its definition's body hash
and stale when that hash moves, and every definition with no purpose held in a pending population
checked both ways against the record (night pass point 3, item 3; the owner's NP-11).

## 2. Scope (IN)

The record, its definition key `<path>::<qualified name>` and its body hash `code_row.hash` are
TOOL-dTotalRecall-8's S2 and S7 (shared interface I18), cited and never re-spelled; a row with no hash
is never fresh. The ledger factory, its `[[ledger]]` registration, `write_rows` and its both-ways
compare are TOOL-dWitnessedBar-13's S1, S2, S4 and S10. The memory-tree policy adapter
`read_policy_value` is TOOL-dTotalRecall-8 S10's `tools/memory-tree/policy_value.py`, over
dGroundRules' `resolve` (`tools/policy/policy.py:752`). All but `resolve` are DEFERRED at base
`5fede642` and are a build-run precondition.

- **S1** — The module, `tools/memory-tree/code_enrich.py`. `derive_source_purpose(lang, text, line,
  end_line)` reads one definition's own text: for Python, the first sentence of its docstring through
  `ast.get_docstring`; for every other language, the contiguous `#` or `//` comment block ending on
  the line above `line`, first sentence. The text rules are TOOL-dTotalRecall-16 §4 "Derivation
  order"'s: one line, at most 120 bytes cut at a word boundary, and a text that only repeats the
  definition's name is no purpose; they are applied through `derive_purpose`'s normaliser in
  `record_kinds.py`, imported within the kit, and factored out of it at this second instance if it is
  inline. Derived purposes are cached per blob in an index table `code_purpose(blob, key, hash,
  purpose, source)`, written through PLAY-dOrderedCharter-19 S4's `build_index`, so a blob is read
  once. Observed by AC1.
- **S2** — The key, `memory.code-enrich`, read once per run by `read_policy_value("memory.code-enrich",
  root)`, choosing the second source after the derived one, per §4 "The values": `symbol-hash-slots`,
  the default, a written slot; `in-code-notes`, a `gov:note` line on the definition, read through
  TOOL-dLinkedLibrary-4's `parse_note_line`; `derived-only`, none. The catalogue row
  (`tools/policy/catalogue.toml:1416`, owner dLinkedLibrary, default `symbol-hash-slots`) gains its
  `summary` and `usage`, and its name leaves `tools/policy/unsummarised-keys.txt` (line 125 at base)
  through `policy.py lists --write`; the mirror `.governance/policy.json` is regenerated by
  `policy.py mirror --write`. Observed by AC4 and AC7.
- **S3** — The slots, `memory/project/code-purposes.tsv`, one row `<key>\t<hash>\t<purpose>` per
  written purpose, sorted by key. A slot is fresh while its key is in the record and its hash equals
  the definition's body hash; stale when the key is there and the hash differs; an orphan when the key
  is gone. Observed by AC2 and AC3.
- **S4** — The write boundary, `python code_enrich.py write <file>`, the one writer of the slots:
  each input row `<key>\t<hash>\t<purpose>` is refused, exit 2 naming the row and the reason, when its
  key is not in the record at HEAD, its hash is not that definition's hash, its purpose breaks S1's
  text rules or carries a control character or a backtick, or the key already holds a fresh slot.
  Accepted rows replace any stale slot for the key. Under `in-code-notes` and `derived-only` the verb
  refuses, naming the value. Observed by AC5.
- **S5** — The agent's pass. `python code_enrich.py pending [--kit <kit>] [--limit <n>] --brief`
  prints a self-contained task: up to `<n>` pending definitions (default 40), each with its key, its
  hash, its `path:line-end_line` range and the text rules, and the answer format S4 reads. Any agent
  run with that task, a session's own `Agent` call or a later cadence item, reads each range and
  returns the rows; the caller writes its return to a file under its scratch and runs S4. Under a
  value other than `symbol-hash-slots`, `pending --brief` refuses, naming the value, so no agent is
  asked to write a purpose that will not be read. Observed by AC6.
- **S6** — The pending population, `code-purpose-pending`: a `[[ledger]]` table in
  `tools/memory-tree/kit.toml`, `key = "key"`, `fields = ["definition", "reason"]`, `drain = "none"`,
  `direction = "declared-set"`, `seed = ["python", "{prefix}/memory-tree/code_enrich.py",
  "--measure"]`, `home = "memory/project/code-purpose-pending.txt"`. `--measure` prints one row per
  definition with no purpose, `reason` being `none` or `stale`. The two files join the conf's
  `PROJECT_REGISTRY_EXTRA` so hygiene check 3 admits them. Observed by AC3.
- **S7** — The both-ways check, `python code_enrich.py --check`: red, exit 1, on an orphan slot, and
  on any finding of the factory's both-ways compare of the population against `--measure`, so a
  purposeless definition missing from the population and a population row whose definition now has
  a purpose are each red. `--write` re-renders the population through `write_rows` and writes the slot
  file without its orphan rows; it is a `[[generated]]` row of `tools/memory-tree/kit.toml` (`write` `--write`, `check`
  `--check`), so a landing regenerates both. A stale slot is always kept: it stays, marked stale,
  until S4 replaces it. Observed by AC3.
- **S8** — `gov_code.py show` (TOOL-dLinkedLibrary-14 S2) ends each line with the definition's
  purpose, `· <purpose>` when fresh or derived, `· <purpose> (stale)` for a stale slot, and `·
  purpose pending` otherwise. Observed by AC2.
- **S9** — The fixture, `python code_enrich.py --fixture --plant <case>`: a scratch repository with a
  committed `.governance/policy.toml`, holding `a.py` (`f` with a docstring, `g` without), `s.sh` (a
  function under a header comment and one without), and its record derived by `code_record.py`. The
  plants are §6's. Observed by AC1 to AC6.
- **S10** — The page `help/code.md` (TOOL-dLinkedLibrary-14 S10) gains a section on purposes: where
  each comes from under each value, what stale means, and how to run the agent's pass. Observed by
  AC8.

### Alternatives rejected

- **Purposes keyed by file or dossier.** The research measured them rotting: 60% of files change in
  a week against 3.4% of bodies.
- **Slots in the index alone.** The index is a node-local cache; an agent's written purpose would not
  reach another node, so written slots are tracked and only derived ones are cached.
- **A workflow script for the agent's pass.** A new `tools/workflows/` script moves that kit's
  version, read from the review harness's template, for a pass that is one agent and one task;
  `pending --brief` gives any caller the same task with no new surface.

## 5. Production-readiness checklist

- security — S4 is the one write boundary for agent-written text other agents read: one line, at
  most 120 bytes, no control characters or backticks, key and hash checked against the record; the
  pass runs under no new grant.
- perf / scale — derived purposes are cached per blob; `--measure` reads the cached tables only.
  The population is about one row per undocumented definition, re-rendered at each landing.
- error / empty / loading states — a refused row names its reason; a refused value names itself; an
  empty slot file reads as no slots.
- observability — `--check` names each orphan and each compare finding; `show` names each purpose's
  state.
- risks — a stale slot's text may still be right; it stays visible, marked stale, so a writer can
  confirm it with one S4 row.
- testing — the plants of S9.
- migration — the population's first seed, S6.
- user docs — `help/code.md`, S10.

## 6. Acceptance criteria

- **AC1** — When `python code_enrich.py --fixture --plant derive` runs, `a.py::f` takes its
  docstring's first sentence with source `docstring`, the commented shell function takes its header
  with source `header`, and `a.py::g` and the bare shell function are in `--measure`'s output with
  reason `none`.
  Red when: a definition with a docstring is pending, or a name-only comment counts as a purpose.
- **AC2** — When the plant `slot` writes one row for `a.py::g` through `code_enrich.py write`,
  `gov_code.py show a.py::g` ends `· <that purpose>`; after a second commit edits one line of `g`'s
  body, `show` ends `(stale)` and `--measure` lists `a.py::g · stale`.
  Red when: a slot survives a body change as fresh, or a change to another definition stales it.
- **AC3** — When the plant `join` deletes `g` from `a.py` while its slot stays, `code_enrich.py
  --check` exits 1 naming the orphan; with the population's `a.py::g` row deleted while `g` still has
  no purpose, it exits 1 naming the missing row; with a docstring added to `g` and its row kept, it
  exits 1 naming the stale row; after `--write`, it exits 0.
  Red when: either side of the join can drift without a red.
- **AC4** — When the plant `values` commits `memory.code-enrich = "in-code-notes"`, a `gov:note`
  inside `g`'s range gives `g` its definition text as the purpose and the slot file is not read; with
  `"derived-only"`, `g` is pending though a slot names it.
  Red when: a value's second source is read under another value.
- **AC5** — When the plant `refuse` passes `write` five rows, one each with a key not in the record,
  a wrong hash, a two-line purpose, a 121-byte purpose and a purpose equal to the name, each is
  refused, exit 2 naming the row and the reason, and the slot file is unchanged.
  Red when: any of the five reaches the file.
- **AC6** — When the plant `brief` runs `pending --limit 2 --brief`, it prints two definitions with
  their keys, hashes and ranges and the answer format; under `derived-only` it exits 2 naming the
  value.
  Red when: the brief omits a hash, or a non-default value still yields a task.
- **AC7** — When `python policy.py get memory.code-enrich` runs in a repository whose policy file
  sets no value, it prints `symbol-hash-slots`, and after `policy.py lists --write` the summary list
  no longer names `memory.code-enrich`.
  Red when: the row is missing or still unsummarised.
- **AC8** — When `grep -n "memory.code-enrich" code.md` runs over the help page, it finds the purposes
  section naming the three values and the stale state.
  Red when: the page does not describe where purposes come from.
