## HIGH

### D-1 — The walk's repository test fails on a malformed-config submodule, so AC9's refusal is unreachable (id 9)

- **Where:** TOOL-dSafePassage-45 §2 S12, §4 "The walk's repository test", §6 AC9.
- **What is wrong:** S12 classes a directory as a repository when `git --git-dir=<d> rev-parse --git-dir` exits 0. On a real submodule repository whose `config` is malformed, that command exits 128 (`fatal: bad config line 8`, reproduced on git 2.54.0.windows.1). The walk (`spec-45.md:233-238`) lists `c` only on exit 0 and sends every other directory to `walk(c)` as a name segment. So such a repository is never listed, and the `config --list` that S12 (`:138`) makes a refusal never runs on it. The walk also descends into its `objects/` and `refs/` trees, which S12 says it never walks.
- **Consequence:** Built as written, a submodule repository with an unparseable config is skipped without a word. AC9 (`:356-360`) requires `submodule-config-malformed` to be refused, naming the config file, and calls "a failed read is skipped" red. So AC9's second half is red on a correct build, or a builder invents a rule the spec never states.
- **Fix:** REJECTED by the skeptic, whose corrected fix is the following. Classify `c` as a repository by its structure alone: a `HEAD` file plus `objects/` and `refs/` directories, the shape git's own `is_git_directory` checks. Do not parse rev-parse's stderr. Run `git --git-dir=c config --list` on every directory so classified, and refuse any non-zero exit, naming `c/config`. Descend only through directories that are not so shaped and through each repository's `modules/`. State in §4 which case lands where. The build runs `--plant submodule-config-malformed` and sees exit 1 naming the module's config file.
- **Left-shift gate:** A checklist entry: a classifier that decides "is this an X" must not be a command that itself fails on a broken X. The spec plants a broken X and shows which branch it lands in.

### D-2 — `sendemail.sendmailCmd` and the identity forms of send-email's executor keys pass the step contract (id 10)

- **Where:** TOOL-dSafePassage-45 §2 S5 and S6, §7 "What the check does not cover".
- **What is wrong:** S5 and S6 ground the send-email executor row in git-send-email's own source, but cover only `sendemail.smtpServer` and its identity form. That same source reads `sendemail.sendmailCmd` (`git-send-email:394`) and runs it through `sh -c` (`:1787`). It also reads every known key under `sendemail.$identity` (`:541`), so `ccCmd`, `toCmd`, `headerCmd` (`:381-384`) and `sendmailCmd` all have identity forms. `git help --config` lists neither `sendemail.sendmailCmd` nor any identity form, only `sendemail.<identity>.*`. TOOL-dSafePassage-29's class arm keeps only keys that listing names, and its table row (`spec-29.md:99`) covers only the three unqualified `Cmd` keys. No spec mentions `sendmailCmd`, and §7 names no executor gap.
- **Consequence:** A target config holding `sendemail.sendmailCmd = <cmd>` or `sendemail.work.ccCmd = <cmd>` passes the step contract. Any step that reaches git send-email then runs the target's command, which is the executor class this contract exists to refuse. The path is narrow, but it is a security bypass, and §7 reads as if send-email were closed.
- **Fix:** Judged SOUND. Add rows to S6 and §4 for `sendemail.sendmailCmd` and for `sendemail.<x>.sendmailCmd`, `sendemail.<x>.ccCmd`, `sendemail.<x>.toCmd` and `sendemail.<x>.headerCmd`, refused with any value. Extend AC3 with `sendemail.sendmailcmd` and `sendemail.work.cccmd` valued `x`, both refused. State in §7 that `git help --config` does not list every key git's own scripts read, naming `sendemail.sendmailCmd`. D-8 is the same defect at medium; make both edits as one.
- **Left-shift gate:** A checklist entry: a key class derived from `git help --config` is cross-checked against the consuming script's own option table, and a cited source's rule (here, "every key under `sendemail.$identity`") is applied to every key it covers, not to one instance.
