## HIGH

### H1. Rolling back a case-only rename deletes the file it just restored, and reports it restored [id 3]

- **Where:** `tools/govkit/govkit.py:11078` (88's `own_file`/`in_place` split), the snapshot at `tools/govkit/govkit.py:10745-10747`, and the restore loop at `tools/govkit/govkit.py:8390-8461` (the unlink at `:8426`).
- **What is wrong:** Before 88, a case-only rename (`d/keep.txt -> d/Keep.txt`) was refused as occupied, because `ndp.exists()` is true on a case-insensitive filesystem (base line 11101). In 88, `own_file` lets it through by samefile while `in_place` stays false, so it runs `git mv`. Then `renamed.extend([old_path, new_dest])` at `:11215` puts both spellings into written_paths (`:11718`). The snapshot records them as two separate paths, [old, new]. index_read keys on the path git returns, so the new spelling's before-entry is None (`:10804`). On rollback the loop restores the old spelling first, with `update-index` and `checkout-index -f`. It then takes the absent-before branch for the new spelling: `git rm --cached --ignore-unmatch`, then `(target / p).is_file()` and `unlink()` at `:8426`. On a case-insensitive filesystem the new spelling resolves to the file it just restored.
- **Consequence:** The trigger is a kit holding a case-only renamed row that is held back or whose check goes red. If the bytes are equal, the rollback deletes the restored file from the working tree. Both paths still go into `restored`, so the order reports success while `git status` shows ` D d/keep.txt`. If the bytes differ, `git rm --cached` refuses, and the row is PART restored with both spellings left in the index. A skeptic reproduced both outcomes in a scratch repo with `core.ignorecase=true`. The path is narrow, but a rollback that reports `restored` while the file is gone grades high.
- **Fix (finder's fix REJECTED by the skeptic; this is the skeptic's corrected fix):** Process each snapshot row's absent-before paths ahead of its pre-existing ones. Unstage and unlink the new spelling first, while its index entry still matches the landed bytes. Only then run update-index and checkout-index on the old spelling. The alternative is to keep the order, skip the unlink when the absent-before path is `os.path.samefile` to a path already restored in this row, and still drop its index entry (for example with `git rm --cached -f`). Either way, add the [dSP-88] rollback check below.
- **Gate:** A `[dSP-88]` rollback check in selftest. Run a case-only rename of `pinned/demo/keep.txt` in a kit whose check goes red, or which a refused sibling row holds back. On a case-insensitive node, assert that `pinned/demo/keep.txt` is on disk with its pre-run bytes, that the index holds exactly one entry for the path, and that the order does not report a restore it did not make. Observe the check red at 112e587ea before landing the fix. Also see M2, which is the same defect.

## MEDIUM

### M1. The samefile exemption skips the index check, so a case-only rename overwrites a different tracked file's index entry [id 1]

- **Where:** `tools/govkit/govkit.py:11109`, with `own_file` set at `:11078`.
- **What is wrong:** At base the guard was `if new_dest in _at_dest or ndp.exists():`. At 112e587ea it is `if not own_file and (...)`, and `own_file` is true whenever samefile holds, which also skips the index arm. Take a case-insensitive checkout whose index holds two case-colliding entries, such as `d/x` and `D/x`. A case-only rename `d/x -> D/x` skips the occupancy refusal, and `git mv` then silently overwrites the other file's index entry.
- **Consequence:** This is the harm the comment at `:11089-11092` says the index read exists to stop ("git mv would take its index entry without a word"). Update stages the loss of a different tracked file. The target's next commit deletes `D/x`, and if that blob was only staged it is left dangling. A scratch repo with `core.ignorecase=true` reproduced it: `git mv -- d/x D/x` exited 0 and left one entry, `D/x`, holding d/x's blob, and the planted blob was gone from the index. The path is narrow, the loss is staged and visible, and committed content is still in HEAD, so the grade is medium.
- **Fix (judged SOUND by the skeptic):** Let samefile exempt only the disk check, and keep the index check unless the spelling is exact: `if (new_dest in _at_dest and not in_place) or (ndp.exists() and not own_file):`. A genuine case-only rename still passes, because `ls-files` matches pathspecs case-sensitively, so `D/x` is absent from `_at_dest` when only `d/x` is tracked.
- **Gate:** A `[dSP-88]` check in build_rename_gov's block. It plants a case-colliding index entry with `update-index --cacheinfo`, then asserts that the row is refused and that both entries survive. Observe it red at 112e587ea before landing the fix.
