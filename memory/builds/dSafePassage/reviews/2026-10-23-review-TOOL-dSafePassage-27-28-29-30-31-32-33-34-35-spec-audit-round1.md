### D-1 — The modules walk reads the common dir, so it misses a linked worktree's own submodules (id 8)

- **Where:** TOOL-dSafePassage-30 §2 S1 (second bullet) and §4 "Why both halves of the population".
- **What is wrong:** S1 walks `<common dir>/modules/`. A linked worktree keeps its submodules' git dirs under its own `$GIT_DIR/modules/`. The skeptic reproduced it on git 2.54.0.windows.1. In a linked worktree `wt1`, `s/.git` read `gitdir: ../../sup/.git/worktrees/wt1/modules/s`, and two configs existed: `sup/.git/modules/s/config` (the main worktree's) and `sup/.git/worktrees/wt1/modules/s/config`. The walk visits only the first.
- **Consequence:** Gov's own tree under `.claude/worktrees/` is usually a linked worktree. An absorbed submodule there that is not checked out can declare an executor in `.git/worktrees/<wt>/modules/<name>/config`. The modules walk never visits it, and the gitlink walk skips it because it has no `.git` entry. The check passes. A step that runs `submodule update` then populates the submodule and runs its config, which is the hole S1 says it closes. The walk also refuses on the main worktree's submodule configs, which this target never enters.
- **Fix:** Judged SOUND. In S1, walk `<git dir>/modules/` (from `rev-parse --absolute-git-dir`), and also `<common dir>/modules/` only when the two directories are the same. Correct §4's reason to match. Add a plant `submodule-unpopulated-worktree`: a linked-worktree target whose own `$GIT_DIR/modules/<name>/config` sets `filter.canary.clean`, refused under AC3.
- **Left-shift gate:** A checklist entry: a walk over git's on-disk layout names which directory (git dir or common dir) each artefact lives in, and its plants include a linked-worktree target.

### D-2 — The predicate keeps a key by its last segment alone, so `gc.recentObjectsHook` and the `ext::` transport pass (id 28)

- **Where:** TOOL-dSafePassage-29 §4 "The predicate" and "Data model", §5 security, §7 "What the check does not cover".
- **What is wrong:** The predicate over `git help --config` keeps only keys whose last segment is in a hand-typed list. The skeptic applied it to git 2.54.0's 1006-line listing: it kept 43 keys, matching the pin, and the only kept keys containing `hook` were `core.hooksPath` and `hook.<friendly-name>.command`. `gc.recentObjectsHook` runs a shell command during gc or cruft packing and can be reached from `git commit` through auto-gc. `protocol.allow` / `protocol.<name>.allow` plus `url.<base>.insteadOf` enables the `ext::` transport, which runs an arbitrary command on a fetch or push. Neither table lists them. §5 claims "deny by default over the whole class git documents", and §7 exempts only keys git adds later.
- **Consequence:** A target config with `gc.recentObjectsHook` and a low `gc.auto`, or with an `ext::` rewrite, runs adopter code in a step while the arm certifies the class covered.
- **Fix:** REJECTED by the skeptic, whose corrected fix is the following. Make the predicate keep any key whose last segment ends in `hook`. Give `advice.ignoredHook` (a boolean) and `uploadpack.packObjectsHook` (honoured only from protected config, which `build_step_env` turns off) unrefused rows. Add a refused row for `gc.recentObjectsHook` (any value). Close `ext::` structurally rather than by value rules: add `protocol.ext.allow=never` as a further command-scope `GIT_CONFIG_KEY_<n>` pair in `build_step_env`. It outranks any local `protocol.allow` or `protocol.<x>.allow`, and it covers `url.<base>.insteadOf`, `pushInsteadOf` and `remote.<x>.url = ext::…` alike. Have an isolation plant assert that an `ext::` fetch is refused by git. Correct §5 to say "the class the predicate names", and list in §7 the executors the predicate reaches by no suffix.
- **Left-shift gate:** A checklist entry for the bug class "a derived class claimed whole while its predicate is a name list". The arm must also grep the source listing for "shell", "command" or "program" and red on a hit that neither table names.

- **Where:** TOOL-dSafePassage-35 §2 S8 and §6 AC8.
- **What is wrong:** S8 lists `remote.<x>.url`/`pushurl`, `http.proxy`, `remote.<x>.proxy`, and `http.sslKey`/`sslCert`/`cookieFile` with their `http.<x>.` forms. `git help --config` also documents `submodule.<name>.url`, `url.<base>.insteadOf`/`pushInsteadOf`, `branch.<name>.remote`/`pushRemote` and `remote.pushDefault` (which may hold a URL), `http.proxySSLKey`/`proxySSLCert`, and `http.<url>.*` keys whose `<url>` segment can carry userinfo. - **Left-shift gate:** A checklist entry: every refusal that prints a config key passes the key through the same redactor as the value, and a secrets plant asserts the secret is absent from all output.
