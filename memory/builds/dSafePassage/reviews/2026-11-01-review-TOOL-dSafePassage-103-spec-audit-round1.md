README line 650 states the same rule: the legacy-homes arm is announced `not graded` "in any tree holding an install receipt". README line 650 will still say such a tree is not graded, while line 653 and the line-174 paragraph carry the exception. The README then gives two answers to one question, and the arm docstrings leave out a finding the code raises. The next change to the census or the legacy-homes arm starts from docs that contradict the code. The non-goals forbid only code edits to `arm_legacy_homes`, so they do not cover these doc edits.
- **Fix (skeptic judged SOUND):** Add README line 650 and check_policy.py 401 and 672 to S4. Name the sites as a class: every line in `tools/policy/README.md`, `policy.py` and `check_policy.py` that ties "install receipt" to the adopter reading or to `not graded`, or that lists the derivation's Refusal causes. Extend AC6 so that `git grep -n -e source-mode -- tools/policy/README.md` must also print the line that replaces line 650, and so that `git grep -n "any tree holding an install receipt" -- tools/policy/README.md` must print nothing at the build commit.
- **Left-shift gate:** Add a checklist entry for spec doc lists: run `git grep -n -i 'install receipt\|install.json' -- tools/policy/` (or the equivalent grep for the rule being changed), and every hit outside a code identifier either carries the exception or is listed as unchanged. ### L6. S2's two-registry promise has no scenario that observes it (id 9)

- **Where:** spec section 2 S2 (lines 34-36) and section 4 "The regression case" (scenario table, lines 204-208).
- **What is wrong:** S2 promises that a source-mode receipt beside two or more registries raises the search's existing Refusal, "Observed by AC5". The scenarios cover only `source-mode receipt`, `adopter receipt` and `no registry`, and AC5 checks the `no registry` line and the summary count.
- **Consequence:** A build could make the multi-registry case end somewhere else, for example by re-raising S2's message or by answering from the receipt's `prefix`, and every AC would stay green. The risk is small, because both branches call the one moved function. Breaking it would take a deliberate edit.
- **Fix (skeptic judged the finder's fix UNSOUND; this is the skeptic's corrected fix):** Add a fourth scenario, `source-mode receipt, two registries`. It builds the source receipt, the registry at `written[0]`, and a copy at `planted` from `derive_window_edge_paths` (a depth-2 path inside the search window). It expects a Refusal whose path is `', '.join(sorted((written[0], planted)))`, not `RECEIPT_REL`. Bind it to AC5.
- **Left-shift gate:** Add a checklist entry: every "raises" or "refuses" promise in an S-item names the scenario that builds its tree, and the criterion that cites it checks that scenario's line.

### L7. The regression case does not say an unexpected Refusal must print a WRONG line (id 10)

- **Where:** spec section 4 "The regression case" (blob line 210).
- **What is wrong:** The spec says the case catches only `subprocess.CalledProcessError` and `OSError`, "as its sibling does". It leaves out the sibling's `ask()` wrapper (check_policy.py 4203-4207), which turns a `policy.Refusal` into a value the case can compare. `check_legacy_graded` lets a Refusal propagate to its caller, and the outcome-case loop in `run_fixture` (check_policy.py 4483-4488) does not catch it.
- **Consequence:** An unexpected Refusal in the `source-mode receipt` or `adopter receipt` scenario ends the run in a traceback, not in that scenario's `policy-fixture:` WRONG line, and the case's remaining checks do not run. The bar still goes red, so only diagnosis suffers.
- **Fix (skeptic judged SOUND):** Have each scenario call the functions through one wrapper, as `run_census_window_edge`'s `ask()` does, so that a Refusal becomes a value. The scenario compares that value with its expected result and prints WRONG on a mismatch.
- **Left-shift gate:** Add a checklist entry for fixture cases: a case that calls a Refusal-raising function routes every call through a Refusal-to-value wrapper.
