## 1. Goal

A landing leaves no record a second node can read: today it is a node-local log line, the lander's
marker file and two run-state facts. This unit builds `deploy.record`: one ref-held record per landed
SHA, `refs/gov/landing/<sha>`, carrying what landed, how it was gated and what its checks said, and
`read_landing`, the one reader every later Deploy item goes through.

The clause is three words, "the landing record", and the token arm cannot see it (the packet's Items
line 1), so this spec states the fields: they are `flow-steps.md:439` and `layer-memory.md:430`, with
pin C2 for the home.

## 2. Scope (IN)

- **S1** — The record: one commit over the empty tree at `refs/gov/landing/<sha>`, built by
  `build_gov_commit` and written by `write_gov_ref` (TOOL-dPlacedRequest-11 S1, S2; pin C2). Its
  message is the header `gov-landing <sha>`, a blank line and one `<key>: <value>` line per field of
  `LANDING_FIELDS`, in that order (§4 "Data model"). `render_landing_body(fields)` writes those bytes
  and `parse_landing_body(text)` reads them, both in `tools/loop/deploy_items.py` (pin C1). Observed
  by AC1.
- **S2** — The writer, `unattended.sh --deploy record <slug> <sha>`, the shell verb of `deploy.record`.
  It takes `outcome`, `pre-push` and `landing_prior_tip` from `read_landing_outcome <sha>`
  (DEPL-dShippedRelease-12), `units` from the `units-at-landing` fact of the build's run-state file at
  `<sha>`, and `closes` from `read_policy_value("build.closes", root)`. It writes `core`, `distill` and
  `review` as `pending`, `patch-key` and `carries` as `-`. A class of `refused`, `unreachable` or
  `argument` is no landing: the verb exits 1 naming the class and writes nothing. Observed by AC1, AC2.
- **S3** — The take-over reading: where this node holds no local outcome record, as a second node
  after a take-over does not, `read_landing_outcome` derives from the remote and answers `landed-ungated`
  (DEPL-dShippedRelease-12 S8). This verb copies that class and writes `pre-push: ungated · no outcome
  record on this node`, so it never infers a gate it did not read (flow-steps:439, "otherwise the
  pushed SHA and the remote tip"). Observed by AC3.
- **S4** — The reader, `read_landing(sha, root)` and `python deploy_items.py read-landing <sha>`. One
  bounded fetch of the ref into `refs/gov/remote/landing/<sha>`, then the parse. It prints one
  `<key><TAB><value>` line per field and exits 0; exit 1 printing `landing — <sha8> · absent` for no
  ref; exit 1 printing `landing — <sha8> · refused · <why>` for a record that fails S5; exit 2
  printing `landing — <sha8> · dead probe · <why>` for a failed fetch, which is no answer and never
  `absent`. Observed by AC1, AC4, AC5.
- **S5** — The claim check, inside `read_landing`, because a ref write is no tree change and no bar
  grades the record's content (pin C2). It refuses a record whose header or `sha` field differs from
  the ref's name, a missing or unknown field, an `outcome` outside the three landed classes, and a
  `sha` the advertised default branch does not contain. Observed by AC4.
- **S6** — The field write, `set_landing_field <sha> <key> <value>` in `unattended.sh`, reached as
  `unattended.sh --deploy field <sha> <key> <value>`: it reads the tip, builds a commit parented on
  it through `build_gov_commit <tip> <message>` with the one field changed, and writes through
  `write_gov_ref <ref> <tip> <commit>`, re-reading and re-applying on a lost compare-and-swap, three
  attempts at most. A write of an equal value writes nothing. Only `core`, `patch-key`, `distill`,
  `review` and `carries` are settable. Observed by AC5, AC6.
- **S7** — Idempotence: a second `--deploy record` for one SHA whose first write stands prints
  `landing — <sha8> · already recorded` and writes nothing, whatever later fields have moved.
  Observed by AC2.
- **S8** — The dark switch: `RUN_CLAIMS` off (`tools/unattended/unattended.sh:673`) prints
  `landing — not written: RUN_CLAIMS is off` and exits 0, the switch every lease write honours.
  Observed by AC7.
- **S9** — The kind: a `landing` row in `tools/memory-tree/record-kinds.toml` through `python
  record_kinds.py new` (TOOL-dTotalRecall-1 S9), §4 "The kind row"; its `<!-- gen:record-kinds -->`
  region moves in `tools/memory-tree/HYGIENE.template.md` by `record_kinds.py --write`. Observed by AC8.
- **S10** — The item armed: the `item.deploy.record` row of `tools/loop/loop.toml`
  (TOOL-dDeclaredLoop-12 S2) gains `returns = "record-kind.landing"` and the witness "the landing
  record", and its `[[stand-in]]` row (TOOL-dDeclaredLoop-13 S8) leaves in the same landing, as that
  unit's non-goal asks of an owning build. Observed by AC8.
- **S11** — The leg `deploy items`: one `[[gate_leg]]` row of `tools/loop/kit.toml` running `python
  tools/loop/deploy_fixture.py --all`, made by `leg_factory.py new` (TOOL-dWitnessedBar-11), rendered
  into `tools/gate-legs.json`, the home of this build's core Deploy cases. `deploy_fixture.py` builds a
  bare remote and two clones under `%TEMP%` with short names, as `door_fixture.py` does
  (TOOL-dWellOiledMachine-58 S10). Observed by AC9.
- **S12** — The docs: `tools/unattended/VERBS.template.md`, rendered to
  `memory/guides/UNATTENDED-VERBS.md`, gains `--deploy record` and `--deploy field`; `help/deploy.md`

  `KIT_UNATTENDED_VERSION` moves. NOT OBSERVED by a criterion: prose, read by the memory hygiene leg

  and this one is outside them, so S5 is the guard (§5 security).

### Data model

```
refs/gov/landing/<sha>    message:

gov-landing <sha>

sha: <40 hex>
builds: <slug>
units: <unit id> [<unit id> ...]
outcome: landed-gated | landed-ungated | nothing-pushed
pre-push: <gate run id> | ungated[ · <why>]
core: pending | green | red | refused
patch-key: - | <12 hex>
closes: at-landing | after-release-verifies | at-landing-maintain-owns
distill: pending | <DEPL-dShippedRelease-2's line>
review: pending | <DEPL-dShippedRelease-14's line>
carries: - | <DEPL-dShippedRelease-27's value>
```

| Field | Written by | Source |
|---|---|---|
| `sha`, `builds`, `units`, `outcome`, `pre-push`, `closes` | this unit | S2, S3 |
| `core`, `patch-key` | DEPL-dShippedRelease-13 | `read_core_verdict`, `derive_red_key` |
| `distill` | DEPL-dShippedRelease-2 | the `deploy.distill` line |
| `review` | DEPL-dShippedRelease-14 | the landing review's state |
| `carries` | DEPL-dShippedRelease-27 | the range from `landing_prior_tip` |

`builds` holds the one slug the verb was handed, a list in form only: the lander refuses a carried
commit of another build (`check_carry_set`, `tools/push-main.sh:962`), so a landing carries one build.
A field's value holds no newline and `render_landing_body` refuses one.

`landing_prior_tip` is no field, since `carries` is what the range produces (shared interfaces I1,
I8). This unit prints it, `landing — <sha8> · recorded · from <prior8>`, so the line names the range
DEPL-dShippedRelease-27 reads.

### The kind row

```toml
[[record-kind]]
name = "landing"
tag = "record.landing"
layer = "layer.flow"
home = "refs/gov/landing/*"
id-rule = "<landed sha>"
schema = { form = "header", source = "tools/loop/deploy_items.py:LANDING_FIELDS", fields = [
  "sha", "builds", "units", "outcome", "pre-push", "core", "patch-key", "closes", "distill", "review", "carries"] }
writer = "unattended.sh --deploy record"
readers = ["deploy_items.py read-landing"]
lifecycle = "append-only"
check = "deploy items"
```

`form = "header"` because no tracked file carries `**Key:**` lines for it (TOOL-dTotalRecall-1 §4); a
`refs/gov/<glob>` home is legal (TOOL-dTotalRecall-18). The `source` literal keeps the two field lists
one fact, compared by that unit's gate.

## 5. Production-readiness checklist

- security — any push grant can write this ref, and it sits outside the coordination door, so the
  content is a claim: S5 refuses a mismatched SHA, an unknown field and a SHA the default branch lacks,
  and DEPL-dShippedRelease-13 re-reads `core`. The body is a closed field set with no free text beyond
  `pre-push`'s reason, and no secret reaches it.
- perf / scale — one bounded fetch per read; one ref per landing, so `refs/gov/` grows by one per landing.
- error / empty / loading states — `absent` and `dead probe` are distinct; a non-landing class writes nothing.
- observability — every verb prints one `landing —` line naming the short SHA.
- risks — a record a pusher forged with a true SHA and a false `core`: S5 cannot see it, and the unit
  that reads `core` for a decision reads `read_core_verdict` as well.
- testing — `deploy_fixture.py` cases, one per criterion, over a bare remote and two clones.
- migration — none; absent reads as no record.
- user docs — `help/deploy.md`, `memory/guides/UNATTENDED-VERBS.md`.

## 6. Acceptance criteria

- **AC1** — When `python deploy_fixture.py --case landing-written` runs `--deploy record` on one clone
  and `python deploy_items.py read-landing <sha>` on the other, the second prints all eleven fields of
  `LANDING_FIELDS` in order, with `core` `pending` and `closes` `at-landing`, and exits 0.
  Red when: the record is held node-locally, so the second clone reads `absent`.
- **AC2** — When `python deploy_fixture.py --case landing-idempotent` runs `--deploy record` twice, the
  second prints `already recorded` and `git rev-parse refs/gov/landing/<sha>` on the remote is unchanged;
  with a planted `refused` class the verb exits 1 naming `refused` and no ref exists.
  Red when: a second run writes a commit, or a refused push leaves a record.
- **AC3** — When `python deploy_fixture.py --case landing-takeover` runs the verb on a clone with no
  outcome record, `read-landing` prints `outcome<TAB>landed-ungated` and a `pre-push` line opening
  `ungated · no outcome record`.
  Red when: the verb exits refusing, or writes `landed-gated` from a gate it did not read.
- **AC4** — When `python deploy_fixture.py --case landing-forged` plants each of a `sha` field unlike
  the ref's name, an unknown field and a SHA the default branch lacks, `read-landing` exits 1 printing
  `refused` and naming each cause; without the plant it exits 0.
  Red when: any planted record reads as a landing.
- **AC5** — When `python deploy_fixture.py --case landing-field-race` runs two `--deploy field` writes
  of different keys at once, both values stand on the tip and the ref's history holds a line of
  parented commits; with the remote's URL broken `read-landing` exits 2 printing `dead probe`.
  Red when: one write is lost, or a failed fetch reads as `absent`.
- **AC6** — When `python deploy_fixture.py --case landing-field-guard` runs `--deploy field <sha> sha <x>`,
  it exits 2 naming `sha` as not settable; an equal value writes no commit.
  Red when: an identity field moves, or an equal write grows the ref.
- **AC7** — When `python deploy_fixture.py --case landing-dark` runs under `RUN_CLAIMS="off"`, it prints
  `not written: RUN_CLAIMS is off`, exits 0 and no ref exists on the remote.
  Red when: a dark project writes to its remote.
