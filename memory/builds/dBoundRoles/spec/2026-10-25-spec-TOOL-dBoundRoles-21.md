## 1. Goal

Move a role's effort and model onto the owner's policy keys, `roles.effort.<role>`,
`roles.effort.<workflow>.<stage>`, `roles.effort.default` and `roles.model.<role>.<harness>`, read
through dGroundRules's reader, and make the gate grant a field of each role's definition, so a preset
or an owner sets them in one guarded file and the house file `tools/roles/house/policy.toml` becomes the
fallback dConvergedCharter retires. `resolve_stage_efforts`, R12, `handoff.py`'s `stage-efforts` and
`harness-args` and the gate check are re-pointed in this same unit.

## 4. Design

### The order

A stage `s` of workflow `w`, spawned as role `r`; a role's own level for its agent type is the same
order without its stage rows.

| Step | Source | Read through |
|---|---|---|
| 1 | `roles.effort.<w>.<s>` | `read_policy_setting(f"roles.effort.{w}.{s}", root)` |
| 2 | `roles.effort.<r>` | `read_policy_setting(f"roles.effort.{r}", root)` |
| 3 | `roles.effort.default` | `read_policy_setting("roles.effort.default", root)` |
| 4 | the house file, where present: `[effort.stages.<w>] <s>`, then `[effort.roles] <r>`, then `[effort] default` | `load_policy`, as `resolve_stage_efforts` reads it today (`tools/roles/roles_lib.py:565-576`) |
| 5 | the role's declared `effort` | its front matter, through `load_roles` |

The first step that yields a value wins. Steps 1 to 3 are the clause's "stage key, then its role's key,
then `roles.effort.default`". Step 4 is "the house file's `[effort]` ... read only where no key ... is
set", read whole in today's chain so an adopter's own house levels keep applying until a key is set.
Step 5 is "the role's declared value"; while a house file holds `[effort] default` (R12 requires it of a
present file) step 5 is reached only where the file is absent, which is the state dConvergedCharter's
retirement leaves. §8 F1 records why step 4 sits before step 5.

### The model

```
resolve_role_model(slot, harness, root):
    v = read_policy_setting(f"roles.model.{slot}.{harness}", root)
    return v if v is not None else HARNESS_MODEL_EQUIVALENT[harness](declared model)
HARNESS_MODEL_EQUIVALENT = {"claude-code": the declared value, unchanged}
```

`claude-code` is v2's default for `runtime.harnesses` (v2:1220). A key for another harness is never
read by the `claude-code` render, so `roles.model.gov-builder.codex` leaves the rendered model alone.
An unknown harness name passed to the resolver is a `RolesError`, never a guess.

### The grant

```
gates: memory hygiene, lexicon naming predicates?
```

`render_roles_index` writes the per-role `gates` list from the field, the `?` taken off as `load_policy`
takes it off today (`tools/roles/roles_lib.py:483-484`); a role with no field takes its house row, and
a role with neither runs no gate. `check_gate_names(names, legs, where)` returns the defects and notes
`load_policy` builds for `[gates]` today, so both homes are graded by one function against the tool
root's `gate-legs.json`. The house seed's `[gates]` table keeps its header and comment, stating that a
row there applies only to a role whose definition carries no `gates`, and its two rows move into the
two role files.

### The catalogue rows

| Key | `usage` this unit writes |
|---|---|
| `roles.effort.<role>` | `roles.effort.gov-builder = "high"` |
| `roles.effort.<workflow>.<stage>` | `roles.effort.spec-review.skeptic = "medium"` |
| `roles.effort.default` | `roles.effort.default = "medium"` |
| `roles.model.<role>.<harness>` | `roles.model.gov-builder.claude-code = "opus"` |

Each `summary` states the step the key takes in §4's order. A dotted key with three segments after
`roles.effort` is the stage key and one segment the role key; TOOL-dGroundRules-2 S4's
`read_catalogue_row` matches each to its row by segment count, so `default` reserved (S4) is what keeps
step 2 from reading the blanket as a role.

- **`policy.py get` as a subprocess per key.** A render reads up to one model key and two effort keys

- **The declared effort before the house file.** It silently drops every level an adopter set in its
  house file the moment gov's role declares one (§8 F1).

## 5. Production-readiness checklist

- security — no new write path; every key is read at the landed revision through the guarded file's
  one reader, so an agent's uncommitted edit to the policy file moves no level.
- perf / scale — one landed revision per run and one `resolve` per key read, about forty per render;
  the pass measures the render's wall before and after and states both in its commit.
- error / empty / loading states — no policy kit is one note and the keys read as unset; a reader
  refusal is exit 2 naming the key; an absent house file is an empty fallback.
- observability — `stage-efforts` prints the levels; `resolve` with `--explain` names each key's source.
- risks — a stale render after a key change; the restart line `render_agents.py --write` prints covers
  it, as for the house file today.
- testing — each criterion is a probe over a fixture repository; the arms in §7 are observed RED then
  GREEN by the main loop at the close.
- migration — none owed by a default adopter, as §4 Migration says.
- user docs — `help/policy.md` (TOOL-dGroundRules-1 S8) lists each catalogue row from the catalogue;
  the four rows' `summary` and `usage` are what it shows, filled by S8.
