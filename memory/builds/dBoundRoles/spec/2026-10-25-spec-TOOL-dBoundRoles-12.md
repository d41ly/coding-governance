## 1. Goal

Placement is the one judgment left at entry, and it is the orientation scout's, never the driver's:
the driver reads state only (`driver.reads`, v2:1179) and records what the scout returned (the flow
items research, `memory/builds/dClosedLoop/build/2026-10-15-build-PLAY-dClosedLoop-1-research-flow-items-a.md:97`).
TOOL-dPlacedRequest-4 specs the disposition grammar, the record and `placement.check`; nothing makes
the record rest on a return the orientation scout actually produced in that shape. This unit binds the
scout's placement return to the typed return channel, so a return missing a key or answering another
role's work order is refused before it is recorded, and gives the attended driver its step: record the
return, then run `placement.check`.

## 2. Scope (IN)

- **S3** — The return answers an orientation work order. The work order the return answers, as

## 4. Design

### Where the binding lives

Every route that records an `agent` placement goes through `placement.py place --return`, which
`write_placement` (`tools/loop/placement.py#write_placement`) takes as the placement under
`agent-places`: the loop's `item.entry.place` names the orienter as its actor, and the unattended
driver's `check_prompt_placement` checks a block a `place` already wrote. Putting the check inside `place` is one call
site for every route, the charter's one-core rule, where a wrapper verb in the roles kit would leave
the item body and the prompt path unbound.

```
place --request <key> --return <file>
  1. text = read <file>
  2. run <roles kit>/handoff.py check-return-file --role gov-orienter --file <file>   # a subprocess
       check_return("gov-orienter", text)                       # I16, unit 5: one line per defect
       answered = the work order `answers` names                   # I14, read as check_return reads it
       MARKER_RE over answered -> role != gov-orienter, or no marker
                               -> "answers a <role> work order"
     exit 1                     -> "placement: refused — return — <line>" each; exit 1
     any exit but 0 or 1        -> refused, naming the exit and the verb's first stderr line
  3. read_scout_return, its outcome (placed) and answers lines admitted (§8 F5),
     then add_placement: resolve the disposition, append, as TOOL-dPlacedRequest-4 landed it
```

The loop kit finds the roles kit the way every kit finds a sibling, `resolve_kit_dir`
(`tools/roles/roles_lib.py#resolve_kit_dir`, carried inline in each kit by the `resolve_kit_dir` parity
row, the loop kit's copy `tools/loop/loop_lib.py#resolve_kit_dir`),
and runs its verb as a subprocess, since a kit imports no sibling kit (PLAY-dOrderedCharter-7 §4 "The
policy reads"; TOOL-dDeclaredLoop-12 S4), the way TOOL-dWitnessedBar-3's `judge` reaches its siblings.
Where the roles kit is not installed, `place --return` refuses naming the three places it looked: an
untyped placement is the gap this unit closes, so it never falls back to reading the block unchecked.

### Why the answered work order's role, and not the return's own claim

A return can say anything about who wrote it. The work order it answers is a rendered file whose
marker carries the role and a task-sha the spawn guard compared at spawn
(`tools/hooks/agent-cap.js@935a910d:737-738`). Reading the role from there is reading a witnessed fact
rather than a claimed one, the [trust] classes' distinction
(`memory/builds/dClosedLoop/build/2026-10-15-build-PLAY-dClosedLoop-1-layer-roles.md:240-248`).

### The driver's step

At base and at HEAD the `/build` Skill's Stage 1 says `/session-kickoff` ran orientation and nothing
runs there (`tools/roles/SKILL.template.md@43c0de5f:40-42`). Kickoff's engine is not the place: it
measures 18310 bytes against its 18432-byte leg (`kickoff engine size <=18KiB`), PINNED at `4283cb44`,
and 18354 bytes, PINNED at `a3efb1d50`, and the scout's spawn is not a kickoff step today. Stage 1 gains three sentences: the two commands of S4 in order, that
the driver acts on a passing check only, and that a refusal of either routes back to the scout. The
Skill is rendered by the roles adopter, so the rendered copy is the template's.

### Inventory

under `placement: refused — return —`; and the plants of §7's arm, `return-untyped` and
`return-wrong-role`. No key or file is minted. The verb leads with the declared verb `check`: `python
tools/lexicon/lexicon.py --suggest check_return_file --as py.function` answered OK on 2026-10-26, and
refuses `validate`, so the name is unit 5's `check-return` read from a file.

## 5. Production-readiness checklist

- security — narrows a write path: `place` writes a placement block only from a typed return that
  answers an orientation work order, so a driver or another role cannot type an `agent` placement.
- perf / scale — one subprocess and one marker read per placement.
- error / empty / loading states — an absent roles kit, an unreadable answered file and an empty
  return each refuse naming the cause; nothing is recorded on any refusal.
- observability — every refusal prints under `placement: refused — return —`, the prefix
  TOOL-dPlacedRequest-4 already uses.
- risks — a scout spawned without a rendered work order has no `answers` target and is refused; that
  is the point, and the Skill's step names the render.
- testing — the plants of §7's arm and the probes of §6; the main loop observes the arm RED then GREEN
  at the close.
- migration — none, per §4.
- user docs — `help/roles.md` per S5; `help/loop.md`'s placement section is TOOL-dPlacedRequest-4's.
