## 1. Goal

P18 makes the decision principles outrank practices in an unattended fork: the role that meets a fork
resolves it by the most feature-rich option, then the most expandable, among the options the core
admits, with a full record, and `run.on-owner-question` lets the owner choose to hold instead (v2:907-913,
v2:1231). Today a resolved fork is a mark naming its resolver and nothing else: `check_mark` reads
`RESOLVED (agent, <date>, delegated)` (`tools/memory-tree/check-memory-hygiene.sh@c2fc4073:2290`) and no record
names the admitted options, their ranking or the pick, so a pick outside the admitted set, or one
that is not the ranking's first, passes. The key `run.on-owner-question` is a catalogue row with no
reader, and `--dispatch` admits a FORKED unit. This unit lands the record and its grade, the key's one
reader, and the hold at the one admission point.

## 4. Design

### The record

```
- **F2 — <question>** <options and tradeoffs> RESOLVED (agent, 2026-10-25, delegated): (a), rung 3.
  options: (a) > (c) > (b) · pick: (a) · admitted-by: principle.p18 · widens: none · relaxes: none
```

The tail is read from the F-item span as check 12 already builds it: lines joined, whitespace
squeezed, code spans and double-quoted spans removed (`check_span_mark`,
`tools/memory-tree/check-memory-hygiene.sh@c2fc4073:2292`),
so a record quoted as an example records nothing, exactly as a quoted mark resolves nothing.

```
record   = "options: " opt { " > " opt } " · pick: " opt " · admitted-by: " tag
opt      = one or more characters, none of them the separators " > " or " · "
tag      = "principle." seg, the registry's own tag grammar
```

The ranking is the order of `options`. A one-option record (`options: (a) · pick: (a)`) is legal: one
option surviving the vetoes is a ranking of one. The README's `widens:` and `relaxes:` fields follow
the tail and are not read by this grade.

### Why only `agent` marks

v2's P18 binds the role that meets the fork; the owner resolving a fork is the owner's choice, and an
`(owner, …)` mark already names that resolver (`memory/TEMPLATE-SPEC.md@ff216b36:163-167`). Grading an owner pick
against a ranking would make the gate the owner's judge.

### The two readers, one grammar

`check_mark` and the planning verb's `plan_state` already spell the mark twice, and the marker-contract
suite is what proves they agree (the comment at `tools/memory-tree/check-memory-hygiene.sh@c2fc4073:2285-2289`).
The record joins that pair the same way: one more row in the contract table, one more predicate in
each reader, and `plan_state` reading FORKED for a failing record, so `--dispatch`'s new FORKED case
sees exactly what the hygiene gate sees. Check 12 grades §8 only for a spec at a terminal Status, CLOSED
or WONTDO (`tools/memory-tree/check-memory-hygiene.sh@c2fc4073:2749`), while the planning verb grades
the specs of a running build; the contract table already writes each case twice for that reason
(`tools/memory-tree/marker-contract.test.sh@e147acb7:261-264`), and the record rows follow it.

The cutoff reaches `plan_state` as a fourth argument (§8 F6): `plan_state <spec> <FORK_ITEM_CUTOFF>
[delegated] [FORK_RECORD_CUTOFF]`, blank meaning off as for the item cutoff. Every call site in the
driver and the pass-order leg passes it, seven at HEAD `c93f676e2` (DERIVED: `grep -nE 'plan_state "'`
over `tools/unattended/unattended.sh` and `tools/unattended/check-pass-order.sh`, comment lines
dropped), and the marker-contract caller arm (`tools/memory-tree/marker-contract.test.sh@e147acb7:517-526`)
grades that each does. `read_fork_cutoff` takes the key's name as an optional second argument,
`FORK_ITEM_CUTOFF` by default, so its one re-parse and the guard that compares it with sourcing serve
both keys. The `delegated` mode ignores the record, and so does its one caller outside the driver, the
loop kit's self-test fixture (`tools/loop/breakpoints.py@bc677275:523`).

### The admitted set

"Only options the core admits are options" (v2:907-913). The record cannot prove an option was
admissible; it names what admitted the set, and the grade checks that the name is a real principle.
The registry is read from `tools/playbook/principles.toml` as text, its `tag` lines; at HEAD it holds
42 rows, `principle.p1` to `principle.p42` (`tools/playbook/principles.toml@701c20bb`, DERIVED: `grep -c
'^tag = "principle'`). Where the file is absent, an adopter without the playbook kit, the grade checks
the tag's shape and prints one `note` line naming the absent registry, never green silence.
