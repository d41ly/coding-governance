# Adopter migration — the domain's sweep, at the files where its traps bit

## Symptom

A change that is green in this repository breaks an adopter who installed the prior version: a
shipped checker now refuses what it accepted, a sourced conf's blank value overrides the new default,
or a renamed spelling strands the readers that matched the old one. This repository runs at the new
version only, so no gate here meets the adopter's tree. Each instance has its own record, anchored
where it bit, and a reviewer handed one of them is handed none of the domain's others.

## The sweep

For a subject touching a file below, ask each question of the change, not only the one its member
record answers, from the seat of an adopter on the prior version:

- a changed key, shape, render or gate: does the adopter's existing conf, record or install still
  read, render and pass, and if not, which upgrade step carries it across?
- non-additive data: does the change rename, remove or re-type a field the adopter's data holds,
  where an additive change with a default would do?
- versions in lockstep: must two kits, or a kit and its registry row, move together, and does any
  check refuse the pair that did not?
- an assumed install layout: does the change assume a prefix, a sibling kit or a path this
  repository has and an adopter may not?

## Where it bit

Each file below is an anchor of at least one member, so the sweep reaches a review only where a
recorded defect of the domain already landed: `skills/session-kickoff/manifest-check.sh`,
`WIRE-INTO-PROJECT.md`, `tools/memory-tree/check-memory-hygiene.sh`, `tools/govkit/registry.toml`
and `tools/check-kit-versions.sh`.

## Gate

This class has no machine gate: the sweep is a reviewer's question over a domain, and each member
names its own gate or documented check for its one instance.
